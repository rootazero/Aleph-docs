## Protocol v1 是什么

Protocol v1 已用于 Gateway 的 **Desktop IPC** 和 **Web v1** 入口。两者以有界帧承载 JSON-RPC 2.0，并要求先完成 `system.hello` 握手。旧 `/ws` 仍提供兼容入口，不使用长度前缀（`src/gateway/server/connection/local_ipc.rs`、`src/gateway/server/connection/web_v1.rs`、`src/gateway/server/connection/mod.rs`）。

| 部分 | 代码 |
|------|------|
| 帧编解码 | `shared/protocol/src/framing.rs` |
| 握手 DTO 与协商函数 | `shared/protocol/src/system_hello.rs` |
| 服务端握手处理 | `src/gateway/handlers/system_hello.rs` |
| JSON-RPC 消息与错误码 | `shared/protocol/src/jsonrpc.rs` |

<Callout type="info">
NSH 有两种 Panel 宿主形态，不能用同一种传输概括。

- **默认 Leptos Panel**：`web_view` 默认从 `http://127.0.0.1:18790/` 加载页面，Gateway WebSocket 默认是 `ws://127.0.0.1:18790/ws`（`desktop/nsh-shell/src/main.rs`、`desktop/nsh-shell/src/shell_host.rs`、`desktop/nsh-shell/src/credentials.rs`）。
- **TSX Panel**：在 macOS 上以 `--features tsx-panel` 构建，再用 `ALEPH_SHELL_PANEL=tsx` 启用（不能与 QA 模式同时使用）。Panel 嵌入原生 AppView；宿主只通过 `ALEPH_SHELL_PANEL_IPC` 指定的绝对 socket 路径连接本地 Gateway。其他目标报告 `unavailable`，不会回退到 WebSocket（`desktop/nsh-shell/Cargo.toml`、`desktop/nsh-shell/src/main.rs`、`desktop/nsh-shell/src/panel_surface.rs`、`desktop/nsh-shell/src/panel_host.rs`）。
</Callout>

## 帧格式

一帧 = 4 字节**大端** `u32` 长度前缀 + UTF-8 JSON 载荷。长度只计载荷字节数，不含帧头。`HEADER_BYTES` 为 4，`DEFAULT_MAX_PAYLOAD_BYTES` 为 8 388 608（8 MiB）。Desktop IPC 的 `MAX_FRAME_BYTES` 等于默认上限，Web v1 的 `MAX_MESSAGE` 为 1 MiB（`shared/protocol/src/framing.rs`、`shared/client/src/local_ipc.rs`、`src/gateway/server/connection/web_v1.rs`）。

`shared/protocol/src/framing.rs` 中的编解码函数：

| 函数 | 语义 |
|------|------|
| `encode_header` | 返回大端帧头。长度为零返回 `Empty`；超过传入的上限或放不进 `u32` 返回 `Oversize` |
| `decode_header` | 在读取或分配载荷前检查声明的长度，规则同上 |
| `split_frame` | 借出一帧的 UTF-8 载荷和剩余字节，不解析 JSON。不足一帧返回 `Ok(None)`；UTF-8 无效返回 `InvalidUtf8`，分帧失败即终止该流的分帧 |

上限包含端点：等于上限合法，多一个字节即 `Oversize`。例如，`{"jsonrpc":"2.0","id":2,"method":"health"}` 的载荷是 42 字节，帧头为 `00 00 00 2A`（`shared/protocol/src/framing.rs`）。

```text
00 00 00 2A | 7B 22 6A 73 6F 6E 72 70 63 22 3A 22 32 2E 30 22 ... 7D
 4 字节帧头 | 42 字节 UTF-8 JSON 载荷
```

| 载荷长度 | 按默认上限编码的结果（`shared/protocol/src/framing.rs`） |
|---------|------------------------------------------------------|
| 12 | `00 00 00 0C` |
| 258 | `00 00 01 02` |
| 8 388 608 | `00 80 00 00` |
| 8 388 609 | `Oversize` |
| 0 | `Empty` |

## 握手 `system.hello`

`system.hello` 是两个 v1 入口的首个 RPC 请求。它协商版本、特性并返回连接限额，不是客户端的认证凭据（`shared/protocol/src/system_hello.rs`、`src/gateway/server/connection/local_ipc.rs`、`src/gateway/server/connection/web_v1.rs`）。

### 请求

以下是请求示例，不是 NSH 宿主的实际默认值。`client` 中的 `name`、`version`、`platform`、`ui_runtime` 均为必填字符串；`features` 可以是空数组（`shared/protocol/src/system_hello.rs`）。示例里请求的两个特性正是两个 v1 入口实现的那两个；旧 `/ws` 不实现任何可选特性，因此在旧入口上这两个名字不会被授予。

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "system.hello",
  "params": {
    "protocol": { "major": 1, "minor": 0 },
    "client": {
      "name": "example-client",
      "version": "1.2.3",
      "platform": "linux",
      "ui_runtime": "example"
    },
    "features": ["event_replay", "snapshot", "binary_channel"]
  }
}
```

### 响应

以下是 Desktop IPC 成功响应示例。服务端版本、连接 UUID 与 `subject` 值仅作示例（`src/gateway/handlers/system_hello.rs`、`src/gateway/server/connection/local_ipc.rs`）。

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocol": { "major": 1, "minor": 0 },
    "server": { "name": "aleph-server", "version": "26.9.1" },
    "connection_id": "ipc-3f0c1b52-8a0e-4d0a-9b1a-6a6d2f0a7e11",
    "features": ["live_events", "chat_transcript"],
    "limits": { "max_message_bytes": 8388608, "max_inflight_requests": 8 },
    "subject": "0123456789abcdef0123456789abcdef"
  }
}
```

### `subject`：客户端存储键

`subject` 是不透明的、按用户区分的稳定值，用于 Panel 布局等客户端存储键。**它不是身份或凭据，客户端不得据此推导权限。** `panel_subject` 用 Gateway 的 shared-token secret 对 `"aleph.panel.subject.v1\0"`（末尾含 NUL）与用户 ID 的拼接做 HMAC-SHA256，取前 16 字节编码为 32 个十六进制字符。结果不含原始用户 ID；密钥轮换会改变存储键，只影响客户端展示状态（`src/gateway/handlers/system_hello.rs`、`src/gateway/security/crypto.rs`、`shared/protocol/src/system_hello.rs`）。

旧 `/ws` 始终省略 `subject`。两个 v1 入口在无法取得 shared-token secret 时也省略该字段；`HelloResult` 的 `skip_serializing_if` 让整个字段不出现，而不是输出 `null`（`src/gateway/handlers/system_hello.rs`、`shared/protocol/src/system_hello.rs`）。

### 版本协商

`negotiate_version` 要求双方 major 相同，再取较小的 minor。Gateway 声明 `1.0`，因此 major 不是 1 时握手失败，成功时 minor 始终是 0（`shared/protocol/src/system_hello.rs`、`src/gateway/handlers/system_hello.rs`）。

### 特性协商

`negotiate_features` 按客户端的偏好顺序，选择双方共有的已知特性并去重。未知字符串反序列化为 `Unknown(String)`，不影响解析，也不参加协商（`shared/protocol/src/system_hello.rs`）。

| 特性字符串 | `Feature` 变体（`shared/protocol/src/system_hello.rs`） |
|-----------|-------------------------------------------------------|
| `event_replay` | `EventReplay` |
| `snapshot` | `Snapshot` |
| `binary_channel` | `BinaryChannel` |
| `live_events` | `LiveEvents` |
| `chat_transcript` | `ChatTranscript` |

未知的字符串反序列化为 `Unknown(String)`：它能被解析，但不参加协商（`shared/protocol/src/system_hello.rs`）。

三个入口调用同一个 `negotiate_features(requested, implemented)`，区别只在 `implemented`：

| 入口 | `implemented` | 协商结果 |
|------|---------------|----------|
| 旧 `/ws` | 空列表 | 恒为 `[]`——旧入口不推事件，也没有可选特性 |
| Desktop IPC | `V1_FEATURES` | 请求列表与 `LiveEvents`、`ChatTranscript` 的交集 |
| Web v1 | `V1_FEATURES` | 同上 |

`V1_FEATURES` 就是 `LiveEvents` 与 `ChatTranscript` 两项（`src/gateway/server/connection/mod.rs`）。还有一个附加条件：`chat_transcript` 以 `live_events` 为前提，`negotiate_features` 在没有授予 `live_events` 时会连带去掉 `ChatTranscript`（`shared/protocol/src/system_hello.rs`）。特性标识能解析，不代表该特性已经启用；`event_replay`、`snapshot`、`binary_channel` 至今没有任何入口实现，因此不会出现在协商结果里（`src/gateway/handlers/system_hello.rs`）。

## 服务端行为

`src/gateway/handlers/system_hello.rs` 中的 `negotiate()` 按以下顺序处理：

1. `params` 缺失：返回 `INVALID_PARAMS`，消息 `Missing params`。
2. `params` 无法解析成 `HelloParams`：返回 `INVALID_PARAMS`，消息以 `Invalid system.hello params:` 开头，后接解析错误。
3. major 不为 1：返回 `INVALID_PARAMS`，消息 `incompatible protocol major version`。
4. 成功：返回 `protocol`、`server`（`name` 为 `aleph-server`，`version` 取编译期 `ALEPH_VERSION`）、`connection_id`、`features`、`limits` 和可选的 `subject`。

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": { "code": -32602, "message": "incompatible protocol major version" }
}
```

三个入口复用 `negotiate()`，但各自提供连接 ID、限额与 `subject`（见表中各入口的源码）：

| 入口 | `connection_id` | `limits.max_message_bytes` | `limits.max_inflight_requests` | `subject` | 代码 |
|------|-----------------|---------------------------|-------------------------------|-----------|------|
| 旧 `/ws` | `conn-<uuid4>` | 8 388 608（8 MiB，仅提示） | 128（仅提示） | 不返回 | `src/gateway/handlers/system_hello.rs` |
| Desktop IPC | `ipc-<uuid4>` | `MAX_FRAME_BYTES`（8 388 608，强制） | `MAX_INFLIGHT`（8，强制） | 有密钥时，从 Gateway owner 用户生成 | `src/gateway/server/connection/local_ipc.rs` |
| Web v1 | `web-v1-<uuid4>` | `MAX_MESSAGE`（1 048 576，强制） | 1（串行处理） | 有密钥时，从 Web 会话绑定用户生成 | `src/gateway/server/connection/web_v1.rs` |

在旧 `/ws` 上，`system.hello` 是 `connect` 之后的可选版本探测，既不准入连接，也不设置身份（`src/gateway/handlers/system_hello.rs`）。

## 传输矩阵

| 入口 | 传输 | 认证 | 能调用什么 | 代码 |
|------|------|------|-----------|------|
| Desktop IPC（Unix） | Unix domain socket，长度前缀帧 | 操作系统校验对端为同一用户，不授予网络权限 | 首帧 `system.hello`；之后是挂载清单里的 12 个方法（见下） | `src/gateway/server/connection/local_ipc.rs`、`shared/client/src/local_ipc.rs` |
| Desktop IPC（Windows，未开放） | 本地命名管道代码已入库 | 已实现账户认证，未启用 | 无：客户端连接和 Gateway 监听均受可用性开关限制 | `shared/client/src/local_ipc/windows.rs`、`src/gateway/server/connection/local_ipc/windows.rs`、`shared/client/src/local_ipc.rs` |
| Web v1 | 原生 TLS 上的 WebSocket；每条 Binary 消息恰好一帧 | 同源校验与会话 cookie；以设备令牌或引导票换取会话 | 首帧 `system.hello`；之后是挂载清单里的 12 个方法（见下） | `src/gateway/server/connection/web_v1.rs`、`src/gateway/server/mod.rs` |
| 旧 `/ws`（兼容） | WebSocket Text 消息，无长度前缀 | 升级时检查传输安全与 `Origin`（若提供），再由 `connect` 认证 | 旧版完整 RPC 面，仍受授权限制，见[方法参考](./methods) | `src/gateway/server/connection/upgrade.rs`、`src/gateway/server/connection/mod.rs` |

`system.hello` 在握手时单独处理，不属于握手后的挂载清单。两个 v1 入口共用 `V1_METHODS` 与 `v1_mounted()`，挂载的是这 12 个方法：

| 方法 | 说明 |
|------|------|
| `health` | 健康检查 |
| `sessions.list` | 会话列表 |
| `panel.capabilities.snapshot` | Panel 能力快照（`PANEL_UI_CAPABILITY_SNAPSHOT_METHOD`） |
| `graph.query` / `graph.search` / `graph.node_detail` | 记忆图谱的查询、搜索与节点详情 |
| `chat.history` / `chat.send` / `chat.abort` | 聊天三件套 |
| `chat.transcript_details` | 工具调用的呈现层变更 |
| `trace.tool_output` | 工具输出 |
| `context.breakdown` | 上下文构成 |

这些方法与旧 `/ws` 走同一套分发、归属检查与幂等缓存。`panel.project.select` 会改变状态，未挂载在 v1 上；未挂载的方法不会进入 Core；服务端返回 `METHOD_NOT_FOUND`，Web v1 触发限流时则直接断开（`src/gateway/server/connection/mod.rs`、`shared/protocol/src/panel.rs`、`shared/protocol/src/memory_graph.rs`、`shared/protocol/src/chat_transcript.rs`、`src/gateway/server/connection/local_ipc.rs`、`src/gateway/server/connection/web_v1.rs`）。

认证细节见[身份认证](./auth)，信任边界见 [IPC 协议](../security/ipc)。

### Desktop IPC

用 `aleph-server start --desktop-ipc <socket>` 显式开启。服务端要求使用调用方持有的 0700 目录下新的绝对 Unix socket 路径，不覆盖已有条目，也不在退出时删除 socket 条目（`src/bin/aleph-server/cli.rs`、`src/gateway/server/mod.rs`、`src/gateway/server/connection/local_ipc.rs`、`shared/client/src/local_ipc.rs`）。

| 常量 | 值 | 含义 | 代码 |
|------|----|------|------|
| `MAX_CONNECTIONS` | 8 | 同时服务的 IPC 连接数；达到上限后暂停接受新连接 | `src/gateway/server/connection/local_ipc.rs` |
| `WIRE_BUDGET` | 16 MiB | 每连接的在途载荷字节预算；校验帧头后、分配载荷前预留 | `src/gateway/server/connection/local_ipc.rs`、`shared/client/src/local_ipc.rs` |
| `WRITE_TIMEOUT` | 5 秒 | 单次写帧超时 | `src/gateway/server/connection/local_ipc.rs` |
| `NO_NETWORK_ORIGIN` | `0.0.0.0` | 用于连接状态的来源占位值，不授予网络权限 | `src/gateway/server/connection/local_ipc.rs` |
| `MAX_FRAME_BYTES` | `DEFAULT_MAX_PAYLOAD_BYTES` | 单帧载荷上限 | `shared/client/src/local_ipc.rs` |
| `MAX_INFLIGHT` | 8 | 每连接并发在途请求数 | `shared/client/src/local_ipc.rs`、`src/gateway/server/connection/local_ipc.rs` |
| `HELLO_TIMEOUT` | 5 秒 | 首个请求的读取时限 | `shared/client/src/local_ipc.rs`、`src/gateway/server/connection/local_ipc.rs` |

- 首个有效 RPC 请求不是 `system.hello` 时，返回 `AUTH_REQUIRED` 后断开；等不到首帧或首帧无效时，直接断开。握手结果中的 `subject` 来自 Gateway owner 用户（`src/gateway/server/connection/local_ipc.rs`）。
- 请求必须声明 `"jsonrpc": "2.0"` 并带字符串或整数 `id`。不带 `id` 的通知和其他无效信封会结束连接；重复使用在途 `id` 或发送超出 `MAX_INFLIGHT` 的请求也会断开（`src/gateway/server/connection/local_ipc.rs`）。
- `parse_payload` 限制嵌套深度（`MAX_DEPTH`，64）、每个容器的条目数（`MAX_ITEMS`，4096）及单字符串字节数（`MAX_STRING_BYTES`，65 536）。握手后的响应若超出大小或 JSON 形态限制，服务端用带原请求 `id` 的 `INTERNAL_ERROR` 替代（`shared/client/src/local_ipc.rs`、`src/gateway/server/connection/local_ipc.rs`）。

### Web v1

`native_tls_router` 只在原生 TLS 路由上挂载 Web v1（`src/gateway/server/mod.rs`）。端点与限额定义在 `src/gateway/server/connection/web_v1.rs`：

| 项 | 值 |
|----|----|
| 会话换取 | `POST /v1/session`，请求体最多 4096 字节 |
| JSON 请求体 | `{"device_token": "..."}` 或 `{"bootstrap_ticket": "..."}` |
| 成功响应 | `204 No Content`，附带 `Set-Cookie: __Host-aleph-v1=<uuid>; Secure; HttpOnly; SameSite=Strict; Path=/; Max-Age=300` 和 `Cache-Control: no-store` |
| 升级 | `GET /v1/ws`，`Sec-WebSocket-Protocol` 必须恰为 `aleph.protocol.v1`，并携带上述 cookie |
| 会话有效期 | 300 秒（`TTL`） |
| 单帧载荷上限 | 1 MiB（`MAX_MESSAGE`），不含 4 字节帧头 |
| 会话数 / 并发 socket | 256（`MAX_SESSIONS`）/ 8（`MAX_SOCKETS`） |
| 读请求体和写 WebSocket 超时 | 5 秒（`IO_TIMEOUT`） |

两条路由都先通过 `same_origin` 核对 `Origin`（必须与请求目标的 HTTPS 来源一致），再通过 `throttle` 按客户端 IP 限流。常见失败包括来源不符（403）、限流（429）、请求体不合法或子协议不符（400）、凭据或 cookie 无效（401）、容量不足或服务未就绪（503）及读取请求体超时（408）（`src/gateway/server/connection/web_v1.rs`）。

升级后，每条承载 RPC 的消息必须是 Binary，且恰好包含一个完整帧；Text 消息、帧不完整、有剩余字节或信封无效都会结束连接。首个 RPC 请求必须是 `system.hello`，且在 5 秒或会话到期前到达，以先到者为准。握手后每次处理一个请求；会话到期、设备凭据失效（每秒检查）或 Gateway 停止时关闭连接（`src/gateway/server/connection/web_v1.rs`）。

配置静态包目录后，Gateway 只在原生 TLS 路由的 `/v1/panel/` 提供 TSX Panel 的 Web 静态包，使页面与使用 cookie 认证的 `/v1/ws` 同源。`panel_routes` 添加 `Content-Security-Policy: script-src 'self' 'wasm-unsafe-eval'; img-src 'self' blob: data:; connect-src 'self'` 和 `X-Content-Type-Options: nosniff`（`src/gateway/server/mod.rs`、`src/gateway/server/connection/web_v1.rs`）。

### 旧 `/ws`

旧入口以 WebSocket Text 消息边界划分 JSON-RPC 消息。收到 Binary 消息只记录警告并忽略（`src/gateway/server/mod.rs`、`src/gateway/server/connection/mod.rs`）。它保留旧 RPC 方法面，包括 `panel.capabilities.snapshot` 和 `panel.project.select`（`src/gateway/handlers/mod.rs`）。连接流程见[旧 WebSocket 入口](./protocol)。

## 事件与订阅

旧 `/ws` 的主题事件是不带 `id` 的 JSON-RPC 通知，`method` 为 `event`（`TOPIC_EVENT_METHOD`），主题与载荷位于 `params` 的 `topic` 与 `data`（`shared/protocol/src/jsonrpc.rs`、`src/gateway/server/connection/mod.rs`）：

```json
{
  "jsonrpc": "2.0",
  "method": "event",
  "params": { "topic": "agent.run.complete", "data": {} }
}
```

- 主题包括 `agent.run.complete`、`session.lifecycle.changed` 和 `config.changed`（`src/gateway/events/frame.rs`）。
- `events.subscribe` 接收 `topics`：每项为字符串模式或 `{topic, where}` 过滤对象（`src/gateway/handlers/events.rs`）。只有旧 `/ws` 挂载了这个方法——两个 v1 入口的事件面是握手协商出来的，不需要订阅。
- 订阅并不绕过可见性检查；事件投递仍受所有者、会话和角色约束（`src/gateway/event_visibility.rs`、`src/gateway/event_scope.rs`）。详见[事件方法](./methods/events)。

### v1 的事件面

两个 v1 入口在握手时协商到 `live_events` 之后才开始下发事件。推送的帧还要再过两道闸：先是共用的准入判定 `admit_event`（身份、作用域、所有权、投影），然后是 v1 自己的主题白名单 `V1_EVENT_TOPICS`（`src/gateway/server/connection/event_admission.rs`、`src/gateway/server/connection/mod.rs`）。

白名单里只有六个主题：

| 主题 | 含义 |
|------|------|
| `stream.run_accepted` | 一次 run 被接受 |
| `stream.response_chunk` | 响应增量 |
| `stream.run_complete` | run 正常结束 |
| `stream.run_error` | run 出错 |
| `stream.chat_tool` | 工具调用的呈现层变更 |
| `connection.warning` | 连接级警告（溢出、丢帧） |

`stream.chat_tool` 只在同时协商到 `live_events` 与 `chat_transcript` 时才产生，它推送的呈现层数据与 `chat.transcript_details` 方法返回的是同一份投影（`src/gateway/handlers/chat_presentation.rs`）。方法面的说明见 [chat 方法](./methods/chat)。

v1 直接订阅事件总线，因此丢帧会以 `Lagged` 的形式出现在这条连接上，而不会被缓冲悄悄吞掉。丢帧时服务端先发一帧 `connection.warning`（`reason` 为 `events_overflow`），再结束连接，客户端需要自行重同步；而单帧超出上限时只发警告、连接继续服务（`src/gateway/server/connection/forward.rs`、`src/gateway/server/connection/event_admission.rs`）。

## 错误模型

帧层错误不会生成 JSON-RPC 响应。Desktop IPC 通过 `decode_header` 检查长度（内部错误消息为 `invalid IPC frame length`），再解码 UTF-8；Web v1 通过 `split_frame` 检查完整性与 UTF-8，并拒绝尾部多余字节。失败时这两个入口都结束连接（`shared/protocol/src/framing.rs`、`shared/client/src/local_ipc.rs`、`src/gateway/server/connection/web_v1.rs`）。

对有效 RPC 请求的拒绝通常返回带原 `id` 的 `error` 响应，不终止已建立的连接。握手失败则在发出错误后结束连接；Web v1 对未挂载方法使用独立的 `web-v1-unsupported:<ip>` 限流键，超限时直接断开（`src/gateway/server/connection/local_ipc.rs`、`src/gateway/server/connection/web_v1.rs`）。

| 场景 | 错误码（`shared/protocol/src/jsonrpc.rs`） | 消息 | 代码 |
|------|------------------------------------------|------|------|
| 首个有效请求不是 `system.hello` | `AUTH_REQUIRED`（-32000） | `system.hello must be first` | `src/gateway/server/connection/local_ipc.rs`、`src/gateway/server/connection/web_v1.rs` |
| Desktop IPC 上的方法未挂载 | `METHOD_NOT_FOUND`（-32601） | `method not mounted on Desktop IPC` | `src/gateway/server/connection/local_ipc.rs` |
| Web v1 上的方法未挂载，未触发限流 | `METHOD_NOT_FOUND`（-32601） | `method unavailable on Web v1` | `src/gateway/server/connection/web_v1.rs` |
| Desktop IPC 普通响应超出限制 | `INTERNAL_ERROR`（-32603） | `response exceeds Desktop IPC limits` | `src/gateway/server/connection/local_ipc.rs` |
| Web v1 响应超出限制 | 原错误码（若生成此响应时已传入）或 `INTERNAL_ERROR`（-32603） | `response exceeds Web v1 limits` | `src/gateway/server/connection/web_v1.rs` |

完整错误码见 [JSON-RPC](../api/jsonrpc)。

## Windows 命名管道 Desktop IPC

**代码已就位，尚未开放。** Windows 客户端代码校验显式本地端点（例如 `\\.\pipe\aleph`）并实现账户认证，Gateway 侧用 `PipeAccount` 绑定命名管道并验证客户端账户（`shared/client/src/local_ipc/windows.rs`、`src/gateway/server/connection/local_ipc/windows.rs`）。但 `local_ipc::AVAILABLE` 仍是 `cfg!(unix)`；公开的客户端连接与 Gateway 监听入口都受此开关限制，当前 Windows 上不可用（`shared/client/src/local_ipc.rs`、`shared/client/src/connection.rs`、`src/gateway/server/mod.rs`）。

## 迁移与兼容

- **新客户端**：按部署环境选择显式开启的 Desktop IPC 或原生 TLS 上的 Web v1。先发送 `system.hello`，核对返回的协议版本与限额，再调用挂载的只读方法。Desktop IPC 的 `AlephClient::connect_local` 不回退到网络传输，也不使用设备凭据（`src/gateway/server/connection/local_ipc.rs`、`src/gateway/server/connection/web_v1.rs`、`src/gateway/server/mod.rs`、`shared/client/src/connection.rs`）。
- **旧客户端**：继续使用 `/ws` 与 `connect`；需要时再调用 `system.hello` 探测版本，响应中的限额仅作提示。需要事件订阅或写操作的客户端仍应使用旧 RPC 入口（`src/gateway/server/connection/mod.rs`、`src/gateway/handlers/system_hello.rs`）。

## 历史：NSH Phase 2 原生连接设计

<Callout type="warn">
`desktop/nsh-shell/src/connection.rs` 是 Phase 2 的原生连接设计，**没有**出现在 `desktop/nsh-shell/src/main.rs` 的 `mod` 声明里，因此不在当前编译出的 NSH 二进制中；`desktop/nsh-shell/Cargo.toml` 也没有额外的 `[[bin]]` 或 `[lib]`。`desktop/nsh-shell/src/runtime.rs`、`desktop/nsh-shell/src/session.rs`、`desktop/nsh-shell/src/supervisor.rs` 和 `desktop/nsh-shell/src/components/mod.rs` 同样未接入该二进制。不要将这些文件当作现行连接行为。
</Callout>
