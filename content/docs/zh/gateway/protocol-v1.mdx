## Protocol v1 是什么

Protocol v1 是 Gateway 的连接协议：**有界帧** + **握手** + **特性协商**。它解决三件事：帧边界可预测（先读定长帧头再分配内存）、能力可协商（双方各自声明支持什么）、握手可审计（版本不兼容时服务端明确拒绝）。

| 部分 | 代码 |
|------|------|
| 帧编解码 | `shared/protocol/src/framing.rs` |
| 握手 DTO 与协商函数 | `shared/protocol/src/system_hello.rs` |
| 服务端握手处理 | `src/gateway/handlers/system_hello.rs` |
| JSON-RPC 消息与错误码 | `shared/protocol/src/jsonrpc.rs` |

消息语义仍是 JSON-RPC 2.0（见 [JSON-RPC](../api/jsonrpc)）；v1 只规定这些消息如何分帧、如何开场。

<Callout type="info">
旧的 `ws://127.0.0.1:18790/ws` 是历史兼容入口，不使用长度前缀分帧，见[旧 WebSocket 入口](./protocol)。

v1 的 **Desktop IPC** 与 **Web v1** 两个入口是给新客户端准备的。当前 NSH 桌面宿主仍走旧路径：它经 HTTP(S) origin 加载 Panel（`desktop/nsh-shell/src/shell_host.rs`），Panel 在 WebView 里再连 Gateway 的旧 `/ws`（`desktop/nsh-shell/src/credentials.rs`）。NSH 曾经用 v1 握手的那套参数见 `desktop/nsh-shell/src/connection.rs`——历史设计，见下方说明。
</Callout>

<Callout type="warn">
`desktop/nsh-shell/src/connection.rs` 是 Phase 2 的原生连接设计，**没有**出现在 `desktop/nsh-shell/src/main.rs` 的 `mod` 声明里，因此不在当前编译出的 NSH 二进制中；`desktop/nsh-shell/Cargo.toml` 也没有额外的 `[[bin]]` 或 `[lib]`。本页引用它只是为了说明「NSH 曾经这样实现握手」，请勿当作现行行为——现行宿主与 Panel 的连接方式见[桌面宿主](/docs/zh/desktop-hosts/overview)。
</Callout>

## 帧格式

一帧 = 4 字节**大端** `u32` 长度前缀 + UTF-8 载荷。长度只计载荷字节数，不含这 4 字节帧头。

```text
 0        1        2        3        4 ...
+--------+--------+--------+--------+---------------------------+
|  len (u32, big-endian, payload bytes only)  |  UTF-8 JSON payload (len bytes) |
+--------+--------+--------+--------+---------------------------+
```

`shared/protocol/src/framing.rs` 的常量与错误：

```rust
pub const HEADER_BYTES: usize = 4;
pub const DEFAULT_MAX_PAYLOAD_BYTES: u32 = 8_388_608; // 8 MiB，不含帧头

pub enum FrameError { Empty, Oversize, InvalidUtf8 }
```

`DEFAULT_MAX_PAYLOAD_BYTES` 是推荐上限；各端点自行强制自己的上限（Web v1 用 1 MiB，见下文传输矩阵）。

| 函数 | 语义 |
|------|------|
| `encode_header(payload_len, max_payload) -> Result<[u8; 4], FrameError>` | 长度为 0 返回 `Empty`；超过 `max_payload`（或放不进 `u32`）返回 `Oversize`；否则返回大端字节 |
| `decode_header(header, max_payload) -> Result<u32, FrameError>` | 在读取或分配载荷**之前**校验声明的长度，规则同上 |
| `split_frame(bytes, max_payload) -> Result<Option<(&str, &[u8])>, FrameError>` | 从缓冲区借出一个 UTF-8 载荷和未消费的后缀；不足一个完整帧返回 `Ok(None)`，表示还需要更多字节；`Err` 表示这条流的分帧到此终止；载荷不是合法 UTF-8 返回 `InvalidUtf8` |

上限是**闭区间**：长度恰好等于 `max_payload` 合法，大一个字节即 `Oversize`。

字节级示例：载荷 `{"jsonrpc":"2.0","id":2,"method":"health"}` 共 42 个字节，帧头是 `00 00 00 2A`：

```text
00 00 00 2A | 7B 22 6A 73 6F 6E 72 70 63 22 3A 22 32 2E 30 22 ... 7D
 ^^^^^^^^^^^   ^ 载荷共 42 字节（UTF-8 JSON）
 len = 42
```

另外几个长度对应的帧头：

| 载荷长度 | 帧头（十六进制） | 结果 |
|---------|-----------------|------|
| 12 | `00 00 00 0C` | 合法 |
| 258 | `00 00 01 02` | 合法 |
| 8 388 608 | `00 80 00 00` | 合法（等于默认上限） |
| 8 388 609 | 不可编码 | `Oversize` |
| 0 | 不可编码 | `Empty` |

`framing.rs` 的单元测试覆盖了其中 258、8 388 608 与 8 388 609 三例。

## 握手 `system.hello`

`system.hello` 是连接上的第一个业务请求：客户端报告协议版本、身份和希望启用的特性，服务端返回协商结果与连接限额。字段定义在 `shared/protocol/src/system_hello.rs`。

### 请求

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "system.hello",
  "params": {
    "protocol": { "major": 1, "minor": 0 },
    "client": {
      "name": "aleph-nsh-desktop",
      "version": "1.2.3",
      "platform": "linux",
      "ui_runtime": "nsh"
    },
    "features": ["event_replay", "snapshot", "binary_channel"]
  }
}
```

`client` 的四个字段（`name`、`version`、`platform`、`ui_runtime`）都是必填字符串。`version` 为示例值。历史设计中 NSH 的取值来自 `desktop/nsh-shell/src/connection.rs` 的 `build_hello_params()`：`platform` 取 `std::env::consts::OS`，`ui_runtime` 为 `"nsh"`；该文件不在当前编译产物中（见本页开头说明）。

### 响应

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocol": { "major": 1, "minor": 0 },
    "server": { "name": "aleph-server", "version": "26.9.1" },
    "connection_id": "conn-3f0c1b52-8a0e-4d0a-9b1a-6a6d2f0a7e11",
    "features": [],
    "limits": { "max_message_bytes": 8388608, "max_inflight_requests": 128 }
  }
}
```

`server.version` 与 `connection_id` 中的 UUID 为示例值。`features` 为空数组的原因见下文「服务端行为」。

### 版本协商

`negotiate_version(client, server) -> Option<ProtocolVersion>`：

- major 不同返回 `None`，握手失败；
- major 相同则返回 `{ major, minor: min(client.minor, server.minor) }`。

服务端当前声明的版本是常量 `1.0`（`src/gateway/handlers/system_hello.rs`），所以成功响应的 `protocol.minor` 恒为 `0`。历史设计中的 NSH 客户端在收到 `result.protocol.major != 1` 时视为握手失败（`desktop/nsh-shell/src/connection.rs`，不在当前编译产物中）。

### 特性协商

`negotiate_features(requested, implemented) -> Vec<Feature>`：保留客户端请求、服务端实现、且为已知类型的特性，按**客户端顺序**输出并去重。

| 特性字符串 | `Feature` 变体 | 含义（见源码注释） |
|-----------|---------------|------------------|
| `event_replay` | `EventReplay` | 从存储的流偏移重放事件 |
| `snapshot` | `Snapshot` | 时间点能力快照 |
| `binary_channel` | `BinaryChannel` | WebSocket 通道上的二进制分帧 |
| 其他字符串 | `Unknown(String)` | 来自更新版本的特性；反序列化时原样保留，不会让旧客户端解析失败，但不会进入协商结果 |

## 服务端行为

`src/gateway/handlers/system_hello.rs` 的 `negotiate()` 按以下顺序处理：

1. `params` 缺失：`INVALID_PARAMS`，消息 `Missing params`。
2. `params` 解析为 `HelloParams` 失败：`INVALID_PARAMS`，消息 `Invalid system.hello params: <原因>`。
3. major 不为 1：`INVALID_PARAMS`，消息 `incompatible protocol major version`。
4. 成功：返回协商后的 `protocol`、`server`（`name` 固定为 `"aleph-server"`，`version` 取编译期 `ALEPH_VERSION`）、`connection_id`、`features`、`limits`。

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": { "code": -32602, "message": "incompatible protocol major version" }
}
```

**`features` 目前恒为空。** handler 调用的是 `negotiate_features(&params.features, &[])`，即服务端实现列表为空；NSH 即使请求了三个特性，也只会拿到 `[]`。特性协商的机制已就位，对应能力尚未实现，见下文「规划中」。

**`connection_id` 与 `limits` 随入口不同。** 同一个 `negotiate()` 被三个入口复用，各自传入自己的值：

| 入口 | `connection_id` | `limits.max_message_bytes` | `limits.max_inflight_requests` | 是否强制 |
|------|-----------------|---------------------------|-------------------------------|---------|
| 旧 `/ws`（`system_hello::handle`） | `conn-<uuid4>` | 8 388 608 | 128 | 否。源码注释为 legacy wire hints, not enforced transport limits，只是提示值 |
| Desktop IPC | `ipc-<uuid4>` | `MAX_FRAME_BYTES`（8 388 608） | `MAX_INFLIGHT`（8） | 是，见下文 |
| Web v1 | `web-v1-<uuid4>` | `MAX_MESSAGE`（1 048 576） | 1 | 帧上限强制；请求串行处理 |

在 `/ws` 上，`system.hello` 是 `connect` 之后的探测方法：handler 注释写明它既不准入连接，也不设置身份。

## 传输矩阵

| 入口 | 传输 | 认证 | 能调用什么 | 代码 |
|------|------|------|-----------|------|
| 旧 `/ws`（历史兼容） | WebSocket Text 消息，无长度前缀 | 升级时检查传输与 `Origin`，再由 `connect` 认证 | 完整 RPC，见[方法参考](./methods) | `src/gateway/server/connection/upgrade.rs` |
| Desktop IPC | Unix domain socket，长度前缀帧 | 校验对端为同一用户；不授予网络权限 | 只读：`system.hello`、`health`、`sessions.list` | `src/gateway/server/connection/local_ipc.rs` |
| Web v1 | 原生 TLS 上的 WebSocket Binary 消息，每条消息恰好一帧 | 同源校验 + 会话 cookie（由设备令牌或引导票换取） | 只读：`system.hello`、`health`、`sessions.list` | `src/gateway/server/connection/web_v1.rs` |

认证细节见[身份认证](./auth)，安全边界见 [IPC 协议](../security/ipc)。

### Desktop IPC

入口由 `aleph-server start --desktop-ipc <socket>` 显式开启（`src/bin/aleph-server/cli.rs`）：路径必须是新的绝对 Unix socket 路径，位于调用方持有的 0700 目录；服务端退出后不会删除 socket 条目。仅 Unix 平台可用，其他平台返回 `Desktop IPC is unavailable on this platform`（`src/gateway/server/mod.rs`）。

常量（`src/gateway/server/connection/local_ipc.rs` 与 `shared/client/src/local_ipc.rs`）：

| 常量 | 值 | 含义 |
|------|----|------|
| `MAX_CONNECTIONS` | 8 | 同时服务的连接数；达到上限后暂停 `accept` |
| `WIRE_BUDGET` | `16 * 1024 * 1024` | 每连接在途帧的字节预算；帧头校验通过后、分配载荷前先预留 |
| `WRITE_TIMEOUT` | 5 秒 | 单次写帧超时 |
| `NO_NETWORK_ORIGIN` | `0.0.0.0` | 连接的来源地址，不授予任何网络权限 |
| `MAX_FRAME_BYTES` | `DEFAULT_MAX_PAYLOAD_BYTES` | 单帧载荷上限 |
| `MAX_INFLIGHT` | 8 | 单连接并发在途请求数 |
| `HELLO_TIMEOUT` | 5 秒 | 首帧 `system.hello` 的等待时限 |

行为约束：

- 首帧必须在 `HELLO_TIMEOUT` 内到达且是 `system.hello`，否则返回 `AUTH_REQUIRED`（`system.hello must be first`）并断开。
- 请求必须是 `"jsonrpc": "2.0"` 且带字符串或整数 `id`；不带 `id` 的通知、其他形态的信封都会使连接终止。
- 握手之后只放行 `health` 与 `sessions.list`；其他方法返回 `METHOD_NOT_FOUND`（`method not mounted on Desktop IPC`）。
- 在途请求数达到 `MAX_INFLIGHT`，或出现重复的在途 `id`，连接以 `IPC request limit exceeded` 终止。
- 响应超过帧上限时，改为返回 `INTERNAL_ERROR`（`response exceeds Desktop IPC limits`），不会破坏传输。
- `parse_payload` 还限制 JSON 形态：嵌套深度 64（`MAX_DEPTH`）、单容器条目数 4096（`MAX_ITEMS`）、单字符串 65 536 字节（`MAX_STRING_BYTES`）。

### Web v1

仅在原生 TLS 模式下挂载：`native_tls_router` 把 `connection::web_v1::routes` 合并进路由（`src/gateway/server/mod.rs`）。

| 项 | 值 |
|----|----|
| 会话换取 | `POST /v1/session`，请求体上限 4096 字节 |
| 请求体 | `{"device_token": "..."}` 或 `{"bootstrap_ticket": "..."}` |
| 成功响应 | `204 No Content` + `Set-Cookie: __Host-aleph-v1=<uuid>; Secure; HttpOnly; SameSite=Strict; Path=/; Max-Age=300` |
| 升级 | `GET /v1/ws`，`Sec-WebSocket-Protocol` 必须恰为 `aleph.protocol.v1`，并携带上述 cookie |
| 会话 TTL | 300 秒（`TTL`） |
| 单帧上限 | 1 MiB（`MAX_MESSAGE`） |
| 会话数 / 并发 socket | 256（`MAX_SESSIONS`）/ 8（`MAX_SOCKETS`） |
| IO 超时 | 5 秒（`IO_TIMEOUT`） |

两个端点都先做同源校验（`same_origin`：`Origin` 必须与请求的 `Host` 对应的 `https` 来源一致），再按来源 IP 做速率限制（`throttle`）。失败时返回 `403`（来源不符）、`429`（限流）、`400`（请求体或子协议不合法）、`401`（凭据或 cookie 无效）、`503`（容量或服务未就绪）、`408`（读取请求体超时）。

升级后，每条 WebSocket 消息必须是 **Binary**，且恰好包含一个完整帧（`split_frame` 之后不得有剩余字节）；Text 消息或格式错误会使连接终止。首帧必须是 `system.hello`（5 秒内），之后只放行 `health` 与 `sessions.list`，其他方法返回 `METHOD_NOT_FOUND`（`method unavailable on Web v1`）。会话到期、设备凭据被撤销（每秒检查）或 Gateway 停止时，连接关闭。

### 旧 `/ws`

旧入口用 WebSocket Text 消息承载 JSON 文本，依赖 WebSocket 自己的消息边界；收到 Binary 消息只记录警告并忽略（`src/gateway/server/connection/mod.rs`）。它保留完整 RPC 面，详见[旧 WebSocket 入口](./protocol)。

## 事件与订阅

事件以不带 `id` 的 JSON-RPC 通知下发，`method` 恒为 `"event"`（`TOPIC_EVENT_METHOD`，`shared/protocol/src/jsonrpc.rs`），主题和载荷在 `params` 里：

```json
{
  "jsonrpc": "2.0",
  "method": "event",
  "params": { "topic": "agent.run.complete", "data": {} }
}
```

主题名举例：`agent.run.complete`（`src/gateway/events/frame.rs`）、`session.lifecycle.changed`、`config.changed`（`src/gateway/event_visibility.rs`）。完整主题目录见[事件方法](./methods/events)。

- 订阅用 `events.subscribe`，参数键是 `topics`（字符串模式，或 `{topic, where}` 过滤对象），见 `src/gateway/handlers/events.rs` 的 `SubscribeParams`。
- 当前事件订阅**只在旧 `/ws` 上可用**。Desktop IPC 与 Web v1 只放行 `health` 与 `sessions.list`，没有挂载 `events.subscribe`，因此不会下发主题事件。
- 可见性受 `src/gateway/event_visibility.rs`（按所有者与会话隔离）和 `src/gateway/event_scope.rs`（按角色拦截管理类主题）约束；订阅某个主题不代表能收到其他用户的事件。

## 错误模型

错误分两层，处理方式不同：

| 层 | 例子 | 表现 |
|----|------|------|
| 帧层 | `FrameError::Empty`、`Oversize`、`InvalidUtf8` | 该条流无法继续分帧，连接终止，**没有** JSON-RPC 响应 |
| JSON-RPC 层 | `INVALID_PARAMS`、`AUTH_REQUIRED`、`METHOD_NOT_FOUND` | 带原请求 `id` 的 `error` 响应，连接可继续（握手失败除外） |

帧层的具体表现：Web v1 的 `read` 用 `split_frame`，任何 `FrameError` 或尾部多余字节都使连接结束；Desktop IPC 用 `decode_header` 校验长度（失败即 `invalid IPC frame length`），载荷用 `String::from_utf8` 解码，失败同样使连接结束（`shared/client/src/local_ipc.rs`）。

错误码全集和语义见 [JSON-RPC](../api/jsonrpc)；v1 入口特有的拒绝消息：

| 场景 | 代码 | 消息 |
|------|------|------|
| 首帧不是 `system.hello` | `AUTH_REQUIRED`（-32000） | `system.hello must be first` |
| Desktop IPC 上调用其他方法 | `METHOD_NOT_FOUND`（-32601） | `method not mounted on Desktop IPC` |
| Web v1 上调用其他方法 | `METHOD_NOT_FOUND`（-32601） | `method unavailable on Web v1` |
| Desktop IPC 响应过大 | `INTERNAL_ERROR`（-32603） | `response exceeds Desktop IPC limits` |
| Web v1 响应过大 | 原错误码或 `INTERNAL_ERROR` | `response exceeds Web v1 limits` |

## 规划中：尚未落地的部分

蓝图 `docs/research/NSH_PROTOCOL_V1.md` 自述为「设计基线，实施前需与当前仓库接口盘点对齐」，下列内容属于蓝图而非现状。

> **状态：规划中** — 蓝图为 `docs/research/NSH_PROTOCOL_V1.md`（§10 背压、流控和资源限制）；当前实现见 `src/gateway/server/connection/local_ipc.rs`（`MAX_INFLIGHT`、`WIRE_BUDGET`）与 `src/gateway/server/per_client_buffer.rs`。

蓝图要求每订阅的待发送事件与缓冲字节限额、Ephemeral 事件合并或丢弃、Durable 事件缓冲耗尽时断开或要求 resync。现状只有每连接的在途请求数与字节预算，没有按订阅的背压策略。

> **状态：规划中** — 蓝图为 `docs/research/NSH_PROTOCOL_V1.md`（§9 Snapshot + Replay）；当前实现见 `shared/protocol/src/system_hello.rs`（仅 `Feature::EventReplay`、`Feature::Snapshot` 两个特性标识）。

握手里已有这两个特性名，但服务端实现列表为空（`negotiate_features(&params.features, &[])`），不会协商成功。蓝图中的快照、订阅游标、历史不可用时的 resync、去重与游标语义均无对应实现。

> **状态：规划中** — 蓝图为 `docs/research/NSH_PROTOCOL_V1.md`（§11 二进制数据通道）；当前实现见 `shared/protocol/src/system_hello.rs`（`Feature::BinaryChannel` 仅为特性标识）。

没有二进制通道：Web v1 的 Binary 消息只是承载同一个 JSON 帧的容器，不是蓝图中的资源引用与数据传输通道。

> **状态：规划中** — 蓝图为 `docs/research/NSH_PROTOCOL_V1.md`（§8 Event Envelope、§9.5 去重和游标）；当前实现见 `shared/protocol/src/jsonrpc.rs`（`TOPIC_EVENT_METHOD`）。

当前事件信封是 `{"method":"event","params":{"topic","data"}}`，没有蓝图中的 Durable/Ephemeral 分类与游标字段。

下面两个文件名容易被误认为是 v1 的重放与恢复实现，实际不是：

| 文件 | 实际内容 |
|------|---------|
| `shared/protocol/src/trace_replay.rs` | Agent 执行追踪的查询 DTO：`AgentTraceReplay`、`AgentTraceReplayEntry`、`AgentTraceTaskSummary`，以及 `trace.list` 的 `AgentTraceListRow`、`AgentTraceListPage`、`AgentTraceListCursor`。它回放的是持久化的任务追踪，不是连接上的事件流偏移 |
| `shared/protocol/src/resume.rs` | `ResumeReceipt` 与 `RefusedEntry`：崩溃后恢复中断运行（`agent.resume`、`POST /v1/admin/resume`、`aleph-server resume --json`）的统一回执，与连接断线重连无关 |

## 迁移与兼容

- **旧客户端**继续使用 `/ws` 与 `connect` 握手，无需改动；`connect` 之后也可以调用 `system.hello` 做版本探测，响应里的 `limits` 只是提示值。
- **新客户端**应先握手再发业务方法：Desktop IPC 与 Web v1 强制 `system.hello` 为首帧，业务方法在握手前一律被拒。
- 客户端应检查 `result.protocol.major`，不为 1 即放弃连接，并容忍响应 `features` 中出现自己不认识的字符串。
- 需要订阅事件、调用写类方法的客户端，目前仍只能走 `/ws`。v1 入口的只读范围是现状，扩展方法面属于后续工作，本页不作承诺。
