`exec.*` 是运行时执行等级门控的审批接口。运行时仅提供**两个真实 JSON-RPC 方法**(`exec.approval.resolve`、`exec.approvals.pending`);其余的审批 UX——审批卡的触发、审批卡、Ask / Auto / Full 切换——都内嵌在**代理循环**中,通过 `chat.send` 或 `agent.run` 触发,而不是本命名空间。

26.7.15+ 引入的 Ask/Auto/Full 执行等级门控在 `src/tools/scoped/` 中(动作感知的审批卡,以及绕过斜杠快路径、`tools.invoke` 和后台延续的拦截);相关接线细节见 `docs/superpowers/specs/2026-05-21-gateway-robustness-kit-design.md`。本页面仅记录 RPC 接口。

## 方法

### exec.approval.resolve

用决定解决待处理的审批请求。审批结果是一次性授权(`allow_once`)或更长生命周期的范围(`allow_session`、`allowlist`)。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | 是 | 审批 id(随审批卡/询问卡片一同下发) |
| `decision` | string | 是 | `allow_once` / `allow_session` / `allowlist` / `deny` |
| `resolved_by` | string | 否 | 解决审批的操作员的显示名 |
| `reason` | string | 否 | 自由文本原因;在 `deny` 时原样回传给模型,使其能基于真实反对理由重规划;在 `allow_*` 时被忽略。 |

**响应:** 找到并解决时 `{ "ok": true }`;否则返回 `INVALID_PARAMS: Approval not found or already resolved: <id>`。

### exec.approvals.pending

列出所有仍在等待决定的审批。只读;卡和工具都从同一份内存映射中消费。

**响应:** `{ "pending": [ ...PendingApproval... ] }`。

每个 `PendingApproval` 包含工具调用、运营可授予的作用域,以及产生该卡的 agent session key,这样面板在重载后能重新渲染任何进行中的卡片。

## 不作为 RPC 存在的方法

以下审批 UX 概念不是独立 RPC；当前注册项见 `src/gateway/method_census.rs`:

| UX 操作 | 不作为 RPC 存在的原因 |
|------|---------------------|
| 审批卡的触发 | 模型从不主动调用——`src/tools/scoped/` 中的动作感知门控在工具元数据提示需要确认时,直接在事件总线上抛出审批卡。 |
| 读取审批配置 | 没有"审批配置"可读——授权是内存中的一次性 / 会话级产物,无磁盘形态。 |
| 写入审批配置 | 同上,没有可写的配置。 |

客户端若想程序化驱动流程,唯一的合法入口是 `exec.approval.resolve`(回答一张卡)和 `exec.approvals.pending`(枚举开放中的卡)。
