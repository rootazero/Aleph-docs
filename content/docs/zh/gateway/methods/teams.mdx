`teams.*` 是每团队的 CRUD + 协调面。大约三十个方法分布在两次注册中:

- `register_teams_handlers`(`src/bin/aleph-server/commands/start/builder/handlers/agents.rs`)——仅依赖 store 的处理器,只要 `team_store` 构造了就一直注册。
- 两个在 `agent_init/mod.rs` 中手动连线的 `teams.chat.send` 和 `teams.chat.cancel`——仅在 team store 存在时注册,因为它们需要 `GatewayContext` + 执行路径来驱动 leader 运行和中止 fan-out 树。

团队的工作线程是持久的(`CoordTask` 看板 + `team_messages`);实时对话气泡(leader / member 叙述)在事件总线上以 `team.<id>.*` 流式传输,不作为 `teams.*` RPC 可查询。重载后,Panel 显示持久记录(任务 + 交付物),而非实时叙述。

## 方法

### CRUD

#### teams.create

创建持久团队。leader 自动以 `role="leader"` 注册。`auto_name: true` 触发一次性自动命名标志,使第一次 `teams.chat.send` 用 LLM 生成的主题替换临时名称。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `name` | string | 是 | 团队名(非空) |
| `description` | string | 否 | 自由文本描述 |
| `leader_id` | string | 是 | leader 的 agent id(规划 + 审查成员工作) |
| `members` | object[] | 否 | 每项 `{ "agent_id", "role" }`(默认 role:`member`)。leader 自动注册;重复跳过。 |
| `auto_name` | boolean | 否 | `true` 触发首发自动命名 |

**响应:** `{ "team_id", "name", "leader_id" }`。

#### teams.get

获取团队的完整记录(团队、成员、任务)。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |

**响应:** `{ "team": { ...Team... }, "members": [ ...TeamMember... ], "tasks": [ ...CoordTask... ] }`。

#### teams.list

列出所有团队。**响应:** `{ "teams": [ ...TeamSummary... ] }`。

#### teams.rename

重命名团队。Panel 侧边栏的 inline-edit 走这条路径。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |
| `name` | string | 是 | 新名称(非空) |

**响应:** 成功时 `{ "ok": true }`;未知 id 返回 `RESOURCE_NOT_FOUND`(`-32004`)。

#### teams.disband

将团队标记为已解散(工作状态被拆除,历史保留)。触发 `team.changed` 事件,使群聊侧边栏和团队标签都刷新。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |

**响应:** `{ "success": true }`。

#### teams.delete

永久删除团队并级联清理。完整变体(`handle_delete`)级联五个从属存储(任务 / 工件 / 事件 / 消息 / 快照)。基础变体(`handle_delete_basic`)在从属存储未配置时使用。运行时只连接其中的一个,取决于哪些存储存在。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |

**响应:** `{ "success": true }`。

#### agents.teams

列出 agent 所属的所有团队(作为 leader 或 member)。当提供 live `AgentManager` + `MessageStore` 时,每个团队摘要会增加 `members_preview`(最多 4 个成员,含 name + emoji)和 `last_message` / `last_message_at`(最近的转写条目,截断到 60 字符)。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `agent_id` | string | 是 | agent id |

**响应:** `{ "teams": [ ...含 members_preview + last_message + last_message_at 的 TeamSummary... ] }`。

### 聊天

团队工作线程是持久的(任务 + 工件),但实时对话气泡是流式的。重载后,Panel 显示持久记录。

#### teams.chat.send

启动(或继续)团队工作线程。将用户消息存入共享转写,然后通过 `GroupChatBroadcaster` 按 `@mention` 进行扇出(无 `@` 时回退到 leader)。扇出树先注册为跟踪节点,因此返回的 `run_id` 立即可被取消。

在第一条消息上,如果团队是用 `auto_name: true` 创建的,主题 LLM 会在后台触发,替换临时名称。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |
| `message` | string | 是 | 用户消息(非空) |

**响应:** `{ "run_id": "<uuid>" }`。将这个 `run_id` 与 `teams.chat.cancel` 配合使用即可停止扇出。

#### teams.chat.cancel

停止进行中的 `teams.chat.send` 扇出树。树级令牌先被投毒,然后每个仍运行的成员运行通过引擎的每运行 `CancellationToken` 被取消。未知的或已结束的 `run_id` 返回 `RESOURCE_NOT_FOUND`。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `run_id` | string | 是 | `teams.chat.send` 返回的 `run_id` |

**响应:** `{ "run_id", "cancelled": true, "members_running", "members_signalled" }`。

#### teams.chat.history

将团队的持久群聊转写作为归属气泡回放。丢弃定向收件箱流量(通知器摘要、路由提示、发现 ping)——只呈现对话行(`MessageType::Message`)和广播器的对话内通知。返回最新的 200 个对话可见行。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |

**响应:** `{ "items": [ ...{from_agent, content, msg_type, kind: "user"|"agent"|"system", created_at}... ] }` 按时间正序。

#### teams.chat.thread

hydrate 团队的持久工作线程:`CoordTask` 和它们的提交工件按时间合并。实时对话气泡**不**包含在内——它们在运行期间通过 `team.<id>.*` 流式传输。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |

**响应:** `{ "items": [ ...{kind: "task"|"artifact", agent_id, title, content, timestamp, artifact_id?}... ] }` 按 `timestamp` 排序。

### 任务 / 看板

看板状态机为 `Pending → InProgress → WaitingReview → Completed`(还有 `Blocked` / `Failed` / `Cancelled` / `Skipped` / `Paused` / `Unsatisfiable` 用于 Panel 绘制路径)。

#### teams.create_task

在团队的看板上创建一个 `CoordTask`。当提供 `owner` 时,任务被打上 `metadata.managed_by = "dispatcher"` 标记,自主调度器就会认领它;没有这个标记,`select_schedulable` 会过滤掉该任务,看板就不会推进。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |
| `subject` | string | 是 | 非空任务主题 |
| `description` | string | 否 | 自由文本描述 |
| `owner` | string | 否 | agent id;触发 `managed_by=dispatcher` |
| `priority` | string | 否 | `low` / `normal` / `high` / `critical`(未知 id 返回 `INVALID_PARAMS`) |
| `blocked_by` | string[] | 否 | 此任务被阻塞的其他任务 id |
| `metadata` | object | 否 | 每任务元数据(原样保留) |

**响应:** `{ "task": { ...CoordTask... } }`。

#### teams.update_task

增量更新任务。`metadata` 是**浅合并补丁**(读取之前的元数据并合并),因此 Panel 用户的 `metadata.managed_by=...` 写入不会擦除调度器的其他控制键。

`status` 接受 `pending` / `in_progress` / `completed` / `failed` / `cancelled`。`blocked` 是派生的,不存储——发送 `status="blocked"` 会被 `INTERNAL_ERROR` 拒绝。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `task_id` | string | 是 | 任务 id |
| `status` | string | 否 | 新状态(见上) |
| `owner` | string | 否 | 新 owner agent id |
| `result` | string | 否 | 自由文本任务结果(在重试 / 重置时清除) |
| `metadata` | object | 否 | 浅合并补丁 |

**响应:** `{ "task": { ...更新后 CoordTask... } }`。

#### teams.list_tasks

列出团队任务,可选过滤。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |
| `status` | string | 否 | 完整 10 变体词表:`pending` / `blocked` / `in_progress` / `waiting_review` / `completed` / `failed` / `cancelled` / `skipped` / `paused` / `unsatisfiable`(未知字符串返回显式错误) |
| `owner` | string | 否 | 按 owner agent id 过滤 |

**响应:** `{ "tasks": [ ...CoordTask... ] }`。

#### teams.list_task_runs

任务每次尝试的执行历史,按时间正序。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `task_id` | string | 是 | 任务 id |

**响应:** `{ "runs": [ ...CoordTaskRun... ] }`。

#### teams.add_task_comment / teams.list_task_comments

每个任务的自由文本交接便签。由成员留下上下文,由 Panel 用户标注状态。

`add_task_comment`:

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `task_id` | string | 是 | 任务 id |
| `author` | string | 是 | 非空作者 |
| `body` | string | 是 | 非空正文 |

**响应:** `{ "comment": { ...CoordTaskComment... } }`。

`list_task_comments`:

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `task_id` | string | 是 | 任务 id |

**响应:** `{ "comments": [ ...CoordTaskComment... ] }`(按时间正序)。

#### teams.list_task_events

读取团队事件日志中筛选到单一任务的部分。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `task_id` | string | 是 | 任务 id |

**响应:** `{ "events": [ ...EventLogStore::Event... ] }`(按时间正序,payload 中 `task_id` 匹配)。

#### teams.task.trace

单个任务的统一审计时间线:`task` + `runs` + `comments` + `events` + `artifacts` + `journal` 一次往返。缺失的可选存储(event_store / artifact_store)降级为空数组。Panel 的"Replay"抽屉在打开时调用此接口。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `task_id` | string | 是 | 任务 id |

**响应:** `{ "task", "runs": [...], "comments": [...], "events": [...], "artifacts": [...], "journal": CoordTaskJournal | null }`。

#### teams.task.journal.get / teams.task.journal.list

每任务退出 journal 的读面(写面是 `task_exit_journal` 内建工具)。退出 journal 是成员在运行完成时写入的持久记录。

| 方法 | 参数 | 说明 |
|------|------|------|
| `teams.task.journal.get` | `task_id` | `{ "journal": CoordTaskJournal_or_null }` |
| `teams.task.journal.list` | `team_id` | `{ "journals": [ ...CoordTaskJournal... ] }`(最新在前) |

#### teams.task.pause / resume / retry / skip

管理员上下文的任务控制(处理器见 `src/gateway/handlers/teams/workflow.rs`)。评审上下文的任务改用 `teams.workflow.{approve,reject}_step`。

- `teams.task.pause` — 仅允许从 `pending` / `blocked` / `unsatisfiable` 暂停;对已是 `paused` 的任务幂等返回 `paused`;其他状态(包括 `in_progress` 与 `waiting_review`)返回 `INVALID_PARAMS`。暂停时会把 `paused_from` 标记显式写为 `null`,避免上一轮暂停→重试遗留的标记把这次暂停误还原。调度器不会认领 `paused` 任务。
- `teams.task.resume` — 仅允许从 `paused` 恢复。若元数据里的 `paused_from` 标记指向 `waiting_review`,则还原为 `waiting_review`,否则还原为 `pending`;同一次写入清除该标记。
- `teams.task.retry` — 除 `in_progress`(返回 `INVALID_PARAMS`,需先取消)外任何状态都可重试:状态置为 `pending`、清空 `result`、重新装填自动重试预算,并用真实持有者(而非空串)释放遗留的锁。历史运行记录保留。
- `teams.task.skip` — 管理员跳过,对状态没有前置要求,不需要已完成的运行;任务置为 `skipped`,下游依赖随之解除阻塞。

四者都只接收 `task_id`。响应:`{ "status": "paused" | "pending" | "skipped" }`(`resume` 返回被还原后的状态,即 `pending` 或 `waiting_review`)。他人团队的任务与不存在的任务不可区分。

### 工作流

#### teams.workflow.approve_step / reject_step / teams.task.retry

评审上下文的工作流步骤评审(`src/gateway/handlers/teams/workflow.rs`)。最新一次运行会被盖上评审结论,任务随后转为 `completed` / `failed`。仅当任务当前状态允许评审(已经有运行产出)时才受理,否则返回 `INVALID_PARAMS`;任务已处于目标终态时幂等返回,不重复写入。`comment`(非空白时)会作为任务评论写入,作者为 `reviewer_id`,缺省为 `review:<kind>`。

`reviewer_kind` 必须是 `user` / `lead_agent` / `auto` 之一,缺省为 `user`。

| 方法 | 参数 | 说明 |
|------|------|------|
| `teams.workflow.approve_step` | `task_id`, `reviewer_kind?`, `reviewer_id?`, `comment?`, `grounding?` | `{ "status": "completed" }`。任务带有 `require_grounding: true` 时必须提供 `grounding` 度量(`kind` 取 `exit_code` / `numeric` / `line_count`),否则返回 `grounding_required` 的 `INVALID_PARAMS` |
| `teams.workflow.reject_step` | `task_id`, `reviewer_kind?`, `reviewer_id?`, `comment?` | `{ "status": "failed" }`。评论只进入任务评论线程(供重做的成员阅读),**不会**写入任务 `result` |
| `teams.task.retry` | `task_id` | 管理员任务控制:重置自动重试预算并清空 `result`,不是工作流评审方法 |


#### team_workflow_canvas: export / import

以内建工具 `team_workflow_canvas` 导出/导入 Obsidian JSON Canvas 1.0 **，不是 Gateway RPC 方法**。工具实现见 `src/builtin_tools/team/workflow_canvas.rs`,底层转换在 `src/teams/workflow_canvas.rs`,画布文档类型为 `aleph_protocol::json_canvas::Document`。

工具参数(`action` 取 `export` 或 `import`):

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `action` | string | 是 | `export` 或 `import` |
| `team_id` | string | 是 | 团队 id;团队不可达时报「team not found」 |
| `status` | string | 否 | 仅 `export`:与 `teams.list_tasks` 相同的完整 10 变体词表,未知值直接报错 |
| `canvas` | object | `import` 必填 | 要落地的 JSON Canvas 文档 |
| `dry_run` | boolean | 否 | 仅 `import`:只返回计划,不写入(默认 `false`) |

代码里没有 `owner` 过滤参数。

**导出结果:** `{ "team_id", "canvas": { ...Document... }, "node_count", "edge_count" }`。

**导入结果(dry_run):** `{ "team_id", "created", "dry_run": true, "tasks": [ ...{subject, description, blocked_by, metadata}... ] }`,其中 `created` 是计划任务数。

**导入结果(正式):** `{ "team_id", "created", "dry_run": false, "tasks": [ ...{id, subject}... ] }`。每个文本节点成为一个任务,每条边成为 `blocked_by`;实现会做拓扑遍历,先延后本批次内尚未创建的阻塞者,并把画布节点 id 改写为真实任务 id;存在环或无法解析的依赖时整体报错。

### ACP 成员

外部编码 CLI 会话(Claude Code、Codex 等)作为一等团队成员接入。调度器会把归属于 ACP 成员的任务经 ACP 适配器池派发,而不是进程内的代理注册表(处理器见 `src/gateway/handlers/teams/workflow.rs`)。

| 方法 | 参数 | 说明 |
|------|------|------|
| `teams.acp_member.add` | `team_id`, `harness_id`, `cwd`, `session_name?`, `role`(默认 `acp-worker`) | 对 (team, harness, cwd, name) 幂等;返回 `{ "member": { ...NewTeamMember::for_acp_session... } }`。其 `agent_id` 即后续任务 `owner` 所用的值 |
| `teams.acp_member.remove` | `team_id`, `agent_id` | 返回 `{ "success": true }`。只移除 ACP 成员行,池中底层 ACP 会话**不会**被终止(其他团队可能仍在引用;需要终止请用 `acp.sessions.shutdown`)。非 ACP 成员返回 `INVALID_PARAMS`(请改用 `teams.remove_member`),不存在的成员返回 `RESOURCE_NOT_FOUND` |
| `teams.acp_member.list` | `team_id` | `{ "members": [ ...仅 ACP 成员... ] }`(过滤 `kind == TeamMemberKind::AcpSession`) |

### 用量

#### teams.usage

按团队聚合 provider token 用量,数据来自 `task_traces` 中 `event_kind = 'provider_usage'` 的事件(网关执行引擎已写入这些事件),按团队当前成员的 `agent_id` 汇总(`src/resilience/database/traces.rs` 的 `aggregate_usage_by_agents`)。没有用量的成员不会出现在 `per_agent` 中。这里刻意**不**计算成本——token 是事实,成本属于费率策略。需要 `state.db`,未接入时该 RPC 不会注册。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `team_id` | string | 是 | 团队 id |
| `since` | number | 否 | 下界,epoch 秒(缺省:不限) |
| `until` | number | 否 | 上界,epoch 秒(缺省:不限) |

**响应:** `{ "team_id", "since", "until", "member_count", "total": { "call_count", "input_tokens", "output_tokens", "cache_read_tokens", "cache_creation_tokens", "reasoning_tokens", "cache_hit_ratio" }, "per_agent": [ ...AgentUsageTotal... ] }`。


#### teams.list_templates

列出可用的团队模板(内置 + 用户目录)。实例化本身走 `team_from_template` 内建工具,因此重依赖不会在网关里重复接线。

**请求:** 无参数。

**响应:** `{ "templates": [ ...{name, description, default_goal, leader_id, leader_role, member_count, task_count}... ] }`。

### 快照

与内建工具 `team_snapshot` 对应,使面板和外部调用方无需经过 tool-invoke 即可访问快照存储。五个处理器共用同一套底层函数,因此行为、dry-run 默认值和依赖边还原语义与该工具一致(处理器见 `src/gateway/handlers/teams/snapshot.rs`)。

| 方法 | 参数 | 说明 |
|------|------|------|
| `teams.snapshot.create` | `team_id`, `tag?`, `note?` | `{ ...捕获结果... }` |
| `teams.snapshot.list` | `team_id?` | `{ "snapshots": [ ...SnapshotMeta... ] }`(最新在前);不带 `team_id` 时只返回调用方可见团队的快照 |
| `teams.snapshot.get` | `snapshot_id` | `{ "meta", "payload" }`,不存在(或不可见)时返回 `RESOURCE_NOT_FOUND` |
| `teams.snapshot.restore` | `snapshot_id`, `apply`(默认 `false`,即 dry-run) | `{ ...SnapshotDiff... }`(两种模式都返回 diff;`apply=true` 时同时还原依赖边) |
| `teams.snapshot.delete` | `snapshot_id` | `{ "snapshot_id", "existed": <bool> }`(幂等;不可见的快照同样返回 `existed: false`) |

快照处理器仅在启动时构造了 `SqliteSnapshotStore` 的情况下才会注册(`src/bin/aleph-server/commands/start/builder/handlers/agents.rs`);否则这些 RPC 不存在,调用方仍可通过 `team_snapshot` 内建工具操作快照。
