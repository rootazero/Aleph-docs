## 概览

Aleph 的执行审批系统是一个 **action-aware** 的人机回环门：每个 shell
命令、每个变更操作、每个审批门后的工具调用都通过同一个强制点
`src/sandbox/exec_approval/`，人类看到的是 *这次调用* 而不是 *工具名*，
授权指纹键绑定在**原始规范化参数**上。

核心设计要点：

1. **默认拒绝** —— 任何工具若 `ScopedToolService` 判定为非幂等/要求审批，
   都必须经过门。
2. **元数据驱动** —— 门读 `ToolFacts { name, idempotent, requires_approval }`
   的 `idempotent` / `requires_approval`，**不**读工具名 —— MCP 工具以
   `{server}__{tool}` 注册，名字白名单会让一整个家族无声地通过门。
3. **Action-aware** —— 看到的是 *真实调用*（`ApprovalAction` 携带实际命令
   / `operation=delete path=…`），不是 `bash` 这种单词。
4. **授权指纹键 = 规范化参数** —— 用原始参数，**不**用脱敏摘要（脱敏把
   不同密钥塌成同一占位符，一个授权会覆盖另一个密钥）。

**源位置：**
- 强制点：`src/tools/scoped/`（`dispatch.rs`、`builder.rs`、`traits.rs`）
- Action-aware 门：`src/sandbox/exec_approval/`（`gate.rs`、`action.rs`、
  `session_memory.rs`、`denial_ledger.rs`）
- Exec tier：`src/config/types/policies/exec_tier.rs`
- Pending / resolve 配对：`src/exec/manager.rs`（`ExecApprovalManager`）
- 渲染助手：`src/exec/parser.rs::analyze_shell_command`（仅渲染）

## 架构

```
工具调用
   │
   ▼
ScopedToolService::execute_inner
   │
   ├── [policies.tool_permissions]   ──  显式条目胜出
   │
   ├── exec tier  ──────────────────►  Ask / Auto / Full
   │                                    │
   │                                    ▼
   │                              ToolFacts 读取
   │                              (idempotent, requires_approval)
   │
   ├── [sandbox.command_policy] ───  硬线命令底线（任何 tier 不能降级）
   │
   ▼
ApprovalGate (action-aware)
   │
   ├── grant_fingerprint(tool, 规范化参数)
   │       │
   │       ├── 在 session_memory 命中？──► Allow（cached）
   │       │
       └── 否则：
           渲染 ApprovalAction（命令 / op=delete path=…），
           通过 ApprovalRequester 路由给人类
           │
           ├── AllowOnce  ─► 这次调用
           ├── AllowSession ─► 这次 + 同指纹的未来调用（按 fingerprint 缓存）
           ├── AllowAlways ─► 由 clamp_decision 收紧到 AllowSession
           │                  （没有持久 allowlist —— 此按钮永远不渲染）
           ├── Deny <reason> ─► 拒绝；reason 渲染回模型
           └── Timeout ─► 拒绝（不写入 ledger）
```

## Exec tier（Ask / Auto / Full）

`[policies] exec_tier` 是工具权限之上唯一面向用户的旋钮。**不是**第二个
策略引擎，也不是第二个强制机制：它是同一个 chokepoint 上的一组规则，在
没有显式 `[policies.tool_permissions]` 条目命名工具时被咨询。

| Tier | 行为 | 备注 |
|------|------|------|
| `Ask` | 每个变更 / 副作用工具都需要审批；只读工具保持允许 | 模型仍能调查 |
| `Auto`（默认） | 仅不可逆尾部审批 | `*_delete`、`vault_*`、`team_disband`、MCP 服务器的 `destructiveHint`、`file_ops` 参数级 `delete` / `move` |
| `Full` | 不审批 | `[sandbox.command_policy]` 底线仍然有效 |

### Lattice（谁胜出）

```
显式 [policies.tool_permissions] 条目   (精确名 > glob)
        ↓  (没有条目命名这个工具)
配置 default   被 tier 判决收紧
        ↓  (restrictive_min —— tier 只能收紧不能放宽)
[sandbox.command_policy] 硬线底线      (没有 tier 能降低 —— Full 也不能)
```

`effective_permission(permissions, tier, facts)` 是这个优先级**唯一**的
组合点。两个消费者（`ScopedToolService::permission_for` 与 gateway
slash-command 快路径）都调用它，两个 surface 不可能漂移。

### Tier 来自哪里（per-turn）

`resolve_turn_permissions` 每 run 解析一次：**request > session > global**。

- **request** —— Panel composer pill 把 tier 跟首条消息一起发
  （`chat.send`），所以它治理的就是它被装备的那个 turn。
- **session** —— 持久化到 `identity_meta.custom["exec_tier"]` 经
  `sessions.patch`（与 `project_root` 同载体）。`null` = 跟随 global。
  `sessions.patch` 校验值与 `ExecTier::from_id`，与 `chat.send` 完全相同。
- **global** —— `[policies] exec_tier`，per-turn 实时读取（无需重启）。
- **非操作员调用方**（chat-tier 通道）在解析后被收紧：能收紧 tier 但
  永远不能放宽。

### 未知工具默认 fail-closed

`ToolFacts` 从工具的 `ToolDefinition` 填充：

- `idempotent` ← `LoopTool::is_idempotent()` —— 内置纯读 allowlist
  （`tools/retry.rs::is_idempotent_builtin_name`，委托给
  `tools/adapters/registry_adapter.rs::READ_ONLY_TOOLS` 这一个列表 —— 是
  并发安全声明、自动重试、本 tier 规则的**单一**来源），或 MCP 服务器
  的 `readOnlyHint` / `idempotentHint`。任何不声明的 = `false`。
- `requires_approval` ← `ToolDefinitionMetadata`（MCP 服务器的
  `destructiveHint`）。

于是 **非幂等 = mutating**，**未知工具 = 非幂等**，所以 `Ask` tier 对
Aleph 从未听过的工具 fail-closed。名字 globs 表做不到这一点 —— MCP 工具
以 `{server}__{tool}` 注册（`github__delete_repo`），任何 glob 表都会让
整个家族无声通过它声称要守卫的门。

唯一例外是参数级：`file_ops` 把 `list` 和 `delete` 多路复用到同一个名字
下，所以 `ExecTier::asks_for_arguments` 读 `operation` 字段。这是
R7 明确允许的确定性硬过滤，不是关于意图的判断。

## Action-aware 审批门

### `ApprovalAction`

门被问到的是 *这次调用*，不是 *这个工具*：

```rust
// src/sandbox/exec_approval/action.rs
pub struct ApprovalAction {
    pub tool_name: String,
    pub summary: String,             // 实际调用（脱敏 + 截断）
    pub cwd: Option<String>,
    pub analysis: Option<CommandAnalysis>,
    pub reason: String,
}

// src/sandbox/exec_approval/gate.rs
trait ApprovalRequester {
    async fn request_approval(&self, action: &ApprovalAction) -> ApprovalResponse;
}
pub struct ApprovalResponse {
    pub outcome: ApprovalOutcome,
    pub deny_reason: Option<String>, // 人类在 /deny <reason> 时的原话
}
```

`summary` 渲染**实际**发生的事 —— `bash` / `code_exec` 的命令（过真正的
`exec::parser::analyze_shell_command`）、`file_ops` 的 `operation=delete
path=…`、否则 `k=v` —— 然后过 `SecretMasker`，换行被压平，在
`char_indices()` 边界上截断到 200 字符。**一个对被它守卫的东西遮遮掩掩
的确认门会训练用户去点 Approve**，这让整个 tier 系统变成演戏；现在
每个 surface（Panel 卡片、纯文本通道提示、集群节点反向 RPC）都显示
真实动作。

### 授权键绑定在动作上，不绑定在工具上

`confirm_with_memory` 一次计算 `grant_fingerprint(tool, &args)` —— 对
**原始**规范化参数（**不**是脱敏摘要 —— 脱敏把不同密钥塌成同一占位符，
一个授权会覆盖另一个密钥），并用于**会话内存**和**拒绝账本**。

后果："Allow for this session" 授权**那个精确调用**。`Ask` 下，`bash`
对每个不同命令重新提示，而不是一次授权后任意 argv 都被白名单
（codex 的 `ApprovalStore` 语义）。更吵，故意为之。

### 决策

```rust
// src/exec/socket.rs
pub enum ApprovalDecisionType {
    AllowOnce,    // 仅此次调用
    AllowSession, // 此次调用 + 本会话内同指纹（按 fingerprint 缓存）
    AllowAlways,  // 由 clamp_decision 收紧到 AllowSession
                  // —— 没有持久 allowlist，所以这个按钮永远不渲染
    Deny,
}
```

- **超时 ⇒ 拒绝**。`DEFAULT_APPROVAL_TIMEOUT_MS = 120s`；
  `ApprovalOutcome::is_approved` 排除 `Timeout`。超时被故意**不**写入
  denial ledger —— 过期卡片不是决策。**没有** fail-open 路径。
- **孤儿无法劫持卡片**。`PendingEntry::is_live()`（非过期 ∧ 接收者未
  关闭）过滤 `resolve_for_session` 和 `list_pending`，所以被取消 run
  的僵尸再也不能赢得 `/approve` FIFO 或渲染。
- **拒绝是终结的**（对此调用），以一个 in-context 指令返回给模型：
  不要重试、不要改写、不要用其他方式达到相同结果。三次拒绝触发
  `denial_ledger.rs` 里的粘性暂停。
- **拒绝可以携带人类的理由**：`/deny wrong directory, use /tmp`（频道）
  或 `exec.approval.resolve {reason}`（RPC）把 `ExecApprovalRecord.deny_reason`
  打上戳；门把它原样渲染到面向模型的错误（`The user said: "…"`），让
  模型按实际异议重新规划。**显示层** —— ledger 仍按 fingerprint 键控。

### 决策传输

所有审批都通过 WebSocket JSON-RPC 路由：

- Panel → `exec.approval.list` / `exec.approval.resolve {outcome, reason}`
  RPC；
- 频道（Telegram / Discord / iMessage）→ 同一组 RPC，UI 渲染为按钮；
- 集群节点 → 反向 RPC（`exec.approval.resolve` 也接受可选 `reason`
  参数；老节点忽略它）。

历史上有过一个 Unix-socket IPC 传输（`src/exec/socket.rs` 文档说明）——
它从未被接入 server，已经移除；唯一的线协议就是 WebSocket + JSON-RPC。

## 命令分析（仅用于审批卡渲染）

`src/exec/parser.rs::analyze_shell_command` 把 shell 字符串拆成程序 / 参数 /
段。它的输出给**审批卡摘要**（让人类在批准 `bash` 调用时看到真实命令，
不是单词 `bash`）—— 它是**渲染助手**，不是强制门。实际拒绝命令的
硬线底线是 `sandbox::command_policy`，其真实的硬线规则
（`command_policy/rules.rs::hardline_rules`）覆盖：
- fork bomb；
- 裸根 `rm -rf /` / `rm -rf //` / `/.`（cycle 7 收紧 multi-slash /
  dot bypass）；
- `dd` / `mkfs` / 重定向到裸块设备；
- Windows 上驱动器 / 配置单元根的递归删除、`format`、shadow-copy 销毁链；
- `powershell -EncodedCommand` 载荷解码后再匹配，所以给脚本加编码不会
  让它从底线视野中消失。

## 输出屏蔽

两个独立路径，按消费者：

- **`SecretMasker`**（`src/exec/masker.rs`）—— 面向人 / 日志字符串
  脱敏（审批卡摘要用它）。
- **`sandbox::scrub::scrub_and_gate_output`**（`src/sandbox/scrub.rs`）
  —— 已完成命令的 stdout / stderr 的**单一**真实来源：字节级脱敏、
  剥离隐形 / bidi 控制字符、返回 **block-class** 判定。block-class 命中
  （PEM 私钥 —— `leak_detector::BLOCK_CLASS_SECRETS`）让沙箱**失败关闭**，
  而非返回周围上下文。`WorkspaceSandbox` 与 `WorktreeSandbox` 都把输出
  路由通过它 —— 底线不可能在执行路径间漂移。

两个密钥正则的目录在 `src/secrets/leak_detector.rs` 与
`src/exec/secret_patterns.rs`，相互对齐（私钥正则两边都是
`-----BEGIN[A-Z ]*PRIVATE KEY-----`，裸 PKCS#8 头无法只躲过一个）。

## 三个被关掉的旁路（不要重开）

每一个都是一个能执行工具而**不**通过 `ScopedToolService` 的 surface。
加新 surface 时，这是第一个要问的问题。

1. **Slash-command 快路径**（`execution_engine/slash_command.rs`）。`/bash`
   `/file_ops` 等直接进 `BuiltinToolRegistry` —— 没有 tier、没有
   `tool_permissions`、没有 `requires_confirmation`、没有操作员门，并且
   该路径可从**通道**触达。现在 `slash_gate_reason()` 对任何 gated 调用
   返回已有的 `ExecutionError::Fallthrough`，把它路由进完全 gated 的
   agent loop；ungated slash 保留它们确定性快路径。
2. **`tools.invoke` RPC**（`gateway/handlers/tools_invoke.rs`）。它的
   denylist（`security/dangerous_tools.rs`）曾经列 7 个**不存在的**工具
   —— 它一辈子都不可用。现在它列真实存在的工具并拒绝 confirmation-gated
   的工具（`is_confirmation_gated` 读 `CONFIRMATION_REQUIRED_TOOLS`）。
   *已知限制*：参数级 ask（一个 `Auto` tier 的 `file_ops delete`）在这
   个直接 invoke surface 上仍然 ungated —— 关这个需要 RPC 上的审批
   transport。
3. **后台 run**（goal / loop continuations、cron、heartbeat、a2a）。过去
   一个延续会丢掉 `caller_role` 和通道的 `tool_permissions` 层 —— 一个
   chat-tier Telegram 会话通过延续把自己升级成本地操作员权限。
   `carry_policy_metadata` 现在精确转发那两个键（**故意不**带
   `channel_id` / `conversation_id` —— 那会让一个 unattended run 的审批
   看起来可下发）。

## 未出席 = 失败关闭

无人类在场的 run 在每个 headless producer 处打上 `UNATTENDED_KEY`
戳（`execution_engine/mod.rs`）：cron **当它的审批不可路由时**（携带源
通道与会话的 job 有真正的 `/approve` 路径 —— 打戳会让工作的 HITL 流程
auto-deny）、heartbeat 总是、a2a 总是。`continuation_metadata` **最后**
插入这个标记，所以继承的 key 永远不能把延续降级为 attended。这个标记
也搭 `TurnContext.unattended` —— 所以 `session_send` 给 headless 父的
wait-mode 子也打戳（`fire_and_forget || parent.unattended`）——
过去只有 fire-and-forget 子被打戳，headless 父的 wait-mode 子在每个
gated 工具上挂满 120 秒才拒绝。

`ScopedToolService` 然后**立即**拒绝 confirm-gated 工具，而不是把审批
卡片发到虚空中再阻塞 120 秒。模型被告知该 run 是 unattended。

Team（dispatcher / broadcast）被故意**不**打戳：成员的审批解析成一张
Panel 卡片，调度 team 的用户就是看着它的操作员。

## 审计

**Session event log** 是活的 trail（`tools/scoped/dispatch.rs::record_approval_decision`
写 `ToolCallApproved` / `ToolCallDenied` session 事件）。通过 session
service 查，与产生该决策的 run 的其它事件一起。

**不要再去查** `src/exec/approval/storage.rs` 或 `audit.rs` —— 它们与
`aleph-server audit` CLI 在 2026-07-14 一起删除了：三个 SQLite 表
（`~/.aleph/approval_audit.db`）的**唯一**写入者是测试 helper，让
操作员跑 `audit` 得到 0，得出"什么都没发生"的结论，而真正的 trail
在 session event log 里。这比死代码更糟。同时删除的零消费者模块：
`src/exec/approval/{escalation,binding,path_canonicalize}.rs`、
`benches/approval_performance.rs`、
`exec/allowed_decisions.rs::{decisions_for_risk, assess_command_decisions,
risk_segments}`。
