## 概览

设备配对是 Aleph 的信任建立协议。新设备（macOS 应用、iOS 客户端、Web
浏览器）或新聊天发送者（Telegram 用户、Discord 成员）在与 Aleph 交互
之前，必须完成验证"连接是否由服务器所有者授权"的配对流程。

两类信任建立：

| 类型 | 用途 | 凭证 |
|------|------|------|
| **设备配对** | 远程桌面 / 手机 / CLI 客户端 | `aleph-bt-*` 启动票换取 `aleph-dt-*` 设备 token |
| **频道发送者配对** | Telegram / Discord / iMessage 未知发送者 | 6 字符字母数字代码（inbound router 单源存储） |

两者都通过 **RPC** 管理（`pairing.list` / `pairing.approve` /
`pairing.reject` / `gateway.ticket.create`），不是 CLI 命令。

**源位置：**
- 设备票 + token 管理：`src/gateway/security/device_token_manager.rs`
- 频道配对存储：`src/gateway/pairing_store.rs`
- 设备注册表（共享 + 集群节点）：`src/gateway/security/store/devices.rs`
- 加密工具：`src/gateway/security/crypto.rs`
- 安全存储：`src/gateway/security/store/`
- CLI：`src/bin/aleph-server/commands/pair.rs`、`bootstrap_token.rs`
- 票 + 设备 RPC：`src/gateway/handlers/gateway_ticket.rs`、
  `src/gateway/handlers/gateway_devices.rs`

## 为什么配对？

Aleph 是一个自托管的 AI 助手，可以访问你的文件、shell 和在线账户。
允许不受限制的连接将是一个重大安全风险。配对协议解决三个问题：

1. **身份验证** —— 确保连接的设备或用户由服务器所有者授权。
2. **密钥交换** —— 设备在配对期间提交（或获得）其密钥材料，用于未来
   连接的加密认证。
3. **范围限制** —— 频道发送者在配对时获得有限的权限。

## 设备配对（远程 Panel / CLI）

### 流程

```
设备                            Gateway                         操作员
 │                                │                              │
 │── gateway.ticket.create ──────►│                              │
 │                                │                              │
 │◄── { ticket: "aleph-bt-x",   ──│                              │
 │     urls: [...] } ────────────│                              │
 │                                │                              │
 │   [设备 / QR 扫描 / 键入]      │                              │
 │   [URL 来自服务端,             │                              │
 │    含 ?bt=aleph-bt-x]          │                              │
 │                                │                              │
 │── WS /ws connect {             │                              │
 │     bootstrap_ticket:          │                              │
 │     "aleph-bt-x" } ──────────►│                              │
 │                                │                              │
 │   [exchange_bootstrap_ticket]  │                              │
 │   [mint device_token]          │                              │
 │                                │                              │
 │◄── { device_token:            ─│                              │
 │     "aleph-dt-…",              │                              │
 │     role: "operator" } ────────│                              │
 │                                │                              │
 │   [设备存储 token 供后续重连]   │                              │
```

### 启动票 —— `aleph-bt-*`

`aleph-bt-*` 票是 5 分钟 TTL、单次使用的凭证。它的存在意义是让长生命周期
凭证（device_token / shared Gateway token）**永远不进 URL 或 QR**。

`gateway.ticket.create` 返回：

```json
{
  "ticket": "aleph-bt-...",
  "urls": [
    "http://192.168.1.20:18790/?bt=aleph-bt-...",
    "http://[fd00::1]:18790/?bt=aleph-bt-..."
  ],
  "expires_at": "..."
}
```

`urls` 字段由服务端组装（`tls::discover_interface_ips`）—— 不要让 Panel
用 `window.location` 自己拼，localhost 生成时永远是
`http://127.0.0.1:<port>/…`，远程操作员永远看不到。

### 设备 token —— `aleph-dt-*`

成功交换启动票后，握手返回一个 `aleph-dt-*` 设备 token。Panel 把它
持久化并在每次重连时作为 `connect.device_token` 提交。

设备 token：

- 长生命周期，绑定到一台设备；
- SHA-256-hashed 存储在 `security.db`；
- 通过 `connect::resolve_connect_auth` 在 `connect` 握手中验证。

### 无头核心：CLI 路径

不需要 daemon 运行即可 mint 一个票或打印恢复 token：

```bash
# Mint a 5-minute bootstrap ticket
aleph-server pair                    # default TTL = 300s
aleph-server pair --ttl 3600         # 1 hour (clamped to 60..=86400)

# Print the shared Gateway token (recovery / manual entry)
aleph-server bootstrap-token
```

`aleph-server pair` 直接打开 0600 `security.db`（WAL），不需要 daemon
在运行。`aleph-server bootstrap-token` 打印共享 Gateway token，用于
手动恢复（粘贴进 Panel / iOS App 的"Authorize"对话框）。

### 撤销

两种粒度，都**立即**生效：

- `gateway.token.rotate` —— 重新生成共享 token，**撤销所有配对设备**，
  关闭所有远端 socket。
- `gateway.devices.revoke {device_id}` —— 仅撤销**一台**设备：把它
  活跃的会话同步打回登录墙，然后关闭 socket（WS 4001 `device_revoked`）。
  `gateway.devices.list` 是清单，带 `connected` 实时标志。

两者都限定 `device_type = 'panel'`，从不影响集群节点。`device_id`
是客户端断言的，`devices` 表与集群节点共享一个命名空间 —— 交换过程会
拒绝一个已经命名了非 Panel 设备的 `device_id`（`cluster::admit_node` 拒
镜像情况）。没有这道保护，一张票就能换一个 Panel 看不到、无法撤销的
操作员 token。

## 频道发送者配对

新聊天发送者（Telegram 用户、Discord 成员、iMessage 未知发送者）走
更轻量的流程：6 字符字母数字代码通过**单一**入站配对存储
（`src/gateway/pairing_store.rs`）路由 —— 通道不再有本地配对存储。

```
发送者                        Gateway                         操作员
  │                                │                              │
  │── "你好, Aleph" ──────────────►│                              │
  │   (来自未知发送者)              │                              │
  │                                │── 生成 6 字符代码 ──►        │
  │◄── "请使用代码验证:             │                              │
  │     MRKV52" ──────────────────│                              │
  │                                │── 通知 ─────────────────────►│
  │                                │   "Telegram 上的新发送者"     │
  │                                │   "代码: MRKV52"             │
  │                                │                              │
  │                                │◄── pairing.approve ──────────│
  │                                │    { channel, code }          │
  │                                │                              │
  │◄── "你已验证!" ────────────────│                              │
```

### 6 字符代码

频道配对代码是 **6 字符字母数字**（不是 8 字符 Base32；后者已经移除）：

```rust
fn generate_code() -> String {
    // 6 alphanumeric characters, ambiguous chars (0/O, 1/I/l) excluded
    ...
}
```

### 过期与容量

`[routing] pairing_code_expiry_secs` 控制过期（默认 **24 h**，`0` = 永不
过期）。代码在过期后自动被拒；清理周期定期从数据库中删除过期请求。

待处理配对请求数受 `MAX_PENDING_REQUESTS = 10` 限制 —— 超过则新请求被拒
并返回 `TooManyPending`。

### RPC 管理

```bash
# 通过 aleph-server gateway call 调用 RPC
aleph-server gateway call -p '{"channel":"telegram"}' pairing.list
aleph-server gateway call -p '{"channel":"telegram","code":"MRKV52"}' pairing.approve
aleph-server gateway call -p '{"channel":"telegram","code":"MRKV52"}' pairing.reject
```

或通过 Panel Settings → Pairing UI。**没有** `aleph pairing approve`
CLI 命令 —— 这一切都通过 RPC。

## 设备与频道配对的对比

| | 设备 | 频道发送者 |
|---|------|-----------|
| 凭证 | `aleph-dt-*` 设备 token（长生命周期） | 频道发送者 ID（inbound router 存储） |
| 引入凭证 | `aleph-bt-*` 启动票（5 min TTL，单次） | 6 字符字母数字代码 |
| 持久化位置 | `devices` 表（Panel 类型） | `pairing_requests` 表 |
| 撤销粒度 | 单台设备（`gateway.devices.revoke`） | 频道发送者（`pairing.reject` 或 `pairing.revoke`） |
| 携带者 | WS `/ws` connect 握手（`device_token` 参数） | 入站消息 |
| 共享 secret | 共享 Gateway token 仅作恢复（不进 URL/QR） | —— |

## 加密基础

### 设备票 / token

`device_token_manager` 生成：

- 启动票：`uuid` + TTL 戳；
- 设备 token：`uuid` + SHA-256（明文存 `devices.public_key` 旁的 hash，
  SHA-256-at-rest）。

### 共享 Gateway token

启动时由 `SharedTokenManager` 生成，HMAC-SHA256-hashed，常数时间验证。
`aleph-server bootstrap-token` 是**唯一**打印它的途径；它永远不应进
URL、QR 或 Referer header。

### 安全保证

1. **5 分钟启动票** —— 单次使用，限制凭证泄漏窗口。
2. **可单独撤销的设备 token** —— 不需要轮换全局共享 token。
3. **失败关闭** —— `exchange_bootstrap_ticket` 失败时连接不升级。
4. **`device_id` 命名空间隔离** —— Panel 设备和集群节点 ID 不共享。
5. **立即撤销生效** —— 不是在下一次握手。
