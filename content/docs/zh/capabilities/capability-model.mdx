本页解决一个问题：Aleph 运行时里的一个「能力」（capability）由什么构成，它怎么被授权、怎么被撤销，以及消费方怎样避免拿到陈旧的 handler。代码位于 `src/capability/`（33 个文件）与契约 crate `crates/aleph-slot-api/`。

<Callout type="warn" title="先读这一条">
  2026-11-25 的**能力收敛**删掉了 `src/capability/` 里几组「写好了、测过了，但没有挂到生产路径上」的模块：旧的 ambient / audit / grant 模块，以及能力自身的生命周期与激活状态机。能力的「活 / 死」现在由 provider 生命周期承载（见「Provider 生命周期与代」）。
  本页描述收敛后的现状，并区分生产调用路径、已定义但未挂载的契约，以及蓝图里的规划。

## 能力是什么

能力的**描述符**（`CapabilityDescriptor`）记录**所有者**（`OwnerRef`）、**可见性范围**（`VisibilityScope`）与一组**行为面**（`CapabilityFacet`）。描述符定义见 `src/capability/descriptor.rs`，所有权与可见性类型见 `src/capability/ownership.rs`。

描述符只描述，不授予权限。授权靠所有权绑定、策略与租约（lease）完成。这一点写在 `src/capability/descriptor.rs` 的模块注释里：描述符是「kind-agnostic capability contract」，Tool 与 special capability 后端提供可执行的适配器，其余 kind 在对应后端挂载前只是描述性的。

```text
CapabilityDescriptor ──描述──▶ 能力是什么（id / kind / schema / facets）
OwnershipTree        ──绑定──▶ 谁拥有它、第几代（owner / generation）
Zahir::resolve       ──签发──▶ BackendLease（带 owner_generation 的租约）
Zahir::validate_lease──复核──▶ 使用前再检查一次，失效即拒绝
```

上图的绑定与租约复核分别见 `src/capability/ownership.rs` 和 `src/capability/zahir_facade.rs`。

### 契约 crate 与运行时的边界

`crates/aleph-slot-api/src/` 下有 33 个 Rust 源文件，其中 `crates/aleph-slot-api/src/browser/mod.rs` 组织浏览器契约。依赖只从 `alephcore` 指向 `aleph-slot-api`。契约 crate 不做 I/O，不依赖平台、LLM 或 Tokio runtime（只使用 Tokio 的 `sync`），也不持有隐藏状态；`alephcore::error` 是重新导出，不是第二份定义（`crates/aleph-slot-api/src/lib.rs`）。

`crates/aleph-slot-api/src/capability.rs` 定义各宿主共享的能力标识和服务图关系；`crates/aleph-slot-api/src/descriptor.rs` 是工具注册表描述符、重放与实现契约的权威类型定义。`ContractVersion` 是槽位契约的类型（`crates/aleph-slot-api/src/slot.rs`），不是协议常量 `HOOK_CONTRACT_VERSION`（`shared/protocol/src/hook.rs`）。

## 描述符

### 字段

`CapabilityDescriptor`（`src/capability/descriptor.rs`）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | `CapabilityId` | `{namespace, name}`，如 Tool 的命名空间 `aleph/tools`（`TOOL_NAMESPACE`，`src/capability/backend.rs`） |
| `kind` | `CapabilityKind` | 主分类，见下 |
| `schema` | `SchemaRef` | schema 版本 + SHA-256 指纹 |
| `revision` | `CapabilityRevision` | 单调递增的修订号，由所属注册表在每次成功变更时赋值 |
| `lifetime` | `LifetimeScope` | 所有者绑定能活多久 |
| `visibility` | `VisibilityScope` | 谁能看见它 |
| `owner` | `OwnerRef` | 谁拥有它 |
| `services` | `Vec<Service>` | 关系边：`requires` / `provides` / `conflicts` |
| `metadata` | `ProjectionMetadata` | 投影元数据，见下面的提醒 |
| `facets` | `CapabilityFacets` | 行为面位集合 |

`CapabilityId`、`Service`、`ServiceRelation` 定义在 `crates/aleph-slot-api/src/capability.rs`，由描述符模块重新导出。`Service` 是纯关系边：不带数据、不可调用。

### CapabilityKind 与 CapabilityFacet

`CapabilityKind` 有 12 个变体（`src/capability/descriptor.rs`）：

```rust
pub enum CapabilityKind { Tool, Ambient, Terminal, Ui, Skill, Agent, Task, Resource, EventSource, Subscription, Plugin, Hook }
```

（源码里每个变体独占一行，这里为排版压成一行。）`CapabilityKind::UI` 是 `Ui` 的兼容拼写。

Tool 与 special 能力后端有可执行适配器；kind 枚举本身不保证对应后端已挂载（`src/capability/descriptor.rs`）。`Ambient` 仍留在枚举里，但它原来对应的 `src/capability/ambient.rs` 已在 2026-11-25 的能力收敛中删除——那个模块自述「未挂载」，暴露进程身份与环境变量属于安全面决策，今天没有替代实现。

`CapabilityFacet` 是与 kind 正交的行为轴，有 5 个变体：`Callable`、`EventSource`、`Subscription`、`ProviderLifecycle`、`ExternalEffect`。一个 provider 可以同时暴露事件源和可调用操作，而不必假装整个 provider 是 `Tool`。

`CapabilityFacets(u8)` 是 5 位的位集合，提供 `new` / `with` / `contains`；描述符上用 `supports(facet)` 查询。这些行为面是描述性元数据，不授予权限（`src/capability/descriptor.rs`）。

### SchemaRef 与指纹

`SchemaRef` 定义于 `src/capability/descriptor.rs`：

```rust
pub struct SchemaRef {
    pub version: u32,
    pub fingerprint: [u8; 32],
}
```

`fingerprint` 是规范化输入 schema 的 SHA-256，由 `capability::backend::to_descriptor`（`src/capability/backend.rs`）计算。键顺序不同、内容相同的 schema 得到相同指纹；schema 变了，指纹就变。门面的 `validate_lease` 把指纹作为描述符新鲜度的一项检查（`src/capability/zahir_facade.rs`）。

## 所有权与生命周期

### 生命周期范围与 owner

`LifetimeScope`（`src/capability/ownership.rs`）有 5 个变体；`External` 不在进程内的生命周期层级中：

| 变体 | 含义 |
|---|---|
| `Runtime` | 绑定到进程，活满整个运行时 |
| `Session` | 绑定到一个会话 |
| `Run` | 绑定到一次运行 |
| `Task` | 绑定到一个任务 |
| `External` | 由外部拥有，不在本进程的生命周期模型内 |

`OwnerRef`（`src/capability/ownership.rs`）说明谁拥有一个能力绑定：`Runtime`、`Session(SessionKey)`、`Run(RunId)`、`Task(TaskId)`。

<Callout type="info">
  目前代码库里**还没有**统一的 run-id / task-id 类型。`RunId(pub String)` 与 `TaskId(pub String)` 是 `src/capability/ownership.rs` 里的临时包装，注释明确要求一旦出现规范类型就对齐过去。
</Callout>

`OwnershipTree` 在这些范围之上组织成一棵五层树：Runtime → Session → Run → Task → EffectClaim（`src/capability/ownership.rs` 注释）。两条正交的轴：`LifetimeScope` 是 RAII 轴（绑定活多久），`VisibilityScope` 是 ACL 轴（谁能看见）。

### OwnerGeneration 与 FencingToken

代、令牌和绑定的变更操作见 `src/capability/ownership.rs`：

- `OwnerGeneration(pub u64)`：每个绑定一个当前代。租约只在它记录的代与绑定当前代相同时有效；重新签发所有权或抬高生命周期范围会改变这个代。
- `FencingToken(u64)`：字段私有、`Copy`。唯一的构造点是 owner 层的 `pub(crate) fn new(nonce: u64)`，计数器的单调性是 owner 层的契约；每次 `claim` 铸造一个新令牌，所以陈旧租约无法把旧令牌冒充成有效的。

`OwnershipTree` 的变更操作：

| 方法 | 作用 |
|---|---|
| `bump(scope)` | 抬高 owner nonce，把该范围及以下所有绑定重写为新的代，并把其上的 claim 清空；返回 `Result<OwnerGeneration, OwnershipError>`，计数器耗尽时报 `GenerationExhausted` |
| `rotate_capability(id)` | 对一个能力的所有绑定换代并清空 claim |
| `revoke(id)` | 不可逆：移除该能力的所有绑定，并把 id 加入「已撤销」集合 |
| `dispose(scope)` | 不可逆：移除该范围及以下所有绑定，并把范围加入「已处置」集合 |

撤销与处置一旦发生就无法撤回，之后任何 `resolve` / `claim` 都会被拒绝。

### OwnershipChange：观察者可见的唯一副作用面

`OwnershipChange` 定义于 `src/capability/ownership.rs`：

```rust
pub enum OwnershipChange {
    Bumped { generation: OwnerGeneration, scope: LifetimeScope },
    Rotated { capability: CapabilityId, generation: OwnerGeneration },
    Revoked { capability: CapabilityId },
    Disposed { scope: LifetimeScope },
}
```

（源码为多行写法，这里压缩。）它在 `OwnershipTree` 自己的互斥锁内、与状态变更同一个临界区里发出，是树的变更方法**唯一**对观察者可见的副作用面。订阅用 `OwnershipTree::subscribe_changes`，它**不经过**全局事件总线、会话事件存储或审批权威。订阅是纯观察：不改状态、不推进 nonce、不注册绑定；接收方落后时会得到滞后计数，应据此从新快照重新对账。

### Provider 生命周期与代

能力的「活 / 死」由 **provider 生命周期**承载。`src/capability/provider.rs` 里的 `ProviderLifecycle` 是纯状态机；`ProviderTransport` 只有 `InProcess` 与 `Bridge` 两个变体，表示 provider 实现的运行时边界。

| 状态 | 含义 |
|---|---|
| `Discovered` | 已被发现，尚未准入声明 |
| `Cold` | 已准入声明，没有运行期副作用，也没有可执行租约 |
| `Disabled` | 被显式禁用 |
| `Starting` | 正在启动 |
| `Ready` | 就绪，可以被调用 |
| `Stopping` | 正在停止，不再准入新调用 |
| `Stopped` | 已停止 |
| `Failed` | 启动或运行失败 |

`ProviderLifecycle::transition` 只接受下列迁移，其余返回 `ProviderLifecycleError::InvalidTransition { provider_id, from, to }`：

```text
Discovered → Cold | Disabled | Starting
Disabled   → Cold | Starting
Cold       → Disabled | Starting
Starting   → Ready | Failed | Stopping
Ready      → Stopping | Failed
Stopping   → Stopped | Failed
Stopped    → Starting | Disabled
Failed     → Starting | Stopped | Disabled
```

**每次进入 `Starting` 都把代（generation）加一**，代用尽时返回 `ProviderLifecycleError::GenerationExhausted`。这正是「重启会让旧租约失效」的机制：旧代租约在重启期间无效，替换实例达到 `Ready` 之后依然无效。

每次成功迁移产生一条 `ProviderTransition { provider_id, transport, from, to, generation }`，通过 `ProviderHandle::subscribe_changes` 以 `broadcast::Receiver<ProviderTransition>` 广播。

`ProviderHandle` 是线程安全控制柄（内部是 `Arc<Mutex<ProviderLifecycle>>` 加 `broadcast::Sender`）：`snapshot` 返回 `(ProviderState, u64)`；`acquire_call(expected_generation)` 在代不符或状态不是 `Ready` 时返回 `ProviderCallError { provider_id, state, expected_generation, actual_generation }`；`with_ready_commit`、`with_call_admission`、`with_admitted_completion` 是 crate 内的分段提交原语（`src/capability/provider.rs`）。

<Callout type="warn" title="旧的能力生命周期状态机已删除">
  2026-11-25 的能力收敛删除了 `src/capability/lifecycle.rs`（`LifecycleState`、生命周期 `Lease`、`transition_to`）与 `src/capability/activation.rs`（`CapabilityActivationController`）。这两个文件当时只被运行期策略用来做「代数比对 + 已撤销」两项检查，这两项现在由下节的约束附件与 provider 生命周期承担。要找回旧实现，看 git 历史：`git log --diff-filter=D -- src/capability/lifecycle.rs`。
</Callout>

### 运行期准入：约束附件

生产路径没有「激活闸」这一步；约束检查直接落在**准入**上。`src/capability/policy_runtime.rs` 的 `PolicyEngine::admit_runtime` 按顺序检查：

1. 该 id 在运行期规则表里有约束吗？没有就直接放行，不占附件。
2. 附件存在且 id 匹配，否则 `PolicyDenial::AttachmentUnavailable { id }`。
3. 附件记录的绑定与租约一致（id、revision、generation、owner、visibility），否则 `AttachmentUnavailable`。
4. 事实来源快照可读，否则 `PolicyDenial::ConstraintDenied { reason: "facts_unavailable" }`。
5. 事实来源的 key 没有被换掉，否则 `AttachmentUnavailable`。
6. 复核捕获时的租约（`validate_captured_lease`）。
7. 附件仍在附件表里（用 `Arc::ptr_eq` 比较同一实例），否则 `AttachmentUnavailable`。
8. 评估约束：`ResourceUse::Allocate` 走完整评估，`Existing` 与 `Release` 走非分配评估；失败为 `PolicyDenial::ConstraintDenied { reason: "runtime_constraints" }`。

撤销（revocation）**不是**另一个标志位，而是「从附件表里移除」：`admit` 只对仍在表里的状态可达，而列表与移除共用一把锁，所以被移除的状态不会再被准入（`src/capability/policy_runtime.rs`）。

准入成功返回 `RunningCapabilityCall` 守卫。它必须被持有到真实操作结束（含异步取消）才释放资源计数（`src/capability/policy_runtime.rs`）。

依赖不可用时，工具分发在解析阶段把 `ResolveError::DependencyUnavailable` 转成模型可见的 `ToolError::Execution`，文本形如「`memory.runtime` 当前不可用（状态 Stopped），稍后重试或请用户启用」；工具本身仍留在工具列表里，模型能看到失败原因并稍后重试（`src/tools/scoped/dispatch.rs`）。

<Callout type="warn" title="兼容激活入口已删除">
  scoped tool 层曾提供按工具名登记 `Arc<dyn CapabilityActivation>` 的兼容入口，生产刻意不安装它。2026-11-25 的能力收敛删除了该入口与 `src/capability/activation.rs`（`src/tools/scoped/builder.rs`、`src/tools/scoped/dispatch.rs`）。`src/capability/provider_registry.rs` 里同名的 `ActivationError` 属于 provider 激活，变体是 `Rejected`、`Failed`、`Unknown`、`NotVisible`，与能力生命周期无关。
</Callout>

## 可见性

`VisibilityScope`（`src/capability/ownership.rs`）有 6 个字段，**全部是 `Option`，`None` 表示该维度不受限**，所以 `VisibilityScope::default()` 是「到处可见」：

| 字段 | 类型 |
|---|---|
| `principal` | `Option<String>` |
| `workspace` | `Option<String>` |
| `session` | `Option<SessionKey>` |
| `allowed_kinds` | `Option<Vec<String>>` |
| `allowed_ids` | `Option<Vec<String>>` |
| `approval` | `Option<String>` |

`allowed_kinds` 与 `allowed_ids` 故意用 `String` 而不是 `CapabilityKind`：`ownership` 模块不能依赖 `descriptor::CapabilityKind`，否则 `descriptor` ↔ `ownership` 成环；对应的 kind 和名称比较见 `src/capability/policy.rs`；检查哪些轴取决于调用路径。

`src/scope/` 处理的是另一组范围语义：`src/scope/authority.rs` 在后台任务触发时解析运行身份，`src/scope/carried.rs` 用任务局部状态传播内存、项目与 agent 上下文，`src/scope/directory.rs` 为展示缓存用户名。这些不是 `VisibilityScope` 的 ACL 字段（`src/capability/ownership.rs`）。

## 策略

### 活路径：门面内的绑定校验

生产路径由门面解析和复核绑定，再由运行期策略检查调用限制（`src/capability/zahir_facade.rs`、`src/capability/policy_runtime.rs`）。门面的绑定检查包括：

- 后端条目查找成功后，`resolve` 查 `OwnershipTree` 里的绑定。没有绑定且 id 已撤销可返回 `ResolveError::Revoked`，没有绑定而未撤销返回 `NotVisible`；成功时把当时的 owner 与 owner generation 写进 `BackendLease`。
- `validate_lease` 重新核对：provider 代没变、描述符的 `id`、`revision` 与 schema 的 `fingerprint` 没变，并通过 `OwnershipTree::with_current_bindings` 确认绑定仍然是租约记录的那个（被撤销 → `Revoked`；绑定缺失或已处置 → `Unknown`；代或绑定不一致 → `StaleOwner`）。

### 三闸模型

`PolicyEngine`（`src/capability/policy.rs`）定义了三闸模型，每个方法都 fail-closed，任一闸拒绝即整个请求被拒：

1. **可见性闸**：请求的可见性范围是否与描述符允许的一致。
2. **主体闸**：请求主体是否与绑定的 owner 一致。
3. **权限闸**：绑定是否存活、未撤销、未处置、代与期望相同。

`PolicyEngine::resolve` 通过后签发 opaque 的 `CapabilityLease`，字段均为 `pub(crate)`，crate 外的调用方无法自己伪造；之后用 `PolicyEngine::validate_lease` 复核。

<Callout type="warn" title="三闸里的 resolve 没有挂到生产">
  `src/capability/policy.rs` 的注释记录了 2026-11-20 severed-wire 审计的结论：`PolicyEngine::resolve` 及其调用的 `validate_visibility_scope` 没有生产调用点。不要把其中针对 `allowed_kinds` / `allowed_ids` / `approval` / `workspace` / `session` 的描述符比较当成生产保证。启动期约束与实时准入不依赖这个 `resolve`（`src/capability/production_init.rs`、`src/capability/policy_runtime.rs`）。
</Callout>

### 启动期约束（已挂载）

`PolicyEngine` 在生产里的实际角色是承载**启动期约束**。`build_capability_policy`（`src/capability/production_init.rs`）用共享的 `OwnershipTree` 与 `policies` 下的 `capability_constraints` 配置 组装 `PolicyEngine::with_shared_tree`；`aleph-server` 启动时调用它（`src/bin/aleph-server/commands/start/capability_init.rs`）。该函数的注释说明它是「pure assembly, not authorization or a second ownership authority」。

约束按能力 id 配置，每条规则可含时间窗口、资源上限和必需条件：

```toml
[policies.capability_constraints."aleph/tools/example"]
required_conditions = { provider_ready = true }
```

规则结构见 `src/config/types/policies/capability_constraints.rs`：`time`（`start_hour` / `end_hour`）、`resource`（`unit` 为 `active_calls` 或 `pty_sessions`，加 `max_active`）、`required_conditions`（名称到布尔值）。结构体 `deny_unknown_fields`，未知键会被拒绝。违反约束时由 `ConstraintViolation`（`src/capability/constraints.rs`）报告，例如 `TimeWindowClosed`、`ResourceLimitExceeded`、`ConditionNotMet`。

### 调用上下文与实时准入

`CapabilityCallContext` 记录认证入口捕获的事实（actor、principal、session、workspace、connection、call id），不是反序列化得到的客户端声明。实时策略把启动期规则与来源所有者提供的最新事实结合；它只管理限制，不拥有描述符、handler 或所有权。`ResourceUse` 由具体操作选定，区分 `Allocate`、`Existing`、`Release`；后两者不执行分配专用的资源上限检查（`src/capability/policy_runtime.rs`、`src/capability/constraints.rs`）。

工具分发拿可信上下文执行准入检查（`src/tools/scoped/dispatch.rs`）；注册表用 `RunningCapabilityCall` 跟踪正在执行的调用（`src/tools/registry.rs`）。UI 网关入口也构造可信上下文并执行准入检查（`src/gateway/capability_ui.rs`）；连接关闭时，连接层委托 UI 网关清理该连接拥有的表面（`src/gateway/server/connection/mod.rs`）。

异步 special 能力另有私有分发接缝：`DomainToolCall` 经任务局部的 `DOMAIN_TOOL_CALL` 携带可信上下文、可选 owner actor 和取消令牌；`CapabilityInvocationOrigin` 是 `pub(crate)` 枚举，来源证据由规范认证入口产生，客户端字段不能构造它（`src/capability/special_dispatch.rs`、`src/tools/scoped/dispatch.rs`、`src/capability/tool_adapters.rs`、`src/capability/zahir_facade.rs`）。

## 效果声明

`EffectClaim` 定义于 `src/capability/ownership.rs`：

```rust
pub struct EffectClaim {
    pub request_id: String,
    pub fence: FencingToken,
    pub owner: OwnerRef,
}
```

`OwnershipTree::claim` 对绑定记录一次 claim 并铸造新 `fence`。绑定缺失、能力已撤销、所属生命周期已处置、owner 不匹配或 fence 计数器耗尽时返回 `None`。`claim_state` 只在绑定仍存活且令牌对应的记录与当前绑定代、claim 的 owner 相符时返回 `ClaimState::Active`；撤销、处置、父级 bump 清除记录或查不到 claim 等情况返回 `Unknown`（`src/capability/ownership.rs`）。

`src/capability/effect_claim.rs` 是针对 `SessionEvent::EffectClaim*` 事件历史的纯 reducer（状态 `Prepared` / `Claimed` / `Invoking` / `Succeeded` / `Failed` / `Unknown`），对重复的活跃 claim 与非法迁移保持 fail-closed。

<Callout type="warn" title="effect_claim 尚未接线">
  `src/capability/effect_claim.rs` 头注释写明：生产里没有构造 `SessionEvent::EffectClaim*` 的位置，所以这个 reducer 除了自己的测试外没有生产者也没有消费者，是有记录的延期（见 `AGENTS.md` 的 Capability Phase 4 一节），不是静默的死模块。因此「用 fence 把重复提交识别为重复」目前是 reducer 与 `OwnershipTree` 层面的契约，不是端到端生效的行为。
</Callout>

## 后端证据与解析

### BackendSourceEvidence

`BackendSourceEvidence`（`src/capability/facade.rs`）说明一份租约来自哪类后端，来源身份与 kind 相关，Resource 不会伪造 Tool 条目：

| 变体 | 载荷 |
|---|---|

| `Provider` | `provider_id: ProviderId`、`provider_generation: u64` |

### BackendLease 与 ResolveError

类型定义见 `src/capability/facade.rs`，解析与复核见 `src/capability/zahir_facade.rs`。

```rust
pub struct BackendLease {
    pub descriptor: CapabilityDescriptor,
    pub owner_generation: OwnerGeneration,
    pub owner: OwnerRef,
    pub source: BackendSourceEvidence,
    // required_resources 为 pub(crate)，此处省略
}
```

规则只有一条，但不能违反：**消费方必须在 owner generation 变化的那一刻把租约视为失效，fail-closed，绝不使用陈旧的 handler。** 租约里同时记录 `owner`，因为仅凭代无法区分「所有权转移」与「绑定未变」。`resolve` 返回的是租约，不是活的 handler；使用前再用 `validate_lease` 复核。

`ResolveError` 是闭集：

| 变体 | 含义 |
|---|---|
| `Unknown` | 查找未命中、绑定缺失（且未撤销）、描述符新鲜度不符或任何无法归类的失败 |
| `NotVisible` | 调用方的 由 `Reference` 的 `visibility` 字段指定的范围内该 id 没有绑定（仅 resolve） |
| `Revoked` | 绑定已撤销 |
| `StaleOwner` | 租约的所有权绑定或 `owner_generation` 与当前记录不一致（仅 validate） |
| `StaleProvider` | 租约签发后 provider 实例被停止或替换 |
| `DependencyUnavailable { target, state }` | 依赖的 provider 可见但未就绪（`Cold` / `Starting` / `Stopping` / `Stopped` / `Failed` / `Disabled`）。能力仍列在清单里，调用被拒并带上依赖当前的状态 |

依赖不可用（`DependencyUnavailable`）会一路传到工具分发，转成模型可见的 `ToolError::Execution` 文本（见「运行期准入：约束附件」一节）；`src/capability/zahir_facade.rs` 给它的事件标签是 `dependency_unavailable`。

`StaleOwner` 不会出现在 resolve 阶段：刚签发的租约带的就是当时读到的代，构造时不可能陈旧。

### 快照与变更流

下列类型属于同进程的快照与注册表变更路径，不是能力观测事件（`src/capability/facade.rs`、`src/capability/zahir_facade.rs`）。

- `CapabilitySnapshot { capabilities, committed_cursor }`：内容在快照生命周期内**冻结**。之后的变更不会改写已持有的快照，而是产生新快照或一个 `CapabilityChange::Invalidated` 事件。
- `Cursor(pub u64)`：单调的订阅位置，`0` 表示从头开始。注意 `ZahirFacade::subscribe` 忽略调用方传入的 cursor：这个同步、以快照为锚的 API 没有重放，所以从快照位置起算，传入的 cursor 若领先于快照则 fail-closed 回到快照 cursor。
- `CapabilityChangeStream`：纯值状态机，不持有存储、注册表或订阅接线；提供 `from_snapshot`、`append`、`append_cohort`、`invalidate_and_resync`，历史只保留最近 256 条变更。
- `invalidate_and_resync(snapshot, delta)`：丢弃 cursor 不超过旧位置的陈旧尾部、对与已见变更完全相同的条目去重，先压入一个 `Invalidated`，再按原顺序追加存活的增量，cursor 推进到各方最大值且**永不回退**。仅当快照的 cursor 小于订阅方当前位置（重同步来源落后）时返回 `false`，此时流不被修改（fail-closed）。

`CapabilityChange` 的变体：`Registered`、`Replaced`、`Unregistered`（均带 `id` 与 `revision`）与 `Invalidated`。

## 事件与观测

`src/capability/events.rs` 的事件流只记录有界、按实例隔离的观测。它不是授权来源或重放日志，也不同于门面的 `CapabilityChangeStream`（`src/capability/facade.rs`）及所有权树的 `OwnershipChange`（`src/capability/ownership.rs`）。

记录先提交到内存，再广播，最后运行可选的持久化钩子。持久化失败是在提交后报告的，重发会产生重复观测。钩子在缓冲区锁外运行，可能乱序结束；需要重建顺序的落盘方应按记录的序号排序（`src/capability/events.rs`）。

`CapabilityEventType` 按 `snake_case` 序列化，变体为 `Created`、`Activated`、`Invoked`、`Revoked`、`ConstraintViolation`、`PolicyViolation`、`ExecutionFailed`。枚举声明可表达的观测，不代表每个变体都有生产者（`src/capability/events.rs`）。

### 受信任的受众与生产接线

`EventAudience` 区分 `OperatorOnly` 与 `Principal(PrincipalEventAudience)`。后者记录 `user_id`、以及可选的 `session_key`、`workspace` 与来源实例标识 `source_incarnation`。受众只在受信任的生产者边界捕获，客户端不能通过反序列化声明这个权威（`src/capability/event_audience.rs`）。网关针对连接逐条复核可见性后才转发（`src/gateway/capability_events.rs`、`src/gateway/server/connection/mod.rs`）。

服务启动时构建并挂载事件流（`src/bin/aleph-server/commands/start/capability_init.rs`、`src/bin/aleph-server/commands/start/mod.rs`）。来源证据与观测接线见 PTY 管理器的 `SourceObservationReceipt`（`src/gateway/pty/manager.rs`）、工具注册表（`src/tools/registry.rs`）与分发侧的 `InvocationObservation`（`src/tools/scoped/dispatch.rs`）。能力侧原来的 `src/capability/audit.rs` 收集器没有生产读取方，已在 2026-11-25 的能力收敛中删除；生产审计走 `SecurityAuditLog`，活路径是 `src/gateway/capability_events.rs`。

## Zahir

`Zahir` 是 `src/capability/facade.rs` 里的 trait：它定义供消费方读取能力的统一接口，不代表每种传输都已挂载。它从不直接调用能力，只做描述（`describe`）、解析成租约（`resolve` / `validate_lease`）、订阅变更（`subscribe`）、投影（`project`），再加唯一一个会运行 provider 激活钩子的入口 `activate`。

`ZahirFacade`（`src/capability/zahir_facade.rs`，模块注释「The one live Zahir host」）是它唯一的活实现，由 `ProjectionHost::mount*`（`src/capability/projection_host.rs`）构造，`aleph-server` 启动时调用 `ProjectionHost::mount_with_runtime_and_events`（`src/bin/aleph-server/commands/start/mod.rs`）。它组合：

- `ToolBackendAdapter`：内层 `ToolHandlerRegistry` 是**唯一的可调用 Tool 真值源**（`src/tools/registry.rs`）；
- `Arc<OwnershipTree>`：**唯一的 owner / revoke / dispose 来源**。

此外字段里还有 provider 适配器、可选的 `MemoryRuntime`、`PolicyEngine`、special 能力注册表与事件流。它**不持有**第二份 descriptor map、handler map 或 owner 计数器。

注册表的广播是实时通知的 tap（256 槽，滞后会丢），不是持久恢复来源。`subscribe` 把广播同步排空成纯 `CapabilityChangeStream`；滞后的接收方从新快照重同步并发出 `CapabilityChange::Invalidated`，而不是假装投递了每个事件。该广播不支持持久恢复（`src/capability/zahir_facade.rs`）；会话事件存储是独立的接口（`src/session/store.rs` 的 `SessionEventStore`）。

## 进程级能力句柄

裸 `OnceLock<Arc<T>>` 加安装函数与 getter 时，如果 getter 回退到默认值，读取方无法区分「启动时没安装」与「安装的就是这个值」。`CapabilitySlot::install` 将写值和记录安装结果封装为一步（`MetaGuard` 模式：先写值再盖戳）。条件安装的 `else` 分支可调用 `CapabilitySlot::decline`，应传入缺失的输入，而不是症状，因为 `because` 会原样显示给运维（`src/capability/mod.rs`）。

`Outcome` 的两种结果是 `Installed` 与 `Declined { because }`；结果为 `None` 并不等于 `Declined`，而是启动路径从未到达该槽位。`MissingSemantics` 记录句柄缺失时的行为：`IndistinguishableDefault { reads_as }`、`ConsumerDecides`、`FailsClosed`、`FailsOpen`。要清点的不是所有进程级缓存，而是缺失时可能给出错误答案、而不是崩溃的能力句柄（`src/capability/mod.rs`）。

`MutableCapabilitySlot` 刻意不提供 `decline`（`src/capability/mod.rs`）。唯一实例是 `GLOBAL_POLICY`（`src/spend/mod.rs`），由配置热更新路径替换（`src/config/live_apply.rs`）。

### 推导式句柄名册

测试专用的 `src/capability/census.rs` 从定义所在文件的安装动作推导名册，不依赖手写排除清单。对 `OnceLock`、`OnceCell` 和 `ArcSwap` 系列容器，`Written` 指调用了 `set`、`store` 或 `swap`；first-caller-wins 指 `get_or_init` 或 `get_or_try_init` 的初始化闭包依赖外层函数的参数。若初始化只用容器自身可达的数据，则它是惰性缓存：「还没建好」就是正确答案，不算句柄。
