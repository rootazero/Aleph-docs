Aleph 的代码库使用领域驱动设计（DDD）原则组织，通过 Rust 的 trait 系统实现。Aleph 不依赖于重量级的 DDD 框架，而是使用轻量级的 trait 契约在编译时强制执行领域规则。本页描述了建模方法、核心领域原语以及限界上下文如何将系统划分为内聚模块。

Aleph 中的 DDD 不是仪式性的 —— 它服务于实际目的。通过使领域概念在类型系统中显式化，代码库清晰地传达其意图，并通过编译时保证防止整类错误。

## 为什么 Aleph 使用 DDD

个人 AI 助手是一个复杂的领域。它涉及对话、记忆、任务编排、工具执行、安全策略和多通道通信。没有显式建模，这些关注点会模糊在一起，创建一个所有事物都依赖于所有事物的代码库。

DDD 提供了组织支柱：

- **限界上下文**防止跨领域耦合。记忆系统不需要了解 teams/dispatcher 的调度，teams/dispatcher 也不需要了解网关的会话管理。
- **聚合根**强制执行一致性边界。对相关对象的修改通过一个入口点进行，防止不一致状态。
- **值对象**消除身份混淆。当且仅当两个对象的属性匹配时它们才相等，使它们成为值对象可以防止意外假设身份的错误。
- **实体**使身份显式化。当一个对象需要在操作之间持久化并被其他对象引用时，将其标记为实体使此契约在代码中可见。

## 核心原语

Aleph 在其领域模块中定义了三个基础 DDD trait。这些按设计是最小化的 —— 它们强制执行契约而不增加运行时开销。

### 实体

**实体**是一个具有唯一身份的对象，该身份在状态更改期间持久存在。两个实体相等当且仅当它们共享相同的 ID，无论其其他属性如何。

```rust
pub trait Entity {
    type Id: Eq + Clone + std::fmt::Display;
    fn id(&self) -> &Self::Id;
}
```

**特征**：
- 具有通过 `id()` 访问的唯一标识符。
- 身份是稳定的 —— 同一实体在所有修改中保留其 ID。
- 状态可以更改，但身份不能。
- 相等性完全由 ID 比较决定。

**何时使用实体**：当对象需要在操作之间被跟踪、被其他对象引用或具有生命周期（创建、更新、删除）时。

**示例**：

```rust
pub struct Task {
    id: String,
    name: String,
    status: TaskStatus,
    dependencies: Vec<String>,
}

impl Entity for Task {
    type Id = String;
    fn id(&self) -> &Self::Id { &self.id }
}
```

`Task` 是一个实体，因为它具有生命周期 —— 它被创建，其状态更改，依赖项被更新，最终它完成或失败。具有相同数据但不同 ID 的两个任务是不同的任务。具有相同 ID 但不同状态的两个任务是同一任务的不同状态。

### 聚合根

**聚合根**是聚合的入口点 —— 为了保持一致性目的而被视为一个单元的相关对象集群。对聚合内对象的所有修改必须通过聚合根进行。

```rust
pub trait AggregateRoot: Entity {}
```

**特征**：
- 继承所有实体属性（具有身份，在更改中稳定）。
- 作为事务边界 —— 外部代码仅通过根与聚合交互。
- 负责维护聚合内所有对象的一致性。
- 对聚合内对象的外部引用通过根进行。

**何时使用聚合根**：当一个对象管理一组相关对象并需要跨它们强制执行一致性规则时。

**示例**：

当前持久记忆记录见 `MemoryFact`（`src/memory/context/fact.rs`）；旧的任务图教学示例见文末历史小节。

### 值对象

**值对象**是一个完全由其属性定义的不可变对象。它没有身份 —— 两个值对象相等当且仅当它们的所有属性都相等。

```rust
pub trait ValueObject: Eq + Clone {}
```

**特征**：
- 不可变 —— 一旦创建，值对象永远不会更改。
- 无身份 —— 相等性由比较所有属性决定。
- 可自由复制和替换。
- 无副作用 —— 对值对象的操作返回新值对象。

**何时使用值对象**：当对象表示度量、分类、状态或任何身份无关紧要的概念 —— 只有值重要时。

**示例**：

```rust
#[derive(Eq, PartialEq, Clone)]
pub struct TaskStatus {
    pub state: TaskState,
    pub progress: f32,
}

impl ValueObject for TaskStatus {}
```

`TaskStatus` 是一个值对象，因为我们只关心状态*是什么*，而不关心它是哪个特定实例。"运行中 50%" 的状态与任何其他"运行中 50%" 的状态相同，无论它何时或在何处创建。

## 限界上下文

Aleph 的领域被划分为限界上下文 —— 具有自己的通用语言、自己的模型和自己的规则的领域内聚区域。不同上下文中的对象可能共享名称但具有不同的含义。

### teams/dispatcher 上下文

**职责**：子任务调度、并发分桶、Team 协调。

`teams/dispatcher` 处理代理的执行端 —— `TeamDispatcher` 把复杂请求分解为子任务，`handoff.rs` / `runner.rs` / `schedule/{select,settle,reclaim,failure}.rs` 管理依赖、超时与失败回收。Act 阶段按 `src/tools/concurrency.rs::ConcurrencyClaim` 的资源声明分桶并行调度（桶内并发、桶间串行），不靠中间件做意图判断（R7/R10）。

> **重要**：`src/dispatcher/agent_types/{graph,task,status}.rs` **不存在**；当前源码未提供该任务图类型。下列表格给出源码中与并发 / 任务回收最相关的类型与位置。

| 类型 | DDD 角色 | 位置 |
|------|----------|----------|
| `ConcurrencyClaim` | 值对象（enum） | `src/tools/concurrency.rs` |
| `TaskStatus` | 值对象（enum） | `src/a2a/domain/task.rs`（A2A 协议域，**非** dispatcher 核心） |
| `TeamDispatcher` | 聚合根 | `src/teams/dispatcher/{mod,handoff,runner}.rs` |

并行分桶函数（`batch_parallelizable` / `partition_parallel_groups`）保证：
- 同桶内调用并发执行。
- 不同资源冲突声明的桶按串行顺序执行。
- 资源声明冲突时 `claims_conflict` 退避。

### 记忆上下文

**职责**：事实存储、RAG 检索、知识压缩。

记忆上下文管理代理的持久知识 —— 存储事实、检索相关上下文和压缩旧记忆以保持效率。

| 类型 | DDD 角色 | 位置 |
|------|----------|----------|
| `MemoryFact` | 聚合根 | `src/memory/context/fact.rs` |
| `ContextAnchor` | 值对象 | `src/memory/context/mod.rs` |
| `NoteType` | 值对象（enum） | `src/memory/context/enums.rs` |

> **更正**：上表的路径与类型名是源码中的真实位置（`memory/context` 是一个目录而非文件，类型名是 `NoteType` 而非 `FactType`）。`MemoryFact` 的 `impl Entity` 与 `impl AggregateRoot` 见 `src/memory/context/fact.rs`。

`MemoryFact` 聚合根确保：
- 事实正确锚定到其上下文（对话、主题、领域），由 `ContextAnchor` 表达。
- 事实类型一致且有效，由 `NoteType` 枚举约束。
- 压缩操作保留基本信息（`src/memory/compression/` + `session_compactor/`）。

### 意图上下文（不存在）

当前没有独立的意图检测上下文；配置中的无消费者键由 `src/config/dead_keys.rs` 报告。旧配置壳的移除记录见文末历史小节。

### POE 上下文（已退役）

> **POE（Principle-Operation-Evaluation）运行时架构在 26.5+ 已退役**。其「智慧」已迁移到 system prompt 模板（R9）；成功定义、验证、评估现在由 LLM 一次调用自然完成。Harness 不做完成度判断（**R10「5 个不」之 3**），不参与评估。R10 删除了历史 `DiminishingReturnsDetector` 硬停（`src/harness/tests/budget.rs:280` 注释），因为它是循环内的确定性完成判断。
>

历史职责（仅供考古）：成功合约、验证规则、评估结果。

## 上下文关系

限界上下文通过定义良好的接口交互，而非直接依赖：

```
                  ┌────────────────┐
                  │   Thinker /    │
                  │   PromptLayer  │
                  │  （评估在      │
                  │   prompt 中）  │
                  └───────┬────────┘
                          │ LLM 一次推理自然覆盖
                          v
┌────────────────┐   ┌────────────────┐   ┌────────────────┐
│   Harness      │<──│ teams/         │──>│  记忆上下文    │
│  (Think→Act)   │   │  dispatcher    │   │  （知识）      │
│   R10 笨循环   │   │  （执行）      │   │                │
└────────────────┘   └────────────────┘   └────────────────┘
         │                                         ^
         │          dreaming 反馈                  │
         └─────────────────────────────────────────┘
```

- **Harness ↔ teams/dispatcher**：Harness 的 Act 阶段调用 dispatcher；dispatcher 把并发分桶结果回传 Harness；两者均由 R10「笨循环」约束，不做意图判断。
- **teams/dispatcher ↔ Memory**：dispatcher 自己不检索记忆——它用 `build_handoff_context` 组装确定性上下文（任务描述、团队策略、收件箱摘要、重试恢复日志；`src/teams/dispatcher/handoff.rs`、`src/teams/context.rs`）；记忆检索走成员 agent 的 `memory_search` 工具，底层是 `src/memory/note_retrieval/` 的 `NoteFactRetrieval`。
- **Harness → Thinker / PromptLayer**：Think→Act 的 Think 阶段调 Thinker，裁决由 LLM 一次推理自然输出，而非中间件输出（R10 第 5「不」）。
- **Harness / Memory → dreaming**：每轮成功完成进入 dreaming 管线（`src/memory/dreaming/`），按 SkillOpt 纪律晋升技能，反过来给 Memory 增加事实，给下一次 Think 提供更密集的上下文。

每个上下文拥有自己的模型，不从其他上下文导入类型。通信通过边界处定义的共享接口（trait、消息类型）进行。

## 实现新的领域类型

当向 Aleph 的领域模型添加新概念时，遵循此决策过程：

### 步骤 1：确定角色

问这些问题：

1. **这个对象需要唯一身份吗？** 它需要被跟踪、引用或具有生命周期吗？
   - 是 --> 它是**实体**。
2. **它管理一组具有一致性要求的相关对象吗？**
   - 是 --> 它是**聚合根**（也是实体）。
3. **它只是一个身份不重要的属性容器吗？**
   - 是 --> 它是**值对象**。

### 步骤 2：实现 Trait

```rust
use crate::domain::{Entity, AggregateRoot, ValueObject};

// 实体
impl Entity for MyEntity {
    type Id = String;
    fn id(&self) -> &Self::Id { &self.id }
}

// 聚合根（也先实现实体）
impl AggregateRoot for MyAggregate {}

// 值对象（派生 Eq 和 Clone）
#[derive(Eq, PartialEq, Clone)]
pub struct MyValue { /* 字段 */ }
impl ValueObject for MyValue {}
```

### 步骤 3：放置在正确的上下文中

确定新类型属于哪个限界上下文。如果它不适合任何现有上下文，考虑是否需要新上下文。

### 步骤 4：添加测试

领域不变量一律用普通 Rust 测试表达——不变量与聚合根放在同文件 `#[cfg(test)] mod tests`；跨模块的行为验证放到顶层 `tests/<name>.rs`（**必须是顶层**——cargo 只自动发现 `tests/*.rs`，子目录需要某个 target 显式 `mod` 才会被编译）。

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn memory_fact_keeps_identity_after_validity_change() {
        let fact = MemoryFact::new("user".into(), NoteType::Preference, vec![])
            .with_valid_from(1000);
        assert_eq!(fact.id(), "user");
    }
}
```

不变量与 identity 测试现存放位置（举例）：
- `src/memory/context/tests/fact_tests.rs` — `MemoryFact` 的 ID 稳定性、有效期边界、聚合根不变式
- `src/memory/context/tests/enum_tests.rs` — `NoteType` 的枚举派生 / FromStr 一致性
- `src/domain/mod.rs::tests` — `Entity` / `AggregateRoot` / `ValueObject` 三个 trait 的最小样例

## 设计原则

### 保持聚合小

大聚合创建性能瓶颈和争用。每个聚合应仅包含必须始终彼此保持一致的对象。如果两个对象可以暂时不一致，它们属于不同的聚合。

### 优先使用值对象

值对象比实体更简单、更安全、更高效。如果一个对象不需要身份或生命周期，使其成为值对象。这消除了与身份混淆和引用管理相关的整类错误。

### 在边界强制执行不变量

聚合根负责在其边界内强制执行所有业务规则。外部代码永远不应能够将聚合置于无效状态。这意味着：

- 构造函数验证初始状态。
- 变异方法验证状态转换。
- 类型系统在可能的情况下防止非法操作。

### 使用 Rust 的类型系统

Rust 的所有权模型、trait 系统和类型级编程与 DDD 自然对齐：

- **所有权**强制执行聚合边界 —— 如果聚合根拥有其子项，外部代码不能持有对它们的可变引用。
- **Traits**表达没有运行时成本的领域契约。
- **Enums**使用穷尽匹配对判别联合（如 `NoteType` 或 `TaskState`）进行建模。
- **生命周期**防止跨上下文边界的悬空引用。

pub struct TaskGraph {
    id: String,
    tasks: Vec<Task>,
    edges: Vec<(String, String)>,
}

impl Entity for TaskGraph {
    type Id = String;
    fn id(&self) -> &Self::Id { &self.id }
