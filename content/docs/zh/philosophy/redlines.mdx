---

Aleph 的架构由 **十条红线**管理——优先于所有其他设计考虑的不可协商约束。这些不是指导方针或最佳实践。它们是硬边界。违反任何红线的代码不能合并，无论它启用的功能多么有用。

红线存在是因为某些架构错误是灾难性和不可逆的。一旦核心模块依赖于平台 API，或接口层积累了业务逻辑，损害就会随着每次后续提交而复合。红线在这些问题开始之前防止这些失败模式。

每个贡献者、每个 PR 审查者和每个自动化检查都必须将这十条规则视为公理。

> **完整论述与例外条款**：本节给出红线要点。完整论述与例外条款见 Aleph 仓库的 [`CLAUDE.md`](https://github.com/rootazero/Aleph/blob/main/CLAUDE.md) §「架构红线」一节，以及 [`docs/reference/HARNESS_PHILOSOPHY.md`](https://github.com/rootazero/Aleph/blob/main/docs/reference/HARNESS_PHILOSOPHY.md)。

## R1. 大脑与四肢绝对分离（Brain–Limb Separation）

**核心永不接触平台 API。它只定义能力契约。**

### 规则

核心为平台特定操作定义抽象 trait（能力契约）。物理实现位于原生宿主层（`desktop/`）中，通过 IPC 与核心通信：`desktop/shared` 提供能力 trait，`desktop/{macos,linux,windows}` 提供各平台实现。`src/builtin_tools/desktop/` 是对能力层的工具编排，不是平台实现。

### 原理

如果核心导入 `AppKit` 来捕获屏幕截图，它就成为 macOS 应用程序。如果它调用 `windows-rs` 来读取窗口标题，它就成为 Windows 应用程序。大脑中的平台耦合破坏了「一核多端」的承诺，并使每个新平台都成为分支而非集成。

### 禁止

- 在 `src/` 中导入 `AppKit`、`Vision`、`CoreGraphics`、`windows-rs` 或任何平台特定的系统 API
- 直接从核心调用 OS 级 API 进行屏幕截图、窗口管理、可访问性或输入模拟
- 在核心中引入平台特定行为的条件编译（`#[cfg(target_os)]`）

### 允许

- 在核心中定义诸如 `ScreenCapture`、`WindowManager`、`InputSimulator` 之类的 trait
- 原生桥接通过平台原生 API 实现这些 trait
- 核心通过 trait 接口在 IPC（UDS JSON-RPC）上调用能力

### 例外·进程隔离内核

沙箱的 restricted-token / job-object / AppContainer / 完整性级别 / SID·ACL 系统调用**必须**由 spawn 子进程的父进程在 spawn 时**就地**发起——无法经 IPC 桥委托（你没法从一个独立 helper 进程去沙箱化另一个进程）。本地 PID 存活探测（`OpenProcess`/`GetExitCodeProcess`）同理。因此 `src/sandbox/*` 与 `src/builtin_tools/desktop/session_lock.rs` 的平台 FFI（`windows-sys`）是 R1 立意之外的合法开口，**非违规**——R1 立意针对的是桌面 UI / 屏幕 / Vision 四肢，安全内核不是「桥能提供的 capability」。

## R2. UI 逻辑唯一源（Single Source of UI Truth）

**所有业务 UI 存在于 Leptos/WASM Panel 中。原生外壳只是窗口容器，仅此而已。**

### 规则

复杂的设置页面、表单、列表、仪表板和任何具有业务逻辑的 UI 必须在 Leptos（WASM）Panel 中实现。原生外壳（原生桌面宿主 NSH / Rust + 系统原生 API、Swift、Kotlin 等）仅提供：窗口容器、原生菜单栏项、原生动画和系统级集成（通知、文件对话框）。

### 原理

跨平台重复 UI 逻辑是维护灾难。每个错误必须修复 N 次，每个功能实现 N 次，行为一致性变得不可能保证。单一的 Leptos/WASM 代码库消除了这一整类问题。

### 禁止

- 在原生桥接中实现设置页面、任务列表、对话视图或任何承载业务逻辑的 UI
- 在外壳层构建复杂表单或交互组件
- 在 Leptos 之外渲染数据驱动视图（记忆浏览器、工具配置）

## R3. 核心轻量化（Core Minimalism）

**核心调度。它不为非核心功能做重活。**

### 规则

不要为可以作为技能或 MCP 集成交付的功能向核心添加重量级第三方库。核心是调度器和协调器——它调用专门的工作者而非吸收它们的复杂性。

### 原理

添加到核心的每个依赖项都会增加编译时间、二进制大小、攻击面和认知负载。为一个功能添加的 200 MB 图像处理库会惩罚每个构建、每个部署和每个开发人员——即使那些从不使用该功能的人。技能和 MCP 服务器是隔离的、独立可部署的，可以用任何语言编写。

### 禁止

- 为一次性非核心功能向 core 添加大型 crate（PDF 渲染、视频转码、捆绑的 ONNX 后端）
- 直接在核心中实现领域特定专业知识（PowerPoint 生成、代码审查启发式）

### 允许

- 核心定义工具接口并调度调用到外部技能 / MCP 服务器
- 服务于核心基本职责的轻量级、广泛使用的 crate（序列化、异步运行时、数据库驱动）

## R4. Interface 层禁止业务逻辑（I/O-Only Interfaces）

**接口层是纯 I/O。它们将输入转换为 JSON-RPC 并渲染响应。仅此而已。**

### 规则

每个接口——CLI、Telegram 机器人、Discord 机器人、WebChat、iMessage、桌面壳——都是一个薄转换层。它接收用户输入，将其转换为对核心的 JSON-RPC 调用，接收响应，并为用户渲染它。任何接口层都不得执行数据持久化、记忆检索、任务规划或任何形式的业务逻辑。

### 原理

如果 Telegram 机器人实现自己的记忆搜索，它将与 CLI 的记忆搜索不同。如果桌面应用管理自己的任务队列，它就成为一个并行的大脑。智能必须集中在核心中，以便每个接口提供相同的体验，仅在展示上有所不同。

### 禁止

- 从接口代码持久化数据（写数据库、文件、缓存）
- 在接口层中实现记忆检索、RAG 搜索或知识查询
- 在核心之外构建任务规划器、调度器或多步骤执行逻辑
- 从接口代码进行 LLM API 调用

### 允许

- 将用户消息转换为 JSON-RPC `request` 对象
- 在接口的原生格式中渲染流式响应（markdown、代码块、图像）
- 维护没有业务意义的短暂 UI 状态（滚动位置、输入缓冲区、动画状态）

## R5. AI 主动到达（AI Comes to You）

**减少上下文切换。AI 在用户当前环境中主动提供帮助。**

### 规则

设计所有交互以最小化上下文切换。优先选择覆盖层、内联建议和环境通知，而非模态对话框和专用窗口。AI 应该感觉像用户工作之上的一个层，而非一个单独的目的地。

### 边界

不打扰用户（不抢焦点、不弹模态对话框），但不要因此拒绝必要的交互入口。

---

## R6. 一核多端（One Core, Many Channels）

**Rust 核心是唯一的大脑。多端通道只负责 I/O 与渲染。**

### 规则

所有智能、规划、记忆和决策都存在于 Rust 核心中。多端通道（CLI / Bot / WebChat Panel / 原生 Bridge）只负责 I/O 与渲染，不参与业务推理。R1、R2、R4 是这条原则在不同切面上的具体体现——R6 是产品层面的重申。

---

## R7. LLM 主权原则（LLM Sovereignty）

**严禁用确定性代码替代 LLM 擅长的推理判断。**

### 规则

极简系统 + 强大 prompt = 释放 LLM 全部推理能力。把复杂留给模型，把简单留给系统。

### 判断标准

对每个模块问——「这是在赋能 LLM（给它做不到的能力），还是在越俎代庖（替它做推理）？」

- **赋能层（保留）**：Gateway 多端触达、Memory 持久记忆、Daemon 事件感知、Soul 人格、Provider 多厂商、Tool 执行能力、MCP 外部服务、Extension 插件生态、上下文压缩、安全硬过滤
- **越俎代庖（禁止）**：Intent Detection 规则引擎、POE 目标验证管线、多层 Tool Filter、Context Aggregation 多层合并、Dispatcher 意图分析

---

## R8. 工具即一切（Everything is a Tool）

**Aleph 自身的所有可配置操作都暴露为工具，让 LLM 通过自然语言对话完成配置。**

### 规则

Agent 管理（创建 / 切换 / 删除）、Provider 配置、Channel 配置、Skill / MCP 安装 / 卸载、Daemon 订阅规则——全部是 Tool。

### 核心循环

`用户自然语言 → LLM 理解意图 → LLM 选择工具 → 工具执行 → 结果返回 LLM → LLM 回复用户`

### 效果

对话即管理面板。用户无需学习配置文件或 API，自然语言驱动一切。

## R9. 智慧在 Prompt 中（Intelligence Lives in the Prompt）

**被移除的中间件的「智慧」不是丢弃，而是迁移到 system prompt 模板中。**

### 规则

主循环的 LLM 一次调用自然覆盖所有判断（意图理解 + 工具选择 + 安全评估 + 完成度判断）。零额外 LLM 调用，零中间件税，模型推理能力完整释放。

### 精简原则（prune-the-prompt）

智慧迁进 prompt ≠ 把 prompt 写厚。模型越强越需要**更少**方向 / 约束 / 示例——few-shot 会变笼子（模型模仿范例而非理解问题空间），低密度冗余稀释注意力；新模型发布后第一件事是**修剪上下文**，把验证 / 自我纠错建进**架构（运行时信号）**而非 prompt。

加 prompt 字节前过**两把尺**：

1. **这把尺**：这是模型**做不到的运行时事实**，还是我在**教强模型怎么思考**？后者别进 prompt。
2. **这把尺**（pi 之镜，2026-07-26）：**这句话有没有一个工具拥有它**？有 → 写进那个工具的 `DESCRIPTION`（随 schema 发，且只发给真能调它的请求），别写进 system prompt——system prompt 只承载**没有任何单个工具能说出口的东西**（跨工具取舍 / 运行时事实 / 安全边界）。这把尺量的是「完全正确、完全必要、只是放错地方」的重复。

**两把尺都已建进架构**：`src/thinker/prompt_contract.rs` 的 `reachable_layers`（层必须能开口，否则带理由进白名单）/ `scaffold_bytes_ratchet`（实测骨架天花板，只减不增）/ `no_sentence_is_stated_twice`；量一下用 `aleph-server prompt-size`。

## R10. 薄 Harness 哲学，笨循环编排核心（Thin Harness, Dumb Loop）

> *"If you're not the model, you're the harness."* — Vivek Trivedy
> *"Models get stronger → harness gets thinner."* — Anthropic

### 薄 Harness 哲学（Thin Harness）

Aleph 采纳 Anthropic 流派，运行时极简、信任模型。Harness 是脚手架不是认知层。**模型越强，Harness 越薄**——优秀的 Harness 必须通过「面向未来测试（Future-Proof Test）」：换更强的模型，性能自然提升，无需修改 Harness 代码。

### 笨循环（Dumb Loop）

`src/harness/` 仅承载 Think→Act 轮次调度，**不参与任何推理**。所有智能决策（意图理解、工具选择、安全评估、完成度判断）由 LLM 一次推理调用自然完成。

### 核心边界

- `src/harness/` 锁 **12 文件**；行数由 `src/harness/tests/budget.rs` 的棘轮守（实测非手算、只减不增、增必答下方 3 问）。**代码是权威**——任何文档数字都只是 `CEILING` 的副本
- **行数单一真源**：`src/harness/tests/budget.rs::CEILING`（运行在 `cargo test -p alephcore --lib`）；`src/harness/CLAUDE.md` 是本地强化说明，根 `CLAUDE.md §R10` 给出最高级表述。本页不引用具体行数——任何时候「当前 X 行」应以 `budget.rs` 实测为准
- 顶层 (8)：`mod.rs` / `agent.rs` / `deps.rs` / `trait_def.rs` / `callback.rs` / `chain_context.rs` / `trace.rs` / `trace_sink.rs`
- `agent/` 子目录 (4)：`think.rs` / `act.rs` / `guardrails.rs` / `prompt.rs`（Task 8/9/10 把 `agent.rs` 按 Think/Act/Guardrails/Prompt 拆分为四个子职责）

### 循环里的 5 个「不」

1. 不判断意图分类
2. 不按**消息意图**做工具过滤 / 相关性评分（渐进式工具披露例外，见下）
3. 不做完成度判断（除模型显式 stop）
4. 不做内容审查 / 安全打分
5. 不做错误恢复策略选择

> **渐进式工具披露例外**：core 工具静态常驻 + 全量工具目录 + `tool_search` 元工具按需加载 schema——这是**不看消息内容的静态分区**，加载决策 100% 由模型发起。分区落在工具呈现层，**不进 `src/harness/`**，R10 文件预算零增长。

### YAGNI 撤回模式

任何「零现有消费者」的抽象立即删除 / 撤回，绝不「为未来留口」。Harness dissolution 期间累计删除 ~5,200 行死代码。

### 加代码前必答 3 问

1. 这是脚手架还是认知？认知必须搬到 prompt
2. 模型升级一档还需要它吗？不需要就删
3. 现在有几个真实消费者？零个就撤回

### 关联

是 R3（核心轻量化）+ R7（LLM 主权）+ R9（智慧在 Prompt）在 Agent Harness 工程上的具体落地。

## 北极星

十条红线定义了 Aleph 绝不能做什么。北极星定义了 Aleph 要去哪里。三条原则指导所有前瞻性决策。

### 架构已定——填充，不要重建

1-2-3-4 架构模型（1 核心、2 面孔、3 肢体、4 神经）是稳定且经过验证的。未来的工作是在这个结构中**填充**能力，而非重新设计结构本身。

这意味着：当面对新需求时，第一个问题总是「这适合现有架构的哪里？」——而非「我们需要新架构吗？」第二个问题的答案是否定的。

### 技能驱动未来

架构是骨架。技能是 flesh。一旦 1-2-3-4 结构稳固且红线被强制执行，使 Aleph 更有用的主要向量就是**添加技能**。

技能是可独立部署的领域专业知识单元——Python 脚本、Bash 工作流、MCP 服务器——核心通过其工具系统编排。它们决定 Aleph 可以为用户节省多少实际工作。投资于设计良好的技能的每一小时都在每个接口和每个平台上获得回报，因为技能通过核心运行，而核心平等地服务于所有外壳。

Aleph 的未来不是更多架构。它是更多技能。
