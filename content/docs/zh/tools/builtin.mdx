## 概述

Aleph 附带一组全面的内置工具，涵盖文件操作、代码执行、网页交互、记忆、
浏览器自动化、子 agent 委托、调度等。所有内置工具都实现 `AlephTool`
trait，使用静态分发以获得最大性能，并由 executor 的 builtin 注册表
（`src/executor/builtin_registry/`）在启动时统一装配。

每个工具调用最终都通过 **同一个强制点** `ScopedToolService`
（`src/tools/scoped/`）—— exec tier、命令策略层和按频道的权限合并都在
这里发生。一个工具是否"需要确认"由其 `ToolDefinitionMetadata` 决定，
**不**由它的名字决定。

## 代码执行

| 工具 | 描述 |
|------|------|
| `bash` | 运行 bash 命令（通过 `WorkspaceSandbox`）。 |
| `code_exec` | 多语言代码片段（`shell` / `python` / `javascript`）。 |

两个工具都通过 `Arc<dyn Sandbox>` 执行子进程 —— `src/builtin_tools/` 内
**不允许**裸 `Command::new`。`code_exec` 接收 `language` 与 `code`，`bash`
接收 `cmd`；两者都可带 `working_dir` 与 `timeout`（秒），输出受沙箱超时
（默认 60 秒）与 1 MiB 输出预算约束。

## 文件操作

| 工具 | 描述 |
|------|------|
| `file_ops` | 通过 `action` 参数复用 list / read / write / edit / move / copy / delete / mkdir / search。 |
| `file_read` | 读文件。支持图片（`image_read`），未变更的读取在轮次间通过读缓存去重。 |
| `file_write` | 写文件。 |
| `file_edit` | 对文件应用定点编辑（多个 `edits`，每次 `{oldText, newText}`）。 |
| `apply_patch` | 多文件结构化补丁（`{action, files, …}`）。 |

`file_ops` 是一个多路复用器 —— 它的破坏性子操作（`delete` / `move`）
在 `exec_tier` 下被参数级识别（`ExecTier::asks_for_arguments`）。所以不要
用 `file_ops` 单名作为审批开关 —— 用配置中的明确条目。

## 记忆与检索

记忆有 **三个互补的检索工具**，每个搜的是不同存储，描述措辞经过调优
以避免工具选择混淆：

| 工具 | 搜索的存储 | 何时使用 |
|------|------------|----------|
| `ctx_search` | 工具**输出**的离库（FTS5 内容索引） | 一个工具结果被打上 `[Full output persisted: … Indexed N sections …]`，需要只读相关切片（构建日志、grep、web fetch）。 |
| `recall_events` | **当前会话**的事件时间线（`session_events`，BM25） | 早期工具动作、结果或错误被压缩踢出上下文，需要恢复"已经发生了什么"。 |
| `session_search` | **跨会话**的过去对话（记忆摘要 + 转录） | 需要其他会话的事实或决策（长期记忆）。 |

经验法则：`ctx_search` = "那个工具打印了什么？"；`recall_events` =
"我这次会话已经做了什么？"；`session_search` = "过去的会话发生了什么？"。

其他记忆工具：

| 工具 | 描述 |
|------|------|
| `memory_search` | 跨事实 + 转录的混合检索 + 通过 `ContextComptroller` 去重。 |
| `memory_explore` | 浏览事实图（事实聚类、相似度导航）。 |
| `memory_timeline` | 按时间排序的事实视图。 |
| `memory_browse` | 浏览存储的条目。 |
| `remember` | 显式把一个事实写入长期记忆。 |
| `recall_context` | 拉取与当前会话相关的记忆（用于上下文装配）。 |

## MCP 桥接工具（capability-gated）

以下内置工具 **仅在至少一个连接的 MCP 服务器声明对应能力时才出现在
注册表里**（`src/mcp/tool_bridge.rs::reconcile_capability_tools`）。这样
模型永远不会看到一个每次调用都会失败的工具。

| 工具 | 触发它的能力 |
|------|--------------|
| `mcp_read_resource` | 任一服务器 `resource_count > 0` 或 `resource_template_count > 0` |
| `mcp_list_resources` | 同上（与 `mcp_read_resource` 配对） |
| `mcp_list_resource_templates` | 同上 |
| `mcp_get_prompt` | 任一服务器 `prompt_count > 0` |
| `mcp_list_prompts` | 同上（与 `mcp_get_prompt` 配对） |
| `mcp_login` | 任一服务器 transport 不是 `Stdio`（远程 OAuth 流程） |

`mcp_read_resource` 和 `mcp_get_prompt` 通过 `resolve_server_qualified` 解析
`<server>:<rest>` 形式 id，**最长前缀**匹配服务器 id —— 短前缀/首次匹配
会把一个名字为 `gh:sub` 的服务器上的资源错误地路由到名为 `gh` 的服务器。

## MCP 工具命名与注册

发现自 MCP 服务器的工具以 `<server>__<tool>` 形式注册（如
`github__create_issue`）。`McpHandler::qualified_name` 是命名唯一权威
（`src/tools/handlers/mcp.rs`）：它去掉管理器加上的冗余 `{server}:`
前缀，并把所有不在 `[A-Za-z0-9_-]` 中的字符映射为 `_`，截断到 64 字符。
`{server}__{tool}` 中的双下划线是命名空间分隔符 —— LLM 把它当作名字的
一部分。

非 object 类型的参数 schema 会被**隔离**（quarantine）—— 一个对所有
provider 都会被拒的 schema 会让整轮请求失败而不是污染整个 turn。

## 注册摘要

内置工具的装配入口是 `BuiltinToolRegistry::with_config()`
（`src/executor/builtin_registry/builder/constructor/mod.rs`）。名称与描述的
权威清单是 `src/executor/builtin_registry/definitions.rs:85` 的
`BUILTIN_TOOL_DEFINITIONS`；`create_tool_boxed()`（同文件 `:907`）按名称构造
实例，缺少依赖时返回 `None` —— 该工具这一轮不可用，而不是凭空造一个。

注册表在装配时：

- 为每个 exec 类工具（`bash` / `code_exec` / `code_check`）注入共享的
  `Arc<dyn Sandbox>`；
- 为每个浏览器工具注入 `Arc<ProfileManager>`；
- 为每个 MCP 桥接工具注入 `Arc<McpManagerHandle>`；
- 为每个需要它们的工具注入通道上下文 / ApprovalRequester。

工具名有四个登记面，目录只覆盖第一个：

| 登记面 | 位置 | 含义 |
| --- | --- | --- |
| 目录 | `BUILTIN_TOOL_DEFINITIONS`（`definitions.rs:85`） | 无条件登记，是面向代理的权威清单。 |
| 仅注册表 | `REGISTRY_ONLY_DESCRIPTIONS`（`definitions.rs:1308`） | 依赖或健康状态满足时才注册（如 `scratchpad`、`permission`、`media`、`system`）。 |
| 目录外 | `TOOLS_OUTSIDE_DEFINITIONS`（`src/executor/mod.rs:30`） | `subagent`、`tool_search`，不进目录但模型可调用。 |
| 按请求注入 | `src/tools/scoped/mod.rs` | 例如 `get_tool_schema`，逐请求追加到工具列表。 |

另有六个 MCP 桥接工具（`mcp_read_resource` 等）由 `src/mcp/tool_bridge.rs`
按能力门注册：既不在目录，也不走 `reg(` 点。

每个 `requires_confirmation` 工具由 `CONFIRMATION_REQUIRED_TOOLS` 集合
列出（vault_store、agent_delete、team_disband 等），共享一个
`ApprovalRequester`。这是按构造的 fail-closed —— 不在
`READ_ONLY_TOOLS` 名单里的任何内置工具在 `Ask` tier 下都要求审批。
