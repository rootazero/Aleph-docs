## 概览

Aleph 的工具系统是一个类型安全、可扩展的框架，赋予 agent 对世界进行
操作的能力——执行 shell 命令、读取文件、搜索网络、控制浏览器等。每个
工具都定义为带自动 JSON Schema 生成的 Rust trait 实现，提供编译时正确
性与运行时灵活性。

三个原则：

1. **类型安全优先** —— 工具参数和输出是强类型 Rust 结构体。通过
   `schemars` 从这些类型自动生成发送给 LLM 的 JSON Schema，消除 schema
   漂移。
2. **一个强制点** —— 每次工具调用都通过 `ScopedToolService`
   （`src/tools/scoped/`），它把按频道合并的 `tool_permissions`、exec
   tier（Ask / Auto / Full）与沙箱命令策略层合并到一条路径上。
3. **Capability-gated surfaces** —— 携带能力的内置工具（MCP resource /
   prompt reader、OAuth login helper）仅在至少一个连接的服务器**实际**
   声明该能力时才出现在注册表里。

## 生产强制点 —— `ToolService`

Harness 消费者**只**依赖 `Arc<dyn ToolService>`：

```rust
pub trait ToolService: Send + Sync + 'static {
    async fn execute(&self, name: &str, input: Value) -> Result<ToolOutput, ToolError>;
    async fn list(&self) -> Vec<ToolDefinition>;
    async fn describe(&self, name: &str) -> Option<ToolDefinition>;
    fn dispatcher_schema(&self) -> Arc<[crate::dispatcher::ToolDefinition]>;
}
```

生产实现是 **`ScopedToolService`**（`src/tools/scoped/`）。Gateway 通过
`gateway::execution_engine::tool_service_builder::build_request_tool_service`
**每请求**构建一个，作为 `FlowRequest::tool_service` 提供，所以每个 turn
看到的是共享 `LoopToolRegistry` 的一个 allow-list 视图。

`ScopedToolService` 原生携带 HITL seam：

- `with_confirmation(confirm_tools, requester)` —— 通过 `ApprovalRequester`
  （启动时连接到 `ChannelApprovalBridgeAdapter`）门控 `requires_confirmation`
  工具。
- `with_turn_context(TurnContext)` —— 为每次工具调用作用域化
  `TURN_CONTEXT` task-local，让 HITL 工具（`ask_user`、沙箱升级、通道
  审批）能路由回发起通道。

工具作者实现 `AlephTool`（类型化）或 `LoopTool`（通过
`RegistryToolAdapter` 反类型化）。Harness fallback
`AgentHarnessRunner.tool_service` 是 `NullToolService`
（`src/tools/null.rs`）—— 生产永远到不了它，因为 Gateway 总是提供 per-
request 覆盖；该服务的 `NotFound` 标志上游连线回归。

pre-`ScopedToolService` 的 Phase 2 decorator 链
（`facade.rs` / `dispatch.rs` / `registry.rs` / `middleware/` /
`handlers/`，约 2,700 行）在 2026-05-20 删除了 —— 每个 Gateway 请求覆盖
它，所以它不可达。

## `AlephTool` trait

`AlephTool` 是类型化工具的主要接口。静态分发，JSON Schema 从 `Args`
自动派生：

```rust
pub trait AlephTool: Clone + Send + Sync + 'static {
    const NAME: &'static str;
    const DESCRIPTION: &'static str;
    type Args: Serialize + DeserializeOwned + JsonSchema + Send;
    type Output: Serialize + Send;

    async fn call(&self, args: Self::Args) -> Result<Self::Output>;

    async fn call_json(&self, args: Value) -> Result<Value> { /* blanket */ }
    fn definition(&self) -> ToolDefinition { /* blanket, schemars */ }
}
```

`LoopTool` 是反类型、JSON-`Value` 的形状，被 `McpHandler` 与 capability-gated
内置工具使用。`RegistryToolAdapter` 桥接两者。

### 通过 `schemars` 生成 Schema

工具参数类型派生 `JsonSchema`，自动生成发给 LLM 的 JSON Schema。字段级
文档注释成为参数描述：

```rust
#[derive(Debug, Clone, Serialize, Deserialize, JsonSchema)]
pub struct SearchArgs {
    /// 搜索查询（自然语言）
    pub query: String,
    /// 最大返回结果数（默认：10）
    #[serde(default)]
    pub max_results: Option<u32>,
}
```

`required` 数组自动计算：只有不带 `#[serde(default)]` 的字段是必需的。

## 工具类别

| 来源 | 分发 | 示例 |
|------|------|------|
| **内置**（`src/builtin_tools/`） | 静态（`AlephTool`） | `bash`、`code_exec`、`file_ops`、`web_fetch`、`search`、`memory_*`、`browser_*` |
| **MCP**（外部进程） | 动态（`LoopTool` via `McpHandler`） | `<server>__<tool>`，capability-gated `mcp_read_resource` / `mcp_list_resources` / `mcp_list_resource_templates` / `mcp_get_prompt` / `mcp_list_prompts` / `mcp_login` |
| **Per-action 浏览器**（`src/builtin_tools/browser_tools/`） | 静态 | `browser_open`、`browser_click`、`browser_navigate`、`browser_snapshot`、`browser_screenshot`、`browser_evaluate`、`browser_fill_form` … |

<Callout type="info">
一个 capability-gated 内置工具仅在至少一个连接的 MCP 服务器声明该能力时
才出现在注册表里 —— 模型永远不会看到一个每次调用都会拒绝的工具。bridge
在每次 manager 事件（`src/mcp/tool_bridge.rs`）上重新调和每个服务器的
能力集合。
</Callout>

## 内置工具注册

内置工具不通过手写 builder 注册；它们由 executor 的 builtin 注册表
（`src/executor/builtin_registry/`）装配。每个工具持有它需要的共享依赖
（`Arc<Sandbox>`、`Arc<ProfileManager>`、`Arc<McpManagerHandle>` …），注册表
拥有启动时的连线。

一个没有携带必需依赖的工具返回结构化的"sandbox 未配置"或"manager 未
配置"错误，**不会**回退到无沙箱执行 —— 默认是安全的，不是宽松的。

## 按频道工具权限

限制 *agent 能做什么*（而不是 *谁能连接*）由按频道工具权限层
`ScopedToolService` 处理。它跨三层合并 `ToolPermissionsConfig`
（**global → agent → channel**，最严格胜出），不读 `IdentityContext`。
这与连接信任正交。

三件事在同一强制点按此顺序组合：

1. **`[policies.tool_permissions]`** —— 按工具 `allow` / `ask` / `deny`，
   精确名或 glob，三层最严格胜出。显式条目胜出 tier。
2. **Exec tier**（`Ask` / `Auto` / `Full`）—— 读取 `ToolFacts` 的
   `{idempotent, requires_approval}`，**不**读工具名。默认 fail-closed：
   一个 Aleph 没听过的工具是非幂等的 ⇒ `Ask` 下必拦。
3. **`[sandbox.command_policy]`** —— 硬线命令底线，任何 tier 与任何权限
   条目都不能降低它。

`Deny` 把工具从模型视角隐藏**且**拒绝调用；`Ask` 路由到审批门。

## 与 agent 循环集成

当 LLM 响应一个工具调用：

1. **解析** 调用，作用于 per-request `ScopedToolService`。
2. **过滤** 通过合并的 `tool_permissions`（allow / ask / deny）。
3. **咨询** exec tier，针对未命名的工具。
4. **门控** confirm-gated 工具通过审批请求器（HITL）。
5. **执行** —— exec-class 工具走 `WorkspaceSandbox`。
6. **记录** 决策到 session event log；签名工具也追加到 per-agent 签名
   账本。
