## 什么是 MCP？

[Model Context Protocol](https://modelcontextprotocol.io/)（MCP）是一个开放
标准，定义了 AI 应用如何与外部工具服务器通信。它给 LLM 提供了一种结构化
方式来发现和调用工具、读取资源、从外部进程检索提示。

Aleph 充当 **MCP 客户端**，连接到一个或多个提供工具、资源和提示的 MCP
服务器。这种架构让你可以在不修改 Aleph 核心的前提下扩展它的能力 —— 只
需要让 MCP 服务器运行在 Aleph 旁边。

<Callout type="info">
MCP 是三种扩展类型（`Skill`、`Plugin`、`Mcp`）之一。本页介绍底层 MCP
客户端机制 —— 日常使用请走统一的扩展商店。
</Callout>

## 架构

集成有三个层：

1. **`McpClient`**（`src/mcp/client.rs`）—— 管理到外部 MCP 服务器的连接、
   工具发现、`tools/call` 调用。
2. **`McpManager`**（`src/mcp/manager/`）—— actor，通过健康监控和熔断器
   编排服务器生命周期。
3. **`McpHandler`**（`src/tools/handlers/mcp.rs`）—— 把发现到的 MCP 工具
   包装成 `LoopTool`，并在共享 `LoopToolRegistry` 里以 `<server>__<tool>`
   注册。

第四个组件 —— **工具桥**（`src/mcp/tool_bridge.rs`，入口
`spawn_tool_bridge`）—— 订阅 manager 的事件广播，把工具增量同步进注册表。
它**也是**注册 capability-gated 内置工具的唯一场所（`mcp_read_resource` /
`mcp_list_resources` / `mcp_list_resource_templates` / `mcp_get_prompt` /
`mcp_list_prompts` / `mcp_login`）。

```
Aleph Core
├── McpManager (Actor)
│   ├── McpClient (per server)
│   ├── 健康监控 + 熔断器
│   └── 自动重启
│
├── 工具桥（spawn_tool_bridge）
│   ├── ToolsChanged event → register / unregister McpHandler
│   └── capability 聚合 → reconcile_capability_tools()
│
└── LoopToolRegistry
    ├── Builtin handlers
    ├── <server>__<tool> (per server)
    └── Capability-gated builtin tools
```

## 传输类型

| 传输 | 用例 | 连接 |
|------|------|------|
| **Stdio** | 本地进程 | 生成子进程，通过 stdin/stdout 通信 |
| **HTTP** | 远程服务器 | 标准 HTTP 请求 / 响应 |
| **SSE** | 带流式传输的远程服务器 | Server-Sent Events 用于实时更新 |

## 服务器配置

服务器配置存储在 `~/.aleph/mcp_config.json`：

```json
{
  "version": 1,
  "servers": {
    "filesystem": {
      "id": "filesystem",
      "name": "Filesystem Server",
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-filesystem", "/Users/me/projects"],
      "env": {},
      "requires_runtime": "node",
      "auto_start": true,
      "timeout_seconds": 300
    },
    "github": {
      "id": "github",
      "name": "GitHub Server",
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      },
      "requires_runtime": "node",
      "auto_start": true
    }
  }
}
```

### 配置选项

| 字段 | 必需 | 默认 | 描述 |
|------|------|------|------|
| `id` | 是 | — | 唯一服务器标识符 |
| `name` | 否 | 与 `id` 相同 | 显示名 |
| `transport` | 否 | `stdio` | `stdio` / `http` / `sse` |
| `command` | 仅 stdio | — | 可执行路径 |
| `args` | 否 | `[]` | 命令参数 |
| `url` | 仅 http / sse | — | 服务器 URL |
| `env` | 否 | `{}` | 环境变量 |
| `requires_runtime` | 否 | `null` | `node` / `python` / `bun` |
| `auto_start` | 否 | `true` | 服务器启动时自动启动 |
| `timeout_seconds` | 否 | `60` | 请求超时（秒） |

### 环境变量展开

值支持 `${VAR}` 展开。未知变量保留原样，所以你可以安全地引用在某些环境
中没设置的变量。

### 重启规则

配置文件**不会**自动重载，**没有** MCP 管理 RPC。修改后必须
`aleph-server stop && aleph-server start` 才会生效。

## 工具注册与命名

当一个服务器启动时，bridge 调用
`src/tools/handlers/registration.rs::register_mcp_tools`，它为每个发现到
的工具实例化一个 `McpHandler` 并把它放进共享注册表。注册名由
`McpHandler::qualified_name`（`src/tools/handlers/mcp.rs`）合成，是命名的
**唯一权威**：

```rust
pub fn qualified_name(&self) -> String {
    let short = self.tool_name
        .strip_prefix(&format!("{}:", self.server_id))
        .unwrap_or(&self.tool_name);
    sanitize_tool_name(&format!("{}__{}", self.server_id, short))
}
```

也就是说：

- 内部名（`get_weather`）变成 `<server>__get_weather`（`weather__get_weather`）；
- 任何不在 `[A-Za-z0-9_-]` 集合内的字符映射为 `_`；
- 截断到 64 字符（OpenAI 函数调用 / Anthropic / Gemini 都接受）。

`__` 是命名空间分隔符 —— 模型看到的是名字的一部分，不要在内部工具名里
写冒号或点（它们会被映射为 `_`，可能产生混淆）。

## Capability-gated 内置工具

下面这些工具**仅在至少一个连接的服务器声明对应能力时**才出现在
注册表里：

| 工具 | 触发条件 |
|------|---------|
| `mcp_read_resource` | 任一服务器 `resource_count > 0` 或 `resource_template_count > 0` |
| `mcp_list_resources` | 同上（与 `mcp_read_resource` 配对） |
| `mcp_list_resource_templates` | 同上（template-only 服务器也能列） |
| `mcp_get_prompt` | 任一服务器 `prompt_count > 0` |
| `mcp_list_prompts` | 同上（与 `mcp_get_prompt` 配对） |
| `mcp_login` | 任一服务器 transport 不是 `Stdio`（远程 OAuth） |

`reconcile_capability_tools` 在每次 manager 事件（`ToolsChanged` /
`ServerStarted` / `ServerStopped` / `ServerCrashed`）以及广播 `Lagged` 之后
重新同步 capability 集合。资源 reader + discovery 工具**共享一个门**：
两个同时在场或同时缺席 —— 否则模型要么拿到一个没法发现 URI 的 reader，
要么拿到一个没有 reader 可调用的 discovery 工具。

## `resolve_server_qualified` —— 最长前缀匹配

`mcp_read_resource` / `mcp_get_prompt` 收到的 URI 是 `<server>:<rest>`
形式。`src/builtin_tools/mcp_resource.rs::resolve_server_qualified` 用
**最长前缀**匹配从字符串里剥掉一层服务器前缀：

```rust
fn server_prefix_candidates(qualified: &str) -> Vec<(&str, &str)> {
    let mut out: Vec<(&str, &str)> = qualified
        .match_indices(':')
        .map(|(idx, _)| (&qualified[..idx], &qualified[idx + 1..]))
        .collect();
    out.reverse();  // longest first
    out
}
```

历史上用最短前缀 / 首次匹配实现时：如果一个服务器字面叫 `gh:sub`，它的
资源会被错误地路由到名为 `gh` 的服务器上（`get_client("gh")` 也满足
`<server>:<rest>`）。从右到左迭代（最长先试）后，`get_client` 对任何
非服务器前缀（如 `file:///…` 里的 `file://`）返回 `None`，所以第一个
命中是最长的**已注册**服务器 id。

`qualified_id` 把已服务器限定的 id 再前缀一层 server id —— 形成**双重**
段（如 `github:github:file:///R.md`）。这是 load-bearing：`mcp_read_resource`
剥掉前导的 `server:`，客户端自己的前缀解析再剥第二个，原样往返落到
服务器上的 bare URI。把这个 id 描述为不透明，能阻止模型"贴心地"折叠掉
双层段而破坏往返。

## 注解驱动的元数据

MCP 服务器通过 `tools/list` 的 `annotations` 字段声明工具元数据。
`McpHandler::with_flags` 把它们映射到 `ToolDefinitionMetadata`：

| 注解 | 字段 | 含义 |
|------|------|------|
| `readOnlyHint: true` | `concurrent_safe` | 自动重试 |
| `idempotentHint: true` | `idempotent` | tier 视为安全 |
| `destructiveHint: true` | `requires_approval` | Ask tier 下仍要审批 |

`ScopedToolService`（`src/tools/scoped/`）读这两个字段，**不**读工具名。
未声明 = `false` = 非幂等 = mutating = `Ask` 必然 fail-closed。按设计，
没有名字白名单可以覆盖这个。

## Schema 隔离

`unusable_tool_schema_reason`（`src/tools/handlers/registration.rs`）标记
**所有** provider 都会拒的 schema：

- 顶层 schema 不是 JSON object；
- `type` 不是 `"object"` 且不是包含 `"object"` 的数组。

缺失 `type` 是被允许的（provider 默认 object 形状）。单个不支持的关键字
（`$ref` / `format` …）不动 —— keyword 剥离是 provider 特定的，由别处
（Gemini schema cleaner）处理。

被隔离的工具会跳过注册并 log 一条 warning，不会让整轮请求因为一个 schema
而被拒。

## McpManager actor

McpManager 用 actor 模式进行安全的并发服务器管理：

```rust
let (actor, handle) = McpManagerActor::new(None).await?;
tokio::spawn(actor.run());
handle.add_server(config).await?;
handle.list_servers().await?;
handle.shutdown().await?;
```

### 服务器生命周期命令

| 命令 | 描述 |
|------|------|
| `AddServer` | 注册新服务器配置 |
| `RemoveServer` | 按 ID 移除服务器 |
| `AddTransientServer` / `RemoveTransientServer` | 注册 / 移除**临时**服务器（只活在本次进程里，不写盘） |
| `StartServer` / `StopServer` / `RestartServer` | 生命周期控制 |
| `ListServers` / `ListServerConfigs` | 列出服务器与服务器配置 |
| `GetStatus` | 获取服务器详细状态 |
| `GetClient` | 取某个服务器的客户端句柄 |
| `AggregateInstructions` | 跨服务器聚合 instructions |
| `SetSamplingCallback` | 设置采样回调 |
| `ServerListChanged` | 服务器列表变化通知 |
| `Shutdown` | 优雅关闭所有服务器 |

临时服务器服务于插件自带的 MCP 服务器：生命周期由插件系统掌管，
不写进用户的 MCP 配置，也不会动盘上的配置。

### 事件

manager 广播以下事件用于实时同步（bridge 消费它们）：

```rust
pub enum McpManagerEvent {
    ServerStarted { server_id, tool_count, .. },
    ServerStopped { server_id, .. },
    ServerCrashed { server_id, error, .. },
    ServerRestarting { server_id, .. },
    ServerRemoved { server_id, .. },
    ToolsChanged { server_id, .. },
    // ...
}
```

`Lagged` 关闭重连会触发**全量重同步**（`resync_all`），bridge 不会
靠记忆去猜测漏掉的状态转换。

## 健康监控

McpManager 实现熔断器模式：

```
Healthy → Degraded (2+ failures) → Unhealthy (5+ failures)
                                       ↓
                                   Restarting
                                       ↓
                                   Dead (max restarts exceeded)
```

健康跟踪包括：连续失败计数、重启窗口管理（防止重启风暴）、最后错误消息
保留、自上次健康检查以来的经过时间。

## 工具调用

当 agent 调用一个 MCP 工具时：

1. `LoopToolRegistry` 把 `<server>__<tool>` 解析为 `McpHandler`。
2. `McpHandler::invoke` 调 `McpClient::call_tool`（内部 namespaced 短名）。
3. 服务器执行工具并返回结果。
4. 结果作为 `ToolOutput` 转发给 LLM。

错误映射：`NetworkError` / `IoError` → `ToolError::Transport`；
`McpTimeout` / `Timeout` → `ToolError::Timeout`；其他 → `ToolError::Execution`。
所有错误消息在显示前过 `mcp::redact_mcp_error` —— 服务器回显包含密钥
的参数或 URL 不能泄漏到会话历史。

## OAuth 与远程服务器

远程 MCP 服务器走 OAuth。`mcp_login` 内置工具（仅当至少一个服务器
transport 不是 stdio 时出现）走浏览器 OAuth 流程并把 token 持久化到
`mcp/auth/`。

远程服务器的 URL 必须通过 SSRF 校验（`src/mcp/transport/http.rs` 用
`safe_fetch` + `SsrfPolicy`）—— 私网 / 链接本地 / DNS rebinding 都会拒。
SSE 与 OAuth 预检走的是同一条策略的另一个入口
（`src/security/ssrf` 的 `validate_url_with_pinned`）。

## 运行时检查

`requires_runtime` 字段让 manager 在启动服务器前验证 Node / Python / Bun
是否可用；缺失依赖会让这一个服务器跳过并 log warning，不会让整个启动
失败。

## 安全注意事项

- **进程隔离**：stdio MCP 服务器作为独立进程运行。
- **环境变量**：用 `${VAR}` 展开敏感值（API key 等），永远不要明文。
- **OAuth token 存储**：远程服务器的 OAuth token 由 Rust core 写入加密
  vault，绝不允许 `AlephBridge` 或任何其他进程读写 `~/.aleph/` 下任何
  路径。
- **工具审批**：通过声明 `destructiveHint` 或在
  `[policies.tool_permissions]` 里明确登记让审批门工作。
- **网络边界**：远程 MCP 服务器用 HTTPS + 合适的认证头。
- **运行时验证**：在服务器启动前检查所需运行时，防止任意命令执行。

## 最佳实践

1. 给必须可用的基础服务器设 `auto_start: true`。
2. 设置合理的超时，防止挂起。
3. 设 `requires_runtime`，缺失依赖时报错更清晰。
4. 用环境变量传递机密 —— 永远不要硬编码 API key。
5. 订阅 manager 的事件，监控服务器健康与工具变更。
6. 相关工具放进同一个 MCP 服务器，减少连接开销。
