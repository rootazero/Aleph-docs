本页说明 Panel 如何构建、嵌入 Gateway、被桌面宿主加载，以及改动 Panel 之后怎样让修改真正生效。

## Panel 是什么

Panel 是 `interfaces/webchat/` 里的 Rust + Leptos 单页应用（crate `aleph-panel`，库名 `aleph_panel`，编译为 WASM）。所有产品 UI 都在这里，桌面宿主只提供窗口和系统集成，不再有第二套业务界面（红线 R2：产品 UI 只有一个真值源；`docs/reference/DESKTOP_SHELL.md`）。

同一份 Panel 既能在浏览器里打开 Gateway 的地址使用，也能被 [桌面宿主](./overview) 放进 WebView。宿主加载的地址是连接目标的根路径（`shared/client/src/connection_target.rs` 的 `ConnectionTarget::panel_url`），不带凭据或启动材料。

## 构建与嵌入链

### 资源如何进入 Gateway

Panel 的构建产物 `interfaces/webchat/dist/*` 在 `aleph-server` 编译期通过 `rust_embed` 静态嵌入二进制（`src/gateway/control_plane/assets.rs`，嵌入目录由 `folder` 属性指定为 `interfaces/webchat/dist/`）。运行中的 Gateway 不会从磁盘读取 `dist/*`。

### 刷新步骤

完整链路有三步，缺一不可（`docs/reference/DESKTOP_SHELL.md` 的「Panel ↔ Daemon 资源嵌入链与刷新」）：

1. `just wasm`：重建 `interfaces/webchat/dist/` 下的 `aleph_panel.js`、`aleph_panel_bg.wasm`、`tailwind.css`、`index.html`。配方内部执行 `cargo build -p aleph-panel --lib --target wasm32-unknown-unknown --profile wasm-release`，再用 `wasm-bindgen --target web` 输出到 `interfaces/webchat/dist/`，并校验 js 与 wasm 是匹配的一对（`just check-dist`，`scripts/check_panel_dist.mjs`）。
2. `cargo build --release -p alephcore --bin aleph-server`：让 `rust_embed` 把新的 `dist/` 烧进二进制。
3. 替换正在运行的 `aleph-server`：先停掉旧进程，再用新二进制启动。开发环境下是 `./target/release/aleph-server stop`，然后 `cargo run --release -p alephcore --bin aleph-server start`。Windows 无法覆盖正在运行的 exe，必须先停。

<Callout type="warn" title="改完看不到效果">
几乎都是漏了第 2、3 步。单独运行 `just wasm` 只更新磁盘上的文件；`just dev`（先 `just wasm` 再 `cargo run`）只在 Gateway 尚未启动时有效。已经在跑的 Gateway 必须替换二进制并重启，才能看到 Panel 的改动。
</Callout>

## 模块化 Panel

`interfaces/webchat/Cargo.toml` 里有 `panel-modular` feature，默认不开（`default = ["legacy-terminal"]`）。启用后 `PanelShell` 才会参与渲染，真实的渲染点在 `interfaces/webchat/src/app.rs`（`crate::panel::PanelShell`）。`panel-tab-spike` 依赖 `panel-modular`，另有 `runtime-qa` 用于运行时验证。

模块化面板不是另一个生产 UI 权威：它是同一个 Panel 的可选渲染路径，桌面宿主托管的始终是同一个 Leptos/WASM Panel（`docs/reference/DESKTOP_SHELL.md`）。模块化构建走 `just wasm-modular`，与默认的 `just wasm` 分开。

> **状态：规划中** — 蓝图为 `docs/superpowers/specs/2026-11-22-nsh-panel-modular-refactor-design.md`（单一共享 TSX 源、带 Web 回退的原生组件、由 Core 持有能力与授权）；共享 TSX 渲染与 S4 快照/回放尚未实现，当前实现见 `interfaces/webchat/src/app.rs`。

## 宿主与 Panel 的通道

宿主与 Panel 之间只有一条窄通道：WebView 的 `window.nsh.postMessage`。消息类型定义在 `shared/protocol/src/panel_shell.rs`，宿主侧实现在 `desktop/nsh-shell/src/panel_bridge.rs`，页内脚本是 `desktop/nsh-shell/src/panel_bridge.js`。

### 消息形状

所有消息都是带 `kind` 标签的 JSON（kebab-case），并拒绝未知字段（`deny_unknown_fields`）。

| 方向 | 类型 | `kind` | 作用 |
|---|---|---|---|
| 宿主到 Panel | `ShellRequest::Probe` | `probe` | 探测 Panel 是否就绪，携带 `request` |
| 宿主到 Panel | `ShellRequest::CredentialsReady` | `credentials-ready` | 通知 Panel 凭据通道已绑定到某个 `document` |
| 宿主到 Panel | `ShellRequest::OpenChat` | `open-chat` | 让 Panel 导航到 Chat |
| 宿主到 Panel | `ShellRequest::CredentialReply` | `credential-reply` | 凭据调用的结果 |
| 宿主到 Panel | `ShellRequest::AutostartReply` | `autostart-reply` | 登录项状态的结果 |
| Panel 到宿主 | `PanelReply::Ready` | `ready` | 回应 `probe`，带 `document` |
| Panel 到宿主 | `PanelReply::ChatOpened` | `chat-opened` | 回应 `open-chat` |
| Panel 到宿主 | `PanelReply::Notify` | `notify` | 请求系统通知，带 `title`、`body` |
| Panel 到宿主 | `PanelReply::CredentialRequest` | `credential-request` | 凭据调用，`call` 为 `CredentialCall` |
| Panel 到宿主 | `PanelReply::AutostartRequest` | `autostart-request` | 读取登录项状态 |

`CredentialCall` 按 `operation` 区分：`load`、`save`（`lease_id` 加 `credential`）、`delete`（`lease_id`）。`CredentialReply` 按 `outcome` 区分：`loaded`、`saved`、`deleted`、`failed`。`AutostartStatus` 按 `status` 区分：`enabled`、`disabled`、`requires_approval`、`unavailable`、`failed`。

### 校验与限制

- Panel 发给宿主的每条消息都带前缀 `aleph-shell-v1:<随机 uuid>:`（宿主每次启动生成），宿主只处理带这一前缀的消息（`desktop/nsh-shell/src/panel_bridge.rs`）。
- 单条消息上限 16384 字节（宿主的 `MESSAGE_LIMIT` 与页内脚本的 16384 检查）。
- `document` 是页面加载时随机生成的 32 位小写十六进制串（`valid_document`）；所有请求必须绑定当前页面的 `document`，页面重载后旧的凭据租约与待处理请求都会失效。
- 页内脚本只在顶层窗口、且 `location.origin` 等于宿主传入的 Panel origin 时安装（`desktop/nsh-shell/src/panel_bridge.js`）。
- 通知标题必须非空且不超过 256 字节，正文不超过 2048 字节（`valid_notification`）。

### 导航流程

页面加载后，宿主以 350 毫秒间隔发送 `probe`，最长等待 15 秒；Panel 以 `ready` 回复并给出 `document`，宿主随后发送 `credentials-ready`。需要打开 Chat（`aleph://open` 或点击通知）时，宿主发送 `open-chat` 并等待 `chat-opened`，2 秒内没有确认就放弃，不重放动作。

## 传输矩阵

Panel 与 Gateway 之间有三种入口，权限各不相同：

| 入口 | 传输 | 认证 | 能做什么 |
|---|---|---|---|
| 旧 `/ws` | Gateway 端口（默认 18790）上的 WebSocket JSON-RPC | 既有的 `/ws` 认证；`system.hello` 只做协议探测，不准入、不设置身份（`src/gateway/handlers/system_hello.rs`） | 现有 Panel 与客户端使用的完整 RPC，经共享分发（`src/gateway/server/connection/rpc.rs`） |
| S1-B 只读 Desktop IPC | Unix domain socket；`aleph-server start --desktop-ipc <socket>` 显式开启（`src/gateway/server/connection/local_ipc.rs`） | 同账号的 OS 认证，socket 位于调用方持有的 0700 目录；不回退到 TCP 或 WebSocket | 仅 `health`、`sessions.list`；有界帧（`shared/protocol/src/framing.rs`：4 字节头，单帧上限 8 MiB），并发请求上限 8，hello 超时 5 秒（`shared/client/src/local_ipc.rs`） |
| S1-C 只读 Web v1 | 原生 TLS 监听上的 `POST /v1/session` 与 `GET /v1/ws`（`src/gateway/server/connection/web_v1.rs`） | 同源检查；已配对设备或用户明确绑定的一次性 ticket 换取短期、仅限主机的 Cookie，Cookie 引用已有的设备凭据，不改变 Core 主体 | `system.hello` 之后的有界二进制 `health`、`sessions.list`；不支持由代理终止 TLS |

桌面宿主自带的 `--desktop-ipc-status` 查询走的是第二行（见 [桌面宿主](./overview)）。Panel 在 WebView 里仍使用第一行的既有传输，旧入口和现有 Panel 没有换线。

三种入口的验证回执：`docs/superpowers/runs/2026-11-23-nsh-panel-s1a-shared-dispatch-verification.md`、`docs/superpowers/runs/2026-11-23-nsh-panel-s1b-desktop-ipc-verification.md`、`docs/superpowers/runs/2026-11-23-nsh-panel-s1c-web-v1-verification.md`。S1-B 的 macOS 证据与待完成的 Linux 原生、Windows Named Pipe 工作是分开记录的。

## 已知限制

| 限制 | 谁负责 | 还差什么 |
|---|---|---|
| 深链只能打开 Chat | 宿主与 Panel 共同 | 宿主目前只处理精确等于 `aleph://open` 的 URL（`desktop/nsh-shell/src/panel_bridge.rs`）；把其它 `aleph://` URL 路由到具体视图，需要宿主转发路径并由 Panel 增加处理程序。`docs/reference/DESKTOP_SHELL.md` 的 follow-ups 对此有记录 |
| 冷启动深链可能早于 Panel 加载完成 | 宿主 | `open-chat` 要等 `probe` 得到 `ready` 后才发出，探测 15 秒内没有确认则放弃，该次动作不会重放 |
| 窗口拖拽区扩展 | 未核实 | `docs/reference/DESKTOP_SHELL.md` 记录的是旧壳需要宿主侧处理程序；`interfaces/webchat/src/app.rs` 里的拖拽相关代码仍沿用旧壳的属性名，NSH 侧没有找到对应实现，本页不对 NSH 的拖拽行为下结论 |
| 模块化面板与 S4 快照/回放 | Panel | 见上文「模块化 Panel」的规划中说明 |
