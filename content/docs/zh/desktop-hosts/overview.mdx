## 桌面应用如何运行

Aleph 桌面应用使用 NSH 0.6.0（`desktop/nsh-shell/Cargo.toml`）。NSH 管理窗口、托盘、快捷键、通知和设备凭据。推理、工具、状态与 Gateway 由独立的 `aleph-server` 进程提供。

NSH 的 WebView 打开 Gateway 根地址。本机默认是 `http://127.0.0.1:18790/`，远程模式使用保存的 HTTPS Gateway 地址。Gateway 返回相同的 Leptos/WASM Panel，用户也可以直接在浏览器打开。入口见 `desktop/nsh-shell/src/launch.rs`、`desktop/nsh-shell/src/app.rs` 与 `src/gateway/control_plane/server.rs`。构建及可选 TSX AppView 见 [Panel 宿主](./panel)。

## 本机与远程连接

| 模式 | 启动与服务生命周期 |
|---|---|
| 打包应用，本机目标 | 默认启用 `embedded-core`；宿主尝试接入兼容的本机 Gateway，或启动随包提供的 `aleph-server`。 |
| 打包应用，远程目标 | 打开所选 Gateway 的 HTTPS 地址。连接表单可保存目标，远程服务由部署方管理。 |
| 命令行 `--connect <origin>` | 单次连接已运行的 Gateway。远程地址需要 HTTPS，此选项不持久化目标。 |

NSH 桌面应用连接远程 Gateway 时，使用 HTTPS 源站和操作系统信任的证书。NSH 的连接探测会拒绝自动生成的自签名证书（`desktop/nsh-shell/src/gateway_probe.rs`）。

本机准入先检查回环端口。明确的连接拒绝允许启动同目录的服务二进制；兼容但仍在启动的 Gateway 会被轮询；不兼容或无法确认的监听器使启动失败。兼容性检查读取 `/health`、`/ready` 和 Panel 兼容标记，服务身份与用户授权仍由各自的协议处理。见 `desktop/nsh-shell/src/local_service.rs`、`desktop/host/src/local_server.rs` 与 `desktop/host/src/local_server/admission.rs`。

普通退出关闭桌面应用，随包启动的服务可以继续运行。要一并停止本应用持有的服务，选择 **Quit Aleph and Stop Server**（`desktop/nsh-shell/src/app.rs`、`desktop/nsh-shell/src/menu.rs`）。已运行并被接入的兼容服务由原进程持有。

## 命令行接口

| 参数 | 行为 |
|---|---|
| `--connect <origin>` | 打开已运行 Gateway 的 Panel。 |
| `--autostart-status` | 读取桌面应用的登录项状态。 |
| `--desktop-ipc-status <endpoint>` | 在 Gateway 已启用 Desktop IPC 时，通过本地端点查询一次 `health`。 |

这些参数互斥，定义见 `desktop/nsh-shell/src/cli.rs`。

## 原生集成

以下行为都在 `desktop/nsh-shell/src/app.rs` 与 `desktop/nsh-shell/src/panel_bridge.rs`。

### 窗口与托盘

- 应用窗口与标识由 `desktop/nsh-shell/nsh.json` 声明。
- 关闭主窗口时宿主隐藏窗口（`desktop/nsh-shell/src/app.rs`）。
- 托盘提供打开窗口、连接、通知权限、重载与退出等命令。macOS 还有应用菜单。检查更新入口取决于宿主更新配置（`desktop/nsh-shell/src/menu.rs`、`desktop/nsh-shell/src/update.rs`）。

### 全局热键

默认热键 `mod+shift+a`，用于显示或隐藏主窗口。环境变量 `ALEPH_SHELL_HOTKEY` 可改写，设为 `disabled` 则不注册。热键无效或被系统拒绝时只打日志，不影响启动。

### 通知

Panel 通过桥发出 `Notify` 消息；宿主在窗口不处于「可见且聚焦」时才请求系统通知，且仅在系统权限为 `Granted` 时展示。标题必须非空且不超过 256 字节，正文不超过 2048 字节（`shared/protocol/src/panel_shell.rs` 的 `valid_notification`）。待发队列容量为 1，队列满时丢弃并打日志。点击通知（标识 `aleph-panel-chat`）会显示并聚焦窗口，然后打开 Chat。系统通知权限不是产品功能开关，宿主不提供关闭通知功能的开关（`docs/reference/DESKTOP_SHELL.md`）。

### 深链与 URL scheme

宿主注册 `aleph` URL scheme（`.url_schemes(["aleph"])`）。`desktop/nsh-shell/src/panel_bridge.rs` 用 `next_url_scheme_open` 接收系统打开事件，当前只识别精确等于 `aleph://open` 的 URL，处理为「让 Panel 打开 Chat」；其它 `aleph://` URL 会被忽略。

打开 Chat 的流程是文档绑定的：宿主先发 `Probe`，Panel 回复带 32 位小写十六进制 `document` 标识的 `Ready`，之后宿主发 `OpenChat`，等待 `ChatOpened`，2 秒内没有确认就放弃，不重放动作。

> **已知限制：** 把深链路由到 Chat 以外的具体视图还没有实现。`docs/reference/DESKTOP_SHELL.md` 的 follow-ups 记录了「Panel 侧尚无处理程序」这一缺口，该条是针对旧壳写的；对 NSH，上述代码行为是权威描述。

### 凭据

`desktop/nsh-shell/src/credentials.rs` 为 Panel 提供设备凭据的本机存取，后端是 `aleph_client::DeviceCredentialStore`，按 Gateway 地址分库；默认目标的 Gateway 地址是 `ws://127.0.0.1:18790/ws`。Panel 通过桥发起的 `CredentialCall` 只有三种操作：`Load`、`Save`（带 `lease_id` 和 `DeviceConnectCredential`）、`Delete`（带 `lease_id`）；回复为 `Loaded`、`Saved`、`Deleted { existed }` 或 `Failed { error }`，错误只有 `Unavailable`、`Rejected`、`Malformed` 三种（`shared/protocol/src/panel_shell.rs`）。页面导航或重载时，宿主会使现有凭据租约失效（`CredentialService::invalidate`）。

### 登录项

`desktop/nsh-shell/src/autostart.rs` 只读取「当前应用」的登录项状态，不是服务端自启，也没有写入入口。状态取值为 `Enabled`、`Disabled`、`RequiresApproval`、`Unavailable { reason }`、`Failed`。非 macOS 平台一律返回 `Unavailable { reason: UnsupportedPlatform }`。

macOS 上读的是 `SMAppService::mainAppService().status()`，并先做身份校验：进程必须运行在 `.app` 包里（否则 `NotAppBundle`），包标识必须等于 `APP_ID` 且可执行文件落在 `Contents/MacOS` 下（否则 `IdentityMismatch`），系统需提供 `SMAppService`（macOS 13 起，否则 `ApiUnavailable`）。

## Desktop IPC 与平台支持

Desktop IPC 是 Gateway 的**显式 opt-in 本地只读入口**。代码树里有两个平台形态：Unix 用 Unix domain socket，Windows 用命名管道。两个形态共用同一套帧格式、握手和 RPC 循环，但**生产入口目前只在 Unix 打开**——Windows 上两个 opt-in 命令都会被同一个总闸拒绝。下面先分清两个不同程序的参数，再给跨平台矩阵。

### 只读 IPC 状态查询

宿主侧的查询命令是 `--desktop-ipc-status <socket>`：经 Desktop IPC（Unix 上是 Unix domain socket）读取一次 Gateway 的 `health`，不打开 Panel，也不回退到 WebSocket（`desktop/nsh-shell/src/ipc_status.rs`）。

- 参数必须只有这一组（`--desktop-ipc-status` 加一个端点）；Unix 上端点必须是带文件名的绝对路径，Windows 上必须是显式的本地命名管道名；与 QA 配置同时出现会被拒绝。
- 握手使用 `ProtocolVersion { major: 1, minor: 0 }`、客户端名 `aleph-nsh-shell`、`ui_runtime: "nsh"`、空特性列表。
- `health` 调用超时 5 秒，关闭连接超时 2 秒；响应必须是 `status == "healthy"` 且 `timestamp` 非空，否则失败。
- 非 Unix 平台直接报 `Desktop IPC is unavailable on this platform`。这句拒绝来自客户端侧的总闸，而不是缺少实现代码：Windows 的命名管道端点校验就在树里（`shared/client/src/local_ipc/windows.rs`），只是总闸为假时走不到它。

被查询的 Gateway 需要用服务端侧的 `--desktop-ipc <endpoint>` 预先启动，见 [Panel 宿主](./panel) 的传输矩阵。

### 服务端 opt-in：`--desktop-ipc <endpoint>`

服务端侧的开关是 `aleph-server` 的 `--desktop-ipc <endpoint>`。它和宿主的 `--desktop-ipc-status` 是**两个不同程序的不同参数**：前者让 Gateway 挂载本地监听，后者让宿主读一次状态。

- 参数定义在 `src/bin/aleph-server/cli.rs`：值名是 `ENDPOINT`（commit `5d89d7aff` 之前是 `SOCKET_PATH`，因为 Windows 上它不再是 socket 路径），帮助文本为「Opt in to read-only Desktop IPC at an explicit local endpoint」，并说明「Unix requires a fresh absolute socket path in a caller-owned 0700 directory. The server leaves the Unix socket entry after exit.」。
- 入口校验在 `src/bin/aleph-server/main.rs`：带了这个参数时，先判客户端侧总闸 `aleph_client::local_ipc::AVAILABLE`，为假就返回 `Desktop IPC is unavailable on this platform`；再判命令必须是 `start`（或缺省），否则返回 `--desktop-ipc is only available when starting the Gateway`；Windows 分支随后才调 `aleph_client::local_ipc::windows::validate_endpoint` 做命名管道端点校验。
- 挂载路径在 `src/gateway/server/mod.rs` 的 `run_with_desktop_ipc`：它同样以 `AVAILABLE` 为前提，为假时返回 `Desktop IPC is unavailable on this platform`；为真时走 `run_local_endpoint`，其中调用 `src/gateway/server/connection/local_ipc.rs` 的 `bind`——先过端点校验再绑定；注释写明绑定不会替换已占用的条目，目录由调用方提供，Gateway 绑定之后不再改动目录内容。

### 跨平台实现矩阵

| 维度 | Unix | Windows |
|---|---|---|
| 端点形态 | Unix domain socket，绝对路径 | 命名管道，路径前缀 `\\.\pipe\` |
| 生产是否可用 | 可用 | 关闭：两个 opt-in 命令都拒绝 |
| 端点校验 | 绝对路径；父目录属主必须是当前 uid 且权限恰为 `0700`；父目录解析后不得被替换 | 必须带 `\\.\pipe\` 前缀；管道名非空、不以 `.` 或空格结尾、连前缀共不超过 256 个 UTF-16 码元、不含控制字符与 `\ / :` |
| 认证 | 同账号：对端 uid 必须与本进程一致 | 同账号：管道对象的属主 SID 必须等于服务端账户 SID，服务端再比对被模拟后的客户端账户；客户端用 `GetNamedPipeServerProcessId` 固定服务端进程，并复核该进程的账户与存活状态 |
| 监听实现 | `src/gateway/server/connection/local_ipc.rs` | `src/gateway/server/connection/local_ipc/windows.rs` |
| 客户端实现 | `shared/client/src/local_ipc.rs` 的 `unix` 模块 | `shared/client/src/local_ipc/windows.rs` |
| 宿主状态查询 | `desktop/nsh-shell/src/ipc_status.rs` | 同一文件里的 Windows 分支（在树里，但被总闸挡住） |

矩阵里的校验都实现在客户端侧，两个平台各有一套：

- Unix 端点校验是 `shared/client/src/local_ipc.rs` 的 `private_endpoint`：必须是绝对路径（否则 `IPC endpoint must be an absolute socket path`），父目录必须属主为当前 uid 且权限恰为 `0700`（否则 `IPC endpoint requires an owned mode-0700 parent`），父目录规范化之后不得被替换（否则 `IPC parent changed`），祖先目录里不得有不可信属主或可被他人写入的目录（否则 `IPC parent has an untrusted ancestor`）。
- Unix 认证是同文件的 `require_same_user`：对端 uid 与本进程不一致即断开（`IPC peer account mismatch`）；客户端连接时还会核对端点确实是当前 uid 拥有的 socket（`IPC endpoint is not an owned socket`）。
- Windows 端点校验是 `shared/client/src/local_ipc/windows.rs` 的 `validate_endpoint`；账户侧有 `PipeAccount::current`、`PipeAccount::create`（用账户 SID 构造 DACL、只授予该账户全权，并设置拒绝远程客户端）与 `authenticate_client`，客户端侧有 `connect`。
- Windows 监听器（`src/gateway/server/connection/local_ipc/windows.rs`）在 `bind` 时用 `PipeAccount::current` 取得当前账户，并用它创建首个命名管道实例（`MAX_CONNECTIONS` 是允许的实例上限）；管道忙时在 `HELLO_TIMEOUT` 预算内重试补实例——注释解释了不能立刻放弃的原因：丢弃 Mio 管道会取消重叠 I/O，但内核句柄可能要等完成投递才真正释放。

### 两个平台共享的部分

Windows 不是另一套协议。认证通过的连接复用与 Unix 相同的 RPC 循环（`src/gateway/server/connection/local_ipc/windows.rs` 的文件头注释写的是 admitted connections use the shared RPC loop）。

- 限额一致：`MAX_CONNECTIONS = 8`、`WIRE_BUDGET = 16 MiB`、`WRITE_TIMEOUT = 5s`（`src/gateway/server/connection/local_ipc.rs`）。
- 首帧为 `system.hello`。后续请求受共享 `V1_METHODS` 白名单约束，见 [协议 v1](../gateway/protocol-v1) 与 `src/gateway/server/connection/mod.rs`。
- 连接不授予网络来源权限：`NO_NETWORK_ORIGIN` 是 0.0.0.0（`src/gateway/server/connection/local_ipc.rs`）。

### Windows 生产入口为什么仍然关闭

Windows 的命名管道实现是完整的：客户端、Gateway 监听器、宿主 CLI 校验和 QA 脚本都在树里（`qa/nsh_desktop_ipc_windows.py`）。关闭的是**生产入口**，原因写得很直白：独立账户授权证据还没完成。代码仓 commit `5d89d7aff` 的说明是「Keep production Windows Desktop IPC disabled until its independent-account authorization evidence is complete.」

`docs/reference/DESKTOP_SHELL.md` 记的是同一件事：Windows 生产入口仍拒绝这两个 opt-in 命令，命名管道的验收回执把候选证据与缺失的异账户关卡分开记录——候选结果不代替异账户验收。

<Callout type="info" title="证据层回执">
2026-11-23 的回执（`docs/superpowers/runs/2026-11-23-nsh-panel-s1b-windows-named-pipe-verification.md`）记录的是**当时**测到了什么：拒绝基线在两个二进制上都成立、临时改开总闸的诊断构建能连通、以及安全边界的具体检查项。它描述的是一个时点的实验结果，不是当前的生产状态。
</Callout>

解封条件是补齐独立账户（异账户）的授权验收证据。在此之前，总闸 `AVAILABLE` 保持 `cfg!(unix)`（`shared/client/src/local_ipc.rs`）。
