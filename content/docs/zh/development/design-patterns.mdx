本页记录了 Aleph Rust 代码库中使用的核心设计模式。这些不是抽象的建议 —— 它们是正在积极使用的模式，配有从生产代码中提取的具体示例。遵循它们可以保持代码库的一致性，并使新贡献者更容易上手。

有关文件和模块结构的相关指导，请参阅本页底部的 [模块组织](#模块组织) 部分。

## Context 模式

### 问题

随着 API 的演进，函数签名会累积参数。一个带有九个参数的函数难以阅读、难以扩展且容易误用：

```rust
// 之前：9 个位置参数
pub async fn handle(
    &self,
    message: InboundMessage,
    channel_id: ChannelId,
    conversation_id: ConversationId,
    session_key: SessionKey,
    is_authorized: bool,
    is_mentioned: bool,
    sender_normalized: String,
    workspace: Option<PathBuf>,
) -> Result<(), GatewayError> { ... }
```

布尔开关尤其危险：`handle(message, route, key, true, false, sender, None)` 在调用点上完全无法自解释。

### 解决方案

将相关参数分组到 **context 结构体**中。必需参数放在构造函数里；可选参数使用 builder 风格的 `with_*` 方法：

```rust
#[derive(Debug, Clone)]
pub struct InboundContext {
    pub message: InboundMessage,
    pub reply_route: ReplyRoute,
    pub session_key: SessionKey,
    pub is_authorized: bool,
    pub is_mentioned: bool,
    pub sender_normalized: String,
    pub voice_reply_hint: bool,
    pub transcribed_input: bool,
    pub workspace: Option<std::path::PathBuf>,
}

impl InboundContext {
    pub fn new(
        message: InboundMessage,
        reply_route: ReplyRoute,
        session_key: SessionKey,
    ) -> Self {
        let sender_normalized = message.sender_id.as_str().to_string();
        Self {
            message,
            reply_route,
            session_key,
            is_authorized: false,
            is_mentioned: false,
            sender_normalized,
            voice_reply_hint: false,
            transcribed_input: false,
            workspace: None,
        }
    }

    pub const fn authorize(mut self) -> Self {
        self.is_authorized = true;
        self
    }

    pub const fn with_mention(mut self, mentioned: bool) -> Self {
        self.is_mentioned = mentioned;
        self
    }

    pub fn with_workspace(mut self, workspace: Option<std::path::PathBuf>) -> Self {
        self.workspace = workspace;
        self
    }
}
```

函数签名变得简洁且稳定：

```rust
// 之后：1 个参数
pub async fn handle(&self, ctx: InboundContext) -> Result<(), GatewayError> { ... }
```

注意 `new` 只接收三个必需参数，剩下的字段全部通过 `with_*` 补齐。`with_*` 方法返回 `Self`（消费并返回自身），所以可以链式调用。

### 用法

```rust
let route = ReplyRoute::new(channel_id, conversation_id)
    .with_reply_to(message_id);

let ctx = InboundContext::new(message, route, session_key)
    .authorize()
    .with_mention(true)
    .with_workspace(Some(workspace));

let result = router.handle(ctx).await;
```

### 何时应用

- 函数有 **5 个或更多**参数
- 参数里出现两个以上的布尔开关
- 多个参数是可选的
- 参数形成一个逻辑组
- API 可能会随着新参数而演进
- 函数从多个位置被调用

### 代码库中的位置

- `src/gateway/inbound_context.rs` —— `InboundContext` 与 `ReplyRoute` 的定义
- `src/gateway/inbound_router/` —— 路由与命令分发，context 在这里流转
- `src/gateway/pipeline/mod.rs` —— 流水线装配处消费 context

## Newtype 模式

### 问题

原始类型不携带语义含义。一个接受两个 `String` 参数（用于不同类型的 ID）的函数，即使在参数交换时也能编译：

```rust
fn assign(skill_id: String, plugin_id: String) { ... }

// 能编译，但是错误的 —— 参数被交换了
assign(plugin_id, skill_id);
```

### 解决方案

将原始类型包装在 **newtype 结构体**中，在类型级别赋予它们不同的标识：

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct SkillId(String);

impl SkillId {
    pub fn new(id: impl Into<String>) -> Self {
        let id = id.into();
        debug_assert!(!id.is_empty(), "SkillId must not be empty");
        Self(id)
    }

    pub fn as_str(&self) -> &str {
        &self.0
    }
}

impl fmt::Display for SkillId {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{}", self.0)
    }
}

impl From<&str> for SkillId {
    fn from(s: &str) -> Self {
        Self(s.to_string())
    }
}
```

现在编译器会捕获这个错误：

```rust
fn assign(skill_id: SkillId, plugin_id: PluginId) { ... }

let skill = SkillId::new("core:search");
let plugin = PluginId::new("core");

assign(skill, plugin);   // 正确
assign(plugin, skill);   // 编译错误！
```

Aleph 的 newtype **不实现 `Deref`**。调用方必须显式写 `as_str()`，这样"这到底是不是字符串"永远不会被隐式决定。全仓唯一的 `Deref` 实现是 `src/extension/hooks/registry.rs` 里 `HookReadGuard<'_>` 指向 `HookExecutor` 的那次，属于锁守卫的特例，不是 ID 类型的惯例。

### 集合 Newtype

Newtype 也适用于带有领域特定语义的集合。`DedupKey` 是电信事件的去重身份：

```rust
/// Opaque, collision-free dedup identity (parts are compared as a vector, so
/// no delimiter can be spoofed by a provider id containing one).
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub struct DedupKey(Vec<String>);

/// Derive the dedup key of an event from provider identity only.
pub fn dedup_key(env: &TelecomEnvelope) -> DedupKey { ... }
```

集合 newtype 由**具名构造函数**产出，而不是从迭代器直接收集：去重键的组成规则（提供方账号 + 事件类型 + 提供方事件 id）是协议的一部分，藏在 `collect` 里会让这条规则无从复核。

### 标准 Trait 清单

每个 newtype 应该实现一组一致的 trait：

**必需：**
- `Debug` —— 调试输出
- `Clone` —— 值复制
- `PartialEq`, `Eq` —— 相等比较
- `Hash` —— 用于 `HashMap`/`HashSet`

**推荐：**
- `Display` —— 面向用户的字符串输出
- `as_str()` —— 显式访问内部字符串
- `From<&str>`, `From<String>` —— 符合人体工程学的构造
- `Serialize`, `Deserialize` —— JSON/TOML 支持

**可选：**
- `FromStr` —— 从字符串解析（主要用于枚举型 ID）
- `Default` —— 如果存在合理的默认值

**不建议：**
- `Deref` —— 让调用方忘记"这是一个 ID"。用 `as_str()` 代替

### Newtype 目录

| 类型 | 内部类型 | 用途 | 模块 |
|------|----------|------|------|
| `SkillId` | `String` | 技能 ID（约定 `plugin:skill_name`） | `src/domain/skill.rs` |
| `PluginId` | `String` | 插件 ID | `src/domain/skill.rs` |
| `SkillContent` | `String` | 技能正文 | `src/domain/skill.rs` |
| `ProviderId` | `String` | 能力提供者 ID | `src/capability/provider.rs` |
| `RunId` | `String` | 运行 ID | `src/capability/ownership.rs` |
| `TaskId` | `String` | 任务 ID | `src/capability/ownership.rs` |
| `SubscriptionId` | `String` | 事件总线订阅 ID | `src/event/global_bus.rs` |
| `DedupKey` | `Vec<String>` | 电信事件去重身份 | `src/gateway/telecom/protocol.rs` |
| `CallerDigest` | `String` | 主叫号码加盐摘要 | `src/gateway/telecom/public_context.rs` |

两个反例值得注意：`SkillContent` 刻意**不实现** `Display`，避免技能正文被随手打印；`CallerDigest` 手写 `Debug` 输出 `CallerDigest(<redacted>)`，不泄露号码。

## Builder 模式

### 问题

复杂对象有很多字段，有些是必需的，有些是可选的。一个有十个参数的构造函数不可用，而手动填写每个字段既冗长又容易出错。

### 解决方案

为必需参数提供**构造函数**，为可选参数提供**流畅的 `with_*` 方法**：

```rust
impl AgentDef {
    // 构造函数只接收必需参数
    pub fn new(id: impl Into<String>, mode: AgentMode) -> Self { ... }

    // 通过 builder 方法设置可选参数
    pub fn with_description(mut self, desc: impl Into<String>) -> Self {
        self.description = desc.into();
        self
    }

    pub fn with_when_to_use(mut self, hint: impl Into<String>) -> Self {
        self.when_to_use = Some(hint.into());
        self
    }

    pub fn with_system_prompt(mut self, prompt: impl Into<String>) -> Self {
        self.system_prompt = Some(prompt.into());
        self
    }
}
```

用法读起来像一个句子：

```rust
let def = AgentDef::new("explore", AgentMode::SubAgent)
    .with_description("只读探索陌生模块")
    .with_when_to_use("需要先摸清一个不熟悉的代码区域时")
    .with_system_prompt("你是探索子代理，只汇报发现，不改动文件。");
```

### 好处

- **流畅的 API** —— 方法链读起来很自然
- **自文档化** —— 每个 `with_*` 方法都命名了它设置的参数
- **编译时安全** —— 必需参数由构造函数强制执行
- **向后兼容** —— 添加新的 `with_*` 方法不会破坏现有调用者

注意，在 Aleph 中，Builder 模式通常与 Context 模式结合使用，而不是与单独的 `Builder` 结构体一起独立使用。

## FromStr Trait 模式

### 问题

许多类型需要从字符串解析 —— 配置值、枚举变体、用户输入。没有标准接口，每种类型都会发明自己的 `parse` 或 `from_string` 方法。

### 解决方案

实现 `FromStr` 以与 Rust 的标准 `str::parse()` 集成：

```rust
impl std::str::FromStr for TaskStatus {
    type Err = String;

    fn from_str(s: &str) -> Result<Self, Self::Err> {
        if s.eq_ignore_ascii_case("pending") {
            Ok(Self::Pending)
        } else if s.eq_ignore_ascii_case("running") {
            Ok(Self::Running)
        } else if s.eq_ignore_ascii_case("completed") {
            Ok(Self::Completed)
        } else if s.eq_ignore_ascii_case("failed") {
            Ok(Self::Failed)
        } else {
            Err(format!("Unknown task status: {s}"))
        }
    }
}
```

这实现了标准的 `.parse()` API 和通用解析函数：

```rust
// 直接解析
let status: TaskStatus = "pending".parse()?;

// 在配置加载中
let status = config.get("status")?.parse::<TaskStatus>()?;

// 通用辅助函数
fn parse_config<T: FromStr>(value: &str) -> Result<T, T::Err> {
    value.parse()
}
```

### Aleph 中实现 FromStr 的类型

以下类型为实现一致解析而实现 `FromStr`：

- **团队类型：** `TeamStatus`, `TeamMemberKind`（`src/teams/types.rs`）
- **记忆上下文类型：** `NoteType`, `FactSource`, `FactSpecificity`, `TemporalScope`, `MemoryLayer`, `MemoryCategory`（`src/memory/context/enums.rs`）
- **事件与账本类型：** `EventActor`（`src/memory/events/mod.rs`）, `LedgerAction`, `LedgerOutcome`（`src/identity/record.rs`）
- **技能与安装类型：** `Os`, `PromptScope`, `InstallKind`（`src/domain/skill.rs`）
- **韧性类型：** `TaskStatus`, `RiskLevel`, `Lane`（`src/resilience/types.rs`）
- **扩展与钩子类型：** `ExtensionKind`（`src/hub/types.rs`）, `ThinkLevel`（`crates/aleph-slot-api/src/ai.rs`）, `HookKind`, `HookPriority`（`crates/aleph-slot-api/src/hooks.rs`）
- **MCP 运行时类型：** `RuntimeKind`（`src/mcp/external/runtime.rs`）

注意 `SessionStatus` 和 `EventType` 虽然存在，但**没有**实现 `FromStr` —— 不是每个枚举都值得支持字符串解析。

### 约定

- 使用 `eq_ignore_ascii_case` 逐分支比较，不分配小写副本
- 错误类型多数是 `String`（简单，无额外依赖）；`Os` 用专门的 `ParseOsError`
- 匹配所有已知变体，对未知值返回 `Err`
- 错误文案里带上原始输入，例如 `Unknown task status: {s}`

## 模式组合

Aleph 中的模式很少单独使用。最常见的组合：

### Context + Builder

`InboundContext` 使用 Context 模式来分组参数，使用 Builder 模式来处理可选字段：

```rust
let ctx = InboundContext::new(message, route, session_key)
    .authorize()
    .with_mention(true)
    .with_workspace(Some(workspace));
```

### Newtype + FromStr

许多枚举型 newtype 实现 `FromStr`，以便可以从配置文件解析：

```rust
let status: TaskStatus = "pending".parse()?;
let note: NoteType = config.get("note_type")?.parse()?;
```

### Newtype + 显式访问器

包装 `String` 的 newtype 用 `as_str()` 暴露内部字符串，而不是实现 `Deref`：

```rust
let id = SkillId::new("core:search");
if id.as_str().starts_with("core:") { ... }
```

## 错误处理约定

Aleph 使用两层错误处理方法：

### 边界错误：`thiserror`

对于跨越模块边界且需要调用者匹配的错误，使用 `thiserror` 来派生结构化错误类型：

```rust
#[derive(Debug, thiserror::Error)]
pub enum GatewayError {
    #[error("Failed to bind to {addr}: {source}")]
    BindFailed {
        addr: SocketAddr,
        source: std::io::Error,
    },
    #[error("Connection error: {0}")]
    ConnectionError(String),
    #[error("Protocol error: {0}")]
    ProtocolError(String),
}
```

`thiserror` 适合"调用者需要按变体分支处理"的错误。变体数量保持少而正交 —— 需要十几个变体通常说明这个错误类型混了多个关注点。

### 内部错误：`anyhow`

对于模块内部调用者不需要区分变体的错误，使用 `anyhow::Result`：

```rust
use anyhow::{Context, Result};

fn load_manifest(dir: &Path) -> Result<PluginManifest> {
    parse_manifest_from_dir_sync(dir).context("invalid plugin manifest")
}
```

### 经验法则

- 如果错误跨越 **crate 边界**或是 **公共 API** 的一部分，使用 `thiserror`
- 如果错误在 **单个模块** 或 **二进制入口点** 内处理，使用 `anyhow`
- 在 `anyhow` 错误上使用 `.context()` 添加人类可读的描述
- 领域错误类型统一放在该领域的 `error.rs` 里，并同时提供 `Result` 别名（如 `ExtensionResult`）

## 模块组织

这些原则规定了文件和模块的结构。另请参阅 [代码组织指南](https://github.com/rootazero/Aleph/blob/main/docs/reference/CODE_ORGANIZATION.md) 获取完整参考。

### 核心原则

**单一职责。** 每个文件只拥有一个概念。如果你需要用 "and" 来描述一个文件的功能，它需要被拆分。

**关注点分离。** 沿着自然的断层线拆分：

| 关注点 | 文件名 |
|--------|--------|
| 类型定义（struct/enum） | `types.rs` |
| 业务逻辑 | 主模块文件 |
| 外部集成（数据库、网络） | `store.rs`, `executor.rs` |
| 测试替身 | `mock.rs`，位于 `#[cfg(test)]` 下 |
| 错误类型 | `error.rs` |

**可见性最小化。** 对跨模块访问使用 `pub(crate)`。将 `pub` 保留给 crate 的公共 API 表面。内部细节应该是 `pub(super)` 或私有的。

### 标准文件名

`src/` 下的实际分布（按文件数）：

| 文件名 | 内容 | `src/` 内文件数 |
|--------|------|------|
| `types.rs` | 枚举和值对象 | 72 |
| `error.rs` | 领域特定错误枚举 | 18 |
| `store.rs` | 持久化实现 | 18 |
| `registry.rs` | 查找、注册与查询逻辑 | 16 |
| `executor.rs` | 调用外部系统的逻辑 | 6 |
| `builder.rs` | 构造与装配 | 5 |
| `manager.rs` | 长生命周期管理器 | 5 |
| `callback.rs` | 事件处理程序和钩子 | 4 |
| `factory.rs` | 工厂函数 | 3 |
| `pool.rs` | 连接/资源池 | 1 |
| `mock.rs` | 测试替身（位于 `#[cfg(test)]` 下） | 1 |

`model.rs` 在 `src/` 下**一次都没有出现** —— 聚合根放在主模块文件里，别再新增这个名字。

### 何时拆分文件

**必须拆分**当：
- 行数达到 500+ 且文件涵盖多个概念
- 存在针对不同类型的多个 `impl Trait for T` 块
- 生产代码与测试替身混合
- 单个结构体有 20+ 个公共方法跨越不相关的关注点

**考虑拆分**当：
- 单个 `impl` 块超过 300 行
- 一个函数超过 100 行
- `use` 导入跨越 3 个以上不相关的模块

### 模块模式

**单结构体模块** —— 用于以一个结构体为中心的模块：
```
src/capability/
├── provider.rs          # ProviderId, ProviderState, ProviderLifecycle
├── provider_registry.rs # ProviderRegistry, ProviderActivator
└── events.rs            # CapabilityEvent
```

**领域模型模块** —— 用于具有多种类型的丰富领域模型：
```
src/memory/context/
├── mod.rs          # 模块入口，重新导出
├── enums.rs        # NoteType, FactSource, MemoryLayer, MemoryCategory 等
├── fact.rs         # MemoryFact（聚合根）
├── compression.rs  # CompressionResult
└── paths.rs        # 路径派生
```

**Manager Facade** —— 用于将工作委派给子组件的大型 manager：
```
src/extension/
├── mod.rs          # ExtensionManager（精简 facade，委派）
├── loader.rs       # 插件加载和发现
├── lifecycle.rs    # 挂载 / 卸载 / 重载
├── registry/       # 插件注册表
├── types/          # ExtensionConfig, LoadSummary 等
├── manifest/       # 清单解析
└── error.rs        # ExtensionError
```

**Startup Builder** —— 用于复杂的初始化序列：
```
src/bin/aleph-server/commands/start/
├── mod.rs               # 入口点：解析参数，调用 builder
├── builder/
│   ├── mod.rs           # ServerBuilder
│   ├── agent_init/
│   ├── handlers/
│   ├── startup_resources.rs
│   └── subsystems.rs
├── capability_init.rs
└── runtime_warmup.rs
```

### 需要避免的反模式

- **上帝对象：** 一个结构体有 40+ 个方法跨越不相关的关注点。拆分为一个委派给专注子组件的 facade。
- **扁平脚本：** 一个 700 行的初始化函数。提取一个具有单独 `initialize_*` 方法的 builder。
- **类型倾倒场：** 一个文件中有 14 个类型和 31 个 impl 块。分离到 `types.rs` 和领域特定文件中。

## 迁移指南

### 添加 Context 模式

1. 识别一个有 5+ 参数的函数（几个可选，或有两个以上布尔开关）
2. 创建一个 context 结构体，包含必需字段 + 可选字段的 `Option`
3. 实现 `new()`，只有必需参数
4. 为每个可选参数添加 `with_*` builder 方法
5. 更新函数签名以接受 context
6. 更新所有调用点
7. 在模块的公共 API 中导出 context 类型

### 添加 Newtype

1. 识别一个携带语义含义的原始类型
2. 创建一个包装该原始的元组结构体
3. 派生 `Debug`, `Clone`, `PartialEq`, `Eq`, `Hash`
4. 实现 `new()`、`as_str()`（或等效访问器）
5. 根据需要实现 `Display`, `From<T>`；**不要**实现 `Deref`
6. 更新所有使用点以使用 newtype
7. 将类型添加到 newtype 目录

## 26.7.x 以来确立的硬约束

### Rust toolchain 1.99+

当前 `rust-version` 是 **1.99**，`rust-toolchain.toml` 把工具链固定到 `1.99.1`（含 `rustfmt`、`clippy` 与 `wasm32-unknown-unknown` 目标）。开发时用 `rustup install 1.99`，或直接依赖 `rust-toolchain.toml`。

### Harness 12 文件 + 行数 ratchet

**代码是权威**——任何文档数字都只是 `CEILING` 的副本：

- 顶层 8 + `agent/` 4 = **12 文件**（测试文件在 `tests/`，不入 ratchet）
- 行数由 `src/harness/tests/budget.rs` 的 ratchet 守，绑定常量 `CEILING`
