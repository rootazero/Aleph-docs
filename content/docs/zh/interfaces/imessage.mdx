iMessage 接口通过读取 Messages.app SQLite 数据库中的消息并通过 AppleScript 发送回复来提供原生 macOS 集成，**并且**提供一个跨平台的 **BlueBubbles** 传输，通过 REST + webhook 与正在运行的 BlueBubbles 服务器对话。两条传输都实现同一个 `Channel` trait，并走同一条入站流水线；你可以在同一份配置中启用其中一条或两条。

## 两条传输

```text
┌──────────────────────────────────────────────────────────────────┐
│                         macOS System                              │
│  ┌──────────────────┐     ┌──────────────────────────────────┐   │
│  │   Messages.app   │     │           Aleph Server            │   │
│  │                  │     │                                   │   │
│  │  chat.db ────────┼─────┼──> SQLite 轮询（只读）            │   │
│  │  (SQLite)        │     │  [IMessageChannel，仅 macOS]      │   │
│  │                  │ <───┼─── AppleScript（发送消息）        │   │
│  └──────────────────┘     └──────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│                  BlueBubbles 服务器（任意宿主）                  │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │  REST API + webhook  ◀──▶  [BlueBubblesChannel, 任意 OS]  │   │
│  └──────────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────────┘
```

- **`IMessageChannel`**（local）—— SQLite 数据库轮询接收，AppleScript 发送。需要 macOS、完全磁盘访问和自动化权限。仅在 macOS 上注册（模块上的 `#[cfg(target_os = "macos")]`）。
- **`BlueBubblesChannel`**（`imessage/bluebubbles/`）—— 与 BlueBubbles 服务器的 REST + webhook。纯 HTTP——可在任何 OS 上编译运行。

## 适配器结构

iMessage 适配器位于 `src/gateway/interfaces/imessage/`：

| 模块 | 职责 |
|--------|----------------|
| `mod.rs` | `IMessageChannel`、能力默认值、factory 接线 |
| `config.rs` | `IMessageConfig`、`DmPolicy`、`GroupPolicy` |
| `db.rs` | `MessagesDb`——围绕 Messages 数据库（默认 `~/Library/Messages/chat.db`）的只读 SQLite 包装 |
| `sender.rs` | AppleScript 驱动的出站发送 |
| `target.rs` | 目标标准化（`normalize_phone`、`parse_target`、`IMessageTarget`、`Service`） |
| `reaction.rs` | Tapback code ↔ emoji 映射（两条传输的单一来源） |
| `bluebubbles/` | `BlueBubblesChannel` + REST/webhook staging |

两条传输共享 Gateway 的 **`OffsetTracker`**（当前位于 telegram 模块下）以持久化 catch-up 水位，使得 daemon 离线时抵达的消息在重启后会被补齐。

## 前置条件

### Local 传输

<Steps>
<Step>

#### macOS 要求

Local 传输仅在 macOS 上注册（`#[cfg(target_os = "macos")]`）。在 Linux/Windows 构建上，仅 `BlueBubblesChannel` 可用。

</Step>
<Step>

#### 完全磁盘访问

Aleph 需要**完全磁盘访问**权限来读取 `~/Library/Messages/chat.db`：

1. 打开 **系统设置 > 隐私与安全性 > 完全磁盘访问**
2. 点击 **+** 按钮
3. 添加 Aleph 服务器二进制文件（或如果通过终端运行，则添加 Terminal.app）
4. 重启 Aleph 服务器

没有此权限，数据库打开将失败并显示 "permission denied" 错误。

</Step>
<Step>

#### 自动化权限

Aleph 需要**自动化**权限通过 AppleScript 控制 Messages.app：

1. Aleph 第一次发送消息时，macOS 会显示权限对话框
2. 点击 **允许** 授予自动化访问权限
3. 你可以在 **系统设置 > 隐私与安全性 > 自动化** 中管理此权限

</Step>
</Steps>

### BlueBubbles 传输

<Steps>
<Step>

#### 运行 BlueBubbles 服务器

你需要一台正在运行的 BlueBubbles 服务器（通常在同一台拥有 iMessage 账户的 Mac 上）。按 BlueBubbles 文档安装并启动；记录服务器 URL 与账户密码。

</Step>
<Step>

#### 开放 REST + Webhook 端口

确保 Aleph 能访问 BlueBubbles 服务器（HTTPS），并且 BlueBubbles 的 webhook 能访问 Aleph（Gateway 的 HTTP 服务器）。

</Step>
</Steps>

## 配置

### Local 传输

```toml
[channels.imessage-local]
type = "imessage"
enabled = true

# Messages 数据库路径（默认：~/Library/Messages/chat.db）
db_path = "~/Library/Messages/chat.db"

# 轮询间隔（毫秒）（默认：1000）
poll_interval_ms = 1000

# DM 策略：pairing | allowlist | open | disabled
dm_policy = "pairing"

# 群组消息策略：open | allowlist | disabled
group_policy = "open"

# DM 的电话号码/电子邮件白名单
allow_from = ["+15551234567", "user@example.com"]

# 群组聊天的白名单（按聊天标识符）
group_allow_from = []

# 在群组聊天中需要 @mention（默认：true）
require_mention = true

# 群组中提及检测的机器人名称
bot_name = "Aleph"

# 在入站消息中包含附件（默认：true）
include_attachments = true

# 最大附件大小（字节）（0 = 无限制）
max_attachment_size = 0

# 入站消息去抖（毫秒）（默认：500）
inbound_debounce_ms = 500
```

### BlueBubbles 传输

```toml
[channels.imessage-bb]
type = "imessage"
transport = "bluebubbles"
enabled = true

# 与 local 传输相同的 DM / 群组 / 白名单策略
dm_policy = "pairing"
group_policy = "open"
allow_from = ["+15551234567"]

[channels.imessage-bb.bluebubbles]
# BlueBubbles 服务器 URL（HTTPS）
server_url = "https://bluebubbles.local:1234"

# BlueBubbles 账户密码
password = "your-bluebubbles-password"

# Aleph 侧入站 webhook 监听地址与路径（BlueBubbles 服务器侧要指向它）
webhook_host = "0.0.0.0"
webhook_port = 8645
webhook_path = "/bluebubbles-webhook"

# catch-up 补偿轮询间隔（秒，默认：30；实时推送由 webhook 驱动）
poll_interval_secs = 30

# 是否为入站消息发送已读回执（默认：true）
send_read_receipts = true
```

<Callout type="info">
`type` 只接受平台名：`imessage`。传输方式由 `transport` 决定（`local` 或 `bluebubbles`）；若存在 `[channels.<id>.bluebubbles]` 子块而 `transport` 未设置，Aleph 会在启动时自动切到 `bluebubbles`（`IMessageConfig::effective_transport`）。

频道凭据保险库的键是 `channel:<实例 ID>:<字段名>`，但它只覆盖**顶层**的凭据字段（`bot_token`、`password` 等）。BlueBubbles 的密码嵌在 `[channels.<id>.bluebubbles]` 里，因此仍需写在配置文件中；用 `channel.create` 冷创建带嵌套密码的频道会被拒绝，报 `Channel contains a credential this vault layout cannot store`。
</Callout>

## DM 与群组策略

`dm_policy` 设置控制 Aleph 如何处理来自未知发送者的直接消息：

| 策略 | 行为 |
|--------|----------|
| **`pairing`**（默认） | 未知发送者在 Aleph 响应之前被提示输入配对码 |
| **`allowlist`** | 仅处理 `allow_from` 中的发送者；忽略所有其他发送者 |
| **`open`** | 无限制地接受所有发送者 |
| **`disabled`** | 完全禁用 DM |

<Callout type="info">
**pairing** 策略使用 Gateway 的单一 `PairingStore`。操作员签发配对码，未知发送者通过 iMessage 发送该码，操作员从 Panel 通过 `channel.pairing.approve` 批准——批准后该号码或邮箱被加入白名单。不存在每频道的配对数据库。
</Callout>

### 群组策略

| 策略 | 行为 |
|--------|----------|
| **`open`**（默认） | 接受所有群聊（带有可选的提及要求） |
| **`allowlist`** | 仅处理 `group_allow_from` 中的群组 |
| **`disabled`** | 完全禁用群组消息 |

## 消息轮询如何工作

### Local 传输（`IMessageChannel`）

轮询循环在后台 Tokio 任务中运行：

1. **打开数据库** — Messages 数据库以 `SQLITE_OPEN_READ_ONLY` 只读模式打开
2. **记录最后 ROWID** — 启动时，当前最大消息 ROWID 被记录为基线
3. **轮询循环** — 每 `poll_interval_ms` 毫秒：
   - 查询 `ROWID > last_seen` 且 `is_from_me = 0` 的消息
   - 对于每条新消息，解析发送者句柄和聊天信息
   - 如果设置了 `cache_has_attachments`，提取附件
   - 转换为 `InboundMessage` 并通过频道状态 broadcast
4. **更新标记** — 每批处理后更新最后看到的 ROWID

### BlueBubbles 传输（`BlueBubblesChannel`）

`BlueBubblesChannel` 在 BlueBubbles 服务器上注册 webhook 接收推送（回调地址由 `webhook_host`/`webhook_port`/`webhook_path` 拼出），并以 `poll_interval_secs` 的秒级轮询循环作为 catch-up 回退。共享的 `OffsetTracker` 让两条传输都能在重启后从最后持久化的 GUID/ROWID 恢复，而不是直接跳到最新消息。

### Apple 时间戳

Messages.app 使用 "Apple Cocoa Core Data 时间戳" — 自 2001 年 1 月 1 日 UTC 以来的纳秒数。Aleph 将其转换为标准 Unix 时间戳：

```
unix_timestamp = apple_timestamp / 1,000,000,000 + 978,307,200
```

## 发送消息

### Local 传输 — AppleScript

```applescript
tell application "Messages"
    set targetService to 1st account whose service type = iMessage
    set targetBuddy to participant "+15551234567" of targetService
    send "Hello from Aleph!" to targetBuddy
end tell
```

群聊通过聊天 ID 寻址：

```applescript
tell application "Messages"
    set targetChat to chat id "chat123456"
    send "Hello group!" to targetChat
end tell
```

### BlueBubbles 传输 — REST

BlueBubbles 传输通过 BlueBubbles REST API 发送，不需要 AppleScript，因此 BlueBubbles 可在任意宿主、非 Mac 账户上工作。Reaction、reply、typing indicator、read receipt 都走同一套 REST 接口。

## Tapback 反应

Tapback code 的单一来源（`src/gateway/interfaces/imessage/reaction.rs`）将 Apple/BlueBubbles 的数字 `associatedMessageType` 映射到规范名称与 emoji：

| Code | 名称 | Emoji |
|------|------|-------|
| 2000 | love | ❤️ |
| 2001 | like | 👍 |
| 2002 | dislike | 👎 |
| 2003 | laugh | 😂 |
| 2004 | emphasize | ‼️ |
| 2005 | question | ❓ |

"remove" 变体（3000–3005）和未知 code 故意缺席，因此针对它们的 emoji 查询返回 `None`，并在映射层丢弃——这就是"只上抛 add-tapback"如何在没有第二道过滤器的情况下强制。入站 *add* tapback 作为上下文上抛给模型（用户对先前助手消息的反应）；*remove* tapback 被丢弃。

## 媒体处理

### 接收附件

附件通过消息表中的 `cache_has_attachments` 标志检测，并通过 `message_attachment_join`（local 传输）或 BlueBubbles 附件元数据（BlueBubbles 传输）解析：

| 字段 | 来源 |
|-------|--------|
| `id` | 附件 GUID（local：`AttachmentInfo` 的 `guid` 字段；BlueBubbles：服务器给出的附件 GUID） |
| `mime_type` | local：`AttachmentInfo` 的 `mime_type` 字段；BlueBubbles：服务器返回的 MIME 类型 |
| `filename` | local：`AttachmentInfo` 的 `transfer_name` 字段，回退到 `filename` 字段的 basename；BlueBubbles：不填 |
| `size` | local：`AttachmentInfo` 的 `total_bytes` 字段；BlueBubbles：不填 |

### 发送附件

Local 传输要求本地文件路径（通过 AppleScript `send POSIX file`）。BlueBubbles 传输通过 BlueBubbles REST API 上传。

## 会话路由

| 上下文 | 会话密钥 |
|---------|------------|
| 与 `+15551234567` 的 DM | `agent:main:dm:+15551234567` 或 `agent:main:imessage:dm:+15551234567` |
| 群组聊天（聊天 ID） | `agent:main:imessage:group:{chat_identifier}` |

`chat_identifier` 通常是 DM 的电话号码或群组聊天的内部 ID。

## 数据库架构（Local 传输）

Aleph 从 Messages 数据库中的三个主要表读取：

### `message` 表

| 列 | 类型 | 用途 |
|--------|------|---------|
| `ROWID` | INTEGER | 自增消息 ID |
| `guid` | TEXT | 唯一消息标识符 |
| `text` | TEXT | 消息正文 |
| `handle_id` | INTEGER | `handle` 表的外键 |
| `date` | INTEGER | Apple 时间戳（纳秒） |
| `is_from_me` | INTEGER | 如果由 Mac 所有者发送则为 1 |
| `cache_has_attachments` | INTEGER | 如果消息有附件则为 1 |

### `handle` 表

| 列 | 类型 | 用途 |
|--------|------|---------|
| `ROWID` | INTEGER | 句柄 ID |
| `id` | TEXT | 电话号码或电子邮件 |
| `service` | TEXT | "iMessage" 或 "SMS" |

### `chat` 表

| 列 | 类型 | 用途 |
|--------|------|---------|
| `ROWID` | INTEGER | 聊天 ID |
| `guid` | TEXT | 聊天 GUID |
| `chat_identifier` | TEXT | 电话号码或群组 ID |
| `display_name` | TEXT | 群组名称（如果已设置） |
| `group_id` | TEXT | 群组聊天非空 |

## 限制

### Local 传输

- **仅限 macOS** — 无法在 Linux 或 Windows 上运行
- **需要完全磁盘访问** — 数据库受 macOS TCC（透明度、同意和控制）保护
- **非实时交付** — 基于轮询，可配置间隔（最小实际值：~500ms）
- **无富文本** — AppleScript 仅发送纯文本
- **无输入中指示器** — 需要更深入的系统集成
- **出站 tapback 不可靠** — 通过 AppleScript 发送 tapback 在跨 macOS 版本上不稳定
- **无消息编辑/删除** — AppleScript 不公开这些操作

### BlueBubbles 传输

- **需要 BlueBubbles 服务器** — 在一台拥有 iMessage 账户的 Mac 上运行；Aleph 通过 HTTPS 与之通信
- **无富文本** — 仅纯文本
- **无消息编辑/删除** — BlueBubbles REST API 不公开这些操作

## 故障排除

| 问题 | 解决方案 |
|---------|----------|
| "Failed to open Messages database" | 在系统设置中授予 Aleph 二进制文件完全磁盘访问权限（local 传输） |
| "AppleScript execution failed" | 授予自动化权限；确保 Messages.app 已安装并登录 |
| 机器人看不到新消息 | 验证 `db_path` 指向正确的数据库；检查 `is_from_me = 0` 过滤器是否工作 |
| Messages.app 意外打开 | 这是正常的 — AppleScript 在发送时可能会激活应用 |
| 响应时间慢 | 减少 `poll_interval_ms`（例如到 500）；注意这会增加 SQLite 读取频率 |
| "Invalid target" 错误 | 确保收件人是有效的电话号码（带国家代码）或电子邮件地址 |
| 群组消息被忽略 | 检查 `group_policy` 和 `group_allow_from`；验证 `require_mention` 设置 |
| BlueBubbles：收不到 webhook | 确认 Aleph 侧 `webhook_host`/`webhook_port` 可达，并在 BlueBubbles 服务器侧指向同一地址；检查 `webhook_path` 与密码 |
