Aleph 建立在事件驱动架构之上。每个重要动作 —— 工具调用、会话启动、cron 作业触发、配置更改 —— 都会发出结构化事件。您可以实时通过 WebSocket 订阅这些事件，启用仪表板、监控系统、外部集成和反应式自动化管道。

## 架构

事件流经两个内部总线：

1. **核心事件总线** —— 处理代理生命周期事件 (`AlephEvent`)。基于 `tokio::sync::broadcast` 通道构建，用于低延迟进程内交付。代理循环的每个组件都在这里发布：工具调用、会话状态更改、规划事件、子代理活动。

2. **守护进程事件总线** —— 处理系统级事件 (`DaemonEvent`)。感知守护进程监视环境 —— 文件系统更改、进程活动、系统状态、时间触发器 —— 并在此发布观察结果。

两个总线都输入到 Gateway 的事件订阅系统，该系统将它们作为统一的流通过 WebSocket 暴露给外部客户端。

```
┌──────────────────────────────────────────────────────────────┐
│                      内部总线                                 │
│                                                               │
│  代理循环 ──▶ 核心事件总线 ──┐                           │
│                                   ├──▶ Gateway 事件路由器   │
│  守护进程  ──▶ 守护进程事件总线 ──┘         │                │
│                                              │                │
│                                     ┌────────┴────────┐      │
│                                     │  模式匹配器     │      │
│                                     └────────┬────────┘      │
│                                              │                │
│                              ┌───────────────┼───────────┐   │
│                              ▼               ▼           ▼   │
│                         客户端 A        客户端 B    客户端 C  │
│                        stream.*        agent.*        *       │
└──────────────────────────────────────────────────────────────┘
```

## 事件类别

### 流式事件 (`stream.*`)

在代理运行期间发出。这些是最频繁的事件，为实时 UI 提供动力。

它们以 **JSON-RPC 通知**送达：`method` 是 `stream.*` 之一，`params` 就是事件负载本身（不再包一层 `event` 信封）。订阅匹配用的就是这个 `method` 名。

| 方法 | 说明 | 关键字段 |
|-------|-------------|------------|
| `stream.run_accepted` | 运行已接受 | `run_id`, `session_key`, `accepted_at` |
| `stream.run_queued` | 运行排队中 | `run_id`, `session_key`, `ahead` |
| `stream.reasoning` | 推理步骤（思维链） | `run_id`, `seq`, `content`, `is_complete` |
| `stream.tool_start` | 代理正在调用工具 | `run_id`, `seq`, `tool_name`, `tool_id`, `params` |
| `stream.tool_update` | 工具调用进度 | `run_id`, `seq`, `tool_id`, `progress` |
| `stream.tool_end` | 工具执行完成 | `run_id`, `seq`, `tool_id`, `result`, `duration_ms` |
| `stream.agent_trace` | 代理内部轨迹 | `run_id`, `seq`, `event` |
| `stream.response_chunk` | 来自代理的文本块 | `run_id`, `seq`, `delta`, `full_text`, `is_final` |
| `stream.context_gauge` | 上下文用量 | `run_id`, `seq`, `context_tokens`, `context_window`, `total_tokens` |
| `stream.run_complete` | 运行完成 | `run_id`, `seq`, `summary`, `total_duration_ms` |
| `stream.run_error` | 运行出错 | `run_id`, `seq`, `error`, `error_code` |
| `stream.ask_user` | 代理向用户提问 | `run_id`, `seq`, `session_key`, `request_id`, `question` |
| `stream.clarification_ended` | 澄清回合结束 | `session_key`, `request_id`, `outcome` |
| `stream.uncertainty_signal` | 代理表达不确定 | `run_id`, `seq`, `uncertainty`, `suggested_action` |
| `stream.model_resolved` | 本次运行选定的模型 | `run_id`, `seq`, `model_info` |
| `stream.run_retrying` | 运行正在重试 | `run_id`, `seq`, `provider`, `attempt`, `max_attempts`, `reason` |
| `stream.session_updated` | 会话元数据更新 | `session_key` |
| `stream.session_user_message` | 用户消息落进会话 | `session_key`, `author_user_id`, `content`, `timestamp` |
| `stream.running_set_changed` | 在跑的会话集合变化 | `seq`, `running` |

### 代理事件 (`agent.*`)

代理注册与绑定的变化。

| 主题 | 说明 | 关键字段 |
|-------|-------------|------------|
| `agent.lifecycle.registered` | 代理已注册 | `agent_id`, `workspace`, `model` |
| `agent.lifecycle.deleted` | 代理已删除，工作区归档 | `agent_id`, `workspace_archived` |
| `agent.lifecycle.bound` | 频道的代理绑定被切换 | `agent_id`, `channel`, `previous_agent` |
| `agent.lifecycle.unbound` | 频道的显式绑定被清除 | `channel`, `previous_agent` |

代理**运行**的生命周期（开始、输出、结束）不走这个命名空间：那些帧在网络上是 `stream.*` 通知（见上一节）。帧内部另有一个 `agent.*` 主题名，但订阅匹配用的是通知的 `method`，不是它。

### 会话事件 (`session.*`)

会话状态与内容的变化。

| 主题 | 说明 | 关键字段 |
|-------|-------------|------------|
| `session.updated` | 会话元数据更新 | `session_key` |
| `session.user.message` | 用户消息落进会话记录 | `session_key`, `author_user_id`, `content`, `timestamp`, `seq` |
| `session.lifecycle.changed` | 会话状态迁移 | `session_key`, `old_state`, `new_state`, `reason` |

### Cron 事件 (`cron.*`)

计划作业**定义**本身的变化。

| 主题 | 说明 | 关键字段 |
|-------|-------------|------------|
| `cron.job.changed` | 作业被创建、更新、删除，或仅运行状态变化 | `job_id`, `change` |

`change` 的取值是 `created`、`updated`、`deleted`、`state_changed`。

作业的**执行结果**不在事件流里：用 `cron.runs` 查某个作业的运行记录（`status` 取值为 `ok`、`error`、`skipped`、`timeout`），用 `cron.status` 看整体（`running`、`last_tick_at_ms`、`job_count`、`enabled_count`）。

### 配置事件 (`config.*`)

配置更改。

| 主题 | 说明 | 关键字段 |
|-------|-------------|------------|
| `config.changed` | 某个配置段被修改 | `section`, `value` |
| `config.reloaded` | 配置文件被重新加载 | `agents`, `timestamp` |
| `config.error` | 配置文件校验失败 | `error`, `timestamp` |

### 审批事件 (`approval.*`)

命令执行审批流程。

| 主题 | 说明 | 关键字段 |
|-------|-------------|------------|
| `approval.requested` | 需要人工审批 | `approval_id`, `session_key`, `channel_id`, `conversation_id`, `tool_call_id` |
| `approval.reminder` | 尚无应答的审批被再次提醒 | `approval_id`, `session_key` |
| `approval.resolved` | 审批已决策 | `approval_id`, `session_key`, `decision`, `resolved_by` |
| `approval.expired` | 审批超时作废 | `approval_id`, `session_key` |

`decision` 的取值是 `allow-once`、`allow-session`、`allow-always`、`deny`。

审批事件走 `approval.*` 主题；`exec.*` 是**方法**命名空间，用来查待批列表和下决策：`exec.approvals.pending`、`exec.approval.resolve`、`exec.grants.list`、`exec.grant.revoke`。

### 守护进程事件

守护进程为环境感知发出自己的事件层次结构：

**原始事件** —— 来自监视器的直接观察：
- `TimeEvent` —— cron 调度匹配、间隔滴答、绝对时间触发器
- `ProcessEvent` —— 进程启动、停止、CPU/内存阈值超出
- `FsEvent` —— 文件创建、修改、删除、重命名
- `SystemStateEvent` —— 电池电量、网络状态、显示器睡眠、用户活动、系统负载

**派生事件** —— 从原始事件中的模式推断：
- `ActivityChanged` —— 用户活动类型更改（编码、浏览、会议等）
- `ProgrammingSessionStarted` / `ProgrammingSessionEnded` —— 检测到的编码会话
- `ResourcePressureChanged` —— 系统资源压力级别转换
- `MeetingStateChanged` —— 检测到的会议开始/结束
- `IdleStateChanged` —— 用户空闲或返回

**系统事件** —— 守护进程自我管理：
- `WatcherStarted` / `WatcherStopped` —— 监视器生命周期
- `ConfigReloaded` —— 守护进程配置更改
- `Error` —— 守护进程级错误

## 订阅事件

### 通过 WebSocket (Gateway RPC)

接收事件的主要方式。连接到网关 WebSocket 并使用 glob 模式订阅：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "events.subscribe",
  "params": {
    "patterns": ["stream.*", "agent.*", "cron.*"]
  }
}
```

事件作为 JSON-RPC 通知到达（无 `id` 字段）：

```json
{
  "jsonrpc": "2.0",
  "method": "event",
  "params": {
    "topic": "session.lifecycle.changed",
    "data": {
      "session_key": "agent:main:main",
      "old_state": "idle",
      "new_state": "running"
    },
    "timestamp": 1706400000000
  }
}
```

流式帧走的是另一种信封 —— `method` 直接是 `stream.*`，负载就在 `params` 里：

```json
{
  "jsonrpc": "2.0",
  "method": "stream.run_complete",
  "params": {
    "run_id": "run-uuid-123",
    "seq": 42,
    "summary": "done",
    "total_duration_ms": 5000
  }
}
```

<Callout type="info">
事件是即发即弃的。服务器不等待确认。如果客户端断开连接，断开连接期间的事件将丢失。没有重放或追赶机制 —— 设计您的消费者以容忍间隙。
</Callout>

### 管理订阅

订阅是累加的。多次调用 `events.subscribe` 会添加新模式而不移除现有模式。

```json
// 添加更多模式
{ "method": "events.subscribe", "params": { "patterns": ["config.*"] } }

// 移除特定模式
{ "method": "events.unsubscribe", "params": { "patterns": ["stream.*"] } }

// 列出活动订阅
{ "method": "events.list" }
```

有关完整 API 规范，请参阅 [events.* RPC 方法](/docs/zh/gateway/methods/events)。

## Glob 模式匹配

事件订阅模式使用 glob 风格匹配来针对主题字符串：

| 模式 | 匹配 |
|---------|---------|
| `stream.*` | 所有流式事件 |
| `agent.*` | 所有以 `agent.` 开头的主题（如 `agent.lifecycle.registered`） |
| `session.*` | 所有会话主题 |
| `cron.*` | 所有 cron 主题（如 `cron.job.changed`） |
| `*` | 所有事件 |
| `stream.response_chunk` | 仅精确匹配 |
| `*.changed` | 两段式、以 `changed` 结尾的主题（如 `config.changed`） |

匹配规则：`*` 单独使用或处于末尾时匹配其后所有段；出现在中间时只匹配一个段；其余按段精确匹配。`cron.job.changed` 有三段，所以 `*.changed` 匹配不到它 —— 要匹配它请用 `cron.*`。

## 事件负载结构

通过 WebSocket 传递的每个事件都遵循此信封：

```typescript
interface EventNotification {
  jsonrpc: "2.0";
  method: "event";
  params: {
    topic: string;        // 例如 "session.lifecycle.changed"
    data: Record<string, any>;  // 事件特定负载
    timestamp: number;    // Unix 时间戳（毫秒）
  };
}

// 流式帧不走上面的信封：method 就是 stream.* 之一
interface StreamNotification {
  jsonrpc: "2.0";
  method: string;         // 例如 "stream.run_complete"
  params: Record<string, any>;  // 帧负载
}
```

两种形状可以归一化成同一个处理函数：

```javascript
function readEvent(frame) {
  if (frame.method === "event") {
    return {
      topic: frame.params.topic,
      data: frame.params.data,
      timestamp: frame.params.timestamp
    };
  }
  if (typeof frame.method === "string" && frame.method.startsWith("stream.")) {
    return { topic: frame.method, data: frame.params, timestamp: null };
  }
  return null;
}
```

### 核心事件类型（内部）

在内部，Aleph 使用带有序列号的类型化事件系统进行排序：

```rust
pub struct TimestampedEvent {
    pub event: AlephEvent,
    pub timestamp: i64,      // 毫秒精度
    pub sequence: u64,       // 单调递增
}
```

`AlephEvent` 枚举涵盖所有核心事件类型：`InputReceived`、`ToolCallStarted`、`ToolCallCompleted`、`ToolCallFailed`、`SessionCreated`、`SubAgentStarted`、`AiResponseGenerated` 等。网关将这些映射到基于主题的格式以供外部消费。

## 构建反应式集成

### 实时仪表板

订阅所有事件并在 Web UI 中渲染它们：

```javascript
const ws = new WebSocket("ws://localhost:3001");

ws.onopen = () => {
  ws.send(JSON.stringify({
    jsonrpc: "2.0",
    id: 1,
    method: "events.subscribe",
    params: { patterns: ["*"] }
  }));
};

ws.onmessage = (msg) => {
  const frame = JSON.parse(msg.data);
  const evt = readEvent(frame);
  if (!evt) return;
  updateDashboard(evt.topic, evt.data, evt.timestamp);
};
```

### 监控和警报

监视整个系统中的错误和失败：

```javascript
// 订阅失败事件：代理运行失败走 stream.run_error，
// 频道错误走 channel.error，配置校验失败走 config.error
ws.send(JSON.stringify({
  jsonrpc: "2.0",
  id: 1,
  method: "events.subscribe",
  params: { patterns: ["stream.run_error", "channel.error", "config.error"] }
}));

ws.onmessage = (msg) => {
  const frame = JSON.parse(msg.data);
  const evt = readEvent(frame);
  if (!evt) return;
  sendAlert({
    channel: "#aleph-alerts",
    text: `[${evt.topic}] ${JSON.stringify(evt.data)}`
  });
};
```

### 工具使用分析

跟踪代理最常使用哪些工具以及它们花费多长时间：

```javascript
ws.send(JSON.stringify({
  jsonrpc: "2.0",
  id: 1,
  method: "events.subscribe",
  params: { patterns: ["stream.tool_start", "stream.tool_end"] }
}));

const toolMetrics = {};

ws.onmessage = (msg) => {
  const frame = JSON.parse(msg.data);
  const evt = readEvent(frame);
  if (!evt) return;

  const { topic, data } = evt;

  if (topic === "stream.tool_start") {
    toolMetrics[data.run_id] = {
      tool: data.tool_name,
      startedAt: Date.now()
    };
  }

  if (topic === "stream.tool_end") {
    const start = toolMetrics[data.run_id];
    if (start) {
      recordMetric(start.tool, Date.now() - start.startedAt);
      delete toolMetrics[data.run_id];
    }
  }
};
```

### Cron 作业状态板

监控计划作业健康状态：

```javascript
ws.send(JSON.stringify({
  jsonrpc: "2.0",
  id: 1,
  method: "events.subscribe",
  params: { patterns: ["cron.*"] }
}));

ws.onmessage = (msg) => {
  const frame = JSON.parse(msg.data);
  const evt = readEvent(frame);
  if (!evt) return;

  const { topic, data } = evt;

  // cron.job.changed 只说明作业定义变了（change: created | updated | deleted | state_changed）；
  // 执行结果（ok / error / skipped / timeout）要用 cron.runs 查。
  if (topic === "cron.job.changed") {
    setJobStatus(data.job_id, data.change);
  }
};
```

## 守护进程事件驱动自动化

守护进程的事件系统启用环境感知自动化。守护进程监视世界并发出可以触发代理操作的事件：

### 上下文感知响应

守护进程检测您何时开始编程会话，并可以主动提供帮助：

- **`ProgrammingSessionStarted`** —— 检测到 IDE 启动 + 项目目录中的文件更改
- **`ActivityChanged`** —— 在编码、浏览、会议等之间转换
- **`IdleStateChanged`** —— 用户空闲（后台任务的机会）
- **`ResourcePressureChanged`** —— 系统内存或电池不足

### 基于时间的触发器

守护进程评估 cron 表达式和间隔计时器，发出 `TimeEvent` 事件：

- `Cron { expression }` —— 匹配 cron 调度
- `Interval { seconds }` —— 间隔计时器滴答
- `Absolute { time }` —— 达到特定时间戳

这些时间事件是内部驱动 cron 作业系统的原因 —— 守护进程触发触发器，cron 调度器拾取它进行执行。

## 设计原则

1. **事件是不可变的事实** —— 一旦发出，事件永远不会被修改。它们代表发生的事情。
2. **即发即弃交付** —— 发布者不等待消费者。这使代理循环保持快速。
3. **不保证交付** —— 如果没有订阅者在监听或缓冲区溢出，事件可能会丢失。相应地设计消费者。
4. **内部类型化，外部字符串化** —— 核心使用 Rust 枚举进行编译时安全。网关将它们映射到点分隔的主题字符串以供语言无关消费。
5. **序列排序** —— 每个事件携带单调递增的序列号，用于单个 Aleph 实例内的因果排序。
