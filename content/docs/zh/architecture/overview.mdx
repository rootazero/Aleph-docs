Aleph 组织为五个水平层，形成一个清晰的处理管道：**接口层**、**网关层**、**编排器层**、**工具链层**和**存储层**。每个用户消息从上到下遍历这些层；每个响应从下到上返回。本页映射整个系统，展示模块如何相互依赖，并跟踪请求的完整生命周期。

要深入了解各个子系统，请参阅[网关架构](./gateway)、[工具链](./harness)、[会话服务](./session-service)、[工具架构](./tools)和[记忆系统](./memory)。

## 设计理念

> **一核多端，壳核分离；网关互通，权限控制。**

Aleph 的架构建立在四个原则之上，这些原则指导每一个设计决策：

1. **一核多端** —— 一个 `aleph-server` 进程驱动所有界面。无论你通过桌面应用、CLI、Telegram 还是 Discord 聊天，同一个核心处理所有推理、工具执行和状态管理。

2. **壳核分离** —— 桌面应用是一个*薄原生宿主*（NSH，`desktop/nsh-shell`）。它拥有窗口、托盘、通知和 OS 集成——但**零业务逻辑和零业务 UI**。所有产品 UI 在由核心提供的 Leptos Panel（`interfaces/webchat`）中。所有推理、工具和状态在 `aleph-server` 中。宿主连接已存在的本机或远程核心（远程使用 HTTPS），不托管其生命周期。

3. **网关互通** —— 每个终端使用相同的认证 WebSocket 协议（`JSON-RPC 2.0` over `ws://`）。CLI 工具、Telegram 机器人和桌面宿主承载的 Panel 都在同一个网关上调用相同的方法。

4. **权限控制** —— 每个连接都经过认证。桌面宿主经原生凭据通道保存并出示设备凭据（`desktop/nsh-shell/src/credentials.rs`）。远程连接同样要求认证。访客会话携带受限范围。详细信息请参阅[身份与安全](#身份与安全)。

> **从「多端」到「多体」。** 一核多端让一个大脑拥有多个 I/O 通道。[集群联邦](./cluster) 把同一原则推进到多个*执行体*：一个中心核编排多台机器（节点）协同工作 —— 而集群始终只有一个心智。

### 第 1 层：接口

最顶层包含所有客户端。每个客户端——无论是桌面宿主承载的 Panel、终端 CLI / TUI 还是 Telegram/Discord 机器人——都连接到同一个网关，使用同一套 JSON-RPC 2.0 协议。既有入口是经过认证的 WebSocket 端点 `ws://127.0.0.1:18790/ws`（路由注册在 `src/gateway/server/mod.rs`）。

**桌面宿主（NSH）。** 原生桌面宿主是"最后一公里原生壳"：`desktop/nsh-shell`，crate `aleph-nsh-shell`，基于 nsh 0.6.0（`desktop/nsh-shell/Cargo.toml`）。它提供：
- 原生窗口 + WebView，承载由网关提供的 Leptos Panel（本机目标为 `http://127.0.0.1:18790`，见 `shared/client/src/connection_target.rs`）
- 系统托盘（`desktop/nsh-shell/src/main.rs` 中的 `set_tray`）
- 经 Panel 桥接转发的 OS 通知（`desktop/nsh-shell/src/panel_bridge.rs`，协议类型在 `shared/protocol/src/panel_shell.rs`）
- 全局召唤热键（默认 `mod+shift+a`；`ALEPH_SHELL_HOTKEY=disabled` 关闭）
- 用于深度链接的 `aleph://` URL 方案（`main.rs` 中的 `.url_schemes(["aleph"])`）
- 登录项状态的只读查询（`--autostart-status`，`desktop/nsh-shell/src/autostart.rs`）；宿主不写入登录项
- 设备凭据的原生存取（`desktop/nsh-shell/src/credentials.rs`）

NSH 没有自动更新器，也没有守护进程监督——它不托管 Gateway 的生命周期。平台验收状态以 `docs/reference/DESKTOP_SHELL.md` 为准：目前只有 macOS 有本机验收证据，NSH 也还没有发布流水线。

关键的是，宿主包含**零业务逻辑和零业务 UI**。所有产品 UI（聊天、记忆、设置）在 Panel（`interfaces/webchat`，由核心提供的 WASM）中；NSH 承载的是同一个 Panel，而不是第二套业务 UI（`docs/reference/DESKTOP_SHELL.md`）。所有推理、工具和状态在 `aleph-server` 中。这种分离意味着：
- 宿主可以独立于核心更新
- 核心可以在服务器上无头运行，而宿主远程连接
- 同一个核心同时服务桌面宿主、CLI 和消息机器人

**连接而非托管。** 宿主连接已存在的 Gateway，不启动、停止或重配服务（`main.rs` 的帮助文本）。唯一的例外是默认关闭的 `embedded-core` feature：启用后，本机目标在打开 Panel 前经 `aleph-desktop-host` 做准入检查，仅当 `127.0.0.1:18790` 拒绝连接时才启动同级的 `aleph-server` 二进制（`desktop/host/src/local_server.rs` 的 `ensure_compatible_ready`）；端口被其他进程占用或已有 Gateway 时，宿主都不会接管或停止它。

**远程核心支持。** 宿主可以用 `--connect <origin>` 连接远程 `aleph-server`，远程源必须使用 HTTPS。Panel 的目录选择器通过 JSON-RPC（`fs.*`，见 `src/gateway/lane.rs`）浏览*服务器*的文件系统，确保远程部署的正确语义。宿主不读取核心的安全数据库；认证凭据由宿主经 `credentials.rs` 存取，`aleph-server bootstrap-token` 子命令（`src/bin/aleph-server/commands/bootstrap_token.rs`）仍在核心侧。

### 第 2 层：网关

网关是控制平面。它接受 WebSocket 连接，解析 JSON-RPC 消息，将它们路由到正确的处理程序，并管理会话、事件和认证。它还托管接口注册表（跟踪活动聊天集成）、配置热重载监视器和后台任务的 cron 调度器。详细信息请参阅[网关架构](./gateway)。

### 第 3 层：编排器

编排器为每个传入请求解析 `AgentDef` 和 `FlowSpec`，组装 `HarnessDeps`（注入 `SessionService`、`ToolService`、`Sandbox` 和 `AiProvider`），并分发到 `HarnessRunner::run`。这一层将路由关注点与执行逻辑分离，使网关保持为薄控制平面。请参阅[工具链](./harness)了解编排器-工具链交互。

### 第 4 层：工具链

工具链层运行核心智能循环。当消息到达时，`AgentHarness` 执行 **Think→Act** 循环，包括上下文预算执行、停止钩子评估和可选压缩：它在预算约束下收集上下文，调用 LLM 决定做什么，如果需要则执行工具，评估停止钩子和守卫，并可选地压缩历史记录。`ToolService` 处理工具执行，而守卫强制执行迭代上限和令牌预算等安全限制。请参阅[工具链](./harness)了解完整循环。

### 第 5 层：存储

底层提供持久存储和状态管理。**记忆**使用 SQLite 和 `sqlite-vec` 扩展进行向量搜索，加上 markdown 笔记和 wikilink 图。**弹性恢复**在 SQLite 中存储任务恢复和状态。**配置**通过 TOML 文件和密钥管理持久化设置。详细信息请参阅[记忆系统](./memory)。

## 数据流：请求生命周期

当用户发送消息时，会发生以下序列：

```
客户端请求 (WebSocket 上的 JSON-RPC)
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 网关：InboundRouter                                  │
│   • 解析 JSON-RPC 消息                              │
│   • 路由到适当的处理程序                             │
│   • 认证检查（如果启用）                             │
│   • 构建 FlowRequest { agent_id, input, ... }      │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 编排器                                              │
│   • 解析 AgentDef + FlowSpec                        │
│   • 构建 HarnessDeps (SessionService, ToolService, │
│     Sandbox, AiProvider)                            │
│   • 分发到 HarnessRunner::run                       │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ AgentHarness: Think → Act 循环                      │
│   1. 上下文：应用预算、预检准备                      │
│   2. 思考：调用 Thinker (LLM) 做决定                 │
│   3. 行动：通过 ToolService 执行工具                 │
│   4. 停止钩子：评估完成/守卫                         │
│   5. 压缩：如果溢出，压缩历史                        │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ FlowOutcome → 网关渲染响应                           │
│   • 通过 TraceSink / EventBus 流式传输事件           │
│   • 最终响应作为 JSON-RPC 结果                       │
│   • 会话历史持久化到 SQLite                          │
└─────────────────────────────────────────────────────┘
```

### 工具执行子流程

当 Thinker 决定调用工具时，执行通过分发器和引擎分支：

```
Thinker 决策 (tool_use)
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 分发器                                              │
│   • 分析工具请求                                    │
│   • 检查权限 (ToolFilter)                           │
│   • 风险评估                                        │
│   • 确认流程（如果需要）                             │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 引擎                                                │
│   • 查找工具 (Builtin / MCP / Extension)            │
│   • 反序列化参数                                    │
│   • 带超时执行                                      │

    ├─── 内置工具 (AlephTool trait)
    │       • 直接 Rust 执行
    │
    ├─── MCP 工具 (Model Context Protocol)
```

Exec 类工具 (`code_exec`, `bash_exec`) 在工具和进程执行之间通过额外的**沙箱层** (`src/sandbox/`)。沙箱拥有每会话工作空间配置 (`~/.aleph/workspaces/{session_id}/`)、能力执行和通过 `OsSandboxDriver` 的 OS 级 seatbelt 隔离。

## 设计模式

Aleph 在代码库中采用了几种 Rust 惯用的设计模式。

### 上下文模式

将相关函数参数分组到专用结构体中，减少参数膨胀并启用构建器模式：

```rust
// 之前：7 个参数直接传递
legacy_agent_loop.run(request, context, tools, identity, callback, abort_signal, initial_history).await

// 之后：结构化 deps + FlowRequest
let deps = HarnessDeps { session, tool_service, sandbox, provider, trace_sink };
let flow = FlowRequest::new(agent_id, input, identity)
    .with_abort_signal(abort_rx);
HarnessRunner::run(flow, deps).await
```

**好处：**
- 可扩展性：添加参数而不会破坏更改
- 可读性：清晰的参数分组
- 类型安全：编译时验证
- 人体工程学：可选参数的构建器模式

### 新类型模式

将原始类型包装在 distinct 结构体中以实现编译时安全。你不能意外地将 `SessionId` 传递给需要 `ProviderId` 的地方：

```rust
// src/domain/skill.rs
#[derive(Debug, Clone, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct SkillId(String);

impl SkillId {
    pub fn new(id: impl Into<String>) -> Self { Self(id.into()) }
    pub fn as_str(&self) -> &str { &self.0 }
}
```

这些 newtype **不实现 `Deref`**：全仓唯一的 `Deref` 实现是 `src/extension/hooks/registry.rs` 的 `HookReadGuard<'_>`（`Target = HookExecutor`）。隐式解引用会让「本该是 ID 的地方」悄悄变成字符串比较，因此访问一律走 `as_str()`。

**新类型目录：**
- **ID**: `SkillId`, `PluginId`, `ProviderId`, `RunId`, `TaskId`, `SubscriptionId`
- **集合**: `DedupKey`（事件去重身份，`src/gateway/telecom/protocol.rs`）
- **值**: `SkillContent`（技能正文，`src/domain/skill.rs`）

### FromStr Trait 模式

在整个代码库中提供一致的解析接口：

```rust
// src/resilience/types.rs
impl std::str::FromStr for TaskStatus {
    type Err = String;

    fn from_str(s: &str) -> Result<Self, Self::Err> {
        if s.eq_ignore_ascii_case("pending") {
            Ok(Self::Pending)
        } else if s.eq_ignore_ascii_case("running") {
            Ok(Self::Running)
        } else {
            Err(format!("Unknown task status: {s}"))
        }
    }
}

// 用法
let status: TaskStatus = "pending".parse()?;
```

**已实现于：** `TaskStatus`, `NoteType`, `FactSource`, `FactSpecificity`, `TemporalScope`, `MemoryLayer`, `MemoryCategory`, `EventActor`, `ExtensionKind`, `RuntimeKind`, `Os`, `PromptScope`, `InstallKind`, `LedgerAction`, `LedgerOutcome`, `RiskLevel`, `Lane`, `TeamStatus`, `TeamMemberKind`, `BindingPeerKind`。

## 身份和安全

不可变的 `IdentityContext` 从会话创建到工具执行贯穿整个执行链。这支持细粒度的、基于角色的访问控制：

- **所有者**会话对所有工具有完全访问权限
- **访客**会话携带限制哪些工具可用以及会话何时过期的 `GuestScope`
- **匿名**会话默认被拒绝

`PolicyEngine` 在执行器级别执行无状态权限检查，确保每个工具调用在执行前都经过授权。

### 安全属性

1. **不变性**: `IdentityContext` 创建后无法修改
2. **冻结权限**: 访客范围在会话创建时冻结
3. **无状态检查**: `PolicyEngine` 没有可变状态
4. **授权证书**: 身份构建一次并向下传递
5. **故障安全**: 缺失或无效的元数据默认为所有者（向后兼容）

## 26.7.x 补充

### 第三双生子：会话模式

`chat` / `work` / `code` 是与 `exec_tier`、`think_level` 并列的**第三个**用户可调维度。它**只对工具呈现面**做静态分区（progressive-disclosure 核心集 + deferred-tool 层级），不影响权限。可在 Panel composer pill、Settings → Policies（全局默认）或 `session_set_mode` 工具里切换。每个模式还驱动一个独立的右侧面板行为（chat = 徽章、work = 计划面板、code = 工具详情）并附加一行缓存稳定的提示词。

### 治理拓扑层（loop_graph）

`loop_graph` 在 harness 之上叠加一层治理拓扑：

- **团队节点** —— 将多代理系统融合进图
- **审计环** —— 闭环审计动作日志
- **客观 ACL** —— 按图节点身份客观授权
- **胜利声明 watcher** —— 团队/循环宣告完成触发
- **内置 `loop-auditor` 智能体** —— 审计/监督默认走独立上下文

它给单循环的四种失败模式（Goodhart、参考盲、环冲突、测量衰减）一个拓扑答案。

### 自签名 TLS + TOFU

26.7.17/18+：

- 网关进程内终止 TLS（自签名或用户提供）
- 自签名证书 SAN 自动覆盖主机非环回接口 IP
- 漂移 sidecar + 原子 regen marker
- 客户端 TOFU（fingerprint + SAN 审批 + 固定信任存储）
- macOS WKWebView + iOS Keychain 适配器

### 真成本与 token 核算

26.7.15+：`session.usage` 现在携带真实花费账本（之前部分伪造）；提示缓存纪律恢复；思考深度端到端接线。

### 守护进程端计算的会话成本

`session.usage` 通过核心定价计算成本，shell 里的重复价格表被删除。

### 完整 RPC 计数

当前网关暴露 **396 个 RPC 方法**（详见 [网关方法参考](/docs/zh/gateway/methods)）。26.7.22+ 之后新增的大类：`teams.*`（36 RPC）、`projects.*`（19 RPC）、`memory.*`（16 RPC）、`agents.*`（13 RPC）、`sessions.*`（12 RPC）、`acp.*`（12 RPC）、`channel.*`（11 RPC）、`plugin.*`（10 RPC）、`cron.*`（9 RPC）、`voice.*`（8 RPC）、`chat.*`（7 RPC）、`pty.*`（7 RPC）、`capabilities.*`（7 RPC）、`graph.*`（6 RPC）、`extensions.*`（6 RPC）、`artifacts.*`（2 RPC）、`loop.*`（1 RPC）等。

### 完整模块清单

`aleph-server` 进程内 69 个 `src/<module>` 目录 + 6 个顶层 `.rs` 文件。26.7.22+ 之后**新增** / **重组**的顶层模块：

| 模块 | 路径 | 用途 |
|------|------|------|
| **artifacts** | `src/artifacts/` | 工件存储（`ArtifactStore` + `MAX_ARTIFACT_BYTES = 50 MB` + 4 个 `ArtifactOrigin`） |
| **export** | `src/export/` | session HTML / Markdown 导出 + CSS + collect + page + document |
| **hub** | `src/hub/` | **Aleph Hub 单一源**（替代已退役的独立 store 模块）——`primer` / `catalog_client` / `official_{mcp,plugins,skills}` / `install` / `reconcile` / `trust` / `verify` / `secrets` |
| **looping** | `src/looping/` | Loop 子系统（进程内 `LoopRegistry` + 状态机 Active/Paused/Stopped） |
| **goal** | `src/goal/` | Goal 子系统（持久化 `GoalStore` + 客观 gate + TreeBudget） |
| **strategy** | `src/strategy/` | Strategy 子系统（composite-keyed `StrategyStore` + planner + renderer） |
| **projects** | `src/projects/` | 项目存储（`projects.json` + lock） |
| **vision** | `src/vision/` | 视觉子系统（claude / OpenAI-compat / 多模） |

**重组 / 重命名**（路径变化但概念延续）：

| 旧模块（相对 src 目录） | 新路径 | 说明 |
|--------|--------|------|
| `store/` | `src/hub/` | Hub 收敛：`SourceProvider` trait 退役；改为直接 HTTP 客户端 + `primer` 冷启动投影 |
| `dispatcher/` | `src/tool_metadata/` | 工具元数据 + loom 并发 + risk + unified 索引 |
| `tasks/goal_pursuit.rs` | `src/goal/pursuit.rs` | goal 子系统独立 |
| `builtin_tools/store/` | `src/builtin_tools/hub/` | Hub 内置工具：`hub_catalog_sync` / `hub_fetch_docs` / `hub_resolve_spec` / `hub_install_run` / `hub_install_verify` |
| `builtin_tools/skill_reader.rs` | `src/builtin_tools/skill_reader/{mod,list,read,tests}.rs` | 技能读取子目录化 |
| `builtin_tools/browser_tools.rs` | `src/builtin_tools/browser_tools/{cookies,dialog,drag,emulate,hover,network,pdf,resize,scroll,session,upload}.rs` | 浏览器工具按动作拆开 |

**新增顶层文件**：`src/json_canvas_io.rs`、`src/pricing.rs`、`src/command/{mod,parser}.rs`（轻量命令补全聚合）。
