# 执行器

执行器是工具执行引擎。它接收来自网关执行引擎（`src/gateway/execution_engine/`）的工具决策，并把它们路由到正确的处理程序；底层实现是 `src/executor/` 中的统一 `BuiltinToolRegistry`。

**位置**: `src/executor/`

---

## 与 Harness 的关系

```
Thinker 决策 (tool_use)
     │
     ▼
Harness 循环（harness::agent::loop_graph / harness::agent::think）
     │
     ▼
ToolService (scoped tool stack: src/tools/scoped/builder.rs)
     │   Adapter: src/tools/adapters/registry_adapter.rs
     │   将 Arc<dyn ToolService> 暴露为 LoopTool
     │
     ▼
执行器
     │
     ├─ BuiltinToolRegistry  （src/executor/builtin_registry/）
     │     把 Arc<ToolRegistry> 暴露给 tool stack
     │
     └─ ToolRegistry trait   （src/executor/tool_registry.rs）
           把名称解析为 UnifiedTool，执行工具调用
```

Exec 类工具（`code_exec`、`bash_exec`）通过 `src/sandbox/` 之间的**沙箱层**。沙箱拥有每会话工作空间配置、能力执行、以及通过 `OsSandboxDriver` 的 OS 级 seatbelt 隔离（macOS sandbox-exec / Windows job-object / Linux cgroups-v2 / seccomp）。

## `ToolRegistry` trait（`src/executor/tool_registry.rs`）

```rust
pub trait ToolRegistry: Send + Sync {
    fn get_tool(&self, name: &str) -> Option<&UnifiedTool>;

    fn execute_tool(
        &self,
        tool_name: &str,
        arguments: Value,
    ) -> std::pin::Pin<Box<dyn std::future::Future<Output = Result<Value>> + Send + '_>>;

    // 可选的 per-run 共享句柄（默认 None）：

    /// 共享 workspace 句柄：执行引擎在 workspace 解析后写入，工具（memory_search 等）读
    fn workspace_handle(&self) -> Option<Arc<tokio::sync::RwLock<String>>> { None }

    /// 共享的 per-agent SmartRecallConfig map：memory_search 的两阶段 smart recall
    fn smart_recall_config_handle(&self) -> Option<Arc<tokio::sync::RwLock<HashMap<String, SmartRecallConfig>>>> { None }

    /// 共享的 SessionContext：agent 切换需要绑定到正确的会话
    fn session_context_handle(&self) -> Option<Arc<tokio::sync::RwLock<SessionContext>>> { None }

    /// 共享的 ToolContextHandle：workspace-scoped 输出路径
    fn tool_context_handle(&self) -> Option<crate::tools::ToolContextHandle> { None }

    /// 共享的 session key 句柄：memory_search 的 scope=current_session 过滤
    fn session_key_handle(&self) -> Option<Arc<tokio::sync::RwLock<String>>> { None }
}
```

生产实现是 `BuiltinToolRegistry`（`src/executor/builtin_registry/registry/`），由 `src/tools/adapters/registry_adapter.rs::RegistryToolAdapter` 包装为 `LoopTool`，再由 gateway 的 `ScopedToolService` 暴露给 harness。句柄访问器让执行引擎在不污染每次调用签名的情况下，把 workspace 和 session-scoped 上下文传递给工具。

公开类型（`src/executor/builtin_registry/definitions.rs` + `groups.rs`）：

| 类型 | 用途 |
|---|---|
| `BUILTIN_TOOL_DEFINITIONS` | 全部内置工具的 JSON Schema / 参数定义（单一来源） |
| `TOOL_CATEGORIES` | 工具按功能分组的元数据（Settings UI 用） |
| `BuiltinToolConfig` | 构造 `BuiltinToolRegistry` 的可选项（gateway context、tool catalog 等） |
| `get_builtin_tool_names()` | 列出全部已注册名字 |
| `create_tool_boxed()` | 类型擦除的工具构造工厂 |

测试（`src/executor/builtin_registry/mod.rs` 的 `test_resolve_plugin_handler_*`）验证插件工具走 `plugin:<plugin_id>:<name>` 直接 fast-path，并通过 `ExtensionManager::sync_runtime_snapshots` 同步。

## 工具元数据来源

注册表里每个工具都是 `UnifiedTool`（`src/tool_metadata/types/unified/`）：

```rust
pub struct UnifiedTool {
    pub id: String,                          // "builtin:search" | "mcp:fs:read_file" | "plugin:diagnostics:ping" | ...
    pub name: String,                        // 命令名（不含命名空间前缀）
    pub source: ToolSource,                  // Builtin | Native | Mcp { server } | Skill { id } | Plugin { .. } | Custom { .. }
    pub routing_regex: Option<String>,       // 用于 builtin → RoutingRuleConfig 的转换
    pub routing_strip_prefix: bool,          // 命令匹配后是否剥离前缀
    pub routing_system_prompt: Option<String>,
    pub routing_capabilities: Vec<String>,   // skill 允许的工具白名单
    pub routing_intent_type: Option<String>,
    pub routing_context_format: Option<String>,
    pub aliases: Vec<String>,                // 模糊匹配 + slash 命令解析
    pub visible_channels: Vec<ChannelType>,
    pub sort_order: u32,
    pub is_active: bool,
    pub is_builtin: bool,
    pub /* … */ …
}
```

`ToolCatalog::get_builtin_routing_rules`（`src/tool_metadata/registry/query.rs`）把 `UnifiedTool.routing_regex` 反向编译为 `RoutingRuleConfig`——单一来源，配置模块不应再硬编码命令规则。

## 公共接口（`src/executor/mod.rs`）

executor 模块只导出注册表及其 trait，没有独立的结果/上下文类型层（旧的 `ExecutionResult` / `ToolCallRecord` / `ExecutionContext` / `ExecutorError` 一族已不存在——工具结果是 `serde_json::Value`，错误是 `AlephError`）。

```rust
pub use builtin_registry::{
    create_tool_boxed, BuiltinToolConfig, BuiltinToolRegistry,
    BUILTIN_TOOL_DEFINITIONS, TOOL_CATEGORIES,
};
pub use tool_registry::ToolRegistry;
pub const TOOLS_OUTSIDE_DEFINITIONS: &[&str];   // subagent, tool_search
pub const REGISTRY_ONLY_TOOL_NAMES: &[&str];    // 已注册但不在 BUILTIN_TOOL_DEFINITIONS 中
pub fn is_builtin_tool_name(name: &str) -> bool;
```

`ToolRegistry`（`src/executor/tool_registry.rs`）是分发接缝：`get_tool(name) -> Option<&UnifiedTool>`、`execute_tool(name, arguments) -> Result<Value>`、`execute_plugin_tool_with_authority`（默认拒绝，仅受控插件运行时覆写），以及上文所述的可选句柄访问器。

循环退出原因不属于 executor：它们是 `src/orchestrator/dispatch.rs` 中的 `TerminateReason`。`TerminateReason::DiminishingReturns` 是**已退役信号**，仅为 i18n 与摘要向后兼容而保留——R10 之后硬检测器已被删除，循环通过 `max_iterations`、工具循环验证、连续失败上限和模型自停来约束。

## 中间件栈

所有工具调用都经过 `src/tools/scoped/` 中的标准中间件栈：

```
ExecAuditLayer → PermissionLayer → ContextRuleLayer → TimeoutLayer → CoreDispatch
```

| 层 | 用途 |
|-------|---------|
| `ExecAuditLayer` | 审计日志 |
| `PermissionLayer` | 权限检查（`SmartFilter`） |
| `ContextRuleLayer` | 基于上下文的规则 |
| `TimeoutLayer` | 超时执行 |
| `CoreDispatch` | 最内层，持有 `ToolRegistry` |

斜杠快路径（`execute_slash_command_fast_path`）、`tools.invoke`、后台延续旁路**全部**被强制走 `src/tools/scoped/` 审批门——这是 26.7.15+ 的修复，确保审批对实际命令可见。

## Exec 类工具与沙箱

- `code_exec`、`bash_exec` 通过沙箱层路由
- `Sandbox` trait → `WorkspaceSandbox` → `OsSandboxDriver`
- 每会话工作空间位于 `~/.aleph/workspaces/{hash(session_id)}/`
- 工具级权限（`SmartFilter`）控制**是否**允许调用
- 沙箱的能力检查控制一旦允许**子进程可以做什么**

---

## 三级执行权限

| 等级 | 行为 |
|------|------|
| `ask` | 每次工具执行前请求审批；未知工具失败关闭 |
| `auto` | 幂等工具自动放行，破坏性工具仍需审批 |
| `full` | 全部自动放行（独立的安全硬过滤除外） |

---

## 进程隔离内核

沙箱 restricted-token / job-object / AppContainer / integrity-level / SID·ACL 系统调用在 spawn 时就地发起（R1 进程隔离例外）。
