---
title: "工作流"
description: "声明式、可重用的工作流模板——agent-workflow 谱系中的工作流部分；编译为 coord_tasks DAG、由 TeamDispatcher 执行。"
---

`workflow` 模块提供**声明式、可重用的工作流模板**，通过预定义的确定性编排来补充 Aleph 的代理驱动推理。虽然代理动态地指导自己的过程（Think→Act 循环、LLM 编写的团队任务 DAG），但工作流是**命名的、可保存的、可重复运行的模板**，其中 LLM 通过预定义的代码路径进行编排。

## 概览

工作流支持：

- **命名、可重用的模板** —— 将多步骤工作流保存到磁盘，按需运行
- **声明式编排** —— 将代理步骤、依赖关系和执行顺序定义为纯数据
- **三种步骤特性** —— `Agent` / `Clarify` 步骤类型；`review` / `timeout_seconds` / `max_retries` 逐步覆盖
- **DAG 执行** —— 依赖边通过 `TeamDispatcher` 驱动 Tokio 并发执行
- **澄清交互性** —— 暂停工作流以向用户提出结构化问题，然后恢复
- **Claude Code 互操作性** —— `.workflow.js` 格式的双向导入/导出（通过 AWI 超集清单）
- **MetaSkill 提案** —— 从观察到的技能共现模式自动起草工作流模板

## 设计理念

> **没有新的调度器，没有新的推理。**

`WorkflowDef` 是纯数据。它被持久化到磁盘（`store`），在运行时通过*编译*（`compile::materialize`）到 `coord_tasks` DAG 中，然后由现有 `TeamDispatcher`（`src/teams/dispatcher/`）执行。该模块**不贡献新的调度器和新的推理**——它是一个模式 + 文件存储 + 确定性编译器。

每个步骤都是一个完整的代理运行；依赖边驱动的并发执行是单代理参考设计无法表达的。

## 架构

```
src/workflow/
├── mod.rs           # 入口 + 公共 API；导出 WorkflowDef / WorkflowManifest / materialize
├── def.rs           # WorkflowDef / WorkflowStepDef / WorkflowStepKind + 验证 + 拓扑排序
├── store.rs         # 文件系统持久化（原子写入：temp-file + rename）
├── compile.rs       # 将 WorkflowDef 实例化为 coord_tasks DAG
├── clarify.rs       # ClarifyContext / ClarifyTaskMeta / CLARIFY_META_KEY
├── proposal.rs      # 门控 MetaSkill 草稿层（proposals/ 目录）
└── interop/         # 与 .workflow.js 格式的双向桥接
    ├── mod.rs       # parse_workflow_js / render_workflow_js / ImportOutcome
    ├── manifest.rs  # WorkflowManifest —— AWI（Aleph Workflow Interchange）超集
    ├── import.rs    # 三路径解析（裸 JSON / 嵌入块 / 裸 .workflow.js 扫描）
    ├── export.rs    # 渲染为 .workflow.js
    └── consts.rs    # 有界数据字面量归一化器（bare-scan schema-const 解析）
```

## 核心组件

### `WorkflowDef`（`src/workflow/def.rs`）

```rust
pub struct WorkflowDef {
    pub name: String,                                  // 存储键 + coord_task subject 前缀；保存时 sanitise
    #[serde(default)]
    pub description: String,
    pub steps: Vec<WorkflowStepDef>,                   // 顺序由 depends_on 推导，不是 list 位置
}

pub enum WorkflowStepKind {
    #[default]
    Agent,    // 运行 agent 字段指定的代理与 prompt（默认；缺省 kind 字段的旧模板照常反序列化）
    Clarify,  // 暂停运行、向用户提问题（prompt 即问题；choices 是菜单）；不跑 agent
}

pub struct WorkflowStepDef {
    pub id: String,                                    // step 局部 id；depends_on 引用
    #[serde(default)]
    pub agent: String,                                 // 编译为 coord_task.owner；clarify 步骤忽略
    pub prompt: String,                                // {input} 占位；clarify 时是问题
    #[serde(default)]
    pub depends_on: Vec<String>,                       // 编译为 coord_task 的 blocked_by
    #[serde(default, skip_serializing_if = "WorkflowStepKind::is_agent")]
    pub kind: WorkflowStepKind,                        // Agent（默认） | Clarify
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    pub choices: Vec<String>,                          // Clarify 步骤的菜单；空 = 自由文本
    #[serde(default, skip_serializing_if = "is_false")]
    pub review: bool,                                  // gate lead review：完成后停在 WaitingReview
    #[serde(default, skip_serializing_if = "Option::is_none", alias = "timeout_secs")]
    pub timeout_seconds: Option<u64>,                  // 单步超时；None = 全局 [team_dispatcher] task_timeout_secs
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub max_retries: Option<u32>,                      // 单步自动重试上限；0 = 首次失败即终态
}
```

验证（`WorkflowDef::validate`）检查：非空名称、至少一个步骤、唯一的步骤 id、可解析的 `depends_on`、无自依赖、无环依赖图（Kahn 拓扑排序保证），以及每个 Agent 步骤必填 `agent` + `prompt`，每个 Clarify 步骤必填问题（`prompt`）、不得携带 `review` / `timeout_seconds` / `max_retries`（无 agent 可评审 / 受限）。

`validate()` 通过保证 `topo_order()` 必然成功。

### 实例化（`src/workflow/compile.rs`）

编译器把每个 `WorkflowStepDef` 映射为 `agent` 字段所指代理拥有的 `coord_task`，`depends_on` 映射为 coord_task 的 `blocked_by`。任务被标记为 `{"managed_by": "dispatcher"}`，由 dispatcher 的自主循环拾取：

```rust
pub async fn materialize(
    def: &WorkflowDef,
    input: &str,
    team_id: &str,
    store: &dyn CoordTaskStore,
    clarify_ctx: Option<&ClarifyContext>,
) -> Result<MaterializedWorkflow>;
```

任务按拓扑顺序创建（保证 `blocked_by` 引用已存在的 task id）。渲染提示时把 `{input}` 替换为运行输入。逐步覆盖：
- `timeout_seconds` → task metadata `timeout_secs`（与 `task_create` 同 override 通道）
- `max_retries` → task metadata `max_retries`
- `review: true` → task metadata `require_grounding` / `lead_review_required`（在 `agents::swarm::tasks::acceptance` 中读取）

上游步骤的输出通过 dispatcher's `build_handoff_context` 自动流入每个步骤。run 全局 welded 战略（`workflow_strategy`）由 `Strategy` → `render_workflow_global_frame` 在每个 agent step 上盖章一次。

### 澄清步骤（`src/workflow/clarify.rs`）

**Clarify** 步骤暂停 DAG 以从用户那里收集结构化答案。它的 `prompt` 是问题，`choices`（如果有）是菜单——`agent` 被忽略。该步骤由哨兵 `__clarify__` 拥有，并在 `coord_task` 元数据中携带等待记录：

```rust
pub struct ClarifyTaskMeta {
    pub question: String,
    pub choices: Vec<String>,
    pub channel_id: String,
    pub conversation_id: String,
    pub session_key: String,
}

pub const CLARIFY_DELIVERY_PENDING_KEY: &str;
pub const CLARIFY_META_KEY: &str;
pub const CLARIFY_OWNER: &str = "__clarify__";
```

dispatcher 通过 `src/teams/dispatcher/clarify.rs::handle_clarify_task` 检测 clarify 任务，传递问题，并将任务停放在 `Paused` 状态。入站路由器通过完成停放任务及其答案来解析用户的回复。这种设计意味着澄清步骤可以在进程重启后存活，无需重建内存状态。

### 持久化（`src/workflow/store.rs`）

工作流以 JSON 文件存储于 `$ALEPH_HOME/workflows/*.json`。**持久化文档是 `WorkflowManifest` 超集**——单一事实来源，保留 `.workflow.js` 兼容的元数据（`whenToUse`、`phases`、每个步骤的 `label`/`model`/`phase`/`schema`/`isolation`/`agentType`）跨越 `import → save → export`，让导出模板忠实再现工程格式。执行时仅消费 `WorkflowManifest::to_def` 投影的核心（R10——执行器看不到额外元数据）。

```rust
pub fn workflow_dir() -> PathBuf;                         // $ALEPH_HOME/workflows/
pub struct WorkflowMeta { pub name: String }
pub fn resolve_path_at(dir: &Path, name: &str) -> PathBuf;
pub fn save_at(dir: &Path, manifest: &WorkflowManifest) -> Result<PathBuf>;
pub fn save(manifest: &WorkflowManifest) -> Result<PathBuf>;
pub fn write_text_at(dir: &Path, name: &str, ext: &str, body: &str) -> Result<PathBuf>;
pub fn load_at(dir: &Path, name: &str) -> Result<WorkflowManifest>;
pub fn load(name: &str) -> Result<WorkflowManifest>;
pub fn list_at(dir: &Path) -> Result<Vec<WorkflowMeta>>;
pub fn list() -> Result<Vec<WorkflowMeta>>;
pub fn delete_at(dir: &Path, name: &str) -> Result<bool>;
pub fn delete(name: &str) -> Result<bool>;
```

写入是原子的（temp-file + rename）——读取器永远不会看到撕裂的写入。`resolve_path_at` 用 `canvas_io::sanitise_name` 防止路径穿越。

### Claude Code 互操作性（`src/workflow/interop/`）

`interop` 模块在 Aleph 的 `WorkflowDef` 与 Claude Code 的 `.workflow.js` 工程格式之间做双向翻译：

**导入** (`parse_workflow_js`)——三条路径，按优先级排序：
1. **裸清单 JSON**（以 `{` 开头）→ 精确解析，无损失
2. **嵌入块**（`/* @aleph-workflow {json} */`）→ 精确解析，无损失
3. **裸 `.workflow.js`** → 对纯字面量 `meta` 块 + 有序 `phase()` / `agent()` 调用进行轻量级扫描；命令式构造进入 `dropped`

**导出** (`render_workflow_js`)——把清单渲染为 `.workflow.js` 源字符串：
1. 无损往返头（`/* @aleph-workflow {json} */`）
2. `meta` 块（纯字面量）
3. 主体：拓扑层 → `parallel()` / 顺序 `agent()` 骨架

**Bare-scan schema-const 解析**（R3 兼容）：工程格式把 schema hoist 成顶层 `const` 再按名引用；裸扫描经 `interop/consts.rs` 的**有界数据字面量归一化器**解析 hoisted const（及 inline schema），把 JS-lax 写法（裸键 / 单引号 / 尾逗号）归一为 JSON；遇任何表达式值（标识符 / 函数调用 / 模板串 / 计算键）整个 schema **弃权**并记 `dropped`。

### MetaSkill 提案（`src/workflow/proposal.rs`）

`proposal` 模块在活动工作流存储之上实现了**门控草稿层**。梦境管道挖掘重复的技能共现，并在 `proposals/` 中起草候选工作流。提案**永远不会**是活动工作流——只有在显式 `accept` 之后（"提案门控"）才会运行：

```rust
pub fn list_proposals() -> Result<Vec<WorkflowMeta>>;
pub fn accept(name: &str) -> Result<PathBuf>;  // 将草稿提升为活动状态
```

这保持了循环的 R5 安静——能力在后台增长，但没有任何东西自动激活，也没有任何窃取焦点。

## 工作流示例

```json
{
  "name": "research-report",
  "description": "Research a topic and write a report",
  "steps": [
    {
      "id": "gather",
      "agent": "researcher",
      "prompt": "Research the topic: {input}. Collect key facts, sources, and perspectives."
    },
    {
      "id": "ask-focus",
      "prompt": "What angle should the report take?",
      "kind": "clarify",
      "choices": ["Technical deep-dive", "Executive summary", "Critical analysis"],
      "depends_on": ["gather"]
    },
    {
      "id": "write",
      "agent": "writer",
      "prompt": "Write a report on {input} based on the research and the chosen angle.",
      "depends_on": ["ask-focus"],
      "timeout_seconds": 900,
      "max_retries": 1
    },
    {
      "id": "review",
      "agent": "editor",
      "prompt": "Review the report for clarity, accuracy, and completeness. Suggest improvements.",
      "depends_on": ["write"],
      "review": true
    }
  ]
}
```

这定义了一个菱形工作流：研究 → 澄清 → 写作 → 审阅。Clarify 步骤暂停执行以向用户询问焦点方向；`review: true` 让 lead review 决定完成与否。

## 执行流程

```
用户运行 workflow(action='run', name='research-report', input='quantum computing')
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 网关：workflow 工具处理程序                          │
│   • 从存储加载 WorkflowManifest                      │
│   • WorkflowManifest::to_def → WorkflowDef            │
│   • WorkflowDef::validate                            │
│   • 确保团队存在                                     │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 工作流编译器（compile::materialize）                  │
│   • 拓扑排序步骤（Kahn）                              │
│   • 为每个 step 创建 coord_task                      │
│   • 映射 depends_on → blocked_by                     │
│   • 替换 {input}；盖 strategy / model / effort 元数据│
│   • 标记为 dispatcher-managed                         │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ TeamDispatcher（src/teams/dispatcher/）              │
│   • 拾取待处理任务                                    │
│   • 对 agent 步骤：路由到 agent 字段指定的代理        │
│   • 对 clarify 步骤：CLARIFY_OWNER 停放              │
│   • 从上游输出构建交接上下文                          │
│   • 使用 Tokio 并发执行                              │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 入站路由器（用户回复澄清时）                          │
│   • 从回复解析会话                                    │
│   • 完成停放的澄清任务                                │
│   • 解除下游步骤的阻塞                                │
└─────────────────────────────────────────────────────┘
```
