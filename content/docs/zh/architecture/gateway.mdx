网关是与 Aleph 通信的单一入口点。它在 `ws://127.0.0.1:18790/ws` 上运行 WebSocket 服务器，使用 JSON-RPC 2.0，并将来自任何连接客户端（无论是原生 macOS 应用、Telegram 机器人还是终端 CLI）的请求路由到适当的处理程序。本页涵盖协议层、消息管道、多频道路由、为实时流式传输提供支持的事件系统，以及自签名 TLS + 客户端 TOFU 信任、单源错误回执等硬化机制。

要了解请求到达后如何管理会话，请参阅[会话服务](./session-service)。要了解路由到达代理后会发生什么，请参阅[代理工具链](./harness)。

## 网关组件

```
┌─────────────────────────────────────────────────────────────────────┐
│                        网关服务器                                    │
│                  ws://127.0.0.1:18790/ws                            │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐        │
│  │   入站       │     │   处理程序   │     │   出站       │        │
│  │   路由器     │ ──▶ │   注册表     │ ──▶ │   发射器     │        │
│  │              │     │              │     │              │        │
│  │ • 解析请求   │     │ • 路由       │     │ • 流式传输   │        │
│  │ • 验证       │     │ • 执行       │     │ • 事件       │        │
│  └──────────────┘     └──────────────┘     └──────────────┘        │
│                                                                     │
│  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐        │
│  │   会话       │     │    事件      │     │  频道        │
│  │   管理器     │     │    总线      │     │  注册表      │
│  │              │     │              │     │              │
│  │ • SQLite     │     │ • 发布/订阅  │     │ • Telegram   │
│  │ • 压缩       │     │ • 主题       │     │ • Discord    │
│  │ • 历史       │     │ • 订阅       │     │ • iMessage   │
│  └──────────────┘     └──────────────┘     └──────────────┘        │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

网关有六个核心组件：

- **入站路由器** — 解析传入的 JSON-RPC 帧，验证结构，并分派到正确的处理程序
- **处理程序注册表** — 将方法名（如 `agent.run`、`session.list`）映射到处理函数
- **出站发射器** — 将流式事件和最终响应发送回客户端
- **会话管理器** — 在 SQLite 中持久化对话历史（`session.*` RPC 仍走 `SessionManager`，`session_events` 表是单一源，由 `src/session/` 的 actor 写入）
- **事件总线** — 支持 glob 模式订阅的实时事件分发发布/订阅系统
- **频道注册表**（`ChannelRegistry`）— 跟踪活动聊天集成（Telegram、Discord、iMessage 等），不再使用旧 `InterfaceRegistry` 名称

## JSON-RPC 2.0 协议

所有通信都使用基于 WebSocket 帧的 [JSON-RPC 2.0](https://www.jsonrpc.org/specification)。有三种消息类型。

### 请求（客户端到网关）

```json
{
  "jsonrpc": "2.0",
  "id": "uuid-xxx",
  "method": "agent.run",
  "params": {
    "message": "Hello, what can you do?",
    "session_key": "agent:main:main"
  }
}
```

`id` 字段是客户端生成的 UUID。网关在响应中返回相同的 `id`，以便客户端可以将请求与响应匹配。

### 响应（网关到客户端）

```json
{
  "jsonrpc": "2.0",
  "id": "uuid-xxx",
  "result": {
    "run_id": "run-123",
    "status": "running"
  }
}
```

对于 `agent.run`，初始响应确认运行已启动。实际的 AI 输出通过流式事件到达。

### 事件（网关到客户端，无 id）

```json
{
  "jsonrpc": "2.0",
  "method": "event",
  "params": {
    "topic": "stream.chunk",
    "data": {
      "run_id": "run-123",
      "content": "Hello! I can help you with..."
    }
  }
}
```

事件是服务器发起的通知（无 `id` 字段）。客户端通过 `events.subscribe` 方法订阅事件主题。

## 消息管道

当 WebSocket 帧到达时，网关通过分层中间件管道处理它：

```
WebSocket 帧
    │
    ▼
┌────────────────────────────────┐
│ 1. 帧解析                      │
│    • 反序列化 JSON-RPC         │
│    • 验证结构                  │
│    • 提取方法 + 参数           │
└────────────────┬───────────────┘
                 │
                 ▼
┌────────────────────────────────┐
│ 2. 中间件管道                  │
│    • TraceLayer (跨度/请求-id) │
│    • MetricsLayer (计时)       │
│    • AuthLayer (认证检查)      │
│    • RateLimitLayer (配额)     │
│    • ValidateLayer (模式)      │
│    • HandlerService (分发)     │
└────────────────┬───────────────┘
                 │
                 ▼
┌────────────────────────────────┐
│ 3. 处理程序分发                │
│    • 在注册表中查找方法        │
│    • agent.run → ExecutionEngine│
│    • session.* → SessionManager│
│    • config.* → ConfigManager  │
└────────────────┬───────────────┘
                 │
                 ▼
┌────────────────────────────────┐
│ 4. 执行                        │
│    • 处理程序处理请求          │
│    • 可能生成 AgentLoop        │
│    • 通过 EventBus 流式传输事件│
└────────────────┬───────────────┘
                 │
                 ▼
┌────────────────────────────────┐
│ 5. 响应                        │
│    • JSON-RPC 结果帧           │
│    • 或 JSON-RPC 错误帧        │
└────────────────────────────────┘
```

中间件管道按此顺序为每个 JSON-RPC 请求运行：

1. **TraceLayer** — 附加请求跨度和跟踪 ID 以实现可观察性
2. **MetricsLayer** — 记录请求计时和方法级指标
3. **AuthLayer** — 验证认证（当 `auth.mode = "none"` 时跳过）
4. **RateLimitLayer** — 强制执行每个身份、每个范围的速率限制
5. **ValidateLayer** — 在到达处理程序之前验证请求模式
6. **HandlerService** — 分发到注册的处理程序进行执行

## 多频道路由

Aleph 同时支持多个聊天接口。每个接口（Telegram、Discord、iMessage 等）将其平台特定的消息转换为统一的 JSON-RPC 协议，并将其转发到网关。

### 频道适配器（`src/gateway/channel.rs`）

每个频道适配器实现 `Channel` trait；不通过功能标志开启，按需在运行时通过 `[channels.<type>]` 注册到 `ChannelRegistry`：

```rust
#[async_trait]
pub trait Channel: Send + Sync {
    fn info(&self) -> &ChannelInfo;
    fn state(&self) -> &ChannelState;
    fn id(&self) -> &ChannelId;
    fn capabilities(&self) -> &ChannelCapabilities;
    async fn health(&self) -> ChannelHealth;
    async fn start(&mut self) -> ChannelResult<()>;
    async fn stop(&mut self) -> ChannelResult<()>;
    async fn send(&self, message: OutboundMessage) -> ChannelResult<SendResult>;
    async fn send_typing(&self, conversation_id: &ConversationId) -> ChannelResult<()>;
    fn approval_capability(&self) -> Option<Arc<dyn ChannelApprovalCapability>>;
}
```

内置适配器通过 `ChannelFactory` 注册到 `interfaces::register_channel_plugins`；未在该表注册的工厂不会被 `[channels.<type>]` 选中。`imessage` 和 `cli` 不走工厂表——iMessage 由 `initialize_channels` 直接构造，CLI 不是可配置频道。

### 可用接口

| 接口 | 位置 | 平台 |
|-----------|------|----------|
| CLI | `interfaces/cli/` | 所有平台 |
| Telegram | `src/gateway/interfaces/telegram/` | 所有平台 |
| Discord | `src/gateway/interfaces/discord/` | 所有平台 |
| iMessage | `src/gateway/interfaces/imessage/`（Local + BlueBubbles 两种传输） | Local 仅 macOS，BlueBubbles 任意 |
| Slack / Matrix / Mattermost / Signal / IRC / Nostr / XMPP / Email / Webhook / WeChat / Feishu / Line / QQ / MS Teams | `src/gateway/interfaces/<name>/` | 各平台 |
| WebChat | 内置于 `aleph-server`（由 `rust_embed` 嵌入） | 所有平台 |

### 会话键解析

每个频道生成一个唯一的会话键，决定对话是共享还是隔离（格式由 `DmScope` 与 `PeerKind` 决定，详见 [`src/routing/session_key.rs`]）：

| 会话键格式 | 用例 |
|-------------------|----------|
| `agent:main:main` | 跨频道共享会话（`DmScope::Main` 或主会话） |
| `agent:main:dm:user123` | 每用户隔离 DM（`DmScope::PerPeer`，**默认**） |
| `agent:main:telegram:dm:user123` | 每频道每用户 DM（`DmScope::PerChannelPeer`） |
| `agent:main:discord:group:guild-id` | Discord 服务器频道（群组） |
| `agent:main:cron:daily-summary` | Cron 作业 / webhook（任务） |
| `subagent:agent:main:translator` | 子代理委托（子代理） |
| `agent:main:ephemeral:uuid` | 临时的，不持久化（短暂） |

DM 范围可以按接口配置：

```rust
pub enum DmScope {
    Main,           // 所有 DM 共享主会话
    PerPeer,        // 每个用户隔离的会话（默认）
    PerChannelPeer, // 按频道 + 用户隔离
}
```

## 事件系统

EventBus 提供用于实时事件分发的发布/订阅机制。客户端使用 glob 模式订阅。

### 事件主题

| 模式 | 事件 |
|---------|--------|
| `stream.*` | 所有流式事件 |
| `stream.chunk` | 文本内容块 |
| `stream.agent_trace` | 结构化循环发起的执行跟踪 |
| `stream.tool_start` | 工具执行开始 |
| `stream.tool_end` | 工具执行完成 |
| `agent.*` | 代理生命周期事件 |
| `agent.started` | 运行开始 |
| `agent.completed` | 运行完成 |
| `agent.error` | 运行错误 |
| `session.*` | 会话事件 |
| `config.*` | 配置更改事件 |
| `system.tick` | 定期心跳（正常运行时间、连接、状态版本） |
| `system.shutdown` | 服务器关闭通知 |

### 订阅事件

```json
{
  "jsonrpc": "2.0",
  "id": "sub-1",
  "method": "events.subscribe",
  "params": { "pattern": "stream.*" }
}
```

订阅后，客户端接收所有匹配的事件作为服务器发起的通知，直到取消订阅。

## 连接生命周期

### 认证流程

```
客户端 WebSocket 连接
    │
    ▼
┌─────────────────────────────────┐
│ 环回连接？                       │
│   是 → 零配置 operator           │
│         （无需凭据）             │
│   否  → 第一帧必须是             │
│         "connect" 方法          │
└─────────────────────────────────┘
    │
    ▼ (远程)
┌─────────────────────────────────┐
│ resolve_connect_auth            │
│   1. 设备令牌 (aleph-dt-*)     │
│      —— 已配对设备长期令牌       │
│   2. 引导票据 (aleph-bt-*)      │
│      —— 5 分钟单次使用           │
│   3. 共享 Gateway 令牌           │
│      (aleph-<uuid>, HMAC)       │
└─────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────┐
│ 授权 → 角色 = operator          │
│   WS 派发接收所有方法            │
│   远程 WS 接 4001 关闭           │
│   （设备撤销 / 令牌轮换）        │
└─────────────────────────────────┘
```

默认绑定 `127.0.0.1`（仅环回），环回即零配置 operator。设 `[gateway] host = "0.0.0.0"` 开放局域网后，远程连接**必须**在 `connect` 帧上呈现有效凭据；`is_loopback` 判断读取原始 socket 端点，不解析 `X-Forwarded-For`（防伪）。授权完成即可获得完整 operator 权限（与本地等同）；远程 WS 在令牌轮换（`gateway.token.rotate`）或设备撤销（`gateway.devices.revoke`）时被即时踢出。

### Connect 请求

远程连接必须将 `connect` 消息作为第一帧发送：

```json
{
  "method": "connect",
  "params": {
    "minProtocol": 1,
    "maxProtocol": 1,
    "client": {
      "id": "macos-app",
      "version": "1.0.0",
      "platform": "macos"
    },
    "device_token": "aleph-dt-...",
    "bootstrap_ticket": "aleph-bt-..."
  }
}
```

> 环回客户端省略 `device_token` / `bootstrap_ticket` 字段。远程客户端首配对时发送 `bootstrap_ticket`（换取 `device_token` 回执），后续重连发送 `device_token`。`token`（旧版共享 Gateway 令牌）仍作为兜底接受。`device_id` 由客户端声明，与集群节点共用 namespace，因此会被拒与同名非 Panel 设备。

## OpenAI 兼容路由

除了 WebSocket JSON-RPC API 外，网关还在同一端口 (`18790`) 上暴露 OpenAI 兼容的 HTTP API（`src/gateway/openai_api/`）。这允许使用 OpenAI API 格式的现有客户端和工具无需修改即可连接到 Aleph。

| 路由 | 方法 | 说明 |
|-------|--------|-------------|
| `/v1/models` | GET | 列出可用模型 |
| `/v1/models/{model_id}` | GET | 获取模型详情 |
| `/v1/chat/completions` | POST | 聊天完成（流式 + 非流式） |
| `/v1/embeddings` | POST | 文本嵌入 |
| `/v1/responses` | POST | OpenAI 响应 API |
| `/v1/health` | GET | API 健康检查 |

这些路由支持 bearer 令牌认证（与 WebSocket 共享令牌机制）。在 `[gateway] allow_insecure_remote = false` 的默认策略下，远程连接必须经过 TLS；非环回明文连接会被网关拒绝。

## 热重载

网关监视 `~/.aleph/config/aleph.toml` 的更改并应用它们而不重启：

```
~/.aleph/config/aleph.toml 修改
    │
    ▼
┌─────────────────────────────────┐
│ 去抖 (500ms)                    │
└─────────────────┬───────────────┘
                  │
                  ▼
┌─────────────────────────────────┐
│ 解析 + 验证新配置               │
└─────────────────┬───────────────┘
                  │
                  ▼
┌─────────────────────────────────┐
│ 应用更改：                      │
│ • 重启受影响的频道              │
│ • 更新路由规则                  │
│ • 发出 config.changed 事件      │
└─────────────────────────────────┘
```

`[execution]` 下的运行上限（`max_runs_global` / `max_runs_per_agent`）通过 arc-swap 全局信号量热重载，无需重启。

## HTTP 端点

除了 WebSocket 服务器外，网关还在同一端口上提供 HTTP 端点：

| 端点 | 用途 |
|----------|---------|
| `/ws` | WebSocket 升级端点 |
| `/health` | 健康检查（返回 200 OK） |
| `/metrics` | Prometheus 兼容指标 |
| `/` | 内置 WebChat UI 的静态文件 (ControlPlane) |
| `/login` | 会话 cookie 登录页面 |
| `/auth/login` | 登录表单提交 |
| `/auth/logout` | 注销（清除会话 cookie） |

启用 A2A（代理到代理）时，额外的 A2A 路由会挂载在同一 HTTP 服务器上。

## 26.7.x 补充

### 网关核心地位

`aleph-server` 进程内 gateway 处理：

- **WebSocket 协议**（JSON-RPC 2.0 over ws/wss）
- **TLS**（自签名或用户提供，axum-server in-process 终止）
- **认证**（环回零配置 operator / 设备令牌 / 引导票据 / 共享令牌 / WS Origin 校验）
- **路由**（chat / config / memory / agents / tools / mcp / skills / plugins / extensions / channels / teams / projects / workspaces / runtimes / voice / artifacts / hub / strategy / goal / loop / ...）
- **完整 RPC（详见 [方法参考](/docs/zh/gateway/methods)）**

### 单源错误回执

26.7.21+：执行错误统一通过 `ExecutionError::user_receipt(locale)`（位于 `src/gateway/execution_engine/`）转换为带稳定错误码与本地化短消息的用户回执，作为网关给 Panel / 频道的**单一来源**。原始类型化错误链不外泄——`src/bin/aleph-server/server_init.rs` 的 RPC 处理器与频道回执路径都通过同一函数取数，避免「两条错误冒泡」。

### WS 任务泄漏修复

26.7.21+（见 `src/gateway/server/handler.rs::forward_bus_to_client`）：每连接事件转发任务在 `try_send` 失败时立即退出，不再持全局 `broadcast::Receiver` 到进程退出；`RecvError::Lagged(n)` 不再被视为致命（落入溢出指标、由 ping/idle watchdog 触发 1008 重连）；webhook 反压返回 503 而不是默默丢弃。

### 自签名 TLS + 客户端 TOFU

26.7.17 引入 in-process TLS（`src/gateway/tls.rs`），26.7.18 引入 SAN 自动发现 + drift sidecar，Panel 端 WKWebView 适配器（macOS 参考平台 + iOS Keychain 镜像）实现 **TOFU 证书信任**（fingerprint + SAN 审批 + 固定信任存储）。配置：

- `[gateway.tls]` —— 自签名或用户提供（`cert` / `key` 留空 → 自动生成）
- `[gateway] trusted_proxy` —— 反向代理真实 IP
- `[gateway] allow_insecure_remote = false`（默认）—— 失败关闭

### 设备 / 凭据 / 票 / 令牌 RPC

26.7.21 在 `HandlerRegistry` 中注册：

- `gateway.credentials`
- `gateway.identity.get`
- `gateway.metrics.lanes` / `gateway.metrics.run_concurrency`

`gateway.token.current` / `gateway.token.rotate` / `gateway.devices.list` / `gateway.devices.revoke` 通过启动期 `gateway_state` 注入（见 `src/gateway/handlers/mod.rs` 的 boot-phase 注册块）。
