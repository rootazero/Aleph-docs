Aleph 网关是客户端与 agent、工具、工作流之间的控制平面：它接受连接、裁决调用方身份、把请求路由到对应的处理程序，并把内部产生的事件按主题广播给订阅者。本页只讲这些机制在当前代码里的实际形态；报文格式见 [Protocol v1](../gateway/protocol-v1)，凭据与配对见 [认证](../gateway/auth)，方法清单见 [方法参考](../gateway/methods/index)。

## 网关的职责

网关进程把三件事收敛在一起：

- **接入连接**：HTTP 路由表在 `src/gateway/server/mod.rs:1133` 组装。`/ws` 是 WebSocket 升级入口，`/health`、`/ready`、`/metrics` 是运维探针，其余请求落到控制面（`control_plane`）。面板静态资源、artifacts、canvas、attachments 与受限的浏览器 viewer 各自作为独立路由合并进来。同一个路由器上还合并了 OpenAI 兼容的 HTTP 面（`src/gateway/openai_api/router.rs`）：`/v1/models`、`/v1/models/{model_id}`、`/v1/chat/completions`、`/v1/embeddings`、`/v1/responses`、`/v1/health`。
- **执行请求**：JSON-RPC 2.0 请求经中间件链进入方法注册表，落到具体处理程序。
- **广播事件**：内部产生的事件进入 `src/gateway/event_bus.rs` 的总线，按主题投递到订阅了该主题的连接。

## 传输入口

三个入口共用同一套 RPC 执行与事件分发内核，差别在传输、认证方式和可见的方法范围。

| 入口 | 传输 | 认证方式 | 可用方法范围 | 上限 | 代码位置 |
|------|------|----------|--------------|------|----------|
| `/ws` | WebSocket（历史兼容入口） | `connect` 握手换角色 | 完整 RPC 方法集 | 状态上的 `max_connections`；另有按客户端 IP 的并发上限，loopback 豁免 | `src/gateway/server/connection/upgrade.rs` |
| Desktop IPC | Unix domain socket | 同账号（`require_same_user`） | 只读：`system.hello`、`health`、`sessions.list` | `MAX_CONNECTIONS=8`、`WIRE_BUDGET=16 MiB`、`WRITE_TIMEOUT=5s` | `src/gateway/server/connection/local_ipc.rs` |
| Web v1 | 原生 TLS 上的 WebSocket | `POST /v1/session` 换会话 cookie | 完整 RPC 方法集 | `MAX_MESSAGE=1 MiB`、`MAX_SESSIONS=256`、`MAX_SOCKETS=8`、TTL 300s | `src/gateway/server/connection/web_v1.rs` |

### 兼容 WebSocket 入口

`/ws` 是最早的入口，仍在生产路径上，但按现行口径它承担的是历史兼容角色；Protocol v1 的目标入口是下面两个。升级逻辑在 `src/gateway/server/connection/upgrade.rs` 的 `ws_upgrade_handler`，进入连接后走完整 RPC 方法集。

升级前有三道拒绝：

| 条件 | 拒绝 |
|------|------|
| 远端明文（未启用 TLS，且未放行 `allow_insecure_remote`） | 426 `TLS required for remote connections` |
| `Origin` 不被状态上的 `origin_policy` 允许 | 403 `origin not allowed` |
| 全局连接数达到状态上的 `max_connections` | 503 `Connection limit reached` |

按客户端 IP 的并发连接上限对 loopback 豁免，因为面板与本机 CLI 会同时开多条连接。状态上的 `max_connections` 与 `origin_policy` 定义在 `src/gateway/server/mod.rs`。受信代理带来的真实客户端 IP 由 `parse_trusted_ips` 解析——只接受裸 IP，不接受 CIDR。

### Desktop IPC 入口

Desktop IPC 是给桌面宿主用的只读入口：Unix domain socket，同账号才能连上。入口由启动参数指定：`--desktop-ipc <socket>`（`src/bin/aleph-server/cli.rs:54`），服务端在 `src/gateway/server/mod.rs:1424` 的 `run_with_desktop_ipc` 里挂起监听。

连接建立后的约束（`src/gateway/server/connection/local_ipc.rs`）：

- **同账号**：`require_same_user`（`shared/client/src/local_ipc.rs:181`）校验对端 uid，不匹配直接断开。
- **首帧必须是 `system.hello`**：否则回 `AUTH_REQUIRED` / `system.hello must be first`。
- **方法白名单**：`execute` 只放行 `health` 与 `sessions.list`，其余回 `METHOD_NOT_FOUND` / `method not mounted on Desktop IPC`。
- **身份**：角色取自 `active_desktop_owner`，调用方用户固定为 `OWNER_USER_ID`。
- **不授予网络权限**：连接的 origin 记为 `NO_NETWORK_ORIGIN`（0.0.0.0），因此它拿不到任何要求网络来源的权限。

资源上限：

| 常量 | 值 | 含义 |
|------|-----|------|
| `MAX_CONNECTIONS` | 8 | 同时在线的 Desktop IPC 连接数 |
| `WIRE_BUDGET` | 16 MiB | 单连接可同时占用的线上字节预算，信号量许可按帧长扣减 |
| `WRITE_TIMEOUT` | 5s | 单次写超时 |
| `MAX_FRAME_BYTES` | 8 MiB | 单帧载荷上限（`shared/client/src/local_ipc.rs`） |
| `MAX_INFLIGHT` | 8 | 单连接在途请求数（`shared/client/src/local_ipc.rs`） |

响应超过 `MAX_FRAME_BYTES` 时回 `INTERNAL_ERROR` / `response exceeds Desktop IPC limits`。

### Web v1 入口

Web v1 是 Protocol v1 的目标网络入口：原生 TLS 上的 WebSocket，凭据用一次性交换拿到，而不是把长期令牌直接放进查询参数。

两步：

1. `POST /v1/session` 换会话凭据。请求体是 `{"device_token": "..."}` 或 `{"bootstrap_ticket": "..."}`（`Credentials` 枚举，`src/gateway/server/connection/web_v1.rs`）。校验通过后返回 204，并下发 `Set-Cookie: __Host-aleph-v1=<uuid>; Secure; HttpOnly; SameSite=Strict; Path=/; Max-Age=300`，同时带 `Cache-Control: no-store`。
2. `GET /v1/ws` 升级成 WebSocket。凭据由 cookie 携带（`cookie_handle`），子协议是 `aleph.protocol.v1`。

两道前置门：

- **同源**：`same_origin` 要求请求不带 query、`Origin` 恰好等于 authority 的 https origin，且 authority 里不含 `@ / \ ? #`；不满足回 403。
- **限速**：`throttle` 按客户端 IP 以 `RateLimitScope::Auth` 计配额，超限回 429。

会话绑定在 `WebBinding` 上（`store`、`origin`、`token_id`、`device_id`、`user`、`expires`）。`current_role` 在绑定过期时返回 `None`，并且每次都要用 `active_device_principal` 复查设备令牌是否仍然有效、归属用户是否仍然一致。

## 连接与身份

### 登录墙

连接被接受时就进入连接表，此时它还没有任何权限，角色是 `guest`。真正的授权发生在 `connect` 之后。

`wall_admits`（`src/gateway/server/connection/auth.rs:64`）是唯一的授权判定：

```rust
pub fn wall_admits(role: Option<&str>, method: &str) -> bool {
    matches!(role, Some("operator" | "member")) || method == "connect"
}
```

持有 `operator` 或 `member` 角色的连接可以发任何方法；`guest` 只能发 `connect`。未授权连接收到的提示是同文件 `:13` 的 `LOGIN_WALL_MESSAGE`：`Not authorized: present a valid Gateway token via \`connect\` to access this core.`

同一个谓词用在两个方向：请求分发前查一次，事件投递前再查一次。只在一个方向上判定，未授权连接就会收到本该被挡住的事件。

### 握手 system.hello

`system.hello`（`src/gateway/handlers/system_hello.rs`）是 Protocol v1 的握手。它只做协议协商，不授予任何权限。

请求：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "system.hello",
  "params": {
    "protocol": { "major": 1, "minor": 0 },
    "client": {
      "name": "aleph-nsh-desktop",
      "version": "0.1.0",
      "platform": "linux",
      "ui_runtime": "nsh"
    },
    "features": ["event_replay", "snapshot", "binary_channel"]
  }
}
```

响应：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocol": { "major": 1, "minor": 0 },
    "server": { "name": "aleph-server", "version": "26.9.1" },
    "connection_id": "conn-...",
    "features": [],
    "limits": { "max_message_bytes": 8388608, "max_inflight_requests": 128 }
  }
}
```

- `params` 缺失或解析失败回 `INVALID_PARAMS`。
- major 版本不同回 `INVALID_PARAMS` / `incompatible protocol major version`；major 相同则取双方 minor 的较小值（`negotiate_version`，`shared/protocol/src/system_hello.rs`）。
- `features` 是「客户端请求 ∩ 服务端实现」的交集（`negotiate_features`）。当前服务端传入的实现列表是空的，因此协商结果恒为空数组——客户端不能因为握手里列了 `snapshot` 就假定该特性可用。
- `limits` 是提示值而不是传输层强制限制，源码注释写明 `legacy wire hints, not enforced transport limits`。真正生效的帧长限制在 Desktop IPC 侧（`MAX_FRAME_BYTES` 与 `MAX_INFLIGHT`）。
- `server.version` 取编译期常量 `ALEPH_VERSION`。

## 请求分发

一次请求的处理顺序：

```
连接收帧
  → JSON 解析（serde）
  → 角色与权限判定（wall_admits、method_requires_admin）
  → 幂等键与通道规划（rpc::prepare）
  → 中间件链（validate → rate_limit → auth → metrics → trace）
  → 方法注册表查找（HandlerRegistry::handle）
  → 处理程序
  → 响应
```

### 派发入口

`src/gateway/server/connection/dispatch.rs` 提供三条入口：

- `dispatch_for_connection`：旧 `/ws` 路径。`capabilities.ui.invoke` 特判——先用 `live_ui_caller` 取当前真实调用方，取不到就回 `viewer_denied_response`，避免用握手时的快照冒充。
- `dispatch_for_peer`：Desktop IPC 与 Web v1 路径。
- `dispatch_with_caller_context`：内部调用路径。

三者最终都汇到 `dispatch_ordinary` → `validate_live` → `dispatch_snapshot`。`dispatch_snapshot` 从同一次 `ConnectionState` 读里取出角色、用户、已验证用户与设备 id（`CallerSnapshot`），避免分次读取带来的身份漂移。

### 运行期角色门控

`process_request`（同文件 `:511`）是单一 chokepoint：

- JSON 解析失败回 `PARSE_ERROR` / `Parse error: {e}`。
- `method_requires_admin` 命中且调用方是 member 时，回 `AUTH_REQUIRED` 与 `ADMIN_REQUIRED_MESSAGE`：`Not authorized: this method requires operator privileges`。`None`（内部调用）与 `operator` 放行，`guest` 在登录墙那一层就被挡掉了。
- 随后从请求参数里取出 `traceparent` 或新建根 trace，方法名、trace id、span id 进入同一条 span。

`method_requires_admin`（`src/gateway/method_admin.rs:544`）的判定顺序是：`ADMIN_METHODS` 命中即需管理员；`MEMBER_CARVE_OUTS` 命中则豁免；否则按 `ADMIN_PREFIXES` 前缀匹配。

### 方法注册表

方法注册表是 `HandlerRegistry`（`src/gateway/handlers/mod.rs:1229`）。`register` 把方法名映射到处理程序；查不到方法回 `METHOD_NOT_FOUND` / `Method not found: {method}`。批量注册用 `register_handler!` 宏，定义在 `src/bin/aleph-server/commands/start/builder/handlers/mod.rs:35`。

`src/gateway/method_census.rs` 把「哪些方法已注册、各自属于 Open 还是 Admin」做成可执行的普查：它扫描生产代码里的注册调用，为每个方法钉住当前裁决；新增方法或翻转任一条目都会让普查测试失败，直到有人显式记录裁决。

`src/gateway/method_visibility.rs` 是另一张表，形状不同：它记录「方法的返回值是否依赖调用方是谁」，并在每个处理程序里以 `visibility` 谓词落实。它本身不是派发门——数据可见性必须在处理程序内部按会话归属判断。

### 中间件链

`MiddlewareChain::serve_with_panel_context`（`src/gateway/middleware/chain.rs:96`）自外向内是：

| 层 | 文件 |
|----|------|
| `validate` | `src/gateway/middleware/validate.rs` |
| `rate_limit` | `src/gateway/middleware/rate_limit.rs` |
| `auth` | `src/gateway/middleware/auth.rs` |
| `metrics` | `src/gateway/middleware/metrics.rs` |
| `trace` | `src/gateway/middleware/trace.rs` |
| `HandlerService` | `src/gateway/middleware/handler_service.rs` |

链本身报错时回 `INTERNAL_ERROR` / `Middleware chain error`。中间件里的限速会产生 `RATE_LIMITED`。

### 通道与幂等

每个方法被映射到一条通道（lane）：`Query`、`Execute`、`Mutate`、`System`（`src/gateway/lane.rs:37`）。映射顺序是显式覆盖表优先，其次按方法名最后一段的后缀启发式（`get`/`list`/`subscribe` 等归 `Query`，`install`/`uninstall` 归 `System`，`run`/`send`/`invoke`/`execute` 归 `Execute`），最后兜底到 `Mutate`。兜底选 `Mutate` 是有意的：源码注释说明旧实现兜底到 `Query`，会让没被覆盖到的副作用方法绕过幂等保护。

`rpc::prepare`（`src/gateway/server/connection/rpc.rs:63`）负责幂等键与通道许可：

- `idempotency_key` 里含保留分隔符会被拒，回 `INVALID_PARAMS`。
- 要求幂等键的通道缺键时回 `IDEMPOTENCY_KEY_REQUIRED` / `idempotency_key required for mutating RPCs`，`data` 里带 `method`、`lane` 和提示。
- 幂等槽位按「调用方 + 方法 + 键」命名空间化，浏览器 viewer 方法用独立前缀，避免与其他用户撞槽。

执行阶段：

- 拿不到通道许可时回 `INTERNAL_ERROR` / `Service congested, try again later`。
- 重复请求等待在途副本超过 30 秒时回 `Request timed out waiting for in-flight duplicate`。

## 事件出口

### 两种线上形态

服务端把内部事件封装成 JSON-RPC 通知发给客户端。事件走两条不同的线上形态（`src/gateway/event_bus.rs:423` 的 `publish_frame`）：

| 帧类型 | 线上形态 |
|--------|----------|
| 有 `stream_method()` 的帧 | 直接发通知 `{"jsonrpc":"2.0","method":"stream.run_complete","params":帧体}` |
| 没有 `stream_method()` 的帧 | 先发裸事件 `{"topic":"...","data":帧体}`，投递层再包装成 `{"jsonrpc":"2.0","method":"event","params":{"topic":"...","data":...}}` |

第二种形态的 `event` 就是 `TOPIC_EVENT_METHOD`（`shared/protocol/src/jsonrpc.rs:85`），包装发生在 `src/gateway/server/connection/forward.rs:228` 的 `event_wire_form`。

规范主题名与线上方法名是两套命名：规范名（`agent.run.complete`）主要出现在 `source_topic` 诊断字段里，线上订阅用的是 `stream.*`。完整的对照表见 [事件主题册](../gateway/methods/events)。

### 投递过滤链

一帧事件要送达某个连接，必须逐层通过 `src/gateway/server/connection/mod.rs:1373` 起的过滤链：

1. `pty::manager::frame_admits`——PTY 帧按会话归属裁决。
2. `ui_display_admits_connection`——`capabilities.ui.display` 另查一次显示挂载。
3. `wall_admits`——登录墙，与请求方向同一个谓词。
4. `can_receive`（`src/gateway/event_scope.rs`）——按主题前缀的粗粒度作用域。
5. `surface::delivery::audience_allows`——按投递受众。
6. `should_receive`（`src/gateway/handlers/events.rs`）——该连接是否订阅了这个主题。
7. `event_admits_for`（`src/gateway/event_visibility.rs`）——逐帧按归属裁决。

`stream.running_set_changed` 是链上唯一的「投影」帧：它被放行，但数组会按连接裁剪（`project_for`），每个连接只看到与自己相关的运行集。

### 作用域与可见性

两道机制分工不同：

- `src/gateway/event_scope.rs` 是**粗粒度前缀规则**。`default_rules` 只登记了几条前缀（`pairing.`、`guest.`、`config.changed`、`node.`、`pty.`），命中的前缀要求调用方持有管理员作用域；没有规则命中的主题默认放行。`scope_for_role` 对 operator 返回 `["*"]`，对其他角色返回空。
- `src/gateway/event_visibility.rs` 是**逐帧归属裁决**。`classify` 把主题和数据映射成一种 `SessionIdentity`（`BySessionKey`、`ByRunId`、`ByTeamId`、`ByUserId`、`ByCanvasScope`、`ByProjectScope`、`ByPtySession`、`OperatorOnly` 等），`event_admits_for` 按调用方身份逐帧重算。`session_identity_of` 在 `classify` 没命中时返回 `Global`，与作用域规则的默认放行一致。

具体到每个主题归谁，见 [事件主题册](../gateway/methods/events) 的可见性一节。

### 订阅与退订

`events.subscribe`、`events.unsubscribe`、`events.list` 不走方法注册表，而是在连接循环里被单独拦截（`src/gateway/server/connection/mod.rs:630`），处理器在 `src/gateway/handlers/events.rs`。

订阅状态由 `SubscriptionManager`（同文件 `:17`）保存：每个连接一个 `TopicFilter`，记录通配模式、例外模式与 `where` 谓词。匹配逻辑在 `src/gateway/event_bus.rs:150` 的 `topic_matches`：

- 模式是 `*` 或 `**` 时匹配全部。
- 模式最后一段是 `*` 或 `**` 时，匹配剩余任意深度——`stream.*` 能匹配 `stream.run_complete`。
- 模式中间的 `*` 只吃一段——`*.complete` 匹配不到 `stream.run_complete`。
- 两边都必须耗尽。

匹配用的是事件的线上主题串：裸事件形态取 `topic` 字段，通知形态取 `method` 字段（`src/gateway/server/connection/forward.rs:187` 的 `extract_topic_and_data`），所以流式帧按 `stream.` 前缀匹配。

`where` 谓词用 `FieldPredicate` 描述（`{"field":"...","equals":...}`），字段路径按 `.` 分段取值，不是 JSON Pointer。谓词非空而负载里没有对应字段时判为不匹配。

## 配置热重载

`src/gateway/hot_reload.rs` 的 `ConfigWatcher` 监听配置文件并去抖（默认 500ms），变更后重新加载并校验，把结果广播给订阅者。`ReloadMode::should_hot_reload` 决定哪些配置段可以热生效；`Hybrid` 模式下只有 `ui`、`channels`、`skills`、`workspace`、`cron` 这些段走热重载，其余需要重启。

## 与桌面宿主的关系

桌面宿主（NSH）连的是 Gateway 的 Desktop IPC 入口与 Web v1 入口，不经过旧的 `/ws`。宿主的形态、面板与插件边界见 [桌面宿主](../desktop-hosts/overview)。

## 历史：传输入口的演进

最早只有一个入口：`/ws`，一个 WebSocket 承载全部 RPC 与事件。Desktop IPC 与 Web v1 是后来加进来的，职责被明确切开——Desktop IPC 只读，Web v1 走网络且自带 TLS 与凭据交换。`/ws` 没有下线，它继续承担历史兼容入口的角色，新写的客户端应选 Desktop IPC 或 Web v1。
