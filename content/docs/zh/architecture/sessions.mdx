# 会话架构

会话是每个 Aleph run 的有状态骨干。每个会话都有一个结构化的 `SessionKey`、一条通过 `SessionService` 持久化的仅追加 `SessionEvent` 日志、以及由 `SessionRunRegistry` 强制实施的每会话运行互斥。本页涵盖 key 分类、事件日志、actor 管道、已移除的 presence 上报器的历史以及跨切面的生命周期问题。

关于如何在请求路由时创建会话，请参阅[网关架构](./gateway)。关于会话如何喂入工具链，请参阅[工具链](./harness)。

## SessionKey 分类

每个会话由 `SessionKey` 标识（`src/routing/session_key.rs`）。六种变体：

```rust
pub enum SessionKey {
    Main {
        agent_id: String,
        #[serde(default = "default_main_key")]
        main_key: String,
        #[serde(default)]
        epoch: u32,
    },
    DirectMessage {
        agent_id: String,
        channel: String,
        peer_id: String,
        #[serde(default)]
        dm_scope: DmScope,
        #[serde(default)]
        epoch: u32,
    },
    Group {
        agent_id: String,
        channel: String,
        peer_kind: PeerKind,
        peer_id: String,
        thread_id: Option<String>,
    },
    Task {
        agent_id: String,
        task_type: String,
        task_id: String,
    },
    Subagent {
        parent_key: Box<Self>,
        subagent_id: String,
    },
    Ephemeral {
        agent_id: String,
        ephemeral_id: String,
    },
}
```

### 序列化形式

| 变体 | 格式 | 示例 |
|---------|--------|---------|
| `Main` | `agent:{agent_id}:{main_key}[:s{epoch}]` | `agent:main:main` |
| `DirectMessage`（`PerPeer`） | `agent:{agent_id}:dm:{peer_id}[:s{epoch}]` | `agent:main:dm:user123` |
| `DirectMessage`（`PerChannelPeer`） | `agent:{agent_id}:{channel}:dm:{peer_id}[:s{epoch}]` | `agent:main:telegram:dm:user123` |
| `Group` | `agent:{agent_id}:{channel}:{peer_kind}:{peer_id}[:thread:{thread_id}]` | `agent:main:discord:group:guild-abc` |
| `Task` | `agent:{agent_id}:{task_type}:{task_id}` | `agent:main:cron:daily-summary` |
| `Subagent` | `{parent_key.to_key_string()}:subagent:{subagent_id}` | `subagent:agent:main:translator` |
| `Ephemeral` | `agent:{agent_id}:ephemeral:{ephemeral_id}` | `agent:main:ephemeral:a1b2c3` |

仅当 `epoch > 0` 时附加 `:sN` 后缀，让会话可以重命名而不丢失历史。

### DM 范围策略

`[session] dm_scope` 控制直接消息如何坍缩：

| 值 | 行为 |
|-------|----------|
| `per-peer`（默认） | 每个发送者独立会话（跨 channel 按 peer） |
| `per-channel-peer` | 每个 channel × 发送者独立会话（多用户推荐） |
| `main` | 所有 DM 坍缩到该 agent 的 `Main` 会话 |

单一所有者的 bot 可以设置 `dm_scope = "main"`，使 Telegram / Slack / Panel 上的所有 DM 共享同一段 `agent:<id>:main` 上下文。allowlist 中存在多名用户时必须使用 `per-channel-peer`，因为 `main` 会把所有人合并到同一会话。

## SessionService

`SessionService`（`src/session/service.rs`）是事件日志的公共门面：

```rust
#[async_trait]
pub trait SessionService: Send + Sync + 'static {
    async fn attach(&self, id: SessionId) -> Result<SessionHandle, SessionError>;
    async fn get_events(
        &self,
        id: &SessionId,
        from: Option<EventSeq>,
        to: Option<EventSeq>,
    ) -> Result<Vec<SessionEventRecord>, SessionError>;
    async fn emit_event(
        &self,
        id: &SessionId,
        event: SessionEvent,
    ) -> Result<EventSeq, SessionError>;
    async fn subscribe(
        &self,
        id: &SessionId,
    ) -> Result<broadcast::Receiver<SessionEventRecord>, SessionError>;
    async fn wake(&self, id: &SessionId) -> Result<SessionHandle, SessionError>;
    async fn detach(&self, id: &SessionId) -> Result<(), SessionError>;
}
```

默认实现是 `InProcessActorSessionService`（`src/session/in_process.rs`），每个会话生成一个 tokio 任务。每个 actor（`src/session/actor.rs`）启动时从 SQLite 回放事件，然后服务命令直到收件箱关闭或空闲超时触发（默认 30 分钟）。`wake()` 关闭旧 actor（5 秒宽限期），生成从 SQLite 回放的新 actor，并写入一条 `SessionWoken { prior_head }` 事件——这是规范的崩溃恢复路径。

`SessionId = crate::routing::session_key::SessionKey`——会话由网关其他地方使用的同一个 key 标识。

进程级 fallback（`set_global_session_service` / `global_session_service`）让没有本地引用的边缘路径调用者也能通过 actor 管道发出事件。

### 存储

```sql
CREATE TABLE session_events (
    session_id   TEXT    NOT NULL,
    seq          INTEGER NOT NULL,
    turn_id      TEXT,
    event_type   TEXT    NOT NULL,
    payload_json TEXT    NOT NULL,
    created_at   INTEGER NOT NULL,
    PRIMARY KEY (session_id, seq)
);
```

写入是同步的；SQLite 以 WAL 模式运行；`(session_id, seq)` 主键强制每个会话的单调顺序。

## SessionEvent 变体

`src/session/events.rs::SessionEvent` 是一个 `#[non_exhaustive]` 枚举，覆盖完整的会话生命周期：

| 变体 | 用途 |
|---------|---------|
| `SessionWoken { at, prior_head }` | `wake()` 之后的崩溃恢复检查点 |
| `RunStarted { run_id, at, project_root }` | harness run 开始；`project_root` 被盖戳以便崩溃恢复回到同一目录 |
| `RunFinished { run_id, outcome, at }` | harness run 达到终止状态 |
| `TurnStarted { turn_id, trigger, at }` | 一个 Think→Act 轮次开始；`trigger` 区分 user / synthetic / verifier-veto / grace |
| `UserMessage { turn_id, content, at, synthetic }` | 用户输入（当 `synthetic = true` 时为 verifier-veto nudge / grace 提示） |
| `AssistantMessage { turn_id, content, usage, at }` | 每次调用的 LLM 输出；`usage` 是**每次调用**的 token 明细（调用与助手行是 1:1） |
| `AssistantRunMeta { turn_id, run_id, context_tokens, context_window, total_tokens, input_tokens, output_tokens, … }` | 每个 run 的唯一权威账单；会话级计数器挂在这里，**且仅在这里** |
| `SystemMessage { turn_id, content, at }` | 内部系统信号（如 split 子会话用来重建的 `[Context Summary]` 头） |
| `ToolCallRequested { call_id, tool_name, args, at }` | 一个工具调用进入 Act |
| `ToolCallApproved { call_id, source, approver, at }` / `ToolCallDenied { call_id, reason, at }` | 审批卡片裁决 |
| `ToolResult { call_id, output, at }` / `ToolError { call_id, error, at }` | Act 结果（按 `call_id` 配对） |
| `SubagentSpawned { subagent_id, parent_turn_id, at }` / `SubagentReturned { subagent_id, result, at }` | 子代理生命周期 |
| `CompactionPerformed { kind, before_tokens, after_tokens, at }` | 压缩管道输出 |
| `SessionForked { child_session_id, parent_turn_id, at }` | 一个轮次分裂出子会话（如 `SplitSession` 指令） |
| `Error { kind, message, at }` | 域错误事件 |

`src/session/projection.rs` 中的 `project_row` 将一条支持的 `SessionEvent` 转为 `ProjectedRow`；其他事件可以不产生行。网关投影器（`src/gateway/session_projector.rs`）使用这些行生成转录视图，而不是把原始事件直接交给界面。

## 真多会话并行

`SessionRunRegistry`（位于网关执行引擎）是一个 per-session 互斥：一个 agent 可以在多个会话同时运行，但每个单独会话保持互斥。早先的 per-agent 锁让多会话用例挨饿，已在 26.7.7+ 替换。

## 历史：Presence 显式启用（已移除）

本页早期版本记载过 `src/tasks/` 下的 `presence` 上报器：它把 Slack 式主机在线快照（`PresenceSnapshot`：主机名、用户名、平台、空闲秒数）以 `host.presence.update` 广播到 Gateway 事件总线，需通过 `PresenceConfig::enabled`（默认 `false`）显式启用。提交 `aeb94f613` 在 2026-08-09 将它与同类的 `mic_level` 上报器一并被移除：这两个主题从未有订阅者（没有渲染端、RPC 或通道消费它们），且广播会白白泄露主机名与操作系统用户名。详见 `src/tasks/mod.rs` 中的注释块。

能力本身并未丢失：`system_tool` 的 `user_idle_time` 动作可按需回答"键盘前是否有人"，集群节点存活由集群自带的 ping 与空闲看门狗跟踪。`src/gateway/event_visibility.rs` 里的 `host.` 分支被有意保留，作为失败关闭的默认值：此后任何 `host.*` 主题都是 `OperatorOnly`，而不会落入全局广播。

## 哈希化 Carryover 文件名

cron 作业的 carryover 文件（`src/tasks/cron/carryover.rs`）使用一个既能存活冲突又不掩盖冲突的名字写入：

```rust
fn carryover_filename(job_id: &str) -> String {
    let safe = sanitise_job_id(job_id);
    let hash = short_hash(job_id.as_bytes());  // 32 位 FNV-1a，8 个十六进制字符
    format!("{safe}-{hash}.json")
}
```

经清理的前缀保持 grep 友好；FNV-1a 后缀让冲突可区分。两个使用同一人类可读 id 的作业会落到不同的文件上，而不是静默互相覆盖。

## 模板环境确定性排序

`NodeRegistry::list_environments()`（cluster 侧的模板环境投影）按 `(name, id)` 排序：

```rust
envs.sort_by(|a, b| a.name.cmp(&b.name).then_with(|| a.id.cmp(&b.id)));
```

`environments.list` handler(`src/gateway/handlers/cluster.rs`)还会把在线节点排在离线节点之前，再按字母序。早先未排序的 `HashMap` 迭代会把注册表顺序泄漏到 Panel / node_list 视图；确定性排序由 `list_environments_is_sorted_by_name_then_id` 与 `environments_list_orders_online_before_offline_and_by_name` 锁定。

## SessionEvent 体系（高层）

工具链为每个 Think 步骤发出一条 `SessionEvent`，每个 run 发出一条 `AssistantRunMeta`，因此调用与助手行 1:1，token 归属完全准确。`MessageProjector` 在每次写入时把事件物化进遗留的 `messages` 表；启动时 `ProjectionReconciler` 回填事件日志与投影之间的任何漂移。`tool_call_id` 与 `tool_name` 被盖到每条记录上，`AssistantRunMeta` 携带 `run_id` 让投影器挂上 run 级元数据，热路径无需耦合到存储。

## 会话 RPC 方法

| 方法 | 说明 |
|--------|-------------|
| `sessions.preview` | 获取会话预览/摘要信息（`session.get` 不存在） |
