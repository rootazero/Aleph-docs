`teams` 模块为多代理协作提供团队管理，支持具有生命周期管理、Coord Task DAG 调度、计划审批（团队战略）和任务跟踪的结构化团队协作。

> 团队生命周期状态由 `src/teams/types.rs` 中的 `TeamStatus` 表示；计划提交和审查由 `src/teams/plans.rs` 中的 `PlanManager` 负责。

## 概览

团队支持：
- **团队创建** —— 定义由指定**队长**与成员组成的代理团队；成员可以是 in-process agent 或 ACP session（`TeamMemberKind::Agent | AcpSession`）
- **战略协调**（"团队战略协调"，Team Strata）—— 队长先制定计划，该计划被焊入每位成员的提示词
- **协调任务**（Coord Task）—— 通过 `src/agents/swarm/tasks/` 的统一 `coord_tasks` DAG；状态机为 `Pending | Blocked | InProgress | WaitingReview | Completed | Failed | Cancelled | Skipped | Paused | Unsatisfiable`
- **验证循环** —— 队长通过 `task_review` 工具接受或拒绝交付物（详见 [Coord Tasks](#协调任务-coord-task)）
- **团队协议** —— 每个团队可设置 `Team.protocol`（≤32 KiB），由 dispatcher 注入每个成员的启动上下文
- **ACP 成员** —— 通过 `teams.acp_member.add / list / remove` 接入外部 CLI（Claude Code / Codex / Gemini）
- **Snapshot / Kanban** —— `teams.snapshot.*` 记录团队状态；`team_workflow_canvas` 工具暴露可拖放的看板
- **JSON-RPC 驱动** —— `teams.*` 全套 RPC（创建、任务、消息、快照、工作流）

## 核心类型（`src/teams/types.rs`）

```rust
pub struct Team {
    pub id: TeamId,
    pub name: String,
    pub description: String,
    pub leader_id: String,
    pub status: TeamStatus,         // 实际只有 Active | Disbanded
    pub created_at: i64,
    pub disbanded_at: Option<i64>,
    pub protocol: Option<String>,   // 队长团队操作协议（≤32 KiB）
}

pub enum TeamStatus { Active, Disbanded }   // snake_case on the wire

pub enum TeamMemberKind { Agent, AcpSession }

pub struct TeamMember {
    pub team_id: TeamId,
    pub agent_id: String,           // Agent: 注册表 id；AcpSession: 合成 id `acp:<harness>:<cwd>[:name]`
    pub role: String,
    pub joined_at: i64,
    pub kind: TeamMemberKind,
    pub acp_harness_id: Option<String>,
    pub acp_cwd: Option<String>,
    pub acp_session_name: Option<String>,
}
```

`TeamMember` 通过 `kind` 区分运行时分发目标——in-process agent 经 `MemberDispatchTarget::Agent`，ACP session 经 `MemberDispatchTarget::AcpSession`（见 `src/teams/dispatcher/runner.rs`）。

`TeamSummary` 是列表视图（id / name / description / leader / status / member_count / 时间戳），**不含任务计数**——任务计数在 `coord_tasks` DAG（独立数据库）中，使用 `team_status` 工具获取准确分解。

`MAX_PROTOCOL_LEN = 32 KiB` 强制——protocol 会逐字注入每个成员的启动提示词，无界值会让 `set_protocol` 的调用者向队长上下文注入任意指令。

## 战略协调（"团队战略协调"，Team Strata）

团队拥有一名**队长**和若干成员。在团队的**首条消息**时，队长先制定计划——在任何成员开始工作之前。该计划环节**每个团队仅触发一次**（按团队键控的 fire-once 策略），生成的计划被**焊入每位成员的提示词**，使所有成员共享同一战略上下文。

```
向团队发送首条消息
        │
        ▼
  队长先制定计划  ──►  Strategy（fire-once，按团队键控；atomic put_if_absent 防 race）
        │
        ▼
  计划被焊入每位成员的提示词
        │
        ▼
  成员在分配的协调任务下工作
```

`team_key(team_id)` 是 composite-key 命名空间之一，与 loop / goal / session 并列，详见 [Loop / Goal / Strategy](/docs/zh/concepts/looping-goal-strategy)。

## 协调任务（Coord Task）

`coord_tasks` 是统一 DAG（在 `src/agents/swarm/tasks/` 下），**不**是 `src/teams/` 自己的表。团队成员的工作通过该 DAG 表达：

| 状态 | 含义 |
|---|---|
| `Pending` | 等待依赖 + dispatcher 拾取 |
| `Blocked` | **派生**（永不存储）：依赖未完成 |
| `InProgress` | dispatcher 已 claimed，正在运行 |
| `WaitingReview` | 运行完成，等待 lead review；下游仍阻塞 |
| `Completed` | 完成（满足依赖） |
| `Failed` | 失败（不满足依赖；触发派生 `Unsatisfiable`） |
| `Cancelled` | 取消 |
| `Skipped` | 手动跳过（仍满足依赖） |
| `Paused` | 手动暂停；不被 dispatcher claim；**不**满足依赖 |
| `Unsatisfiable` | **派生**：依赖终结失败，自身永远不可运行 |

> `Blocked` 与 `Unsatisfiable` 由查询时派生；`from_stored` 显式拒绝两者（写回路径上不允许）。`CoordTaskStatus::is_terminal()` 与 `is_settled()` 分别给出"持久终态"与"观察者角度已结束"的判定；后者用于团队 / 工作流"全部 settled"完成谓词。

依赖边保存在 coord_task 的 `blocked_by` 字段（`src/teams/artifacts.rs`），dispatcher 通过 `src/teams/dispatcher/schedule/` 的 `select_schedulable` / `settle` / `reclaim` / `failure` 维护就绪性、重新调度、超时回收与失败传播。

### 验证循环：`task_review`

```rust
// src/builtin_tools/team/task_review.rs
#[derive(Clone)] pub struct TaskReviewTool { /* … */ }
impl AlephTool for TaskReviewTool {
    const NAME: &'static str = "task_review";

    async fn call(&self, args: TaskReviewArgs) -> Result<TaskReviewOutput> {
        // 软 leader-only guard（prompt-gating 是主门，此为 defense-in-depth）
        // Approve → CoordTaskStatus::Completed（满足依赖）
        // Reject  → CoordTaskStatus::InProgress（owner 返工）
        // 当 task metadata.require_grounding=true 且 approve 无 grounding 字段 → 回弹
    }
}
```

```jsonc
// task_review 工具调用
{
  "task_id": "<coord-task-id>",
  "decision": "approve",       // 或 "reject"
  "feedback": "…",             // reject 时写回 owner
  "grounding": {               // 可选；approve 时若 require_grounding 则必填
    "kind": "exit_code",       // exit_code | numeric | line_count
    "source": "cargo test -p alephcore --lib",
    "value": "0"
  }
}
```

> 队长的接受/拒绝通过 `task_review` 工具完成（不是 JSON-RPC 方法）；成员通过 `teams.create_task` / `teams.update_task` 创建/更新的协调任务工作。`workflow_step_review` 是工作流步骤的等价工具（`src/builtin_tools/team/workflow_step.rs`）。

### G2 — 每任务 git worktree 隔离

`execute_member_task`（`src/teams/dispatcher/runner.rs`）可选地为每次成员任务创建 detached-HEAD git worktree（`git worktree add --detach`，目录在临时目录下，名字形如 `aleph-subagent-team-{team}-{task}-{uuid}`），并把运行的工作空间绑定指向它——并发 worker 不会互相污染索引。绑定通过 `ExecWorkspace::OwnedWorktree` 表达（`src/sandbox/context.rs`）：沙箱只读这个路径，不拥有它、不重建它，缺失时拒绝执行而不是造一个空目录。

三条硬规则：

- **来源是授权项目归属，不是 daemon 的当前目录** —— `team_worktree_source` 先从 scope 解析项目归属，再取该项目的 `workspace_path`。绑定目录若落在某个 Git checkout 内部则拒绝：「team worktree: the bound directory is inside a Git checkout; bind the checkout root to use a worktree」。
- **同步委托才共享调用方的 checkout** —— 异步派发的成员任务不继承调用方的 live checkout；普通调用方目录也不是项目绑定，不能替换成员的默认工作空间。
- **worktree 由 RAII 拆** —— `WORKTREE_CLEANUP_GRACE_MS` 是超时中止与显式拆除之间的宽限窗；正常路径显式 `cleanup()`，panic / 超时 / 中止走 `Drop` 兜底。

没有授权 Git 项目时，成员保留普通沙箱；已选定的 checkout 搭建失败则直接报告，不静默降级。

## 团队 Run Mode Pin

每个由团队发起的 agent 运行（群聊成员运行、任务派发与工作流步骤）都不继承全局模式，而是由 `stamp` 把 `TEAM_RUN_MODE`（`Work`）与 `TEAM_RUN_BUSY_INPUT_MODE`（`Queue`）写入请求元数据：

- 两个运行入口——`teams::broadcast::member_run_metadata` 与 `teams::dispatcher::runner::task_run_metadata`——都调用同一个 `stamp`，不各自维护副本
- `ExecutionEngine::resolve_turn_mode` 把请求携带的模式视为最高优先级并写回会话，之后每一轮重新钉住
- `is_team_session` 只匹配 `team_chat` 与 `team` 两种直接 `Task` 会话键；成员运行里派生的子代理有自己的会话键和显式传入的模式，`stamp` 不会触碰
- 收窄团队能力的旋钮是每个成员的 `tools` 声明（`teams::member_provision`），不是会话模式

```rust
// src/teams/run_mode.rs
pub const TEAM_RUN_MODE: SessionMode = SessionMode::Work;
pub const TEAM_RUN_BUSY_INPUT_MODE: BusyInputMode = BusyInputMode::Queue;
```
