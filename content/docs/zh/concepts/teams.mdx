团队由一名队长、具名成员、持久对话和共享的 `CoordTask` DAG 组成。队长拆解工作，成员执行任务，依赖关系控制调度，审查策略决定成功运行何时真正完成。

## 协调模型

团队工作包含三个相连层次：

1. **任务与工件** — `CoordTask` 记录包含负责人、优先级、依赖、状态、结果、运行、评论、事件与工件。
2. **消息** — SQLite 支持的团队收件箱提供 to/cc 路由与线程；成员通过 `message_send` 和 `inbox_read` 使用它。
3. **协作会话** — 聚焦的多轮讨论是显式、有界的会话，通过会话工具管理。

事件驱动的 `TeamDispatcher` 原子认领可运行任务，遵守任务 DAG 与并发限制，并在重启后协调中断的进行中任务。只有由 dispatcher 管理的任务会自主运行；`team_delegate` 是队长到成员的同步交接。

## 看板

Panel 看板及其统计标签共用一份规范列定义：

`Pending → Blocked → In Progress → Waiting Review → Paused → Completed → Skipped → Failed → Cancelled`

`Unsatisfiable` 是派生的阻塞状态，会归入 **Blocked** 列而不会消失。看板支持拖放、卡片快捷操作，以及任务抽屉中的完整操作栏；三者共用相同的生命周期规则与后端派发点。

重要转换包括：

- `Pending` 可开始、暂停、跳过或取消。
- `In Progress` 可完成、失败、暂停或取消。
- `Waiting Review` 可批准、拒绝、跳过或取消。
- `Paused` 恢复到 `Pending`；`Failed` 可重试到 `Pending`。
- 终态 `Completed`、`Skipped` 与 `Cancelled` 卡片不可拖动。

可能造成难以撤销结果的拖放需要确认。卡片显示优先级、负责人、依赖数量、审查状态、相对创建时间与简短描述预览。任务抽屉提供运行、评论、事件、工件、统一 trace 与退出 journal。

## 审查与验收

任务可在 metadata 中携带验收策略：

- `acceptance_criteria` 描述完成定义。
- `lead_review_required` 将成功运行路由到 `WaitingReview`。
- `require_grounding` 要求批准前提供结构化审查证据。

面向队长的 `task_review` 工具批准或拒绝提交的交付物。Panel 使用 `teams.workflow.approve_step` 与 `teams.workflow.reject_step` 处理同一审查边界。批准会完成任务并解除下游依赖；拒绝会记录 verdict，并让下游继续阻塞，直到任务被重试或重做。

## 成员工具面

内联创建的成员和模板角色可以声明：

```toml
tools = ["task_*", "message_send", "search", "web_fetch"]
tools_denied = ["file_write"]
```

两个字段都支持末尾 `*` 前缀 glob。两者均省略时保留完整工具面；deny 项优先于 allow 项。`tools` 是按白名单 retain 的；被排除的工具不能通过 `tool_search` 等延迟机制恢复。`team_*` 不应被通配，因为它包含 `team_disband`、`team_create`、`team_from_template`、`team_member_remove` 等管理动作——需要时显式列出 `team_status` 与 `team_delegate`。

声明通过共享的成员配置路径应用并持久化，使当前运行时工具面与重启后重建的工具面保持一致。如果受限 worker 缺少 `task_submit` 或 `message_send`，或者受限 leader 缺少 `task_create`、`team_delegate`、`task_read_artifact`、`task_review`、`team_status` 等必需协调工具，创建会提前失败。

这属于展示与误操作范围收缩，不是安全边界：审批策略、执行等级、作用域工具服务与沙箱规则仍控制执行。模板复用的现有代理保留自己的工具面，`self` leader 也保留调用者的工具面。`role` 字段是自由文本，不会被用来推导工具面。

四个内置模板中，`strategy-room` 与 `code-review` 在每个角色上显式声明工具面；`software-dev` 与 `research-paper` 故意不声明，由成员保留完整工具面。

## 群聊

`teams.chat.send` 启动有界、可取消的成员扇出并持久化带归属的回复。实时 Panel 消费 `team.<id>.*` 事件以获取消息、系统通知、成员活动、扇出状态与任务变化。详见[群聊](/docs/zh/concepts/group-chat)。

## 主要 RPC 界面

- 团队生命周期：`teams.create`、`teams.get`、`teams.list`、`teams.rename`、`teams.disband`、`teams.delete`、`teams.list_templates`
- 任务：`teams.create_task`、`teams.update_task`、`teams.list_tasks`、`teams.list_task_runs`、`teams.list_task_comments`、`teams.list_task_events`、`teams.add_task_comment`，加上 `teams.task.pause`、`teams.task.resume`、`teams.task.retry`、`teams.task.skip`、`teams.task.trace`、`teams.task.journal.get`、`teams.task.journal.list`
- 工作流：`teams.workflow.approve_step`、`teams.workflow.reject_step`
- 对话：`teams.chat.send`、`teams.chat.cancel`、`teams.chat.history`、`teams.chat.thread`
- 快照：`teams.snapshot.create`、`teams.snapshot.list`、`teams.snapshot.get`、`teams.snapshot.restore`、`teams.snapshot.delete`
- ACP 成员：`teams.acp_member.add`、`teams.acp_member.remove`、`teams.acp_member.list`
- 发现与用量：`agents.teams`、`teams.usage`

`team_task_control`（暂停/恢复/重试/跳过/取消）、`task_exit_journal`、`team_workflow_canvas`、`team_snapshot` 等操作通过内置工具提供给代理。LLM 自身审批通过 `task_review`；管理员通过上述 RPC 处理任务级别控制。

没有单独的团队运行 RPC，也没有 `sequential | parallel | hierarchical` 协调模式。并行来自任务 DAG、dispatcher 限制与群聊扇出。
