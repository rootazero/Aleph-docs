`wizard` 模块提供**基于会话的向导框架**：在 gateway WebSocket 上以 `wizard.*` JSON-RPC 调用形式暴露。所有向导交互都走 RPC —— 没有 `aleph` / `aleph-server` CLI 子命令。

## 设计理念

1. **基于会话的状态机** —— 通过 `session_id` 在多次 `wizard.next` / `wizard.answer` 调用之间保持进度
2. **RpcPrompter 抽象** —— flow 实现拿到 `RpcPrompter`，向客户端推 `WizardStep`，等 `wizard.answer` 把值送回
3. **Panel / 桌面 / 任何 RPC 客户端**都能驱动，无需终端
4. **终态 sticky** —— 完成后 `cancel()` 不会再覆盖 `Done` 终态

---

## 架构

```
Client (Panel/桌面)                  WizardSession                   WizardFlow (后台 task)
   │                                    │                                 │
   │── wizard.start ────────────────────▶│                                 │
   │    { wizard_type:"onboarding" }    │── new(flow) 启动 tokio::spawn ─▶│
   │◀── { session_id, step:welcome } ───│                                 │
   │                                    │◀── prompter.prompt(welcome) ────│
   │                                    │                                 │
   │── wizard.answer ──────────────────▶│                                 │
   │    { session_id, step_id, value }  │── answer(step_id,value) ───────▶│
   │                                    │◀── prompter.prompt(next) ───────│
   │◀── { step:primary } ───────────────│                                 │
   │                                    │                                 │
   │── wizard.cancel ──────────────────▶│                                 │
   │    { session_id }                  │── cancel_tx.send(()) ──────────▶│
   │◀── { cancelled:true } ─────────────│◀── settle(Cancelled) ───────────│
```

## 核心组件

### `WizardSession`

会话由 `wizard.start` 创建，在后台 tokio task 中运行 flow，前端每次 `wizard.next` / `wizard.answer` 推进一步：

```rust
pub struct WizardSession {
    id: String,
    status: Arc<RwLock<WizardStatus>>,
    current_step: Arc<RwLock<Option<WizardStep>>>,
    step_rx: Arc<tokio::sync::Mutex<mpsc::Receiver<WizardStep>>>,
    answers: Arc<RwLock<HashMap<String, PendingAnswer>>>,
    error: Arc<RwLock<Option<String>>>,
    cancel_tx: Arc<RwLock<Option<oneshot::Sender<()>>>>,
}
```

要点：

- `step_tx` 仅由 `RpcPrompter` 持有；flow task 退出时 prompter 被 drop、channel 关闭、`next()` 收到 `None` 后正确返回终态。
- 终态 `Done` / `Cancelled` / `Error` 是 sticky —— `settle()` 只接受从 `Running` 的迁移；客户端断开清理时晚到的 `cancel()` 不会覆盖已完成的 `Done`。

### `WizardFlow` trait

```rust
#[async_trait]
pub trait WizardFlow: Send + Sync {
    async fn run(&self, prompter: &RpcPrompter) -> Result<(), WizardSessionError>;
    fn name(&self) -> &str { "wizard" }
}
```

### `RpcPrompter`

唯一的内置 prompter 实现。`prompter.prompt(step)` 把 `WizardStep` 推给客户端并阻塞等待对应 `wizard.answer`；`RpcPrompter` 没有终值写入方法 —— 终态由 flow 的返回值决定。

支持的 step 类型：

| `StepType` | 客户端对应交互 |
|---|---|
| `Note` | 仅展示 |
| `Select` | 单选 |
| `MultiSelect` | 多选 |
| `Text` | 自由文本（支持 `sensitive`） |
| `Confirm` | 是/否（可设默认值） |

## 内置 flow

| Flow | `wizard_type` | 用途 |
|---|---|---|
| `OnboardingFlow` | `onboarding` | 首次启动：provider × 2、模型、thinking、消息通道、复核（6 步） |

目前代码里只接线了这一个 flow：服务器启动时注册的 flow factory 只认 `onboarding`，其它 `wizard_type` 会得到 `Unknown wizard type`。

`OnboardingFlow::run` 的步骤序列：

1. `welcome` — 介绍
2. `configure_primary` — 选主 provider + 模型 + API key
3. `configure_secondary` — 选备用 provider + 模型 + API key
4. `configure_thinking` — thinking 级别（`low` / `medium` / `high`）
5. `configure_messaging` — Telegram / Discord / iMessage（Slack 当前 disabled）
6. `review_and_finalize` — 复核 + 写入

不在 CLI 上触发；由 Panel 设置页 / 安装后的握手窗口主动调 `wizard.start` 启动。

## RPC 协议

方法列表（gateway 注册顺序，`service_unavailable` 占位 → `install_wizard_handlers` 替换为真实 handler）：

| 方法 | 入参 | 返回 |
|---|---|---|
| `wizard.start` | `{ wizard_type, initial_data? }` | `{ session_id, step, status }` |
| `wizard.next` | `{ session_id, answer? }` | `WizardNextResult`（下一步 / 完成 / 取消 / 错误） |
| `wizard.answer` | `{ session_id, step_id, value }` | `WizardNextResult` |
| `wizard.cancel` | `{ session_id }` | `{ cancelled }` |
| `wizard.status` | `{ session_id }` | `{ status, error?, current_step? }` |

`WizardNextResult` 终态只有 `done` / `status` / `error` 三个字段（没有额外的终值载荷）。

## 安全 / 并发性质

- **`AtomicU64`** 生成步 ID（`step-N`），无锁
- **`unwrap_or_else(|e| e.into_inner())`** 锁恢复（Poisoned-lock 安全）
- **显式 step 验证** —— `answer` 校验 `step_id` 与当前 step 匹配；`wizard.next` 携带 `answer` 被拒绝（`wizard.answer` 才接受）
- **通道泄漏防护** —— `RpcPrompter::prompt` 失败时同步从 `answers` map 移除未消费的 pending sender，避免会话生命周期内的内存泄漏
- **没有进程内 CLI prompter** —— 终端 UI 走 RPC 让 Panel 处理；CLI 不直接驱动 wizard
