代理运行时是从入站聊天请求到一串 LLM turns 的路径：
`Gateway` → `FlowRequest` → `Orchestrator` → `AgentHarnessRunner` →
`AgentHarness`。循环本身在 `src/harness/`；提示词组装在 `src/thinker/`；
委派在 `src/agents/`；子代理执行复用同一个 `AgentHarness`，子会话在结构上
与顶层 run 完全一致。

## 拓扑

```
Gateway (protocol adapters, inbound routing)
   │ FlowRequest { agent_id, input, tool_service, trace_sink, identity, ... }
   ▼
Orchestrator (resolve AgentDef + FlowSpec, build HarnessDeps, dispatch)
   │ AgentHarnessRunner::run
   ▼
AgentHarness (Think→Act loop, stop-hooks, context budget, compaction)
   │ 使用
   ├── SessionService   (append-only history)
   ├── ToolService      (tool catalog + execution)
   ├── Sandbox          (exec environment, capability ledger)
   └── AiProvider       (LLM — failover wrapped inside `provider`)
   │
   ▼
FlowOutcome → Gateway 渲染响应
```

> Phase 7（2026-04-21）将 `SubagentTool` 迁移到
> `Orchestrator → HarnessRunner → AgentHarness`。旧 src/agent_loop/ 路径
> 已删除；每个 agent run——顶层或子代理——都使用同一个 harness。

## 设计原则

运行时围绕四条 R10/R11 驱动的红线展开：

1. **薄笨循环** —— `src/harness/` 只调度 Think→Act turns。它不分类意图、
   不给工具相关度打分、不判断完成度、不挑选恢复策略。这一切都在 LLM 的
   一次推理调用中完成（`src/harness/CLAUDE.md` /
   `docs/reference/HARNESS_PHILOSOPHY.md`）。
2. **工具侧资源声明** —— 并发来自每个工具声明的 `Shared` /
   `Exclusive{Global, Paths}` 资源 claim：声明内并发，声明间串行。没有任务
   依赖图。
3. **事件溯源历史** —— 每个 turn 是追加到 `SqliteEventStore` 的
   `SessionEvent`。Replay = append 日志；checkpoint 不是独立框架。
4. **Compaction 是 typed 指令** —— LLM 从不自己释放上下文。`ContextBudget`
   消费方产出 `LoopDirective`；harness 机械地执行 `CompactToFit` /
   `SplitSession`。

## 循环

`AgentHarness::run` 是 `async fn`，循环执行 `run_turn_internal` 直到状态机
报 `Done` 或某个 cap 触发。所有终止点（每一个都写细粒度的 `TerminateReason`）：

| 触发上限                        | TerminateReason 变体               | 结果                       |
|--------------------------------|-------------------------------------|-----------------------------|
| 模型说 `Done`                  | `Completed`                         | 正常                        |
| `cancel` token 触发            | `Cancelled`                         | 协作式中止                  |
| `max_iterations` 超出          | `MaxIterations`                     | `hit_limit = true`          |
| `consecutive_failure_cap`      | `ConsecutiveFailures`               | `hit_limit = true`          |
| Think 阶段 `turn_timeout`      | `TurnTimeout { phase: "Think" }`    | `hit_limit = true`          |
| `StallTracker::is_stalled`     | `StallTimeout { elapsed_ms }`       | `hit_limit = true`          |
| 验证器链 `Veto`                | `VerifierVeto { ... }`              | 额外 Continue 一次          |
| `SplitSession` 成功            | `Completed`                         | 重新绑定到子会话            |

`hit_limit` 在其精度伙伴 `terminate_reason` 之外独立设置，使只看 boolean 的
旧调用方依旧工作。任何 cap 触发后，会跑一段 `grace_turn`
（`fire_boundary_grace_turn`，`GRACE_TIMEOUT_BUDGET = 30s`），让模型在退出
前产出干净的终止摘要；grace turn 用独立 budget 跑 fire-and-forget，挂起的
provider 永远无法阻塞 shutdown。

每回合记录（`src/harness/trait_def.rs`）：

```rust
#[must_use]
pub struct TurnStep {
    pub state: TurnState,           // Continue | Done
    pub executed: usize,            // 本回合成功的工具调用数
    pub vetoed: bool,               // 验证器强制过 Continue
    pub split_child: Option<SessionId>, // SplitSession 重新绑定目标
}

#[must_use]
pub enum TurnState { Continue, Done }
```

`Drop` 一个 `TurnStep` 会静默丢失循环控制信号，所以两种类型都带
`#[must_use]`。`(state, executed, vetoed, split_child)` 四元组取代了
同形四字段被逐个 bolt-on 上去的匿名位置元组。

### 硬上限与软上限（HarnessDeps）

`AgentHarness::new(deps: HarnessDeps)` 携带上限配置。这些都不是强制的；
默认值匹配生产 gateway 的连线。

| 字段                            | 默认值          | 对 `Done` / `hit_limit` 的影响        |
|--------------------------------|------------------|---------------------------------------|
| `max_iterations`               | 无上限           | 累计 N 次 Continue 后 `Done + hit_limit = true` |
| `consecutive_failure_cap`      | 禁用             | `errors > executed` 的回合累计 N 次后 `Done + hit_limit = true` |
| `turn_timeout`                 | 禁用             | `HarnessError::StalledTurn`，设 `hit_limit = true` |
| `stall_config`                 | 禁用             | `StallTimeout` + `hit_limit = true`；跨回合看门狗 |
| `parallel_tool_concurrency`    | `Some(8)`        | 同一批内 `join_all` 的上限              |

`turn_timeout` **只**约束 Think——Act 由每个工具自己的 wall-clock budget
约束，超时作为可恢复的 `ToolError::Timeout` 出现，不当作 stalled-turn 错误
（2026-06 phase 3 墙钟下沉）。回合级 stall 看门狗与工具级执行 budget 是两个
独立的工具，作者不同；混用会让一个慢的人工审批 kill 掉整个 run。

## 子代理委派

顶层 agent 通过 `SubagentTool`（`src/agents/subagent_tool/`）生成子代理。
子代理执行就是 gateway chat 路径用的同一个 `AgentHarness`——只有 wiring 不同：

- `SubagentTool::spawn` 调到 `agent_runtime::execute_via_harness`，后者
  为每个 child 用从 parent `chain.child()` 下推得来的 `HarnessDeps` 构造
  一个 `AgentHarness`。
- 子会话 key 是父 `SessionKey::Main` 套上
  `SessionKey::Subagent { parent, subagent_id }`——序列化为
  `subagent:agent:<main_agent_id>:<subagent_id>`。
- 取消通过 harness 的 `tokio_util::sync::CancellationToken` 参数走协作式取消；
  每个 `AgentHarness` 在每个回合顶部都检查 `cancel.is_cancelled()`。
- 子代理失败由 `AgentRuntime::run` 收集，以
  `Result<LoopRunResult, String>` 抛出——取消是一个 error string，不是
  `LoopRunResult` 上的 boolean（`src/agents/runtime.rs`）。

```
Main Agent (claude-opus-4) — via AgentHarness (Gateway chat)
    │
    ├── Translator Sub-Agent (claude-haiku)
    │       Session:  subagent:agent:main:translator
    │       Runtime:  AgentHarness (via Orchestrator dispatch)
    │
    ├── Code Reviewer Sub-Agent (claude-sonnet)
    │       Session:  subagent:agent:main:code-reviewer
    │       Runtime:  AgentHarness (via Orchestrator dispatch)
    │
    └── Research Sub-Agent (gpt-4o)
            Session:  subagent:agent:main:researcher
            Runtime:  AgentHarness (via Orchestrator dispatch)
```

`AgentRuntime` 是 `AgentHarness` 之上唯一为子代理 run 存在的一层；它持有
生命周期追踪（`SubagentStart` / `SubagentStop` observer hooks）、transcript
持久化、以及下推的 `ChainContext`。它不持有循环、budget、或恢复策略——
那些都留在 harness 上。

## Busy-Input 策略（运行中消息）

当消息落到一个 `AgentHarness::run` 已在跑的 session 上时，gateway 的 busy
分支从三种策略中选一种。策略**按 channel 显式选择**（R7——绝不从消息内容
推断），存到 `ChannelPolicyConfig.busy_input_mode` 的 wire 字符串上，盖戳
到 run 元数据的 `BUSY_INPUT_MODE_KEY` 下。Panel/CLI 路径上没有 → `Steer`。

| Wire 值        | 机制                                                                                                                                                              |
|----------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `steer`（默认） | `steering::try_inject_steering` 把消息注入 live event log；运行中的循环在下一个回合边界吃掉它。`MAX_PENDING_STEERING = 16` 处的背压 + reconcile-preamble 合流。 |
| `interrupt`    | `find_steering_target_id` → `ExecutionEngine::cancel`（`cancel_tx` → `CancellationToken` → `ExecutionError::Cancelled`）→ inbound router 的 busy/retry 把消息作为同会话的新 run 重启。 |
| `queue`        | 不注入运行中循环。inbound router 的按会话 FIFO 暂存消息，当前 run 一结束就把它作为新 run 投递，受队列超时约束。 |

把 channel 切到非默认模式：

```toml
[channels.ops-bot]
busy_input_mode = "interrupt"   # 默认是 "steer"
```

参考对照：hermes 暴露 `HERMES_GATEWAY_BUSY_INPUT_MODE`，openclaw 暴露
`QueueMode`，Pi 暴露 `streamingBehavior`；Aleph 此前硬编码 `Steer`。

### 今日尚未连线

- **子代理感知降级**（hermes `#30170`）：`interrupt` 会取消 in-flight 工作
  以及该 run 已生成的任何子代理。当存在活跃子代理时把 `interrupt` 降级为
  `steer` 需要按会话子代理检测——目前未连线。今日启用 `interrupt` 的运维者
  接受这一点。
- **Follow-up lane**（defer-until-stop，Pi `followUp`）：`steer` 已让模型
  自己决定何时回应插话；单独的 defer-until-stop 队列要去 loop 里多写一段
  drain 逻辑。

## 代码位置

- `src/harness/` — `AgentHarness`（Think→Act driver，12 文件预算棘轮）
- `src/harness/trait_def.rs` — `TurnState`、`TurnStep`、`HarnessError`
- `src/harness/agent/{think,act,guardrails,prompt}.rs` — 子步骤文件
- `src/orchestrator/` — AgentDef + FlowSpec 解析，`AgentHarnessRunner`
- `src/agents/runtime.rs` — `AgentRuntime`、`LoopRunResult`、`SubagentTranscript`
- `src/agents/subagent_tool/` — SubagentTool（spawn / parse / loop_tool）
- `src/agents/registry.rs`、`src/agents/teammates.rs`、`src/teams/`、
  `src/group_chat/` — 多 agent 平面（P5 retraction 之后保留分离）
- `src/session/` — `SessionService`、`SqliteEventStore`、`SessionEvent` log
- `src/gateway/execution_engine/{mod.rs, steering.rs, gate.rs}` —
  `BusyInputMode`、`BUSY_INPUT_MODE_KEY`、`try_inject_steering`
- `src/gateway/inbound_router/{mod.rs, types.rs}` — `ChannelPolicyConfig`
