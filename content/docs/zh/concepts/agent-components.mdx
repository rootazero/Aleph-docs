title: "代理组件"
description: "Think→Act 循环的模块地图——12 个 Harness 模块各自的家，以及为什么没有大一统的 `components` 目录。"
---

Aleph 的 Think→Act 循环**不是**「一个事件总线挂着 6 个 typed handler」。
这个心智模型在 codebase 里不存在——没有 `src/components/` 目录。每个子系统
各自持有自己的 crate 模块；它们通过 `AgentHarness` 边界协同，不通过共享的
事件总线。这种拆分是有意为之，源自 2026-04 到 2026-07 的 harness-dissolution
工作，并在设计哲学里固化为 R3 / R10 / R11。

| # | 模块                  | Aleph 中的家                                  | 备注 |
|---|-------------------------|---------------------------------------------|-------|
| 1 | Orchestration Loop      | `src/harness/`                              | **薄核心**——12 文件 / 棘轮行数预算 |
| 2 | Tools                   | `src/tools/` + `src/builtin_tools/`         | 吸收了原 harness 的 exec_context |
| 3 | Memory                  | `src/memory/`                               | 不动（最干净的一块） |
| 4 | Context Management      | `src/context/{budget,compact}/`             | 5 处合并到 1 处 |
| 5 | Prompt Assembly         | `src/thinker/`                              | 历史名保留，不强行改名 |
| 6 | Tool Calling            | `src/tools/calling/` + `src/providers/bridge.rs` | |
| 7 | State & Checkpointing   | `src/session/`                              | `SessionEventStore` + `replay()` 已经是事件溯源框架 |
| 8 | Error Handling          | `HarnessError` + 各域 typed error            | 跨模块，无单一容身处 |
| 9 | Guardrails              | `src/{security,sandbox,approval,pii}/`      | 4 域分立，不强搞 facade |
| 10 | Verification & Feedback | `src/verification/`                         | 新建，吸收 stop_hooks |
| 11 | Subagent Orchestration  | `src/{agents,teams,orchestrator,group_chat}/` | 4 域职责正交，不合并 |
| 12 | Initialization & Env    | `src/init_unified/` + `src/bin/aleph-server/commands/start/` | 见 `docs/reference/BOOT_ASSEMBLY.md` |

## 薄核心 —— `src/harness/`

编排循环目录被限制为 **12 个文件**和棘轮测试的行数天花板
（`src/harness/CLAUDE.md`、`src/harness/tests/budget.rs`）。新增文件必须通过
三问门控才能落地。

| 文件                          | 职责 |
|-------------------------------|------|
| `mod.rs`                      | 重新导出 `AgentHarness` |
| `agent.rs`                    | `AgentHarness` 结构体 + 顶层 `run()` + stalled-turn grace slot |
| `deps.rs`                     | `HarnessDeps` DI 容器 + `StallConfig` / `StallTracker` |
| `trait_def.rs`                | `HarnessError`、`TurnState`、`TurnStep` |
| `callback.rs`                 | `HarnessCallback` + `NoopHarnessCallback` |
| `chain_context.rs`            | 子代理调用链位置接力 |
| `trace.rs`                    | 循环 `LoopTraceEvent` 收集 |
| `trace_sink.rs`               | `TraceSink` 输出抽象 |
| `agent/think.rs`              | Think：LLM 调用 + 守护 + 验证器通过 |
| `agent/act.rs`                | Act：工具执行 + 资源域并行调度 |
| `agent/guardrails.rs`         | 输入/输出/工具调用护栏挂载点 |
| `agent/prompt.rs`             | 逐回合消息组装 |

harness **不**持有：意图分类、工具相关度打分、完成度判断、内容审查、错误
恢复策略、provider failover（后两者包在 `providers::FailoverProvider` 里面，
对 loop 而言只剩一个 provider）。这些都是 LLM 的责任。

### 循环状态

`src/harness/trait_def.rs` 中的两类型状态机：

```rust
#[must_use]
pub enum TurnState { Continue, Done }

#[must_use]
pub struct TurnStep {
    pub state: TurnState,
    pub executed: usize,
    pub vetoed: bool,
    pub split_child: Option<SessionId>,
}
```

`TurnState` **只有两个**变体，不是五变体。某些草稿里更复杂的
`Restart | Act | Finalize` 拆分在发现 `restart` 支只有一处调用点之后被收起；
现在那条路径以 `HarnessError` 早返回表示，不再是单独的状态。

## 提示词组装 —— `src/thinker/`

分层系统提示词构建器。详见 [提示词系统](/docs/zh/concepts/prompt-system)——层
管线、两个入口点（`Basic` / `Cached`）、可缓存/瞬态边界。harness 的
`agent/prompt.rs` 每回合恰好调用一次
`PromptBuilder::build_system_prompt_cached_with_mode`。

## 工具 —— `src/tools/` + `src/builtin_tools/`

`ToolService` 是注册表也是分派入口点。三个子系统：

- **Scoping**（`src/tools/scoped/`）——每次请求运行时的 allowlist / deny /
  健康过滤。机械的 `retain` 操作，不受 LLM 影响。
- **资源 claim**（`src/tools/resource_claim.rs`）——每个工具自声明 `Shared` /
  `Exclusive{Global}` / `Exclusive{Paths}` 之一，Act 阶段据此判定哪些可并行。
  声明间串行，声明内并发。
- **结果溢出**（`src/tools/{turn_budget, result_store}.rs`）——Layer 3 把超大
  工具输出溢出到磁盘；按会话作用域的 `ToolResultStore`。
- **Calling**（`src/tools/calling/`）——schema 约束的工具调用 parse /
  serialize；harness 的 `act` 通过 provider 适配器消费 `NativeToolCall`。

并发工具批在 harness 的 `act` 步骤内部完成，不在独立的 dispatcher 里；见
`HarnessDeps.parallel_tool_concurrency`。

## 会话 —— `src/session/`

仅追加的事件日志。框架是**事件溯源**，不是快照——
`SqliteEventStore` 加 `InProcessActorSessionService`，通过
`get_events(session, Some(seq), None)` 构造 replay。harness 用
`from: watermark+1` 读，`last_prompt_seq` 记录当前回合 prompt 覆盖到的最后
一个事件 seq。没有独立的 checkpoint 子系统：Git 风格的 checkpoint trait 草稿
作为死抽象被（P5 retraction）撤回。

## 记忆 —— `src/memory/`

三种存储，各自分离：

- **Facts DB / 向量检索** — `src/memory/` 核心
- **Curated memory envelope** — 预渲染的 `<CuratedMemory>` 块
  （`CuratedMemoryLayer` @60，Stable），thread 到每个 `LayerInput` 里，让
  prompt-cache 保持暖。
- **Recall message** — 每次查询的语义 recall 以**瞬态尾部 user message**
  形式传输（`HarnessDeps::recall_context`），从不进 system prompt。放进
  system prompt 会让每次 run 都 re-key 整个会话前缀 cache；放在 message
  尾部只让自己开销自己。

## 上下文管理 —— `src/context/`

两个互补子系统：

- **`src/context/budget/`** ——`ContextBudget`、`PreflightPipeline`、
  `pressure::*`。抛出 `LoopDirective`（`CompactToFit`、`SplitSession` 等），
  harness 机械执行。
- **`src/context/compact/`** ——`ContextCompactor`、`directive.rs`（分派器）、
  `rescue.rs`（反应式救援宿主）、`pipeline.rs`、`plan_carry.rs`。反应式
  救援用 `context/compact/rescue.rs` 的 `MAX_REACTIVE_COMPACT_ATTEMPTS`
  限定，harness 里的救援 slot 走一个 52 行的适配器读这个常量——
  `rg "crate::harness" src/context/` 返回空（缝在 context、state 在 harness）。

## 编排器 —— `src/orchestrator/`

为每次 run 装配 `AgentHarness`：

- `resolver.rs` ——`RoutingOverrides`、`MAX_FLOW_DEPTH`
- `flow_spec.rs` ——`FlowSpec`、`FlowOverrides`、`SessionStrategy`
- `flow_registry.rs` ——按 `agent_id` 注册 `FlowSpec`
- `dispatch.rs` ——`Orchestrator`、`FlowHandle`、`FlowOutcome`、
  `FlowRequest`、`FlowStreamEvent`、`HarnessRunner`、`TerminateReason`
- `harness_bridge/` ——`AgentHarnessRunner`（从 flow dispatch 下到 harness
  构造的桥）
- `deps_builder/` ——装配 `HarnessDeps` 的 helper
- `sandbox_factory.rs` ——每 flow 的 sandbox 策略

orchestrator 是 **DI 装配器**，不是协调器。每个 run 它只做一个决定（honour
哪个 `AgentDef` + 哪个 `FlowSpec`）；之后控制流进 harness。

## 子代理平面 —— 故意保留分离

原本计划搞一个 `SubagentOrchestrator` trait，带 `Fork` / `Handoff` / `Graph`
模式。因为零消费者被（P5 retraction）撤回——没有任何调用点要这个 trait。今天
四个平面正交共存：

- `src/agents/` ——`SubagentTool`、`AgentRuntime`、注册表、subagent spawner
- `src/teams/` ——team 协调器
- `src/orchestrator/` ——多代理 dispatch（上文已述）
- `src/group_chat/` ——群聊 shared-nothing 广播

每个持有不同职责。**没有** facade。

## 验证 & 反馈 —— `src/verification/`

`VerifierChain` 在每次迭代的 Think 和 Act 之间被 consult
（`src/harness/agent/think.rs::run_verifiers`）。组成：

- `StopHookVerifier` ——保持 Stage 6a 之前「veto 前于 Done」的语义
- `ToolLoopVerifier` ——侦测 `tool_use` 死循环

`Veto` 强制额外一次 Continue，让模型可以反应；不是硬停。还有按 model id 的
`ModelRobustnessProfile`，通过 `HarnessDeps.robustness_profile` 传递，让
验证器灵敏度按模型行为伸缩。

## 护栏 —— 4 域分离

`src/{security, sandbox, approval, pii}/` ——四个独立域，不是 `Guardrail`
facade。harness 在合适的缝上挂载：

- **输入护栏** ——`agent/guardrails.rs` 挂 `GuardrailRegistry::screen_session_input`；
  对历史消息也跑（`Block` 决定降级为 redaction，因为不可变历史不能砖一个
  会话）。
- **输出护栏** ——`agent/think.rs`，流式 finalize 之后但在 commit 之前；
  max-output-tokens 续跑拼接各段。
- **工具调用护栏** ——`agent/guardrails.rs::apply_tool_call_guardrail`，outcome
  为 `Pass | Sanitize(Value) | Block`。在 `act` 的 PASS 0 顺序应用，
  然后才进 parallel `join_all`（Pi 风格的先 validate 再 execute）。

`safety.rs`、`truncation_recovery.rs`、`streaming_bridge.rs` 也是 harness
安全面的一部分，但留在 `src/harness/agent/` 里。

## 初始化 & 环境 —— `src/init_unified/`

见 [启动装配](/docs/zh/architecture/boot-assembly)。`InitializationCoordinator`
跑 5 阶段 setup（`src/init_unified/coordinator.rs`，从 `src/lib.rs:99` 重新
导出）；运行时 boot 通过 `src/bin/aleph-server/commands/start/`（5 个
sub-builder，总计约 6,194 LOC）。

## 哪些东西**不存在**（且这份名单很短）

遗产的 `src/components/{intent_analyzer, task_planner, tool_executor,
loop_controller, session_recorder, session_compactor}.rs` 目录和它的 5（或者
6）个 `EventHandler` 风格订阅者，在 2026-04 → 2026-07 的 harness dissolution
浪潮里被解散：

- 意图分类是 LLM 的活（R8），不是基于规则的分析器。
- 在循环里搞任务 DAG 规划破坏 ReAct（R8 / R10 第 1 不）。
- 工具执行住在 `src/tools/scoped/dispatch.rs::execute_inner`——loop 只知道
  `act(call)`。
- 循环保护（`max_iterations`、`consecutive_failure_cap`、每工具超时、
  验证器 veto）是 `HarnessDeps` 上的配置，不是一个组件。
- 会话记录是 `src/session/SqliteEventStore`，一个事件日志——换了个名字的
  同一个东西。

删掉 `src/components/` facade 移除了约 3,000 行死订阅者，没改任何外部
行为。

## 代码位置

- `src/harness/` ——Think→Act driver（12 文件；行数棘轮）
- `src/thinker/` ——PromptBuilder + PromptPipeline 层
- `src/tools/`、`src/builtin_tools/` ——`ToolService`、scoping、资源 claim
- `src/session/` ——`SessionService`、`SqliteEventStore`
- `src/memory/` ——facts DB、向量检索、recall 消息组装
- `src/context/{budget,compact}/` ——压力传感器 + 压缩器 + 反应式救援
- `src/verification/` ——`VerifierChain`、`StopHookVerifier`、`ToolLoopVerifier`
- `src/{security,sandbox,approval,pii}/` ——护栏域
- `src/orchestrator/` ——`Orchestrator`、`AgentHarnessRunner`、`HarnessDeps` builders
- `src/agents/` ——`SubagentTool`、`AgentRuntime`、注册表
- `src/teams/`、`src/group_chat/` ——多代理平面
- `src/init_unified/` ——`InitializationCoordinator` + 启动期连线
