消息是 Aleph 中的基本通信单位。无论用户通过 Telegram 发送文本、在 CLI 中键入命令，还是通过桌面应用提交提示，每个交互在被代理接收之前都被规范化为 Aleph 的统一消息格式。这种抽象允许同一个代理大脑为每个接口服务而无需修改。

## 消息类型

Aleph 在不同边界用三种相关但不同的消息表示：

1. **`UnifiedMessage`**（`src/providers/message.rs`）—— LLM 无关的中间表示；协议适配器把它转成 OpenAI / Anthropic / Gemini / Ollama 的原生形态。三变体：`User { content }`、`Assistant { content }`、`ToolResult { tool_call_id, tool_name, content, is_error }`。
2. **`MessageContent`**（`src/session/events.rs`）—— `session_events` 日志里一条消息的内容；`text` + 可选 `blocks: Vec<serde_json::Value>` + 可选 `thinking` / `thinking_signature`。
3. **`AlephEvent`**（`src/event/types.rs`）—— 系统级事件总线载荷，覆盖 `InputReceived` / `ToolCallRequested` / `ToolCallStarted` / `ToolCallCompleted` / `ToolCallFailed` / `ToolCallRetrying` / `LoopContinue` / `LoopStop` / `SessionCreated` / `SessionUpdated` / `SessionResumed` / `SessionCompacted` / `SubAgentCompleted` / `SubAgentTreeUpdate` / `AiResponseGenerated` / `PartAdded|Updated|Removed` / `Team*`。

### 内容块（`UnifiedMessage`）

助手消息可携带多个 `ContentBlock`，支持丰富多模态响应（`src/providers/message.rs`）：

```json
{
  "role": "assistant",
  "content": [
    { "type": "thinking", "thinking": "让我分析这段代码...", "signature": "..." },
    { "type": "text", "text": "这是重构后的版本：" },
    { "type": "tool_call", "id": "call_1", "name": "file_write", "arguments": { "path": "main.rs", "content": "..." }, "thought_signature": null }
  ]
}
```

`ContentBlock` 五变体：`Text { text, cache_control? }`、`Json { value }`、`Thinking { thinking, signature? }`、`ToolCall { id, name, arguments, thought_signature? }`、`Image { data, mime_type }`。`thinking`/`thought_signature` 字段由 Anthropic / Gemini 3 这类供应商用于把签名块原样回放给后续轮次；没有签名机制的供应商留空。

## 消息路由

当消息从任何接口到达时，它通过网关遵循精确的路由路径到达代理：

```
用户发送消息 (例如 Telegram)
    │
    ▼
通道层 (Telegram Bot → InboundMessage)
    │ 规范化为 InboundMessage { id, channel_id, conversation_id, sender_id, text, attachments, ... }
    ▼
网关: 入站路由器 (inbound_router)
    │ 解析 JSON-RPC，鉴权、配对、DM/群组策略门
    ▼
SessionKey 解析 (src/routing/session_key.rs)
    │ SessionKey::Main | DirectMessage | Group | Task | Subagent | Ephemeral
    ▼
会话管理器 (SessionActor)
    │ 加载 session_events 历史，追加新消息
    ▼
Orchestrator::dispatch(FlowRequest)
    │ FlowRequest { agent_id, input, channel, session_hint?, parent_session?, depth, tool_service?, trace_sink?, interaction_manifest?, ... }
    ▼
HarnessRunner::run(session_key, spec, input, sandbox, events, cancel, ...)
    │ 观察 → 思考 → 行动 → 反馈
    ▼
网关: 出站发射器 (GatewayEventBus)
    │ 订阅 FlowStreamEvent 并广播到客户端
    ▼
通道层
    │ OutboundMessage / Channel::send / NativeStreamHandler
    ▼
用户接收响应
```

### Channel 抽象

每个接口实现 `Channel` trait（`src/gateway/channel.rs`），把平台特定的消息规范化为通用格式：

```rust
#[async_trait]
pub trait Channel: Send + Sync {
    fn info(&self) -> &ChannelInfo;
    fn state(&self) -> &ChannelState;
    async fn start(&mut self) -> ChannelResult<()>;
    async fn stop(&mut self) -> ChannelResult<()>;
    async fn send(&self, message: OutboundMessage) -> ChannelResult<SendResult>;
    // ...
}
```

通道侧的核心数据结构：`ChannelId` / `ConversationId` / `UserId` / `MessageId`（newtype 字符串）、`InboundMessage` / `OutboundMessage`、`ChannelCapabilities`（附件/反应/编辑/删除/打字/已读/富文本/最大长度/最大附件/流协议）、`ChannelStatus`、`StreamProtocol::{None, EditBased, Native}`。

### Interaction Manifest

每个通道声明其能力给 Thinker（`src/thinker/interaction.rs`）：

```rust
InteractionManifest::new(InteractionParadigm::Messaging)   // 默认 RichText + ImageInline
    .with_capabilities(my_set)                              // 覆盖默认能力集
    .with_constraints(
        InteractionConstraints::new()
            .max_output_chars(4096)
            .supports_streaming(true)
            .prefer_compact(false)
    );
```

可用范式：

| 范式 | 说明 | 默认能力 |
|----------|-------------|---------------------|
| `CLI` | 终端接口 | RichText, CodeHighlight, Streaming |
| `WebRich` | 完整 Web 接口 | RichText, CodeHighlight, MultiGroupUI, Streaming, MermaidCharts, ImageInline, Canvas |
| `Messaging` | 聊天平台 (Telegram, Discord, iMessage) | RichText, ImageInline |
| `Background` | 计划/cron 任务 | SilentReply |
| `Embedded` | 受限环境 | 空集 |

`Capability` 完整集合：`RichText` / `InlineButtons` / `MultiGroupUI` / `Streaming` / `ImageInline` / `MermaidCharts` / `CodeHighlight` / `FileUpload` / `Canvas` / `SilentReply` / `NativeIdentity`。`paradigm_for_channel_type` 在 `src/gateway/channel.rs` 末尾给出通道字符串到范式的查表（`cli → CLI`、`telegram|feishu|slack|whatsapp|discord|irc|msteams|wechat|line → Messaging`、`webchat|webrich|web|webhook → WebRich`，未知落 `Background`）。

## 会话线程

Aleph 用一个分层的 `SessionKey`（`src/routing/session_key.rs`）枚举隔离跨通道、用户和上下文的对话 —— 不是自由字符串，而是结构化枚举。

### SessionKey 变体

```rust
pub enum SessionKey {
    Main { agent_id, main_key, epoch },
    DirectMessage { agent_id, channel, peer_id, dm_scope, epoch },
    Group { agent_id, channel, peer_kind: PeerKind, peer_id, thread_id? },
    Task { agent_id, task_type, task_id },
    Subagent { parent_key: Box<Self>, subagent_id },
    Ephemeral { agent_id, ephemeral_id },
}
```

`SessionKey::Display` 把它们序列化成路径式字符串，便于人类阅读与持久化：

| 变体 | 序列化形式示例 | 用例 |
|---------|--------|----------|
| **Main** | `agent:main:main` | 跨通道共享会话 |
| **DirectMessage** | `agent:<id>:<channel>:dm:<peer>` | 每用户 DM |
| **Group** | `agent:<id>:<channel>:group:<peer>[:thread:<id>]` | 群组/频道 |
| **Task** | `agent:<id>:task:<type>:<id>` | Cron、Webhooks |
| **Subagent** | `subagent:<parent>:<id>` | 子代理委派 |
| **Ephemeral** | `agent:<id>:ephemeral:<uuid>` | 临时会话 |

### DM 范围策略

```rust
#[serde(rename_all = "kebab-case")]
#[derive(Default)]
pub enum DmScope {
    Main,             // 所有 DM 共享主会话
    #[default]
    PerPeer,          // 按用户隔离（默认）
    PerChannelPeer,   // 按通道 + 用户隔离
}
```

默认 `PerPeer` 意味着每个与 Aleph 聊天的人都获得自己的对话历史，无论他们使用哪个平台。`SessionKey::dm` 在 `dm_scope == Main` 时直接退化成 `Main`，让所有 DM 共享同一个会话。

## 消息持久化

会话事件以 `SessionEventRecord { seq, event, created_at_ms }`（`src/session/events.rs`）的形态追加进 `session_events` 表。`MessageProjector`（`src/gateway/session_projector.rs`）观察事件流并物化到 `messages` 表；启动时 `ProjectionReconciler` 回填老会话。**两个表都不再被双写**——`session_events` 是单一来源（SSOT），`messages` 是只读投影。

### Session Compaction

当会话积累太多 token（超过配置的阈值）时，会话管理器触发压缩：

1. 从旧消息中提取关键事实。
2. 将提取的事实存储在[内存系统](/docs/zh/architecture/memory)中以供长期检索。
3. 用简洁的摘要替换旧消息。
4. 更新 token 计数。

这个过程对用户透明。代理通过摘要和事实存储保留对完整对话的意识。

## 事件流式传输

当代理处理消息时，它通过 `GatewayEventBus` 发出 `FlowStreamEvent`（`src/orchestrator/dispatch.rs`）实时事件，客户端用 JSON-RPC `events.subscribe` 订阅：

```json
{
  "jsonrpc": "2.0",
  "method": "events.subscribe",
  "params": { "pattern": "stream.*" },
  "id": 1
}
```

`FlowStreamEvent` 变体（面板/客户端主要消费的子集）：

| 主题/事件 | 负载 |
|-------|---------|
| `Delta(text)` | 助手增量文本 |
| `Reasoning(text)` | 思维链片段（当供应商回传 thinking） |
| `ToolCallStart { id, name, args }` | 工具调用开始 |
| `ToolCallDone { id, result?, error?, duration_ms }` | 工具调用结束（完成序而非输入序） |
| `ContextGauge { context_tokens, context_window, total_tokens }` | 实时上下文窗口占用 |
| `SafetyBlock { reason }` | 安全门阻断本轮 |
| `Complete(FlowOutcome)` | 终态事件，必为最后一个 |

底层 `AlephEvent` 总线还携带 `InputReceived` / `ToolCallRequested` / `ToolCallRetrying` / `SubAgentCompleted` / `SubAgentTreeUpdate` / `Team*` 等，供监视器与跨智能体路由使用。

## 安全上下文

每条消息都携带一个流经整个执行链的身份上下文（`shared/protocol/src/auth.rs`）：

```rust
pub struct IdentityContext {
    pub request_id: String,
    pub session_key: String,
    pub role: Role,              // Owner, Guest, Anonymous
    pub identity_id: String,
    pub scope: Option<GuestScope>,
    pub created_at: i64,
    pub source_channel: String,
}
```

身份上下文一旦创建就不可变，并确定代理可以代表用户调用哪些工具。所有者会话具有不受限制的访问权限，而访客会话限于其 `GuestScope` 中列出的工具。详见[安全部分](/docs/zh/security/overview)。

## JSON-RPC 协议

客户端和网关之间的所有消息交换都使用 JSON-RPC 2.0 over WebSocket。`chat.send` 的实际参数形态（`src/gateway/handlers/chat.rs`）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "chat.send",
  "params": {
    "message": "解释 Rust 借用检查器",
    "session_key": "agent:main:main",
    "channel": "cli:term1",
    "stream": true,
    "thinking": null,
    "attachments": [],
    "agent_id": null,
    "project_root": null,
    "model_override": null,
    "exec_tier": null,
    "mode": null,
    "voice_input": false
  }
}
```

字段说明：`stream` 默认 `true`；`thinking` / `mode` / `exec_tier` 都是 `Option<String>`（没有内嵌默认值，`mode` 字段而不是单独的 `session_mode`）；`mode` 在 Panel composer 里被选成 `chat` / `work` / `code` 三态，并由首条消息携带以避免覆盖。

**接收流式响应：**
```json
{
  "jsonrpc": "2.0",
  "method": "event",
  "params": {
    "topic": "stream.chunk",
    "data": {
      "run_id": "run-123",
      "content": "借用检查器是 Rust 的..."
    }
  }
}
```

## 26.7.x 补充

### 会话事件单源真值

26.7.7 引入 `session_events` 作为**规范**事件日志：

- `MessageProjector` 把 `SessionEvent` 物化到 `messages` 表
- 启动时 `ProjectionReconciler` 回填转写
- 消息携带 `tool_call_id` / `tool_name` + `AssistantMessage` 上的 token 戳
- 旧会话被回填并在锁定的 invariant 后读取；不再有 `messages` 表的双写

### UnifiedMessage 与 ProviderDelta

26.7.7+ 的 `src/providers/` 引入 `UnifiedMessage` 与 `ProviderDelta`：

- `UnifiedMessage` 是 LLM 无关的中间消息表示（OpenAI / Anthropic / Gemini / Ollama 都适配到它），三变体 `User` / `Assistant` / `ToolResult`
- `ProviderDelta` 是流式输出（`TextDelta` / `ThinkingDelta` / `ThinkingSignatureDelta` / `ToolCallStart` / `ToolCallArgDelta` / `ToolCallArgsComplete` / `ToolCallEnd` / `Usage` / `Done` / `Error`）
- `DeltaCollector` 单一 reducer 拥有装配后的消息，实时拼接 thinking 签名
- 流式与最终文本通过同一个共享 sanitize atom 路由

### 消息流

26.7.7 引入**叙述引领**的聊天流：

- 紧凑单行工具行（状态符号、实时用时）
- 完成后 `✓N steps` 一行汇总
- 工作区窗格变成 live-follow 前台会话（带 pin）的工具详情查看器
- 工具事件以完成顺序（而非输入顺序）发出（`buffer_unordered` 完成驱动环）

### Steering 中途

26.6.29+ 起支持在聊天还在跑的时候往里打字：

- 队列中的消息渲染为流内 "ghost" 气泡
- 在下一轮边界通过 steering flush，或立即强制插入（Esc + ⚡）
- 注入的消息**不再产生非法消息序列**；工具结果保持连续，所以 OpenAI 兼容代理不再默默返回空响应

### iMessage tapback

26.7.21 起：iMessage 入站 add-tapback（add-reaction）会上抛为模型上下文（通过 `InboundMessage::metadata` 携带），而不是被丢弃。
