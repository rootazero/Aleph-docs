Aleph 把 **Skill**、**Plugin** 与 **MCP server** 统一为面向用户的一种概念：**Extension**。Hub 让用户按功能浏览，查看 Kind 与信任层级，查看安装披露，配置密钥，执行安装、验证、启用/禁用与卸载。

## 一种概念，三种 Kind

| Kind | 内容 | 后端 |
|---|---|---|
| **Skill** | `SKILL.md` 指令与可选支撑文件 | 共享 `SkillSystem` |
| **Plugin** | 静态组件、MCP 配置或 WASM runtime | `ExtensionManager` 与市场安装器 |
| **MCP** | 外部 stdio 或远程 Model Context Protocol server | `McpManager` |

主浏览轴是功能分类：Search、Developer、Data、Productivity、Writing、Communication、Knowledge、Files、Design、Automation、Finance、Utilities、Other。Kind 与信任层级保留为过滤项与卡片徽章。

## Aleph Hub 是目录源

官方目录源是单一的 **`aleph-hub`** 工件：

```text
https://hub.heyaleph.com/catalog.json
```

守护进程把归一化后的目录持久化在：

```text
~/.aleph/hub_catalog.db
```

每个工件包含 schema 版本、Hub ID、客观的扩展条目、信任层级与 `install_spec`。`installed` / `enabled` 等用户态字段在本地贴标，绝不来自线缆。

冷启动时 `hub::primer` 仅在 `aleph-hub` 槽为空时填充它，把捆绑的官方 MCP、技能与插件投影合并进同一槽；非空的成功 fetch 会整体替换该槽；失败或空响应则保留 last-good 缓存。摄取阶段执行 schema 校验与条目文本的提示注入扫描。

目录层不是多个独立 provider 的并发联邦，安装解析是对 `ExtensionEntry.install_spec` 的直接本地缓存查找。插件市场仍是插件安装后端，并非额外的 Hub 目录槽。

已退出的 MCP 预设 RPC 不再是发现入口。MCP 的发现与安装统一收敛到 Hub 目录。

## 已安装状态对账

`extensions.catalog` 读取缓存目录并叠加实时已安装集合。`extensions.installed` 本地查询 MCP 管理器、插件管理器与共享 SkillSystem，因此已安装视图不依赖网络。

本地条目 ID 形如 `local:{kind}:{backend_id}`。目录条目保持目录 ID，不被 toggle 或 uninstall 接受；生命周期操作需要本地已安装 ID。未匹配的本地 MCP server 与本地技能仍以「未在目录中」状态展示。

MCP 目录条目按确定性派生的 server ID 匹配。插件与技能条目按 Kind 与大小写不敏感的 name 匹配。启用状态始终取自实时后端。

## 信任与披露

每次 Hub 安装都会先构建披露。信任层级：

- `Official`
- `Verified`
- `Community`
- `Unverified`

披露按安装规格生成对应字段：

- stdio 模式下的精确命令与参数
- 必需和敏感的密钥，必要时附用途
- 声明的网络端点或文件系统/运行时触达
- 版本
- 当目录或市场提供时附 SHA-256 摘要
- 信任层级与来源
- 条目文本的注入扫描结果

风险从安装规格推导：

| 安装形态 | 显示风险 |
|---|---|
| MCP stdio | 在你的计算机上运行命令 |
| MCP remote | 连接远程端点 |
| Skill 或 Plugin checkout | 可以指挥智能体 |
| OCI image | 会运行命令，但当前版本不可安装 |

Community 与 Unverified 的运行命令类安装需要用户显式确认。用于技能或插件的 Git checkout 始终需要用户手势，因为它写入指令或可执行内容。OCI/Docker MCP 镜像作为目录条目可浏览，但当前安装路由会拒绝。

密钥写入加密保险库的扩展字段命名空间。MCP 配置中保存 `{{secret:NAME}}` 引用而非明文；密钥仅在进程 spawn 边界被解析。

批准路径会扫描名称与描述中的零宽字符、双向覆盖与可疑指令，例如「忽略先前指令」「读取 .env」「外泄数据」「暴露系统提示」等。

## 安装流水线

```text
目录条目
  → 解析缓存的 InstallSpec
  → 构建披露与注入扫描
  → 需要时用户确认
  → 校验必需配置
  → 密钥字段入保险库
  → 按 InstallSpec 路由
  → 安装后验证
  → 返回结果与已批准的 pin
```

路由映射：

- `McpStdio` / `McpRemote` → 通过 `McpManager` 添加并启动
- kind `Skill` 的 `GitDir` → 隔离 checkout，复制进技能目录，记录来源
- kind `Plugin` 的 `GitDir` → 市场安装并校验 SHA-256、原子复制
- `OciImage` → 当前版本拒绝

stdio MCP 的命令必须已经在 `PATH` 上可解析；缺运行时在持久化 server 之前即失败。

## 内置 Hub 工具与代理边界

当前活动内置工具：

| 工具 | 角色 |
|---|---|
| `hub_catalog_sync` | 拉取 Aleph Hub 工件到本地缓存 |
| `hub_resolve_spec` | 读取条目的缓存安装规格 |
| `hub_install_run` | 执行系统信任关卡与干净安装 |
| `hub_install_verify` | 校验 MCP server 或已安装工件 |
| `hub_fetch_docs` | 注入扫描过的长尾文档抓取脚手架 |

主分支目前没有独立 `hub-agent`，`HUB_TOOLS` 也不是由某个代理独占的 allowlist。这些工具都注册在主内置工具注册表里；`hub_install_run` 是 operator 闸门，而只读校验代理会显式拒绝 Hub 工具。LLM 控制的调用无法提供用户确认：需要确认的安装只返回披露与同意提示，不会产生安装或密钥存储副作用。

`hub_fetch_docs` 是带 SSRF 检查、注入扫描与字节上限的脚手架，没有接入任何用户长尾安装流程。不要把它描述为自主仓库安装。

## 网关门面

UI 使用一层薄的 `extensions.*` 门面：

| 方法 | 用途 |
|---|---|
| `extensions.catalog` | 按 Kind、分类、源 ID 或 name 查询浏览缓存 |
| `extensions.installed` | 三后端的实时对账 |
| `extensions.disclosure` | 返回安装前披露与扫描结果 |
| `extensions.install` | 完成信任确认、安装、验证并返回 pin |
| `extensions.toggle` | 启用或禁用本地已安装扩展 |
| `extensions.uninstall` | 移除本地已安装扩展 |

各 Kind 的高级入口仍可用，包括规范的单数 `plugin.*` 命名空间与复数 `plugins.*` 兼容别名。
