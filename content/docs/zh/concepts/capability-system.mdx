Aleph 把三个问题分开处理：

1. 插件或扩展注册了什么。
2. 插件声明需要哪些资源。
3. 当前运行中的代理被允许执行什么。

`src/extension/capability.rs` 回答第一个问题；插件清单的权限段以及共享的 scoped-tool、审批、沙箱层回答另两个问题。

## 能力声明

生产中的声明枚举刻意保持精简：

```rust
pub enum CapabilityDeclaration {
    Tool(ToolRegistration),
    Hook(HookRegistration),
    Service(ServiceRegistration),
    Skill(SkillRegistration),
    Agent(AgentRegistration),
    McpServer(McpServerConfig),
}
```

每条声明由一个插件或运行时（针对 MCP server 配置）所有。注册器校验所有权并派发到 `PluginRegistry` 或 MCP 路径。

| 变体 | 注册目标 | 层级 |
|---|---|---|
| `Tool` | 可调用工具注册表 | Core |
| `Hook` | 钩子执行器 | Core |
| `Skill` | 插件技能注册表与共享 SkillSystem | Core |
| `Agent` | 代理注册表 | Important |
| `Service` | 服务管理器 | Pluggable |
| `McpServer` | MCP 管理器集成 | Pluggable |

插件的 `commands/` Markdown 在技能注册表里以命令型技能存放。当前声明模型不再有独立的 channel、provider、HTTP-route、CLI、gateway-method 变体。

`CapabilitySource` 记录插件 ID、发现来源与清单格式；支持的来源格式包含 Claude Code、Aleph TOML、Codex、Cursor、自动发现与运行时注册。

## 插件权限

Aleph 扩展清单在权限段声明资源需求：

```toml
[aleph.permissions]
network = true
filesystem = "read"
env = true
shell = false
background = false
```

权限词汇：

- `network`
- `filesystem:read` / `filesystem:write` 或完整文件系统访问
- `env`
- `shell`
- `background`

`[[aleph.services]]` 声明需要 `background = true`。WASM 专属声明可以进一步约束工作区前缀、HTTP 端点、凭证、速率限制、工具调用与密钥注入。

这些是声明与宿主注册门，并不给代理无条件的执行权。调用仍会经过 scoped tool service、工具元数据、审批策略、执行档位与沙箱命令策略。

## 工具强制

工具策略是动作感知的，依赖工具自身声明的元数据，而不是从名字猜。有效权限合并显式工具规则、agent 与 channel 策略以及执行档位；最严格的适用规则胜出。

用户视角的执行档位：

| 档位 | 行为 |
|---|---|
| `ask` | 每次可变操作前询问；未知工具默认拒绝 |
| `auto` | 幂等工具自动放行；破坏性操作仍需审批 |
| `full` | 除独立安全硬底线外全部自动放行 |

`[sandbox.command_policy]` 就是这条硬底线：任何执行档位与插件声明都不能压低它。动作感知审批把授权指纹绑定到具体命令，而不是仅绑定到工具名。

operator 闸门是面向自身管理操作的另一道边界。例如 `hub_install_run`、技能管理、身份操作不能仅因为插件声明了能力就被普通 chat 档 channel 启用。

## 运行时能力账本

`node`、`uv`、`ffmpeg`、`playwright-cli` 等运行时二进制使用与扩展能力不同的账本：

```text
~/.aleph/runtimes/ledger.json
```

`CapabilityLedger` 是「Aleph 当前能否使用某个运行时可执行文件」的唯一持久化来源。它不下载也不安装任何东西。探测与引导模块负责这些动作，然后更新账本。

账本条目记录：

- 能力名
- 可执行路径
- 检测到的版本
- 上次成功探测时间
- 来源：`system` 或 `aleph_managed`
- 状态：`missing` / `probing` / `bootstrapping` / `ready` / `stale`

运行时安装流程：

```text
加载账本
  → 探测 PATH 与 Aleph 管理路径
  → 解析依赖
  → 当有支持的安装规格时执行引导
  → 校验产物二进制
  → 原子写入 Ready 状态
```

`runtimes.list` 读取账本与运行时规格。`runtimes.refresh` 探测已知能力。`runtimes.install` 接受能力名，异步执行并发布进度事件；终态持久化在同一份 `ledger.json`。缺失或损坏的账本会被重建而不是被信任。

这份运行时账本既不是 Hub 目录，也不是 Hub 信任披露，也不是每个插件的能力声明。Hub 条目在 `hub_catalog.db` 中自带 `InstallSpec`、信任层级、版本与可选 SHA-256 pin。

## 安全边界

- 清单在注册前经过校验。
- 能力所有权阻止插件注册属于其他插件的组件。
- 插件与技能内容在不可信安装前接受注入与危险模式扫描。
- 密钥走加密保险库与运行时注入边界。
- 工具执行在共享 scoped-tool 闸口强制。
- 运行时安装按能力名串行化，仅记录经验证的可执行状态。
