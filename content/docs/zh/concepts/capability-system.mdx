本页解决第一次遇到「能力」（capability）这个词时的歧义：Aleph 的代码里有三代东西都叫这个名字，必须分清哪一代是现状、哪一代是规划。

## 能力的三层含义

| 层 | 回答的问题 | 代码里叫什么 | 现在到哪一步 |
|---|---|---|---|
| **插件声明的能力**（旧模型） | 这个插件想贡献什么：工具、钩子、服务、技能…… | `CapabilityDeclaration`（`src/extension/capability.rs`） | 现状，插件清单适配器仍在产出它 |
| **运行时能力描述符**（现行） | 运行时里这个能力是什么、谁拥有、对谁可见、此刻还有效吗 | `CapabilityDescriptor`、`OwnershipTree`、`Zahir`（`src/capability/`） | 现状，`ZahirFacade` 已挂载；部分模块未挂载，见 [Capability 模型](../capabilities/capability-model) |
| **槽位与替换** | 一个功能位置由哪个后端实现，用户怎么换掉它 | 契约 crate `crates/aleph-slot-api/`（`SlotId`、`ContractVersion`） | 规划中：契约类型存在，槽位目录与替换机制是蓝图 |

三层互不替代：旧声明只描述「插件说它有什么」，不是运行时能力；描述符才带修订号、所有权、可见性与契约版本；槽位目录目前只存在于蓝图里。

## 旧的声明枚举

`src/extension/capability.rs` 定义 `CapabilityDeclaration`，是插件能贡献内容的统一声明模型。它有 7 个变体：

```rust
pub enum CapabilityDeclaration {
    Tool(ToolDeclaration),
    Hook(HookDeclaration),
    Service(ServiceDeclaration),
    Skill(SkillDeclaration),
    Agent(AgentDeclaration),
    McpServer(McpServerDeclaration),
    Context(ContextDeclaration),
}
```

（源码各变体带文档注释，这里去掉。）每个变体与 `PluginRegistry` 里的一种注册类型一一对应：`ToolDeclaration` 是 `ToolRegistration` 的别名，`HookDeclaration`、`ServiceDeclaration`、`SkillDeclaration`、`AgentDeclaration` 同理，`McpServerDeclaration` 是 `McpManagerConfig`。

| 变体 | 注册目标 | 层级（`Tier`） |
|---|---|---|
| `Tool` | 可调用工具注册表 | Core |
| `Hook` | 钩子执行器 | Core |
| `Skill` | 插件技能注册表与共享 SkillSystem | Core |
| `Agent` | 代理注册表 | Important |
| `Service` | 服务管理器 | Pluggable |
| `McpServer` | MCP 管理器集成 | Pluggable |
| `Context` | 上下文描述符及其 WASM 传输导出；不是授权 | Pluggable |

层级由 `CapabilityDeclaration::tier()` 给出，决定注册顺序与冲突解决。插件的 `commands/` Markdown 在技能注册表里以命令型技能存放，没有独立变体。

`CapabilitySource` 记录插件 ID、发现来源（`PluginOrigin`）与清单格式（`SourceFormat`）。清单适配器 `AdapterOutput.capabilities: Vec<CapabilityDeclaration>`（`src/extension/manifest/adapter.rs`）把各平台格式（Claude Code、Aleph TOML、Codex、Cursor、自动发现）解析成统一的声明列表。

<Callout type="warn" title="声明不是运行时能力">
  `CapabilityDeclaration` 只是**声明**：它说明一个插件打算注册什么，经过注册器校验后落进各自的注册表。它没有修订号、没有 owner generation、不能被撤销、也不保证拿到的 handler 是新的。需要这些保证的消费方应读 `src/capability/` 的描述符与租约。
</Callout>

## 现行能力子系统

`src/capability/` 是 2026-11 起的运行时能力子系统，解决四件事：授权、撤销、失效传播、避免使用陈旧 handler。核心构件：

- **描述符**（`src/capability/descriptor.rs`）：`CapabilityDescriptor` 带 `id`、`kind`（12 种 `CapabilityKind`）、`schema` 指纹、`revision`、`lifetime`、`visibility`、`owner`、`facets`。
- **所有权**（`src/capability/ownership.rs`）：`OwnershipTree` 以代（`OwnerGeneration`）管理绑定，支持 `bump`、`rotate_capability`、`revoke`、`dispose`，变更经 `subscribe_changes` 通知观察者。
- **租约与门面**（`src/capability/facade.rs`、`src/capability/zahir_facade.rs`）：`Zahir::resolve` 签发 `BackendLease`，`Zahir::validate_lease` 在使用前复核；owner 代一变，租约立即视为失效。
- **策略**（`src/capability/policy.rs`、`src/capability/production_init.rs`）：启动期按能力 id 配置时间窗口、资源上限与必需条件。

字段、变体与错误文本的完整参考见 [Capability 模型](../capabilities/capability-model)。

## 关系图

```text
插件清单（Claude Code / Aleph TOML / Codex / Cursor）
        │  src/extension/manifest/adapter.rs
        ▼
CapabilityDeclaration        ← 静态声明：插件说它有什么
        │  注册器校验、写入各注册表（src/extension/registrar/、registry/）
        ▼
ToolHandlerRegistry 等       ← 运行时注册表（可调用 Tool 的唯一真值源）
        │  ToolBackendAdapter（src/capability/backend.rs）折叠成描述符
        ▼
CapabilityDescriptor + OwnershipTree 绑定
        │  Zahir::resolve → BackendLease（带 owner_generation）
        ▼
Zahir::validate_lease        ← 使用前复核；撤销 / 换代 / provider 替换 → 拒绝
```

注意这条链并不覆盖所有声明：只有进入可调用 Tool 注册表（以及 provider、special、memory 后端）的内容会被折叠成描述符；`Skill`、`Agent` 等声明目前走各自的注册表，没有对应的描述符适配器（`src/capability/descriptor.rs` 注释：除 Tool、Ambient、Terminal、Ui 外的 kind 在所属后端挂载前只是描述性的）。

## 相邻机制：权限、工具强制与运行时账本

下面三项不属于能力描述符，但常被一并称为「能力」，放在这里划清边界。

### 插件权限

Aleph 扩展清单在权限段声明资源需求：

```toml
[aleph.permissions]
network = true
filesystem = "read"
env = true
shell = false
background = false
```

权限词汇：`network`、`filesystem:read` / `filesystem:write` 或完整文件系统访问、`env`、`shell`、`background`。`[[aleph.services]]` 声明需要 `background = true`。WASM 专属声明可以进一步约束工作区前缀、HTTP 端点、凭证、速率限制、工具调用与密钥注入。

这些是声明与宿主注册门（解析在 `src/extension/manifest/`），并不给代理无条件的执行权。调用仍会经过 scoped tool service、工具元数据、审批策略、执行档位与沙箱命令策略。

### 工具强制

工具策略是动作感知的，依赖工具自身声明的元数据，而不是从名字猜。有效权限合并显式工具规则、agent 与 channel 策略以及执行档位（`src/config/types/policies/exec_tier.rs`）；最严格的适用规则胜出。

| 档位 | 行为 |
|---|---|
| `ask` | 每次可变操作前询问；未知工具默认拒绝 |
| `auto` | 幂等工具自动放行；破坏性操作仍需审批 |
| `full` | 除独立安全硬底线外全部自动放行 |

`[sandbox.command_policy]`（`src/sandbox/command_policy/`）是这条硬底线：任何执行档位与插件声明都不能压低它。动作感知审批把授权指纹绑定到具体命令，而不是仅绑定到工具名。强制发生在共享的 scoped-tool 闸口（`src/tools/scoped/`）。

operator 闸门是面向自身管理操作的另一道边界：`hub_install_run`、技能管理、身份操作不能仅因为插件声明了能力就被普通 chat 档 channel 启用。

### 运行时能力账本

`node`、`uv`、`ffmpeg`、`playwright-cli` 等运行时二进制使用与扩展能力不同的账本：

```text
~/.aleph/runtimes/ledger.json
```

`CapabilityLedger`（`src/runtimes/ledger.rs`）是「Aleph 当前能否使用某个运行时可执行文件」的唯一持久化来源。它不下载也不安装任何东西；探测与引导（`src/runtimes/ensure.rs`）负责这些动作，然后更新账本。条目记录能力名、可执行路径、检测到的版本、上次成功探测时间、来源（`system` 或 `CapabilitySource::AlephManaged`）与状态（`missing` / `probing` / `bootstrapping` / `ready` / `stale`）。

RPC：`runtimes.list` 读取账本与运行时规格，`runtimes.refresh` 探测已知能力，`runtimes.install` 接受能力名、异步执行并发布进度事件，终态持久化在同一份 `ledger.json`（`src/gateway/handlers/runtimes.rs`）。缺失或损坏的账本会被重建而不是被信任。

这份账本既不是 Hub 目录，也不是 Hub 信任披露，更不是每个插件的能力声明；它与 `CapabilityDescriptor` 也没有关系。

## 规划中

> **状态：规划中** — 蓝图为 `docs/research/aleph_modularization_plan.md`（模块化重构方案）；当前实现见 `src/capability/` 与 `crates/aleph-slot-api/`。

- **槽位目录**（蓝图第 3 节）：为每个功能位置定义固定的槽位 ID、契约版本、内置默认实现与允许的替换后端。当前代码里只有契约类型 `SlotId`、`ContractVersion`（`crates/aleph-slot-api/src/slot.rs`），且该模块注释明确它只关联、不授权。
- **替换机制**（蓝图第 4 节）：用声明式配置把内置实现替换为 MCP、WASM 或插件后端，可热生效、可回退。代码里没有这套配置面。
- **统一分发注册表、非工具槽位统一**（蓝图第 8 节，8.2）：一张注册表对应多种后端，并把非工具槽位也纳入统一分发。当前可调用 Tool 的唯一真值源仍是 `ToolHandlerRegistry`，其它槽位各走各的路径；`src/capability/versioned_registry.rs` 提供的只是不可变快照发布原语。

另见 `docs/research/Everything-externally-composable-is-a-Capability.md`（Zahir 与「一切可外部组合的东西都是能力」的总纲，同为蓝图）；其中「协议即投影」「可逆 / 持久效果」「依赖图」三项与当前实现的差距见 [Capability 模型](../capabilities/capability-model) 的「规划中」一节。

## 历史：静态能力声明模型

早期的能力模型就是上面那个声明枚举：插件在清单里声明自己有哪种能力，注册器按声明类型把它们派发到注册表。当时的枚举比现在更宽，后来被精简成当前的 7 个变体；例如 Aleph 仓库提交 `a0d84eb1f`（extension: withdraw dead Channel capability）撤回了一个没有生产使用方的 Channel 声明。渠道、provider、HTTP 路由、CLI、gateway 方法等不再有独立变体。

它不再足够，是因为静态声明回答不了运行时才出现的问题：

- 无法表达运行时变化：能力在运行中被替换、停止或换代，声明本身不变。
- 无法撤销：声明一经注册，没有统一的撤销与处置路径。
- 无法保证 handler 新鲜度：消费方没有办法知道自己手上的 handler 是否还是当前那一份。

当前代码里的替代路径：描述符带 `revision`（`src/capability/descriptor.rs`），所有权树提供 `revoke` / `dispose` / `bump`（`src/capability/ownership.rs`），门面用 `BackendLease` 加 `validate_lease` 保证使用前复核（`src/capability/facade.rs`）。旧枚举没有被删除，它仍负责「插件声明什么」这一件事。
