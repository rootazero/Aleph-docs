Aleph 把模型供应商的 HTTP 协议与消息频道的收发适配分开。协议适配器负责模型请求和流式增量；频道适配器负责入站事件、权限前置、会话路由和出站能力。Telegram、Discord 和 iMessage 不是模型协议，也不共享供应商协议注册表。

## 提供商协议层

供应商配置引用协议名称，由协议注册表解析动态 YAML 协议或编译进程序的协议实现。OpenAI 兼容供应商可以复用 `openai` 协议，而不需要为每个供应商复制适配器；原生 Messages、Gemini、OpenAI Responses、Codex/ChatGPT 和 Ollama 等协议保留各自的请求与流解析差异。

动态协议位于 `~/.aleph/protocols/`，变更经过防抖、解析和原子注册后生效。动态名称优先于内置名称；找不到时返回包含可用协议的错误。协议层不负责 Telegram/Discord/iMessage 的 pairing、allowlist、频道 ID 或消息长度。

## 频道适配层

所有频道实现 `src/gateway/channel.rs` 的 `Channel` trait，通过 `ChannelInfo` 暴露 `ChannelCapabilities`。能力标志是承诺：声明支持某项能力的适配器必须实现对应方法，否则默认方法返回 `UnsupportedFeature`，不会虚报成功。

配置型频道通过 `src/gateway/interfaces/plugin.rs` 的 `ChannelFactory` 注册。`register_channel_plugins` 当前注册 Telegram、Discord 以及其他可配置频道；iMessage 是例外，由频道初始化流程直接构造，故不依赖该插件表。

## Telegram 边界

Telegram 当前适配器使用 teloxide 长轮询，处理消息、附件、回复、编辑式流、状态 reaction、贴纸和 inline callback。它在接口层只做 DM/群组策略与静态 allowlist 的快速分类：

- `open`、`allowlist`、`pairing` 和 `disabled` 由 DM/群组策略决定；
- 未在静态 allowlist 中、但允许 pairing 的 DM 返回 `NeedsPairing`，随后转交 inbound router；
- pairing 状态、配对批准和最终访问决定由 router 的 `check_permission` 与 `pairing_store` 单源负责；
- 频道不再维护自己的 pairing code store、运行时 paired-user 集合、webhook 服务器、session manager 或 draft API。

Telegram 声明附件、图片、音频、视频、reaction、回复、编辑和 Markdown/HTML 等能力，单条消息上限为 4096 字节级平台限制，流协议为 edit-based。它不是一个 Webhook 适配器。

## Discord 边界

Discord 通过已注册的 `DiscordChannelFactory` 接入，处理 guild/DM 消息、slash command、组件按钮、嵌入、附件、回复、编辑式流和 reaction。入站消息、slash command 以及 approval 按钮都执行同一组 DM、guild 和 channel allowlist：

- `dm_allowed` 控制私信；
- `allowed_guilds` 限制服务器；
- `allowed_channels` 限制服务器内频道；
- 组件按钮只把 callback 转成带 `cb_` 前缀的入站消息并交给 router 的 `ApprovalCallbackSink`；Discord 适配器不保存审批状态。

Discord 声明附件、媒体、reaction、回复、编辑、删除、输入状态和 Markdown，消息上限为 2000，普通附件上限为 25 MB。Bot 权限审计是独立的权限位检查，不等同于 Gateway 的频道 allowlist。

## iMessage 边界

iMessage 是一个频道类型、两种传输：

| 传输 | 入站 | 出站 | 平台边界 |
| --- | --- | --- | --- |
| Local | macOS chat.db 轮询 | AppleScript | 仅 macOS，需要 Full Disk Access 与 Automation；不能发送 tapback，`reactions` 为 false |
| BlueBubbles | REST + webhook，可选 catch-up poll | BlueBubbles REST | 任意操作系统；支持附件、回复、reaction；reaction 需要 private-api，编辑和删除不声明支持 |

本地 iMessage 轮询会把 add-tapback 转成带 `MessageMeta::Reaction` 的入站上下文，并过滤 remove-tapback；因此“模型能看到用户新增 reaction”不表示本地传输能发送 reaction。BlueBubbles 的 reaction 还会校验 tapback 名称和 private-api 能力。

## 地址与路由

频道的 `ChannelId` 标识传输，`ConversationId` 标识平台会话，`ChannelCapabilities` 描述可用操作。Gateway 的 `channel_directory` 只读取路由元数据，`channel_message` 执行发送；DM/群组策略、pairing 和 allowlist 仍由 inbound router 约束，频道适配器不能绕过这些边界。

## 代码位置

- `src/providers/protocols/` — 模型供应商协议与注册
- `src/gateway/channel.rs` — 频道 trait、地址和能力
- `src/gateway/interfaces/plugin.rs` — 频道工厂表
- `src/gateway/interfaces/telegram/` — Telegram 长轮询、策略前置和路由转交
- `src/gateway/interfaces/discord/` — Discord 消息、组件和权限前置
- `src/gateway/interfaces/imessage/` — Local 与 BlueBubbles 传输
- `src/gateway/inbound_router/` — 统一入站权限、pairing 和会话路由
