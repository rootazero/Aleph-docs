Aleph is built on an event-driven architecture. Every significant action — a tool call, a session starting, a cron job firing, a configuration change — emits a structured event. You can subscribe to these events in real time over WebSocket, enabling dashboards, monitoring systems, external integrations, and reactive automation pipelines.

## Architecture

Events flow through two internal buses:

1. **Core Event Bus** — Handles agent lifecycle events (`AlephEvent`). Built on `tokio::sync::broadcast` channels for low-latency in-process delivery. Every component of the agent loop publishes here: tool calls, session state changes, planning events, sub-agent activity.

2. **Daemon Event Bus** — Handles system-level events (`DaemonEvent`). The perception daemon watches the environment — filesystem changes, process activity, system state, time triggers — and publishes observations here.

Both buses feed into the Gateway's event subscription system, which exposes them as a unified stream to external clients over WebSocket.

```
┌──────────────────────────────────────────────────────────────┐
│                      Internal Buses                           │
│                                                               │
│  Agent Loop ──▶ Core Event Bus ──┐                           │
│                                   ├──▶ Gateway Event Router  │
│  Daemon    ──▶ Daemon Event Bus ──┘         │                │
│                                              │                │
│                                     ┌────────┴────────┐      │
│                                     │  Pattern Matcher │      │
│                                     └────────┬────────┘      │
│                                              │                │
│                              ┌───────────────┼───────────┐   │
│                              ▼               ▼           ▼   │
│                         Client A        Client B    Client C  │
│                        stream.*        agent.*        *       │
└──────────────────────────────────────────────────────────────┘
```

## Event Categories

### Streaming Events (`stream.*`)

Emitted during an agent run. These are the most frequent events and power real-time UIs.

They arrive as **JSON-RPC notifications**: `method` is one of the `stream.*` names and `params` is the event payload itself (no `event` envelope around it). Subscription matching uses that `method` name.

| Method | Description | Key Fields |
|-------|-------------|------------|
| `stream.run_accepted` | Run was accepted | `run_id`, `session_key`, `accepted_at` |
| `stream.run_queued` | Run was queued | `run_id`, `session_key`, `ahead` |
| `stream.reasoning` | Reasoning step (chain-of-thought) | `run_id`, `seq`, `content`, `is_complete` |
| `stream.tool_start` | Agent is invoking a tool | `run_id`, `seq`, `tool_name`, `tool_id`, `params` |
| `stream.tool_update` | Tool call progress | `run_id`, `seq`, `tool_id`, `progress` |
| `stream.tool_end` | Tool execution completed | `run_id`, `seq`, `tool_id`, `result`, `duration_ms` |
| `stream.agent_trace` | Agent internal trace | `run_id`, `seq`, `event` |
| `stream.response_chunk` | Text chunk from the agent | `run_id`, `seq`, `delta`, `full_text`, `is_final` |
| `stream.context_gauge` | Context usage | `run_id`, `seq`, `context_tokens`, `context_window`, `total_tokens` |
| `stream.run_complete` | Run finished | `run_id`, `seq`, `summary`, `total_duration_ms` |
| `stream.run_error` | Run failed | `run_id`, `seq`, `error`, `error_code` |
| `stream.ask_user` | Agent asks the user a question | `run_id`, `seq`, `session_key`, `request_id`, `question` |
| `stream.clarification_ended` | Clarification round ended | `session_key`, `request_id`, `outcome` |
| `stream.uncertainty_signal` | Agent signals uncertainty | `run_id`, `seq`, `uncertainty`, `suggested_action` |
| `stream.model_resolved` | Model selected for this run | `run_id`, `seq`, `model_info` |
| `stream.run_retrying` | Run is being retried | `run_id`, `seq`, `provider`, `attempt`, `max_attempts`, `reason` |
| `stream.session_updated` | Session metadata updated | `session_key` |
| `stream.session_user_message` | A user message landed in the session | `session_key`, `author_user_id`, `content`, `timestamp` |
| `stream.running_set_changed` | The set of running sessions changed | `seq`, `running` |

### Agent Events (`agent.*`)

Agent registration and binding changes.

| Topic | Description | Key Fields |
|-------|-------------|------------|
| `agent.lifecycle.registered` | Agent was registered | `agent_id`, `workspace`, `model` |
| `agent.lifecycle.deleted` | Agent was deleted and its workspace archived | `agent_id`, `workspace_archived` |
| `agent.lifecycle.bound` | A channel's agent binding was switched | `agent_id`, `channel`, `previous_agent` |
| `agent.lifecycle.unbound` | A channel's explicit agent binding was cleared | `channel`, `previous_agent` |

The lifecycle of an agent **run** (start, output, end) does not live in this namespace: those frames reach the wire as `stream.*` notifications (see the section above). Each frame also carries an internal `agent.*` topic name, but subscription matching uses the notification's `method`, not that name.

### Session Events (`session.*`)

Session state and content changes.

| Topic | Description | Key Fields |
|-------|-------------|------------|
| `session.updated` | Session metadata updated | `session_key` |
| `session.user.message` | A user message landed in the session transcript | `session_key`, `author_user_id`, `content`, `timestamp`, `seq` |
| `session.lifecycle.changed` | Session state transition | `session_key`, `old_state`, `new_state`, `reason` |

### Cron Events (`cron.*`)

Changes to the scheduled job **definition** itself.

| Topic | Description | Key Fields |
|-------|-------------|------------|
| `cron.job.changed` | Job created, updated, deleted, or only its runtime state changed | `job_id`, `change` |

`change` is one of `created`, `updated`, `deleted`, `state_changed`.

Job **execution results** are not on the event stream: use `cron.runs` for a job's run records (`status` is one of `ok`, `error`, `skipped`, `timeout`) and `cron.status` for the overall picture (`running`, `last_tick_at_ms`, `job_count`, `enabled_count`).

### Config Events (`config.*`)

Configuration changes.

| Topic | Description | Key Fields |
|-------|-------------|------------|
| `config.changed` | A configuration section was modified | `section`, `value` |
| `config.reloaded` | Configuration file was reloaded | `agents`, `timestamp` |
| `config.error` | Configuration file failed validation | `error`, `timestamp` |

### Approval Events (`approval.*`)

Command execution approval flow.

| Topic | Description | Key Fields |
|-------|-------------|------------|
| `approval.requested` | A human approval is needed | `approval_id`, `session_key`, `channel_id`, `conversation_id`, `tool_call_id` |
| `approval.reminder` | An unanswered approval is re-announced | `approval_id`, `session_key` |
| `approval.resolved` | The approval was decided | `approval_id`, `session_key`, `decision`, `resolved_by` |
| `approval.expired` | The approval timed out | `approval_id`, `session_key` |

`decision` is one of `allow-once`, `allow-session`, `allow-always`, `deny`.

Approval events use the `approval.*` topics; `exec.*` is the **method** namespace for listing pending approvals and deciding them: `exec.approvals.pending`, `exec.approval.resolve`, `exec.grants.list`, `exec.grant.revoke`.

### Daemon Events

The daemon emits its own event hierarchy for environmental awareness:

**Raw events** — direct observations from watchers:
- `TimeEvent` — cron schedule matches, interval ticks, absolute time triggers
- `ProcessEvent` — process started, stopped, CPU/memory threshold exceeded
- `FsEvent` — file created, modified, deleted, renamed
- `SystemStateEvent` — battery level, network status, display sleep, user activity, system load

**Derived events** — inferred from patterns in raw events:
- `ActivityChanged` — user activity type changed (coding, browsing, meeting, etc.)
- `ProgrammingSessionStarted` / `ProgrammingSessionEnded` — detected coding sessions
- `ResourcePressureChanged` — system resource pressure level transitions
- `MeetingStateChanged` — detected meeting start/end
- `IdleStateChanged` — user went idle or returned

**System events** — daemon self-management:
- `WatcherStarted` / `WatcherStopped` — watcher lifecycle
- `ConfigReloaded` — daemon configuration changes
- `Error` — daemon-level errors

## Subscribing to Events

### Via WebSocket (Gateway RPC)

The primary way to receive events. Connect to the gateway WebSocket and subscribe with glob patterns:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "events.subscribe",
  "params": {
    "patterns": ["stream.*", "agent.*", "cron.*"]
  }
}
```

Events arrive as JSON-RPC notifications (no `id` field):

```json
{
  "jsonrpc": "2.0",
  "method": "event",
  "params": {
    "topic": "session.lifecycle.changed",
    "data": {
      "session_key": "agent:main:main",
      "old_state": "idle",
      "new_state": "running"
    },
    "timestamp": 1706400000000
  }
}
```

Streaming frames use the other envelope — `method` is directly one of the `stream.*` names and the payload sits in `params`:

```json
{
  "jsonrpc": "2.0",
  "method": "stream.run_complete",
  "params": {
    "run_id": "run-uuid-123",
    "seq": 42,
    "summary": "done",
    "total_duration_ms": 5000
  }
}
```

<Callout type="info">
Events are fire-and-forget. The server does not wait for acknowledgement. If the client disconnects, events during the disconnection are lost. There is no replay or catch-up mechanism — design your consumers to be tolerant of gaps.
</Callout>

### Managing Subscriptions

Subscriptions are additive. Calling `events.subscribe` multiple times adds new patterns without removing existing ones.

```json
// Add more patterns
{ "method": "events.subscribe", "params": { "patterns": ["config.*"] } }

// Remove specific patterns
{ "method": "events.unsubscribe", "params": { "patterns": ["stream.*"] } }

// List active subscriptions
{ "method": "events.list" }
```

See [events.* RPC methods](/docs/en/gateway/methods/events) for the full API specification.

## Glob Pattern Matching

Event subscription patterns use glob-style matching against the topic string:

| Pattern | Matches |
|---------|---------|
| `stream.*` | All streaming events |
| `agent.*` | Every topic starting with `agent.` (e.g. `agent.lifecycle.registered`) |
| `session.*` | All session topics |
| `cron.*` | All cron topics (e.g. `cron.job.changed`) |
| `*` | Everything |
| `stream.response_chunk` | Exact match only |
| `*.changed` | Two-segment topics ending in `changed` (e.g. `config.changed`) |

Matching rules: `*` on its own or in trailing position matches every remaining segment; in a middle position it matches exactly one segment; everything else matches segment by segment, exactly. `cron.job.changed` has three segments, so `*.changed` does not match it — use `cron.*` for that.

## Event Payload Structure

Every event delivered over WebSocket follows this envelope:

```typescript
interface EventNotification {
  jsonrpc: "2.0";
  method: "event";
  params: {
    topic: string;        // e.g. "session.lifecycle.changed"
    data: Record<string, any>;  // event-specific payload
    timestamp: number;    // Unix timestamp in milliseconds
  };
}

// Streaming frames do not use the envelope above: method is one of the stream.* names
interface StreamNotification {
  jsonrpc: "2.0";
  method: string;         // e.g. "stream.run_complete"
  params: Record<string, any>;  // frame payload
}
```

Both shapes can be normalized into one handler:

```javascript
function readEvent(frame) {
  if (frame.method === "event") {
    return {
      topic: frame.params.topic,
      data: frame.params.data,
      timestamp: frame.params.timestamp
    };
  }
  if (typeof frame.method === "string" && frame.method.startsWith("stream.")) {
    return { topic: frame.method, data: frame.params, timestamp: null };
  }
  return null;
}
```

### Core Event Types (Internal)

Internally, Aleph uses a typed event system with sequence numbers for ordering:

```rust
pub struct TimestampedEvent {
    pub event: AlephEvent,
    pub timestamp: i64,      // millisecond precision
    pub sequence: u64,       // monotonically increasing
}
```

The `AlephEvent` enum covers all core event types: `InputReceived`, `ToolCallStarted`, `ToolCallCompleted`, `ToolCallFailed`, `SessionCreated`, `SubAgentStarted`, `AiResponseGenerated`, and more. The gateway maps these to the topic-based format for external consumption.

## Building Reactive Integrations

### Real-Time Dashboard

Subscribe to all events and render them in a web UI:

```javascript
const ws = new WebSocket("ws://localhost:3001");

ws.onopen = () => {
  ws.send(JSON.stringify({
    jsonrpc: "2.0",
    id: 1,
    method: "events.subscribe",
    params: { patterns: ["*"] }
  }));
};

ws.onmessage = (msg) => {
  const frame = JSON.parse(msg.data);
  const evt = readEvent(frame);
  if (!evt) return;
  updateDashboard(evt.topic, evt.data, evt.timestamp);
};
```

### Monitoring and Alerting

Watch for errors and failures across the system:

```javascript
// Subscribe to failure events: a failed agent run is stream.run_error,
// a channel error is channel.error, a failed config validation is config.error
ws.send(JSON.stringify({
  jsonrpc: "2.0",
  id: 1,
  method: "events.subscribe",
  params: { patterns: ["stream.run_error", "channel.error", "config.error"] }
}));

ws.onmessage = (msg) => {
  const frame = JSON.parse(msg.data);
  const evt = readEvent(frame);
  if (!evt) return;
  sendAlert({
    channel: "#aleph-alerts",
    text: `[${evt.topic}] ${JSON.stringify(evt.data)}`
  });
};
```

### Tool Usage Analytics

Track which tools the agent uses most and how long they take:

```javascript
ws.send(JSON.stringify({
  jsonrpc: "2.0",
  id: 1,
  method: "events.subscribe",
  params: { patterns: ["stream.tool_start", "stream.tool_end"] }
}));

const toolMetrics = {};

ws.onmessage = (msg) => {
  const frame = JSON.parse(msg.data);
  const evt = readEvent(frame);
  if (!evt) return;

  const { topic, data } = evt;

  if (topic === "stream.tool_start") {
    toolMetrics[data.run_id] = {
      tool: data.tool_name,
      startedAt: Date.now()
    };
  }

  if (topic === "stream.tool_end") {
    const start = toolMetrics[data.run_id];
    if (start) {
      recordMetric(start.tool, Date.now() - start.startedAt);
      delete toolMetrics[data.run_id];
    }
  }
};
```

### Cron Job Status Board

Monitor scheduled job health:

```javascript
ws.send(JSON.stringify({
  jsonrpc: "2.0",
  id: 1,
  method: "events.subscribe",
  params: { patterns: ["cron.*"] }
}));

ws.onmessage = (msg) => {
  const frame = JSON.parse(msg.data);
  const evt = readEvent(frame);
  if (!evt) return;

  const { topic, data } = evt;

  // cron.job.changed only says the job definition changed
  // (change: created | updated | deleted | state_changed);
  // execution results (ok / error / skipped / timeout) come from cron.runs.
  if (topic === "cron.job.changed") {
    setJobStatus(data.job_id, data.change);
  }
};
```

## Daemon Event-Driven Automation

The daemon's event system enables environment-aware automation. The daemon watches the world and emits events that can trigger agent actions:

### Context-Aware Responses

The daemon detects when you start a programming session and can proactively offer help:

- **`ProgrammingSessionStarted`** — Detected IDE launch + file changes in a project directory
- **`ActivityChanged`** — Transitions between coding, browsing, meetings, etc.
- **`IdleStateChanged`** — User went idle (opportunity for background tasks)
- **`ResourcePressureChanged`** — System running low on memory or battery

### Time-Based Triggers

The daemon evaluates cron expressions and interval timers, emitting `TimeEvent` events:

- `Cron { expression }` — Matched a cron schedule
- `Interval { seconds }` — Interval timer tick
- `Absolute { time }` — Reached a specific timestamp

These time events are what drive the cron job system internally — the daemon fires the trigger, and the cron scheduler picks it up for execution.

## Design Principles

1. **Events are immutable facts** — Once emitted, events are never modified. They represent something that happened.
2. **Fire-and-forget delivery** — Publishers do not wait for consumers. This keeps the agent loop fast.
3. **No guaranteed delivery** — Events can be lost if no subscriber is listening or if the buffer overflows. Design consumers accordingly.
4. **Typed internally, stringly externally** — The core uses Rust enums for compile-time safety. The gateway maps them to dot-separated topic strings for language-agnostic consumption.
5. **Sequence ordering** — Each event carries a monotonically increasing sequence number for causal ordering within a single Aleph instance.
