## How the desktop app runs

The Aleph desktop app uses NSH 0.6.0 (`desktop/nsh-shell/Cargo.toml`). NSH manages windows, the tray, shortcuts, notifications, and device credentials. A separate `aleph-server` process provides inference, tools, state, and the Gateway.

The NSH WebView opens the Gateway root. The local default is `http://127.0.0.1:18790/`. For a remote target, the app opens the saved HTTPS Gateway origin. The Gateway serves the same Leptos/WASM Panel users can open directly in a browser. See `desktop/nsh-shell/src/launch.rs`, `desktop/nsh-shell/src/app.rs`, and `src/gateway/control_plane/server.rs`. [Panel Host](./panel) covers the build and the optional TSX AppView.

## Local and remote connections

| Mode | Startup and service lifetime |
|---|---|
| Packaged app, local target | The default `embedded-core` feature lets the host connect to a compatible local Gateway or start its bundled `aleph-server`. |
| Packaged app, remote target | Opens the selected Gateway's HTTPS origin. The connection form can save the target. The remote deployment owns the service. |
| CLI `--connect <origin>` | Opens an existing Gateway for this launch. A remote origin requires HTTPS. This option does not persist the target. |

For remote NSH desktop connections, use an HTTPS Gateway origin with a certificate trusted by the operating system. A generated self-signed certificate is rejected by the NSH connection probe (`desktop/nsh-shell/src/gateway_probe.rs`).

Local admission first checks the loopback port. A definite connection refusal permits the host to launch the sibling server binary. It polls a compatible Gateway that is still starting and reports an error for an incompatible or unknown listener. Admission checks `/health`, `/ready`, and the Panel compatibility marker. Service identity and user authorization are handled by their respective protocols. See `desktop/nsh-shell/src/local_service.rs`, `desktop/host/src/local_server.rs`, and `desktop/host/src/local_server/admission.rs`.

Ordinary Quit closes the app and allows the bundled service to keep running. Select **Quit Aleph and Stop Server** to also stop the service this app instance owns (`desktop/nsh-shell/src/app.rs`, `desktop/nsh-shell/src/menu.rs`). An existing compatible service stays under its original process owner.

## Command-line interface

| Flag | Behavior |
|---|---|
| `--connect <origin>` | Opens the Panel of an existing Gateway. |
| `--autostart-status` | Reads the desktop app's login-item status. |
| `--desktop-ipc-status <endpoint>` | Queries `health` once over a local endpoint on a Gateway started with Desktop IPC enabled. |

These options are mutually exclusive and defined in `desktop/nsh-shell/src/cli.rs`.

## Native integration

The behavior below lives in `desktop/nsh-shell/src/app.rs` and `desktop/nsh-shell/src/panel_bridge.rs`.

### Window and tray

- `desktop/nsh-shell/nsh.json` declares the app window and identity.
- Closing the main window hides it (`desktop/nsh-shell/src/app.rs`).
- The tray provides commands for opening the window, connecting, notification permission, reloading, and quitting. macOS also has an app menu. Update checks depend on the host updater configuration (`desktop/nsh-shell/src/menu.rs`, `desktop/nsh-shell/src/update.rs`).

### Global hotkey

The default hotkey is `mod+shift+a`, which shows or hides the main window. The environment variable `ALEPH_SHELL_HOTKEY` overrides it, and `disabled` skips registration. An invalid hotkey or a refusal by the OS is only logged and does not affect startup.

### Notifications

The Panel sends a `Notify` message through the bridge. The host requests an OS notification only when the window is not both visible and focused, and shows it only if the OS permission is `Granted`. The title must be non-empty and at most 256 bytes, and the body at most 2048 bytes (`valid_notification` in `shared/protocol/src/panel_shell.rs`). The pending queue holds one item; when it is full the message is dropped and logged. Pressing a notification (identifier `aleph-panel-chat`) shows and focuses the window and then opens Chat. OS notification permission is not a product feature switch, and the host provides no switch that disables the notification feature (`docs/reference/DESKTOP_SHELL.md`).

### Deep links and the URL scheme

The host registers the `aleph` URL scheme (`.url_schemes(["aleph"])`). `desktop/nsh-shell/src/panel_bridge.rs` receives OS open events through `next_url_scheme_open`. Today it recognizes only a URL exactly equal to `aleph://open`, which it handles as "ask the Panel to open Chat"; any other `aleph://` URL is ignored.

Opening Chat is document-bound. The host first sends `Probe`, the Panel answers `Ready` with a 32-character lowercase hex `document` identifier, then the host sends `OpenChat` and waits for `ChatOpened`. If there is no confirmation within 2 seconds the host gives up and does not replay the action.



### Credentials

`desktop/nsh-shell/src/credentials.rs` gives the Panel local access to device credentials. The backend is `aleph_client::DeviceCredentialStore`, keyed by Gateway address; for the default target the Gateway address is `ws://127.0.0.1:18790/ws`. A `CredentialCall` sent by the Panel through the bridge has exactly three operations: `Load`, `Save` (with a `lease_id` and a `DeviceConnectCredential`) and `Delete` (with a `lease_id`). Replies are `Loaded`, `Saved`, `Deleted { existed }` or `Failed { error }`, and the only errors are `Unavailable`, `Rejected` and `Malformed` (`shared/protocol/src/panel_shell.rs`). When the page navigates or reloads, the host invalidates the existing credential lease (`CredentialService::invalidate`).

### Login item

`desktop/nsh-shell/src/autostart.rs` only reads the login-item status of the current application. It is not server autostart and has no write path. The statuses are `Enabled`, `Disabled`, `RequiresApproval`, `Unavailable { reason }` and `Failed`. Every non-macOS platform returns `Unavailable { reason: UnsupportedPlatform }`.

On macOS it reads `SMAppService::mainAppService().status()` after an identity check: the process must run inside an `.app` bundle (otherwise `NotAppBundle`), the bundle identifier must equal `APP_ID` and the executable must sit under `Contents/MacOS` (otherwise `IdentityMismatch`), and the system must provide `SMAppService` (macOS 13 and later, otherwise `ApiUnavailable`).

## Desktop IPC and platform support

Desktop IPC is the Gateway's **explicit opt-in local RPC entry point**. The tree contains two platform shapes: a Unix domain socket on Unix and a named pipe on Windows. Both share the same frame format, the same handshake and the same RPC loop, but the **production entry point is currently open on Unix only** — on Windows both opt-in commands are refused by the same gate. This section first separates the flags of the two programs, then gives the cross-platform matrix.

### Read-only IPC status query

The host-side query command is `--desktop-ipc-status <socket>`: it reads the Gateway's `health` once over Desktop IPC (a Unix domain socket on Unix). It does not open the Panel and does not fall back to WebSocket (`desktop/nsh-shell/src/ipc_status.rs`).

- The arguments must be exactly this pair (the flag plus one endpoint); on Unix the endpoint must be an absolute path with a file name, on Windows it must be an explicit local named pipe; combining it with QA configuration is refused.
- The handshake uses `ProtocolVersion { major: 1, minor: 0 }`, client name `aleph-nsh-shell`, `ui_runtime: "nsh"` and an empty feature list.
- The `health` call times out after 5 seconds and closing the connection after 2 seconds; the response must have `status == "healthy"` and a non-empty `timestamp`, otherwise the query fails.
- On non-Unix platforms it fails immediately with `Desktop IPC is unavailable on this platform`. That refusal comes from the client-side availability gate, not from missing implementation code: the Windows named-pipe endpoint validation is in the tree (`shared/client/src/local_ipc/windows.rs`), it is simply unreachable while the gate is false.

The Gateway being queried must have been started beforehand with the server-side `--desktop-ipc <endpoint>`; see the transport matrix on the [Panel host](./panel) page.

### Server-side opt-in: `--desktop-ipc <endpoint>`

The server-side switch is `aleph-server`'s `--desktop-ipc <endpoint>`. It belongs to a different program than the host's `--desktop-ipc-status` flag: the former makes the Gateway mount a local listener, the latter makes the host read the status once.

- The flag is defined in `src/bin/aleph-server/cli.rs`: the value name is `ENDPOINT` (it was `SOCKET_PATH` before commit `5d89d7aff`, because on Windows it is not a socket path), the help text reads "Opt in to read-only Desktop IPC at an explicit local endpoint", and it goes on to say "Unix requires a fresh absolute socket path in a caller-owned 0700 directory. The server leaves the Unix socket entry after exit."
- The entry check lives in `src/bin/aleph-server/main.rs`: with the flag present it first tests the client-side gate `aleph_client::local_ipc::AVAILABLE` and returns `Desktop IPC is unavailable on this platform` when that is false; it then requires the command to be `start` (or absent), otherwise it returns `--desktop-ipc is only available when starting the Gateway`; only on the Windows branch does it afterwards call `aleph_client::local_ipc::windows::validate_endpoint` for named-pipe endpoint validation.
- The mount path lives in `run_with_desktop_ipc` in `src/gateway/server/mod.rs`: it makes the same `AVAILABLE` assumption and returns `Desktop IPC is unavailable on this platform` when it is false; when it is true it goes through `run_local_endpoint`, which calls `bind` in `src/gateway/server/connection/local_ipc.rs` — validation first, then the bind. The comment there states that binding never replaces an occupied entry, that the caller owns the directory, and that the Gateway does not mutate the directory's entries after binding.

### Cross-platform implementation matrix

| Dimension | Unix | Windows |
|---|---|---|
| Endpoint shape | Unix domain socket, absolute path | Named pipe, path prefix `\\.\pipe\` |
| Available in production | Yes | No: both opt-in commands are refused |
| Endpoint validation | Absolute path; the parent directory must be owned by the current uid with mode exactly `0700`; the parent must not be swapped after canonicalization | Must carry the `\\.\pipe\` prefix; the pipe name must be non-empty, must not end in `.` or a space, must keep name plus prefix within 256 UTF-16 code units, and must contain no control characters and none of `\ / :` |
| Authentication | Same account: the peer uid must match this process | Same account: the pipe object's owner SID must equal the server's account SID, and the server then compares the impersonated client account; the client pins the server process with `GetNamedPipeServerProcessId` and re-checks that process's account and that it is still alive |
| Listener implementation | `src/gateway/server/connection/local_ipc.rs` | `src/gateway/server/connection/local_ipc/windows.rs` |
| Client implementation | the `unix` module in `shared/client/src/local_ipc.rs` | `shared/client/src/local_ipc/windows.rs` |
| Host status query | `desktop/nsh-shell/src/ipc_status.rs` | the Windows branch of the same file (in the tree, but behind the gate) |

The validations in the matrix are implemented on the client side, one set per platform:

- Unix endpoint validation is `private_endpoint` in `shared/client/src/local_ipc.rs`: the path must be absolute (otherwise `IPC endpoint must be an absolute socket path`), the parent directory must be owned by the current uid with mode exactly `0700` (otherwise `IPC endpoint requires an owned mode-0700 parent`), the parent must not be swapped after canonicalization (otherwise `IPC parent changed`), and no ancestor directory may have an untrusted owner or be writable by others (otherwise `IPC parent has an untrusted ancestor`).
- Unix authentication is `require_same_user` in the same file: a peer uid that differs from this process is disconnected (`IPC peer account mismatch`); the client also checks that the endpoint really is a socket owned by the current uid (`IPC endpoint is not an owned socket`).
- Windows endpoint validation is `validate_endpoint` in `shared/client/src/local_ipc/windows.rs`; the account side has `PipeAccount::current`, `PipeAccount::create` (which builds the DACL from the account SID, grants that one account full access and sets remote clients to be rejected) and `authenticate_client`, and the client side has `connect`.
- The Windows listener (`src/gateway/server/connection/local_ipc/windows.rs`) obtains the current account with `PipeAccount::current` in `bind` and uses it to create the first named-pipe instance (`MAX_CONNECTIONS` is the cap on allowed instances); when the pipe is busy it retries and replenishes within the `HELLO_TIMEOUT` budget — the comment there explains why it cannot give up immediately: dropping a Mio pipe cancels the overlapped I/O, but the kernel handle can stay alive until its completion is delivered.

### What the two platforms share

Windows is not a separate protocol. Admitted connections reuse the same RPC loop as on Unix — the file header comment of `src/gateway/server/connection/local_ipc/windows.rs` says that admitted connections use the shared RPC loop.

- The limits are identical: `MAX_CONNECTIONS = 8`, `WIRE_BUDGET = 16 MiB`, `WRITE_TIMEOUT = 5s` (`src/gateway/server/connection/local_ipc.rs`).
- The first frame is `system.hello`; subsequent requests use the shared `V1_METHODS` allowlist. See [Protocol v1](../gateway/protocol-v1) and `src/gateway/server/connection/mod.rs`.
- A connection grants no network-origin privileges: `NO_NETWORK_ORIGIN` is 0.0.0.0 (`src/gateway/server/connection/local_ipc.rs`).

### Why the Windows production entry point is still closed

The Windows named-pipe implementation is complete: the client, the Gateway listener, the host CLI validation and the QA script are all in the tree (`qa/nsh_desktop_ipc_windows.py`). What is closed is the **production entry point**, and the reason is stated plainly: the independent-account authorization evidence is not complete yet. The code repository commit `5d89d7aff` says "Keep production Windows Desktop IPC disabled until its independent-account authorization evidence is complete."

`docs/reference/DESKTOP_SHELL.md` records the same thing: the Windows production entry point still refuses both opt-in commands, and the named-pipe acceptance receipt keeps candidate evidence separate from the missing alternate-account gate — candidate results do not substitute for alternate-account acceptance.

<Callout type="info" title="Evidence-layer receipt">
The 2026-11-23 receipt (`docs/superpowers/runs/2026-11-23-nsh-panel-s1b-windows-named-pipe-verification.md`) records what was measured **at that time**: the refusal baseline held on both binaries, a diagnostic build with the gate temporarily flipped did connect, and the security-boundary checks were spelled out. It describes a point-in-time experiment, not the current production state.
</Callout>

The way out is to complete the authorization acceptance for an independent (alternate) account. Until then the availability gate `AVAILABLE` stays `cfg!(unix)` (`shared/client/src/local_ipc.rs`).
