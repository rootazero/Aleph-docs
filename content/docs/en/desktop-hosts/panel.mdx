The release app opens the Gateway’s Leptos/WASM Panel in an NSH WebView. Browsers can open the same address. The TSX AppView is an opt-in macOS development entry point.

## What the Panel is

The Panel has two renderers. `interfaces/webchat/Cargo.toml` defines the Rust and Leptos `aleph-panel`, which compiles to WASM. `interfaces/panel/App.tsx` is the TSX Panel entry point, and `interfaces/panel/nsh.json` declares its host capabilities. Both use the runtime-neutral model in `shared/ui_logic/src/panel/mod.rs`. They share the model, not the frontend package.

## Two build chains

| Build artifact | What loads it |
|---|---|
| Leptos WASM: `interfaces/webchat/dist/` | Compiled into the release `aleph-server` and served from the binary at runtime (`src/gateway/control_plane/assets.rs`). |
| TSX Web: interfaces/panel/out-web/ | The Gateway's native TLS router can serve this static package from disk at `/v1/panel/` (`src/gateway/server/mod.rs`, `src/gateway/server/connection/web_v1.rs`). |
| TSX native bundle: interfaces/panel/out-bundle/ | Compiled into the NSH desktop shell when `tsx-panel` is enabled (`desktop/nsh-shell/src/panel_surface.rs`). |

### Leptos WASM (default release artifact)

The release workflow checks and uses the committed Leptos WASM assets rather than rebuilding WASM in the release jobs (`.github/workflows/aleph-app-release.yml`). `src/gateway/control_plane/assets.rs` uses `rust_embed` to compile `interfaces/webchat/dist/` into the release `aleph-server`. At runtime, the release binary never reads that directory from disk.

To refresh the embedded Panel, follow these three steps in order:

1. Run `just wasm` to rebuild assets including `aleph_panel.js`, `aleph_panel_bg.wasm`, `tailwind.css`, and `index.html`. The recipe compiles the Rust library for `wasm32-unknown-unknown`, runs `wasm-bindgen` to generate the Web output, and runs the same JS/WASM pairing check as `just check-dist` (`justfile`, `scripts/check_panel_dist.mjs`).
2. Run `cargo build --release -p alephcore --bin aleph-server` to embed the new `interfaces/webchat/dist/` in the binary (`Cargo.toml`, `src/gateway/control_plane/assets.rs`).
3. Stop the old process and start the new binary. For a local release build, run `./target/release/aleph-server stop`, then `./target/release/aleph-server start` (`src/bin/aleph-server/cli.rs`). Running `just wasm` alone does not update a release server that is still running.

### TSX Panel

| Command | What it does (recipes in `justfile`) |
|---|---|
| `just panel-tsx-test` | Runs `nsh test`, `nsh check`, and the Node tests in `interfaces/panel/web/host.test.mjs`. |
| `just panel-tsx-web` | Runs `nsh check`, then uses `nsh package --target web` to write interfaces/panel/out-web/. |
| `just panel-tsx-bundle` | Runs `nsh check`, then uses `nsh build` to write interfaces/panel/out-bundle/. |

Packaging for the Web does not enable the static route. Set `panel_web_dir` under `[gateway]` to interfaces/panel/out-web/ to mount that directory at `/v1/panel/` on the native TLS router. The route is not mounted when the directory is unset (`src/gateway/config.rs`, `src/gateway/server/mod.rs`, `src/gateway/server/connection/web_v1.rs`).

### Modular Panel (opt-in)

`panel-modular` is an optional Leptos feature, not a TSX build path. It is off by default; enabling it makes `interfaces/webchat/src/app.rs` render `PanelShell` (feature definition in `interfaces/webchat/Cargo.toml`). `just wasm-modular` stages the modular build in interfaces/webchat/.panel-modular-dist/ and runs reporting and tests against that output. The default release still uses `interfaces/webchat/dist/` (`justfile`, `.github/workflows/aleph-app-release.yml`).

## How the NSH desktop host embeds the TSX Panel

### Build feature

`tsx-panel` is disabled by default and currently integrates with the NSH JavaScript runtime on macOS (`desktop/nsh-shell/Cargo.toml`, `desktop/nsh-shell/src/app.rs`). With the feature enabled, the build fails if `bundle.js` or `capabilities.json` is missing and tells you to run `just panel-tsx-bundle` first (`desktop/nsh-shell/build.rs`).

### Native component `aleph/panel-surface`

`desktop/nsh-shell/src/panel_surface.rs` uses `include_str!` to compile the bundle and capability manifest into the shell and registers `aleph/panel-surface`. The component loads the JavaScript source in an NSH `AppView`. Only one surface can be active at a time; a second surface does not load the Panel.

### Host functions

`interfaces/panel/nsh.json` declares five host functions and asks for the `openUrl` permission (only the https and http schemes are allowed). `desktop/nsh-shell/src/panel_host.rs` implements them on desktop, and `interfaces/panel/web/host.js` implements them on the Web.

| Function | Behavior on each host (see implementations above) |
|---|---|
| `aleph.rpc` | Takes `method` and `params`; returns `result` or an `error` with a `code` and `message`. |
| `aleph.pair` | Always returns an error on desktop, where the operating system authenticates Desktop IPC. The Web host submits a device token or a one-time ticket to `/v1/session`. |
| `aleph.connect` | Opens a connection and can reconnect after a drop. |
| `aleph.connection` | Reads the current connection state. The event of the same name carries `state`, `endpoint`, `subject`, and `pairing` when the state changes. |
| `aleph.fontScale` | Sets the Panel's text size: a number is a multiple of the system font size, `null` means follow the system. The accepted range is 0.5 to 3; out of range it reports `font scale must be a number from 0.5 to 3`. |

The desktop side hangs `aleph.fontScale` off `aleph/panel-surface` (the surface owns the `AppView`); the web side changes the root element's `font-size` (16px is 100%).

Besides `aleph.connection`, the host also delivers an `aleph.event` event shaped as `{ topic, data }`:

- The desktop side wraps the stream events the Gateway pushes into `stream.<type>` topics (`desktop/nsh-shell/src/panel_host.rs`).
- The web side forwards notifications with a topic unchanged (`interfaces/panel/web/host.js`).
- After dropped frames the desktop side first sends its own `connection.stale` event (the `data` carries the dropped count), telling the Panel to re-fetch instead of trusting its own view.
- Live frames are never replayed: once the connection changes, events from the old connection are no longer delivered.

### Choosing a renderer

In a build that supports `tsx-panel`, set `ALEPH_SHELL_PANEL=tsx` for a non-QA launch to mount `aleph/panel-surface`. Leave it unset to mount `web_view`. The two do not run at the same time. An invalid or unsupported explicit selection makes the shell refuse to start rather than fall back to the WebView (`desktop/nsh-shell/src/app.rs`).

On macOS, start the Gateway with `--desktop-ipc` set to the socket path (`src/bin/aleph-server/cli.rs`), then run:

```sh
just shell-tsx-dev /absolute/path/to/socket
```

The recipe rebuilds the bundle, launches the shell with `tsx-panel`, and sets `ALEPH_SHELL_PANEL_IPC` to the supplied absolute path (`justfile`, `desktop/nsh-shell/src/panel_host.rs`).

## Communication between the host and Panel

Desktop and Web TSX use the host functions above. The messages, validation, and navigation below apply only to the NSH path that loads Leptos in a WebView. `desktop/nsh-shell/src/app.rs` starts the bridge when it mounts `web_view`, and the page sends messages to the host through `window.nsh.postMessage` (`desktop/nsh-shell/src/panel_bridge.js`). The WebView loads the root of the connection target without credentials or bootstrap material in the URL (`desktop/nsh-shell/src/shell_host.rs`, `shared/client/src/connection_target.rs`).

### Message shape

The WebView bridge uses JSON tagged by `kind`. `ShellRequest` and `PanelReply` in `shared/protocol/src/panel_shell.rs` use kebab-case tags and reject unknown fields.

| Direction | `kind` (see `shared/protocol/src/panel_shell.rs`) |
|---|---|
| Host to Panel | `probe`, `credentials-ready`, `open-chat`, `credential-reply`, `autostart-reply` |
| Panel to host | `ready`, `chat-opened`, `notify`, `credential-request`, `autostart-request` |

`CredentialCall` distinguishes `load`, `save`, and `delete` by `operation`; `CredentialReply` carries the outcome under `outcome`, and `AutostartStatus` carries the login item state under `status` (`shared/protocol/src/panel_shell.rs`).

### Validation and limits

- The shell generates a random prefix of the form `aleph-shell-v1:<uuid>:` at startup. The host accepts only page messages with that prefix and limits the JSON payload to 16 KiB (`desktop/nsh-shell/src/app.rs`, `desktop/nsh-shell/src/panel_bridge.rs`).
- The injected script installs only in the top-level window when `location.origin` matches the expected origin. Each load generates a 32-character lowercase hexadecimal `document`. Document-bound messages must match the current document. On navigation, the host clears document state and invalidates old credential leases (`desktop/nsh-shell/src/panel_bridge.js`, `desktop/nsh-shell/src/panel_bridge.rs`, `shared/protocol/src/panel_shell.rs`).
- A notification title must be nonempty and at most 256 bytes; its body is limited to 2048 bytes (`shared/protocol/src/panel_shell.rs`, `desktop/nsh-shell/src/panel_bridge.rs`).

### Navigation flow

The host sends `probe` during a probe window of up to 15 seconds, waiting 350 ms per attempt. The Panel replies with `ready` and its `document`, and the host sends `credentials-ready`. On an exact `aleph://open` match or a click on a Chat notification, the host waits for the document to be ready, sends `open-chat`, and waits up to two seconds for `chat-opened`. On timeout, it drops the action without replaying it (`desktop/nsh-shell/src/panel_bridge.rs`).

## Transport matrix

| Renderer path | Transport to the Gateway | Authentication and admission |
|---|---|---|
| Leptos (browser or WebView) | WebSocket JSON-RPC on legacy `/ws` (`interfaces/webchat/src/context.rs`, `src/gateway/server/mod.rs`). | Uses the legacy ingress authentication. `system.hello` negotiates protocol details but does not establish the caller's identity (`src/gateway/server/connection/upgrade.rs`, `src/gateway/handlers/system_hello.rs`). |
| TSX (NSH desktop) | `aleph.rpc` uses a local Desktop IPC connection opened by `AlephClient::connect_local`, over a Unix socket on macOS (`desktop/nsh-shell/src/panel_host.rs`, `shared/client/src/connection.rs`). | The operating system authenticates the same user. The Unix socket's parent directory must be owned by that user with mode `0700` (`shared/client/src/local_ipc.rs`, `src/gateway/server/connection/local_ipc.rs`). |
| TSX (Web) | Same-origin `wss://…/v1/ws` with the `aleph.protocol.v1` subprotocol. Binary messages contain a four-byte big-endian length followed by UTF-8 JSON; the first frame is `system.hello` (`interfaces/panel/web/host.js`, `shared/protocol/src/framing.rs`). | The native TLS router checks the origin. `POST /v1/session` issues a short-lived, host-only cookie that references an existing device credential (`src/gateway/server/connection/web_v1.rs`). |

Desktop IPC and Web v1 share the Gateway’s [Protocol v1 method list](../gateway/protocol-v1) in `src/gateway/server/connection/mod.rs`.

## Known limits

- Desktop TSX reaches only local Desktop IPC. For example, a WebSocket target set with `--connect` reports `unavailable` rather than falling back to WebSocket. `ALEPH_SHELL_PANEL_IPC` is a socket path, but the endpoint portion of the layout storage key is always `desktop-ipc`, even if the socket path changes (`desktop/nsh-shell/src/panel_host.rs`, `interfaces/panel/shell/Shell.tsx`, `shared/ui_logic/src/panel/layout.rs`).
- The release packages the default NSH build and `aleph-server` with its embedded Leptos assets. `tsx-panel` is disabled by default (`desktop/nsh-shell/Cargo.toml`, `.github/workflows/aleph-app-release.yml`).
- TSX does not yet cover every classic Panel tab. Tabs that require the classic renderer show an unavailable message (`interfaces/panel/shell/Shell.tsx`).
- The TSX `aleph:memory-nebula` tab is declared by the Gateway and depends on `graph.query`, `graph.search`, and `graph.node_detail` all being mounted; when they are not, the tab does not exist (`src/gateway/handlers/panel_capabilities.rs`, `src/gateway/handlers/mod.rs`).

> **Status: Planned** — The S4 consistent snapshot and durable observation replay are described in `docs/superpowers/specs/2026-11-22-nsh-panel-modular-refactor-design.md`. The TSX Panel currently fetches a capability snapshot (`interfaces/panel/shell/Shell.tsx`), which is not session or task recovery. The Gateway does not advertise snapshot or replay features in `system.hello` (`src/gateway/handlers/system_hello.rs`).
