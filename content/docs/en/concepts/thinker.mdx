title: "Thinker (Prompt Engine)"
description: "Prompt construction through composable layers, resolved context, and stable/dynamic cache partitions."
---
The `thinker` module constructs system prompts from composable layers. Stable curated memory enters the system prompt; automatically recalled memory is delivered separately as a transient tail message through `HarnessDeps::recall_context`.

## Design Philosophy

1. Each `PromptLayer` owns a concern and an ordering priority.
2. `LayerStability` separates stable prefix content from dynamic suffix content.
3. `AssemblyPath` selects the basic or cached entry point.
4. Layers wrap their own output; XML helpers live in `src/thinker/xml_util.rs`.
5. `prompt_contract` tests guard reachability, scaffold growth, and repeated sentences.

## Architecture

```text
TurnEnvelope + EnvironmentContract
    → ContextAggregator → ResolvedContext
    → LayerInput → PromptPipeline
    → stable prefix + dynamic suffix (cached path)
Recalled memory → separate transient message
```

## Core Components



### PromptLayer Trait

The trait in `src/thinker/prompt_layer.rs` is synchronous. Its core methods are:

```rust
fn name(&self) -> &'static str;
fn priority(&self) -> u32;
fn inject(&self, output: &mut String, input: &LayerInput);
```

Layers also declare assembly paths, prompt modes, and stability. They append to the supplied buffer rather than returning an asynchronous result.

### ResolvedContext and LayerInput

`src/thinker/context.rs` defines `EnvironmentContract`, `VoiceContext`, `TurnEnvelope`, `EnvelopeParent`, `ResolvedContext`, and `ContextAggregator`. Resolution produces the context consumed by layers; `LayerInput` adds prompt configuration and assembly-specific inputs.

`ResolvedContext` includes optional runtime context, sandbox summary, rendered execution plan, standing goal, graph topology, strategy, and voice state. `execution_plan` is already-rendered scratchpad progress, consumed by `ExecutionPlanLayer`; it is not a separate todo-view object. The harness bridge obtains recalled memory through `build_memory_user_message`, while `build_curated_message` supplies the stable curated envelope.

### PromptPipeline Assembly

`PromptPipeline` owns `Vec<Box<dyn PromptLayer>>`. `new` sorts by priority. `execute` renders an assembly path into a string; cached assembly uses `execute_stable_with_mode` and `execute_dynamic_with_mode` to split content by stability. There is no provider-specific rendering-style selector.

## The Two Rulers (`src/thinker/prompt_contract.rs`)

`reachable_layers` tests that production-shaped input wakes registered layers or that their conditional silence is explained in `CONDITIONALLY_SILENT`. This is a test inventory, not a runtime whitelist API.

`scaffold_bytes_ratchet` limits scaffold growth; dynamic-tail and sentence-duplication checks add separate guards. `aleph-server prompt-size` reports measured layer sizes. These are tests and CLI measurements, not prompt-assembly function signatures.

## `prompt_pipeline`

The default layer list is defined in `src/thinker/prompt_pipeline.rs`. `PromptBuilder` supplies the production entry points; each layer injects into the shared output buffer with `LayerInput`. Shared XML escaping helpers include `escape_xml` and `escape_xml_attr`.

## History: Streaming state machine

The early `thinker::streaming` module provided a per-token `BlockState` state machine (`BlockType`: `Text` / `ToolCall` / `Code` / `Thinking` / `Image`; `BlockEvent`: new block / continue / end) so the Panel could render a two-stage caption during streamed responses. That module and its streaming renderer were removed — there is no per-token caption state machine anymore.

---

## History: Provider-specific rendering

The early `ProviderRenderStyle` enum (`Xml` / `Fenced` / `Inline`) picked per-layer wrapping by provider, with a `render_section` chokepoint and a `style_for_provider(provider_name)` helper caching the choice at pipeline assembly. That rendering model was removed: each `PromptLayer` now self-wraps through `inject(&mut String, &LayerInput)` using the shared helpers in `src/thinker/xml_util.rs`; there is no per-provider wrapping style anymore.

## 26.7.x Addendum



### Layer Reorganization

Layers remain independently reviewable. Use `default_layers` and `layer_info` for the registered inventory rather than assuming an old fixed layer count.

### Voice Mode Layer

`VoiceModeLayer` reads the resolved `VoiceContext` and injects voice-turn instructions.

### Recalled Memory and Cache Friendliness

Stable curated memory is injected by `CuratedMemoryLayer`. Live recalled memory stays in the transient message path, outside the system prompt. The name of that transport field is `recall_context`.

### Prompt Cache Discipline

The cache split follows `LayerStability`, not a rule that priority 1720 must be last. `RuntimeContextLayer` is dynamic, but execution-plan and governance layers can follow it. Its runtime data describes the environment (for example `current_model` and `current_time` in `src/thinker/runtime_context.rs`), not an aggregate token-counter field. Stable-prefix byte changes invalidate prefix caching; dynamic content belongs in the dynamic suffix or transient messages. Skill prompt budgeting is separate: `SkillPromptBudget` lives in `src/skill/prompt.rs`, not in a thinker-wide layer-count budget.
