The `components` module provides the 6 core components of Aleph's agentic loop. Each component is an independent event handler that subscribes to specific event types and publishes outcomes to the event bus.

## Design Philosophy

1. **Event-driven composition** — Each component is an `EventHandler` with typed subscriptions
2. **Clean separation** — Components communicate only via events, no direct coupling
3. **Recoverable state** — Session recording persists state to SQLite for crash recovery
4. **Token awareness** — Session compaction manages context window limits

## IntentAnalyzer

Detects input complexity for routing decisions. Uses rule-based keyword matching (Chinese and English multi-step keywords) to identify whether a request needs multi-step planning.

**Subscribes to**: `InputReceived`  
**Publishes**: `PlanRequested` (multi-step) or `ToolCallRequested` (simple)

## TaskPlanner

Decomposes multi-step requests into executable tasks. Identifies parallel groups and dependency chains for optimal execution order.

**Key feature**: Transitive depth computation for correct parallel group identification. A sequential chain A→B→C produces depths 0, 1, 2 (not 1, 1, 1).

## ToolExecutor

Executes tools with retry logic and timeout handling. Wraps tool calls with error recovery and result formatting.

**Retry policy**: Configurable max attempts with exponential backoff.

## LoopController

Controls the agentic loop with protection mechanisms:

- **Max iterations** — Prevents infinite loops
- **Timeout** — Per-iteration time limit
- **Error budget** — Stops after N consecutive failures
- **Yield points** — Allows cancellation between steps

## SessionRecorder

Persists session state to SQLite:

- Agent events with timestamps
- Task execution records
- Tool call history
- Token usage statistics

**Error handling**: Database errors are propagated via `RecorderError`, not silently swallowed.

## SessionCompactor

Manages context window limits through compaction:

- **Token tracking** — Monitors cumulative token usage
- **Model limits** — Per-model context window limits with longest-prefix matching
- **Pruning** — Removes oldest turns when approaching limits
- **Summarization** — Replaces pruned content with compact summaries

## 26.7.x Addendum

### Act-Stage Parallel Groups

The pre-26.7.x serial execution is now replaced by **resource-claim bucketed** parallelism:

- Tools declare `Shared` / `Exclusive{Global}` / `Exclusive{Paths}` three-state resource claims
- Resource-scope parallel dispatch (**intra-group** concurrent, **inter-group** serial) — not a task-dependency graph
- `batch_parallelizable` checks whether calls admit parallel dispatch
- Serial mode only falls back on single call / parallelism disabled / duplicate call / no parallel group

### Guardrail + Parallel

26.7.x: serial fallback no longer triggers from a wired guardrail registry. The tool-call guardrail (Block / Sanitize / Pass) is applied sequentially in `act_parallel`'s PASS 0 — the same prep/execute split Pi uses (sequential validate + approval, then concurrent execute).

### Cooperative Steer Checkpoint

Before each serial group (and before each parallel group), Act re-checks `has_unanswered_user_message`; if the user has injected a message, the model is let respond first.

### Tool-Loop Verifier

26.7.15+: the tool-loop verifier (`src/verification/`) post-validates each turn's tool calls. Only the model's explicit stop ends a turn (**R10 "Don't #3**). `max_iterations` remains a safety cap.
