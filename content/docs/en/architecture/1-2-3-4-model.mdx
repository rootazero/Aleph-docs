The 1-2-3-4 model is the central organizing principle of Aleph's engineering architecture. It answers one question: **how does a self-hosted AI assistant bridge the gap between pure reasoning and physical/digital action?**

The answer is a strict separation of concerns across four numbered layers:

- **1** Core (the Brain) -- reasoning, state, routing
- **2** Faces (the Interfaces) -- how users interact with Aleph
- **3** Limbs (the Execution Systems) -- how Aleph acts on the world
- **4** Nerves (the Communication Protocols) -- how each layer talks to the Core

## 1 Core -- The Brain

The Rust Core is Aleph's soul. It is responsible for exactly three things and nothing else:

| Responsibility | Description |
|----------------|-------------|
| **Reasoning** | Decide what to do next. The Core orchestrates the [Harness](./harness) (Observe-Think-Act-Feedback), invokes LLM providers, and runs the [Prompt System](../concepts/prompt-system) for goal-oriented execution. |
| **State Management** | Maintain conversation context, task graphs, [session keys](./routing), and the [memory system](./memory). |
| **Routing** | Dispatch work to the correct execution system -- native tools, MCP servers, or skill plugins -- based on task requirements. |

### What the Core does NOT do

The Core never renders UI, never calls platform-specific APIs (AppKit, Vision, CoreGraphics), and never bundles heavy third-party libraries for niche functionality. These are architectural redlines (R1, R3) that keep the Core lightweight and portable.

```rust
// The Core depends only on capability contracts (traits). The physical
// implementations live in desktop/{macos,linux,windows} and are built per
// target OS in src/executor/builtin_registry/builder/constructor/mod.rs,
// then injected into the desktop tool as Arc<dyn aleph_desktop::DesktopPlatform>.
// Example (desktop/shared/src/traits/screen.rs):
#[async_trait]
pub trait ScreenCapability: Send + Sync {
    async fn screenshot(&self, region: Option<ScreenRegion>) -> Result<Screenshot>;
    async fn click(&self, x: f64, y: f64, button: MouseButton) -> Result<()>;
    async fn type_text(&self, text: &str) -> Result<()>;
    // ...
}
```

## 2 Faces -- The Interfaces

Aleph presents two faces to the world. Both are pure I/O layers -- they convert user input into JSON-RPC calls and render responses back to the user. Neither face contains business logic (redline R4).

### Face 1: Unified Panel (Leptos/WASM)

A single Leptos codebase (`interfaces/webchat`) compiled to WASM serves as the UI across all platforms. The Panel assets are statically embedded into `aleph-server` through `rust_embed` (`src/gateway/control_plane/assets.rs`) and are not read from disk at runtime.

| Platform | Host | Notes |
|----------|------|-------|
| Web | Browser | Served by the Aleph server |
| macOS / Windows / Linux | Desktop host `desktop/nsh-shell` (NSH) | Window container + WebView loading the same Panel |

The packaged app enables `embedded-core` by default. It can attach to a compatible local Gateway or launch its bundled `aleph-server` after a definite loopback connection refusal (`desktop/host/src/local_server.rs`). Remote mode opens the selected HTTPS Gateway. See [NSH Desktop Host](../desktop-hosts/overview).

How the desktop-side directories divide the work (the capability layer is detailed under "Limb 1" below):

| Layer | Directory | Runtime | Responsibility |
|-------|-----------|---------|----------------|
| Face 1 · desktop host | `desktop/nsh-shell/` | Rust, crate `aleph-nsh-shell`, built on nsh 0.6.0 | Window, tray, hotkey, URL scheme, notifications, credentials; connects to the Gateway |
| Face 1 · local admission | `desktop/host/` | Rust, crate `aleph-desktop-host` | Probes and admits the local Gateway under `embedded-core` |
| Limb 1 · capability contract | `desktop/shared/` | Rust, crate `aleph-desktop` (compiled into `aleph-server`) | `DesktopPlatform` and `*Capability` traits, Swift helper client |
| Limb 1 · platform implementations | `desktop/{macos,linux,windows}/` | Rust, compiled into `aleph-server`; macOS also has the Swift helper `desktop/macos/bridge/` | Per-platform screen, input, AX, permission, media, and PIM implementations |

### Face 2: Social Bot Gateway

The [Gateway](./gateway) connects Aleph to messaging platforms as a persistent background intelligence:

- **Telegram** -- bot interface via teloxide
- **Discord** -- bot interface via serenity
- **iMessage** -- bridged via AppleScript/Shortcuts

The Gateway translates platform-specific message formats into Aleph's unified JSON-RPC protocol. A single Aleph Core can serve multiple social channels simultaneously, each with independent [session routing](./routing).

## 3 Limbs -- The Execution Systems

Limbs are how Aleph acts on the world. There are three categories, ordered by proximity to the system:

### Limb 1: Native Capabilities (The Muscles)

Direct system control through the desktop capability layer and shell execution. The capability layer is an **in-process library**, not a separate process: traits and shared types live in `desktop/shared`, platform implementations live in `desktop/{macos,linux,windows}`, and all of it is compiled into and runs inside `aleph-server` (`Cargo.toml` pulls in the matching crate per target OS).

| Capability | Implementation | Protocol |
|------------|---------------|----------|
| Screenshots / OCR | `ScreenCapability`; macOS goes through the Swift helper `screen.*`, other platforms use `NativeScreen` | In-process call (macOS helper: JSON-RPC 2.0 over stdio) |
| Mouse / Keyboard | `ScreenCapability`; macOS targeted input goes through helper `input.*` | In-process call (macOS helper: JSON-RPC 2.0 over stdio) |
| Window Management | `ScreenCapability` (`window_list` / `focus_window` / `move_window`) | In-process call |
| Accessibility tree (AX) | `AccessibilityCapability`; macOS helper `ax.*`, Windows UI Automation, Linux AT-SPI2 | In-process call (macOS helper: JSON-RPC 2.0 over stdio) |
| Personal info (PIM) | `PimCapability`; macOS goes through helper `pim.*` | In-process call (macOS helper: JSON-RPC 2.0 over stdio) |
| Shell Commands | Built-in Exec system (`src/exec/`) | Direct |

Only some macOS capabilities are delegated to the Swift helper `aleph-bridge` (source in `desktop/macos/bridge/`): the Core sends JSON-RPC 2.0 requests over stdio through the `SwiftBridge` client (`desktop/shared/src/bridge/client.rs`), with the protocol defined in `shared/protocol/src/desktop_bridge/`. `aleph-server` owns this channel; it does not pass through the desktop host. Lifecycle, timeouts, and the method list are covered in [Desktop Bridge](./desktop-bridge).

### Limb 2: MCP (The External Tools)

The Model Context Protocol lets Aleph leverage the broader tool ecosystem:

```
Core ──JSON-RPC──▶ MCP Server (Playwright)
Core ──JSON-RPC──▶ MCP Server (Google Maps)
Core ──JSON-RPC──▶ MCP Server (GitHub)
```

MCP servers run as separate processes. Aleph's `mcp/` module handles server lifecycle, capability discovery, and JSON-RPC transport.

### Limb 3: Skills and Plugins (The Expertise)

Skills represent domain knowledge and specialized capabilities:

| Skill Type | Runtime | Example |
|------------|---------|---------|
| WASM Plugin | Extism sandbox | Data transformation, custom logic |
| Node.js Plugin | IPC subprocess | Complex integrations |
| Python Skill | Managed subprocess | Data analysis, ML pipelines |
| Bash Skill | Shell execution | System administration |

Skills are the future growth vector for Aleph. The architecture is the skeleton; skills are the muscle and blood.

## 4 Nerves -- The Communication Protocols

Every interaction between the Core and its Faces or Limbs travels through one of four nerve channels:

| Nerve | Channel | Protocol | Purpose |
|-------|---------|----------|---------|
| **N1** | Core -- UI | WebSocket + JSON-RPC | Drive the Unified Panel. Bidirectional: the UI sends user input, the Core streams responses and events. |
| **N2** | Core -- Desktop Layer | In-process trait calls; macOS helper: JSON-RPC 2.0 over stdio | Drive desktop control. The capability layer runs inside the Core process; only the macOS helper is a separate subprocess, see [Desktop Bridge](./desktop-bridge). |
| **N3** | Core -- Gateway | gRPC / NATS | Drive social bots. High-throughput, supports fan-out for multi-channel delivery. |
| **N4** | Core -- MCP | JSON-RPC over stdio/SSE | Drive external tools. Standard MCP transport, one server per tool domain. |

### Protocol Selection Rationale

```
┌──────────────────────────────────────────────────────────────────────┐
│                        PROTOCOL MAP                                  │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  N1 (WebSocket)     Best for: real-time bidirectional streaming     │
│  ────────────────   Why: UI needs live token streaming,             │
│                     event-driven updates, low latency               │
│                                                                      │
│  N2 (in-process)    Best for: local capability calls                │
│  ────────────────   Why: the Desktop Layer runs inside the          │
│                     Core process, so trait calls need no            │
│                     serialization; only the macOS helper            │
│                     speaks JSON-RPC over stdio                      │
│                                                                      │
│  N3 (gRPC/NATS)     Best for: structured service-to-service        │
│  ────────────────   Why: Gateway may run on different host,         │
│                     needs schema evolution, fan-out                  │
│                                                                      │
│  N4 (JSON-RPC)      Best for: standardized tool integration         │
│  ────────────────   Why: MCP ecosystem uses JSON-RPC over           │
│                     stdio or SSE, Aleph follows the standard        │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

## Architectural Redlines

The 1-2-3-4 model is enforced by seven architectural redlines. Violations are not merged:

| Redline | Rule | Consequence |
|---------|------|-------------|
| **R1** | Brain-Limb Separation | `src` never calls platform APIs directly. The Core defines traits; the desktop capability layer (`desktop/{macos,linux,windows}`) implements them. |
| **R2** | Single Source of UI Truth | The native desktop host (`desktop/nsh-shell`) has no business-logic UI. All complex views are in Leptos/WASM. |
| **R3** | Core Minimalism | No heavy third-party crates for niche functionality. Prefer Skills or MCP. |
| **R4** | I/O-Only Interfaces | Faces never persist data, retrieve memories, or plan tasks. |
| **R5** | Menu Bar First | macOS defaults to menu-bar mode with Halo overlay. Full windows only when needed. |
| **R6** | AI Comes to You | Reduce context switching. Halo, notifications, inline suggestions. |
| **R7** | One Core, Many Shells | Rust Core is the single brain. UI is unified via WASM. Native shells only wrap. |

## Data Flow: End-to-End Request

Here is how a user message flows through the 1-2-3-4 model:

```
1. User sends message via Telegram
   │
   ▼
2. Gateway (Face 2) receives message, resolves route
   │  → SessionKey: agent:main:telegram:dm:user123
   │
   ▼
3. Core (Brain) receives JSON-RPC request
   │  → Agent Loop: Observe → Think → Act
   │  → Thinker calls LLM provider
   │  → LLM decides: "take a screenshot, then OCR it"
   │
   ▼
4. Core dispatches to the desktop capability layer (Limb 1, Nerve N2)
   │  → ScreenCapability::screenshot → screenshot
   │  → ScreenCapability::ocr → extracted text
   │
   ▼
5. Core continues reasoning with OCR results
   │  → LLM generates final response
   │
   ▼
6. Core sends response back through Gateway (Nerve N3)
   │
   ▼
7. Gateway delivers response to Telegram
   │
   ▼
8. User sees the reply in their chat
```

## Design Philosophy

The 1-2-3-4 model reflects a core belief: **an AI assistant should be a brain with swappable limbs, not a monolith.** By separating reasoning from execution, Aleph can:

- Add new channels (Face) without touching the Core
- Add new capabilities (Limb) without touching the UI
- Upgrade communication protocols (Nerve) independently
- Run the Core on a headless server while the Faces and Limbs run elsewhere

This is not microservices for the sake of it. It is a pragmatic separation that keeps a complex system maintainable by a small team. The architecture is now stable -- future work fills in capabilities, not restructures the skeleton.
