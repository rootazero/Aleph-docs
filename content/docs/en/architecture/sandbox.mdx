The Sandbox is where exec-class tools actually run. It provides the execution boundary between Aleph and the operating system — ensuring every subprocess runs inside a scoped workspace with restricted filesystem, network, and process capabilities.

For the broader security model, see [Security Overview](../security/overview). For how tools consume the sandbox, see [Tool Architecture](./tools).

---

## Overview

The `Sandbox` trait is the one-method seam between an exec-class tool and the operating system:

```rust
#[async_trait]
pub trait Sandbox: Send + Sync + 'static {
    async fn execute(
        &self,
        command: SandboxCommand,
    ) -> Result<SandboxOutput, SandboxError>;
}
```

**Location**: `src/sandbox/mod.rs`

Production boot wires an `Arc<dyn Sandbox>` pointing at `WorkspaceSandbox`. `WorkspaceSandbox` owns three concerns:

1. **Workspace provisioning** — materialize the session workspace directory on first exec, keep it alive for the session, reuse on subsequent calls. Where it lands depends on the workspace this run was authorized for: the published workspace binding if there is one, otherwise `~/.aleph/workspaces/{hash(session_id)}/`.
2. **Capability enforcement** — classify every `SandboxCommand` against the session's baseline `SandboxCapabilities`, escalate out-of-baseline requests through `ApprovalGate`, cache per-session grants.
3. **OS isolation** — delegate the actual subprocess launch to an `OsSandboxDriverTrait` implementation (macOS `sandbox-exec` or Linux `bwrap`).

## Architecture

```
exec-class tool (code_exec, bash)
        │   Arc<dyn Sandbox>
        ▼
WorkspaceSandbox   ──► ApprovalGate
        │
        │   OsSandboxDriverTrait
        ▼
OsSandboxDriver    ──► macOS sandbox-exec / Linux bwrap
```

The exec-class tool (`code_exec`, `bash`, etc.) holds an `Arc<dyn Sandbox>` injected at boot. When the tool's `execute` method is called, it builds a `SandboxCommand` and passes it through the sandbox seam. `WorkspaceSandbox` handles workspace resolution, capability checking, and approval gating before delegating the actual subprocess launch to the OS-specific driver.

## Lifecycle — Per-Session Workspace

`WorkspaceSandbox` keeps a `HashMap<(SessionId, PathBuf), Arc<SessionWorkspace>>` behind an `RwLock`. `for_session(&sid, cwd, owned)` is the entry point:

- **Fast path**: `read().await` → cache hit → return the existing `Arc<SessionWorkspace>`.
- **Slow path**: `write().await` → double-check (another task may have created it) → `tokio::fs::create_dir_all(cwd)` (skipped for an owned worktree: the sandbox does not own that directory) → insert into the map.

The key is `(session, root)`, not the session alone: one session can run under different authorized roots over its life (the operator repoints the project folder mid-conversation), and `granted_elevations` — the cache of capability escalations a human already approved — describes a **root**, not a session. Keying by session alone hands a grant made for project A to a command running in project B, and pins the first root the session ever saw for the whole process lifetime.

The on-disk path is deterministic:

```
~/.aleph/workspaces/{hash(session_id)}/
```

The directory name is derived by SHA-256 hashing the JSON-serialized `SessionId`, truncated to 16 bytes (32 hex characters). This keeps the path short and safe across every `SessionKey` variant regardless of the characters those variants may carry.

**That hash path is only the fallback.** A gateway run publishes its effective workspace (the project override directory, else the agent's own `~/.aleph/workspaces/{agent_id}`) on `EXEC_WORKSPACE`, and that is the single answer to "where does a shell call land" — the same value the prompt advertises as `cwd=` and that `RuntimeContext.working_dir` documents. The two used to disagree: the gateway injected its answer into the tool's `working_dir` argument while the jail stayed anchored on `workspaces/<hash(session)>`, and since a 32-hex-character directory is neither an agent id nor a project path, **every shell call that omitted `working_dir` was refused as "cwd outside workspace root"**.

Each `SessionWorkspace` carries:

| Field | Type | Purpose |
|-------|------|---------|
| `cwd` | `PathBuf` | The materialized workspace directory |
| `baseline` | `SandboxCapabilities` | Policy ceiling (default: `::session_baseline()`) |
| `granted_elevations` | `RwLock<HashSet<SandboxCapabilities>>` | Cache of user-approved capability grants |

## Six-Step Execute Pipeline

`WorkspaceSandbox::execute` implements the full pipeline:

Before those six steps it runs a driver preflight: `self.os_driver.execution_preflight()?`. It only answers "are the native sandbox prerequisites present on this machine" — **success does not certify a native launch**; a missing prerequisite returns `SandboxError::BackendUnavailable` instead of running the command with no isolation at all.

### 1. Session Resolve

`self.for_session(&cmd.session_id, jail_root, owned)` → lazy directory creation if first call; cached `Arc<SessionWorkspace>` otherwise.

### 2. cwd Validate

`cmd.cwd` is either `None` (defaults to workspace root) or a path that must land inside the workspace root. The check is **symlink-aware**: both the root and the requested path are `canonicalize`d before comparison — a purely lexical `starts_with` is fooled by a symlink inside the workspace that resolves outside the jail. A path that cannot be resolved (missing directory, dangling link) is treated as outside.

Anything else returns:

```rust
SandboxError::CapabilityDenied {
    reason: "cwd outside workspace root".into(),
}
```

That verdict is only true as of **now**. Step 3's approval wait is human-paced and unbounded, and while the card sits on someone's screen a sibling command in the same workspace can swap a component of the approved path for a symlink. So if — and only if — step 3 actually awaited a human, containment is re-established by `revalidate_cwd_containment` before step 4 uses the path, and the command runs in the path the **second** check resolved, not the first one.

### 3. Capability Check

`cmd.capabilities.is_within(&ws.baseline)` is the fast path (no approval needed). Otherwise:

1. Consult `granted_elevations` — if the request is within a prior grant, pass.
2. Otherwise ask `ApprovalGate::request_approval_for_action`, carrying the whole `ApprovalAction` (command, program, capability set) rather than a tool name — a requester that only knows the name can only render the name, and a human shown `bash` has been shown nothing.
   - `ApprovalOutcome::Approved` → insert `cmd.capabilities` into `granted_elevations` (future same-or-narrower requests are cached).
   - `ApprovalOutcome::Denied`, `Timeout`, or `Unavailable` → `SandboxError::CapabilityDenied`.

Two guards back this up:

- **Denial ledger** — a prior refusal of the same capability fingerprint, or a session past the denial threshold, auto-denies without re-prompting. The fingerprint keys on the *normalized* capability summary, never on the model-controlled `justification` text; folding that in would let the model mint a fresh fingerprint for the same escalation just by rewording its reason.
- **Unattended tax** — a run with nobody watching (a goal loop, a heartbeat, a cron job) never parks: the card would expire anyway, but the wait would already have cost the full timeout. Unattended, the gate returns `ApprovalOutcome::Unavailable` without waiting once.

`SandboxCapabilities::is_within` enforces four monotonic checks:
- `fs_read` ⊆ (prefix containment)
- `fs_write` ⊆ (prefix containment)
- `network`: `None` ⊆ `AllowHosts` ⊆ `AllowAll`
- `spawn_subprocess`: `false` ⊆ any

### 4. Profile Generate

`os_driver.profile_for(&caps, &cwd)` returns an opaque `OsSandboxProfile`. On macOS, this is SBPL profile text; on Linux, it is a bubblewrap argument list.

### 5. Run

`os_driver.run(program, args, env, stdin, cwd, profile, timeout, max_output_bytes)`.

| Parameter | Default | Description |
|-----------|---------|-------------|
| `timeout` | 60s | Per-command time limit |
| `max_output_bytes` | 1 MB | Combined stdout + stderr budget (split evenly) |

Both are overrideable on the `WorkspaceSandbox` via `with_timeout` / `with_max_output_bytes`.

#### Background jobs

`bash`'s background mode (`background: true`) hands the command to a task that
escapes the per-call budget wrapper, but it still travels the same
`WorkspaceSandbox::execute` pipeline — the sandbox profile, capability checks
and the approval gate behave exactly as they do in the foreground. Three
things differ: the 180 s foreground ceiling does not apply, the wall-clock
timeout defaults to 3600 s instead of 60 s when none is given, and the job is
recorded in the process registry in
`src/builtin_tools/process_registry.rs`, scoped per session. See
[Builtin Tools](../tools/builtin) for the full model.

### 6. Audit

Emit a `tracing::info!(target: "capability_ledger", ...)` record carrying:
- `session_id`
- `program`
- `caps`
- `exit_code`
- `signal`
- `duration_ms`

This is the capability-ledger hook; downstream tracing subscribers can sink it to any store.

## Workspace ownership — ExecWorkspace

The sandbox does not decide for itself "which directory should this session work in". The effective workspace is published by the runtime:

```rust
pub enum ExecWorkspace {
    Directory(PathBuf),
    OwnedWorktree(Arc<WorktreeHandle>),
}
```

**Location**: `src/sandbox/context.rs`

- `Directory` — an ordinary directory: the project override directory, or the agent's own `~/.aleph/workspaces/{agent_id}`.
- `OwnedWorktree` — a git worktree **owned by someone else** (for example the detached-HEAD worktree team G2 opens for a member task). The sandbox reads its path; it never creates, deletes, or repairs it.

`ExecWorkspace::root()` gives the root path and `is_owned_worktree()` distinguishes the two shapes; `OwnedWorktree` equality compares with `Arc::ptr_eq` — the same ownership, not merely the same path.

**The policy root and the launch directory are separate.** With an owned worktree, the OS profile takes the canonicalized worktree root as its writable root while `CARGO_TARGET_DIR` points at `<root>/target`, so build artifacts do not pollute the checkout. The owned root is re-resolved while the command is being prepared: if the resolution changed (the checkout was replaced or removed), execution is refused with `owned worktree root changed while preparing execution`.

**A missing worktree is never recreated.** `resolve_owned_root` returns `owned worktree is no longer a directory: <path>` when the target is no longer a directory. The sandbox does not own that directory, so it neither rebuilds it nor launches the command against a missing one — creating an empty directory of the same name would let the command "succeed" inside an empty checkout with no code in it.

## Capability Model

`SandboxCapabilities` is a plain struct:

```rust
pub struct SandboxCapabilities {
    pub fs_read: Vec<PathBuf>,
    pub fs_write: Vec<PathBuf>,
    pub network: NetworkPolicy,
    pub spawn_subprocess: bool,
}

pub enum NetworkPolicy {
    None,
    AllowAll,
    AllowHosts { hosts: Vec<String> },
}
```

**Location**: `src/sandbox/capabilities.rs`

The session baseline is `SandboxCapabilities::session_baseline()` — equal to `strict()` except that `spawn_subprocess` is permitted on non-Linux platforms (on Linux `allow_fork` buys `--unshare-pid`, not forking; no shell there asks for it, and lifting the floor would only widen what skips approval):

- No filesystem access outside the workspace cwd (auto-granted by the OS driver profile)
- No network access
- `spawn_subprocess` allowed on non-Linux platforms, denied on Linux

`strict()` and `default()` stay tight: an interpreter that asks to spawn children still routes through approval.

Any command that needs more must escalate via `ApprovalGate`. The `granted_elevations` cache ensures a user only approves a capability pattern once per session.

---

## ApprovalGate

`ApprovalGate` handles escalation for out-of-baseline capability requests. When a tool requests capabilities beyond `strict()`, the sandbox:

1. Checks the session's `granted_elevations` cache
2. If not cached, calls `ApprovalGate::request_approval_for_action(&action)`, carrying the full action description
3. On approval, inserts the granted capabilities into the cache
4. On denial or timeout, returns `SandboxError::CapabilityDenied`

The same `ApprovalGate` instance is shared with the `PermissionLayer` so that Ask-tier tool confirmations and sandbox capability escalations use a single gate.

**Location**: `src/sandbox/exec_approval/gate.rs`

## OsSandboxDriver

The `OsSandboxDriverTrait` is the platform abstraction for OS-level sandboxing:

```rust
pub trait OsSandboxDriverTrait: Send + Sync {
    /// Reject known missing prerequisites; success does not certify a native launch.
    fn execution_preflight(&self) -> Result<(), SandboxError>;

    fn profile_for(
        &self,
        capabilities: &SandboxCapabilities,
        cwd: &Path,
    ) -> Result<OsSandboxProfile, SandboxError>;

    async fn run(
        &self,
        program: &str,
        args: &[String],
        env: &HashMap<String, String>,
        stdin: Option<&[u8]>,
        cwd: &Path,
        profile: &OsSandboxProfile,
        timeout: Duration,
        max_output_bytes: usize,
    ) -> Result<SandboxOutput, SandboxError>;
}
```

**Location**: `src/sandbox/driver.rs`

| Platform | Implementation | Mechanism |
|----------|---------------|-----------|
| macOS | `SeatbeltDriver` in `src/sandbox/platforms/macos/seatbelt.rs` | `sandbox-exec` seatbelt profiles |
| Linux | `BubblewrapDriver` in `src/sandbox/platforms/linux/bwrap.rs` | `bwrap` namespaces + seccomp |
| Windows | `WindowsSandboxDriver` in `src/sandbox/platforms/windows/driver.rs` | Job object (`job.rs`) + WFP network filtering (`wfp.rs`) |

## Configuration

Boot-time tuning lives on `SandboxConfig`:

```rust
pub struct SandboxConfig {
    pub workspace_root: PathBuf,       // default: ~/.aleph/workspaces
    pub enabled: bool,                 // default: true
    pub default_timeout_seconds: u64,  // default: 60
    pub max_output_bytes: usize,       // default: 1 MiB
}
```

**Location**: `src/sandbox/config.rs`

Serde reads the `[sandbox]` TOML section with defaults so existing configs keep working. Tests and CI can set `enabled = false` to disable the subsystem; `build_sandbox` will then return a `NoopSandbox` whose `execute` always errors with `SandboxError::Other("sandbox disabled: ...")` — a deliberate fail-fast, not a silent bypass.

## Task-Local Session Context

Exec-class tools don't know the current session id — their `AlephTool::execute` signature doesn't carry it. The sandbox subsystem uses a tokio `task_local!` to thread the id without touching every tool trait:

- `crate::sandbox::context::SESSION_ID` — declared in `src/sandbox/context.rs`
- `current_session() -> Option<SessionId>` — the read helper
- **Writer**: `crate::session::invoke_with_session_trace` (`src/session/tool_trace.rs`) wraps `tool_svc.execute(...)` in a `SESSION_ID.scope(session_id.clone(), async move { ... })`.

Tools that need a workspace but are called outside a session can choose their fallback policy (today they rely on the caller having passed a `SandboxCommand { session_id, ... }` explicitly).

## Factory — build_sandbox

`src/sandbox/factory.rs` composes the `Arc<dyn Sandbox>` at boot:

```rust
pub fn build_sandbox(
    cfg: &SandboxConfig,
    driver: Arc<dyn OsSandboxDriverTrait>,
    approval: Arc<ApprovalGate>,
) -> Arc<dyn Sandbox>;
```

The resulting `Arc<dyn Sandbox>` is threaded through tool registration into every exec-class tool constructor (`CodeExecTool::with_sandbox`, `BashExecTool::with_sandbox`, etc.). A tool constructed without a sandbox returns a structured "sandbox not configured" error instead of falling back to unscoped execution — the default is safe, not permissive.

advertise it.

Linux behaviour only — macOS and Windows are unverified; a design review is not
an implementation approval; no independent final review has been started. None
of these branches has been merged into `main`.
