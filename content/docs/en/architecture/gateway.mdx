The Aleph gateway is the control plane between clients and agents, tools, and workflows: it accepts connections, decides who the caller is, routes each request to a handler, and broadcasts internally generated events to the connections that subscribed to their topic. This page describes the shape those mechanisms actually have in the current code. For the wire format see [Protocol v1](../gateway/protocol-v1), for credentials and pairing see [Authentication](../gateway/auth), and for the method catalogue see [Method reference](../gateway/methods/index).

## Gateway Responsibilities

The gateway process brings three things together:

- **Accepting connections**: the HTTP routing table is assembled in `src/gateway/server/mod.rs:1133`. `/ws` is the WebSocket upgrade entry, `/health`, `/ready`, and `/metrics` are operational probes, and everything else falls through to the control plane (`control_plane`). Panel assets, artifacts, canvas assets, attachments, and a capability-limited browser viewer are merged in as separate routes. The same router also carries the OpenAI-compatible HTTP face (`src/gateway/openai_api/router.rs`): `/v1/models`, `/v1/models/{model_id}`, `/v1/chat/completions`, `/v1/embeddings`, `/v1/responses`, `/v1/health`.
- **Executing requests**: JSON-RPC 2.0 requests enter the method registry through the middleware chain and land on a concrete handler.
- **Broadcasting events**: internally generated events enter the bus in `src/gateway/event_bus.rs` and are delivered per topic to the connections that subscribed.

## Transport Entries

The three entries share one RPC execution and event dispatch core. They differ in transport, in how they authenticate, and in how much of the method surface they expose.

| Entry | Transport | Authentication | Method surface | Limits | Code |
|-------|-----------|----------------|----------------|--------|------|
| `/ws` | WebSocket (compatibility entry) | `connect` handshake for a role | Full RPC method set | The state's `max_connections`, plus a per-client-IP concurrency cap with a loopback exemption | `src/gateway/server/connection/upgrade.rs` |
| Desktop IPC | Unix domain socket | Same user account (`require_same_user`) | `health`, `sessions.list`, `panel.capabilities.snapshot` (`V1_METHODS`) | `MAX_CONNECTIONS=8`, `WIRE_BUDGET=16 MiB`, `WRITE_TIMEOUT=5s` | `src/gateway/server/connection/local_ipc.rs` |
| Web v1 | WebSocket over native TLS | Session cookie obtained from `POST /v1/session` | `health`, `sessions.list`, `panel.capabilities.snapshot` (`V1_METHODS`) | `MAX_MESSAGE=1 MiB`, `MAX_SESSIONS=256`, `MAX_SOCKETS=8`, TTL 300s | `src/gateway/server/connection/web_v1.rs` |

### Compatibility WebSocket Entry

`/ws` is the oldest entry and is still on the production path, but under the current contract it carries a compatibility role; the target entries for Protocol v1 are the two below. The upgrade logic lives in `ws_upgrade_handler` in `src/gateway/server/connection/upgrade.rs`, and a connection that gets through reaches the full RPC method set.

Three rejections happen before the upgrade:

| Condition | Rejection |
|-----------|-----------|
| Remote plaintext (no TLS, and `allow_insecure_remote` not set) | 426 `TLS required for remote connections` |
| `Origin` not allowed by the state's `origin_policy` | 403 `origin not allowed` |
| Global connection count reached the state's `max_connections` | 503 `Connection limit reached` |

The per-client-IP concurrency cap exempts loopback, because the panel and local CLIs open several connections at once. The state's `max_connections` and `origin_policy` fields are defined in `src/gateway/server/mod.rs`. The real client IP behind a trusted proxy is parsed by `parse_trusted_ips`, which accepts bare IPs only and rejects CIDR ranges.

### Desktop IPC Entry

Desktop IPC is the read-only entry for the desktop host: a Unix domain socket that only the same user account can reach. The entry point is a startup flag, `--desktop-ipc <socket>` (`src/bin/aleph-server/cli.rs:54`), and the server binds the listener in `run_with_desktop_ipc` at `src/gateway/server/mod.rs:1424`.

Once a connection is established, the following constraints apply (`src/gateway/server/connection/local_ipc.rs`):

- **Same user account**: `require_same_user` (`shared/client/src/local_ipc.rs:181`) checks the peer uid and disconnects on mismatch.
- **The first frame must be `system.hello`**: otherwise the gateway replies `AUTH_REQUIRED` / `system.hello must be first`.
- **Method allowlist**: `execute` decides with `v1_mounted` (`src/gateway/server/connection/mod.rs`) and lets through only `health`, `sessions.list`, and `panel.capabilities.snapshot` from `V1_METHODS`; everything else gets `METHOD_NOT_FOUND` / `method not mounted on Desktop IPC`.
- **Identity**: the role comes from `active_desktop_owner`, and the caller user is pinned to `OWNER_USER_ID`.
- **No network rights**: the connection's origin is recorded as `NO_NETWORK_ORIGIN` (0.0.0.0), so it never receives a permission that requires a network origin.

Resource limits:

| Constant | Value | Meaning |
|----------|-------|---------|
| `MAX_CONNECTIONS` | 8 | Concurrent Desktop IPC connections |
| `WIRE_BUDGET` | 16 MiB | Per-connection budget of bytes in flight; semaphore permits are charged by frame length |
| `WRITE_TIMEOUT` | 5s | Timeout for a single write |
| `MAX_FRAME_BYTES` | 8 MiB | Maximum payload size of one frame (`shared/client/src/local_ipc.rs`) |
| `MAX_INFLIGHT` | 8 | In-flight requests per connection (`shared/client/src/local_ipc.rs`) |

A response larger than `MAX_FRAME_BYTES` is answered with `INTERNAL_ERROR` / `response exceeds Desktop IPC limits`.

### Web v1 Entry

Web v1 is the target network entry for Protocol v1: WebSocket over native TLS, with credentials obtained through a one-time exchange instead of putting a long-lived token into a query parameter.

Two steps:

1. `POST /v1/session` exchanges a credential for a session. The request body is `{"device_token": "..."}` or `{"bootstrap_ticket": "..."}` (the `Credentials` enum in `src/gateway/server/connection/web_v1.rs`). On success the gateway returns 204 and sets `Set-Cookie: __Host-aleph-v1=<uuid>; Secure; HttpOnly; SameSite=Strict; Path=/; Max-Age=300`, together with `Cache-Control: no-store`.
2. `GET /v1/ws` upgrades to a WebSocket. The credential travels in the cookie (read by `cookie_handle`), and the subprotocol is `aleph.protocol.v1`.

Two gates run first:

- **Same origin**: `same_origin` requires a request without a query string, an `Origin` header exactly equal to the authority's https origin, and an authority free of `@ / \ ? #`; otherwise the gateway answers 403.
- **Throttle**: `throttle` charges the client's IP against `RateLimitScope::Auth` and answers 429 when the quota is exhausted.

The session is bound in a `WebBinding` (`store`, `origin`, `token_id`, `device_id`, `user`, `expires`). `current_role` returns `None` once the binding expires, and on every call it re-checks with `active_device_principal` that the device token is still valid and still belongs to the same user.

In addition, `panel_routes` (`src/gateway/server/connection/web_v1.rs`) serves the TSX Panel static web package under `/v1/panel/`, **only on the native TLS router** (so the page is same-origin with the Cookie-authenticated `/v1/ws`). The response carries `Content-Security-Policy: script-src 'self' 'wasm-unsafe-eval'; img-src 'self' blob: data:; connect-src 'self'` and `X-Content-Type-Options: nosniff`.

## Connections and Identity

A connection enters the connection table the moment it is accepted, and at that point it holds no permissions; its role is `guest`. The real authorization happens after `connect`.

### The Login Wall

`wall_admits` (`src/gateway/server/connection/auth.rs:64`) is the single authorization predicate:

```rust
pub fn wall_admits(role: Option<&str>, method: &str) -> bool {
    matches!(role, Some("operator" | "member")) || method == "connect"
}
```

A connection holding the `operator` or `member` role may send any method; a `guest` may send only `connect`. The message an unauthorized connection receives is `LOGIN_WALL_MESSAGE` at `:13` of the same file: `Not authorized: present a valid Gateway token via \`connect\` to access this core.`

The same predicate is used in both directions: once before dispatching a request, and once again before delivering an event. Judging only one direction would let unauthorized connections receive events that were meant to be blocked.

### The system.hello Handshake

`system.hello` (`src/gateway/handlers/system_hello.rs`) is the Protocol v1 handshake. It negotiates the protocol and grants nothing.

Request:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "system.hello",
  "params": {
    "protocol": { "major": 1, "minor": 0 },
    "client": {
      "name": "aleph-nsh-desktop",
      "version": "0.1.0",
      "platform": "linux",
      "ui_runtime": "nsh"
    },
    "features": ["event_replay", "snapshot", "binary_channel"]
  }
}
```

Response:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocol": { "major": 1, "minor": 0 },
    "server": { "name": "aleph-server", "version": "26.9.1" },
    "connection_id": "conn-...",
    "features": [],
    "limits": { "max_message_bytes": 8388608, "max_inflight_requests": 128 },
    "subject": "0123456789abcdef0123456789abcdef"
  }
}
```

- Missing or unparsable `params` produces `INVALID_PARAMS`.
- A different major version produces `INVALID_PARAMS` / `incompatible protocol major version`; with the same major, the smaller of the two minor versions wins (`negotiate_version` in `shared/protocol/src/system_hello.rs`).
- `features` is the intersection of what the client asked for and what the server implements (`negotiate_features`). The server currently passes an empty implementation list, so the negotiated result is always an empty array — a client cannot assume a feature is available just because it listed `snapshot` in the handshake.
- `limits` are hints rather than enforced transport limits; the source comment says `legacy wire hints, not enforced transport limits`. The frame size limits that actually bind live on the Desktop IPC side (`MAX_FRAME_BYTES` and `MAX_INFLIGHT`).
- `server.version` comes from the compile-time constant `ALEPH_VERSION`.
- `subject` is an opaque per-user value the server computes for the session's bound user, used as a client-side storage key (Panel layout). It is **not an identity**, and clients must not derive authority from it (`shared/protocol/src/system_hello.rs`). It is the first 16 bytes of HMAC-SHA256 over `aleph.panel.subject.v1\0` concatenated with the user, hex-encoded (32 hex characters); it never contains the user id, and it changes when the secret rotates, which only resets client presentation state (`src/gateway/handlers/system_hello.rs`). On legacy `/ws` and when the Gateway has no shared-token secret, `subject` is `None`, and `skip_serializing_if` makes the field disappear entirely.

## Request Dispatch

The order of a request:

```
Connection receives a frame
  → JSON parse (serde)

  → Role and permission decision (wall_admits, method_requires_admin)
  → Idempotency key and lane planning (rpc::prepare)
  → Middleware chain (validate → rate_limit → auth → metrics → trace)
  → Method registry lookup (HandlerRegistry::handle)
  → Handler
  → Response
```

### Dispatch Entry Points

`src/gateway/server/connection/dispatch.rs` offers three entry points:

- `dispatch_for_connection`: the old `/ws` path. `capabilities.ui.invoke` is special-cased — it first resolves the real caller through `live_ui_caller`, and answers with `viewer_denied_response` when there is none, so the handshake snapshot is never passed off as the current caller.
- `dispatch_for_peer`: the Desktop IPC and Web v1 paths.
- `dispatch_with_caller_context`: the internal call path.

All three end up in `dispatch_ordinary` → `validate_live` → `dispatch_snapshot`. `dispatch_snapshot` reads the role, user, verified user, and device id out of a single `ConnectionState` read (`CallerSnapshot`), which avoids identity drift from reading them separately.

### Runtime Role Gating

`process_request` (same file, `:511`) is the single chokepoint:

- A JSON parse failure produces `PARSE_ERROR` / `Parse error: {e}`.
- When `method_requires_admin` matches and the caller is a member, the gateway answers `AUTH_REQUIRED` with `ADMIN_REQUIRED_MESSAGE`: `Not authorized: this method requires operator privileges`. `None` (internal calls) and `operator` pass through, and a `guest` was already stopped by the login wall.
- After that, a `traceparent` is taken from the request params or a root trace is created, and the method name, trace id, and span id all go into one span.

`method_requires_admin` (`src/gateway/method_admin.rs:544`) decides in this order: a hit in `ADMIN_METHODS` requires an administrator, a hit in `MEMBER_CARVE_OUTS` exempts the method, and otherwise the method name is matched against `ADMIN_PREFIXES`.

### The Method Registry

The method registry is `HandlerRegistry` (`src/gateway/handlers/mod.rs:1229`). `register` maps a method name to a handler; an unknown method produces `METHOD_NOT_FOUND` / `Method not found: {method}`. Bulk registration uses the `register_handler!` macro, defined at `src/bin/aleph-server/commands/start/builder/handlers/mod.rs:35`.

`src/gateway/method_census.rs` turns "which methods are registered, and whether each is Open or Admin" into an executable census: it scans the registration calls in production code and pins the current ruling for every method, so adding a method or flipping any entry fails the census test until someone records the ruling explicitly.

`src/gateway/method_visibility.rs` is a different table with a different shape: it records whether a method's return value depends on who is calling, and each handler enforces it with a `visibility` predicate. It is not a dispatch gate by itself — data visibility has to be decided inside the handler, by session ownership.

### The Middleware Chain

`MiddlewareChain::serve_with_panel_context` (`src/gateway/middleware/chain.rs:96`) runs outer to inner:

| Layer | File |
|-------|------|
| `validate` | `src/gateway/middleware/validate.rs` |
| `rate_limit` | `src/gateway/middleware/rate_limit.rs` |
| `auth` | `src/gateway/middleware/auth.rs` |
| `metrics` | `src/gateway/middleware/metrics.rs` |
| `trace` | `src/gateway/middleware/trace.rs` |
| `HandlerService` | `src/gateway/middleware/handler_service.rs` |

An error raised by the chain itself produces `INTERNAL_ERROR` / `Middleware chain error`. Throttling inside the middleware produces `RATE_LIMITED`.

### Lanes and Idempotency

Every method maps to a lane: `Query`, `Execute`, `Mutate`, or `System` (`src/gateway/lane.rs:37`). The mapping consults an explicit override table first, then a suffix heuristic on the last segment of the method name (`get`/`list`/`subscribe` and friends land in `Query`, `install`/`uninstall` in `System`, `run`/`send`/`invoke`/`execute` in `Execute`), and falls back to `Mutate`. The fallback is deliberate: the source comment explains that the old implementation fell back to `Query`, which let side-effecting methods that were not covered by the table bypass idempotency protection.

`rpc::prepare` (`src/gateway/server/connection/rpc.rs:63`) owns the idempotency key and the lane permit:

- An `idempotency_key` containing the reserved separator is rejected with `INVALID_PARAMS`.
- A lane that requires an idempotency key, called without one, produces `IDEMPOTENCY_KEY_REQUIRED` / `idempotency_key required for mutating RPCs`, with `method`, `lane`, and a hint in `data`.
- Idempotency slots are namespaced by "caller + method + key", and browser viewer methods get a separate prefix so they cannot collide with another user's slots.

During execution:

- Failing to acquire a lane permit produces `INTERNAL_ERROR` / `Service congested, try again later`.
- Waiting more than 30 seconds for an in-flight duplicate produces `Request timed out waiting for in-flight duplicate`.

## The Event Outlet

### Two Wire Shapes

The server wraps internal events into JSON-RPC notifications. Events travel in one of two wire shapes (`publish_frame` at `src/gateway/event_bus.rs:423`):

| Frame kind | Wire shape |
|------------|------------|
| Frames with a `stream_method()` | A notification sent directly: `{"jsonrpc":"2.0","method":"stream.run_complete","params":<frame body>}` |
| Frames without a `stream_method()` | A bare event `{"topic":"...","data":<frame body>}` first, which the delivery layer wraps into `{"jsonrpc":"2.0","method":"event","params":{"topic":"...","data":...}}` |

The `event` method of the second shape is `TOPIC_EVENT_METHOD` (`shared/protocol/src/jsonrpc.rs:85`), and the wrapping happens in `event_wire_form` at `src/gateway/server/connection/forward.rs:228`.

The canonical topic name and the wire method name are two separate namespaces: the canonical name (`agent.run.complete`) mainly appears in the `source_topic` diagnostic field, while subscriptions on the wire use `stream.*`. The full table is in the [event topic catalogue](../gateway/methods/events).

### The Delivery Filter Chain

For a frame to reach a connection it has to pass the filter chain starting at `src/gateway/server/connection/mod.rs:1373`:

1. `pty::manager::frame_admits` — PTY frames are judged by session ownership.
2. `ui_display_admits_connection` — `capabilities.ui.display` additionally checks the display mount.
3. `wall_admits` — the login wall, the same predicate as in the request direction.
4. `can_receive` (`src/gateway/event_scope.rs`) — coarse scope by topic prefix.
5. `surface::delivery::audience_allows` — by delivery audience.
6. `should_receive` (`src/gateway/handlers/events.rs`) — whether this connection subscribed to the topic.
7. `event_admits_for` (`src/gateway/event_visibility.rs`) — per-frame ownership ruling.

`stream.running_set_changed` is the only "projected" frame on the chain: it is admitted, but its array is narrowed per connection (`project_for`), so each connection sees only the running set that concerns it.

### Scope and Visibility

The two mechanisms have different jobs:

- `src/gateway/event_scope.rs` is a **coarse prefix rule set**. `default_rules` registers only a few prefixes (`pairing.`, `guest.`, `config.changed`, `node.`, `pty.`); a matched prefix requires the caller to hold an administrator scope, and a topic that matches no rule is admitted by default. `scope_for_role` returns `["*"]` for operator and an empty scope for every other role.
- `src/gateway/event_visibility.rs` is **per-frame ownership ruling**. `classify` maps the topic and its data to one `SessionIdentity` (`BySessionKey`, `ByRunId`, `ByTeamId`, `ByUserId`, `ByCanvasScope`, `ByProjectScope`, `ByPtySession`, `OperatorOnly`, and others), and `event_admits_for` recomputes the ruling for each frame against the caller's identity. `session_identity_of` returns `Global` when `classify` finds no match, which matches the default-allow behaviour of the scope rules.

For which topic belongs to whom, see the visibility section of the [event topic catalogue](../gateway/methods/events).

### Subscribe and Unsubscribe

`events.subscribe`, `events.unsubscribe`, and `events.list` do not go through the method registry; they are intercepted separately in the connection loop (`src/gateway/server/connection/mod.rs:630`), with the handlers in `src/gateway/handlers/events.rs`.

Subscription state lives in `SubscriptionManager` (same file, `:17`): one `TopicFilter` per connection, holding the wildcard patterns, the excepted patterns, and the `where` predicates. The matching logic is `topic_matches` at `src/gateway/event_bus.rs:150`:

- A pattern of `*` or `**` matches everything.
- A pattern whose last segment is `*` or `**` matches any remaining depth — `stream.*` matches `stream.run_complete`.
- A `*` in the middle of a pattern eats a single segment — `*.complete` does not match `stream.run_complete`.
- Both sides have to be exhausted.

Matching works on the wire topic string of the event: the `topic` field for the bare event shape, and the `method` field for the notification shape (`extract_topic_and_data` at `src/gateway/server/connection/forward.rs:187`), so stream frames are matched by their `stream.` prefix.

A `where` predicate is described by `FieldPredicate` (`{"field":"...","equals":...}`), and the field path is resolved by `.` segments, not by JSON Pointer. A non-empty predicate whose field is missing from the payload counts as no match.

## Configuration Hot Reload

`ConfigWatcher` in `src/gateway/hot_reload.rs` watches the configuration file with debouncing (500ms by default), reloads and validates on change, and broadcasts the result to subscribers. `ReloadMode::should_hot_reload` decides which configuration sections may take effect live; in `Hybrid` mode only `ui`, `channels`, `skills`, `workspace`, and `cron` are hot-reloaded, and the rest need a restart.

## Relationship to the Desktop Host

The desktop host (NSH) connects through the gateway's Desktop IPC entry and its Web v1 entry, not through the old `/ws`. The host's shape, its panel, and the plugin boundary are described in [Desktop hosts](../desktop-hosts/overview).

## Planned: What's Next for the Gateway

The items below have a complete design in the blueprint, but no implementation exists in the code yet.

> **Status: planned** — the blueprint is `docs/research/NSH_PROTOCOL_V1.md` (chapter 10, backpressure, flow control, and resource limits); the current implementation is in `src/gateway/lane.rs` for lane permits and `src/gateway/server/connection/rpc.rs` for `Service congested, try again later`. Today the only flow control is the coarse "reject when the permit is unavailable", with no per-subscriber rate shaping.

> **Status: planned** — the blueprint is `docs/research/NSH_PROTOCOL_V1.md` (chapter 9, Snapshot + Replay); the current implementation is in `shared/protocol/src/trace_replay.rs` and `shared/protocol/src/resume.rs`. `trace_replay.rs` holds query DTOs for persisted traces and `resume.rs` holds receipts for resumed tasks, so neither is an event replay; `session.get_snapshot` is not registered in `src/gateway/method_census.rs`.

> **Status: planned** — the blueprint is `docs/research/NSH_PROTOCOL_V1.md` (chapter 11, the binary data channel); the current implementation is in `shared/protocol/src/framing.rs` and `shared/protocol/src/system_hello.rs`. The frame format is a text frame behind a 4-byte big-endian length prefix, and although `Feature::BinaryChannel` already exists in the handshake DTO, the server's implementation list is empty.

> **Status: planned** — the blueprint is `docs/research/NSH_PROTOCOL_V1.md` (chapter 18, acceptance tests); the current implementation is in `src/gateway/method_census.rs`. The method catalogue is already an executable census, but the protocol-level acceptance test matrix has not been built.

## History: How the Transport Entries Evolved

There was originally one entry, `/ws`, with a single WebSocket carrying all RPC and events. Desktop IPC and Web v1 came later, and their responsibilities were cut apart deliberately: Desktop IPC is read-only, while Web v1 is the network entry with its own TLS and credential exchange. `/ws` was not retired; it continues to serve as the compatibility entry, and new clients should pick Desktop IPC or Web v1. The old desktop shell that predates the current NSH host is a transitional leftover and is on its way out.
