This page explains how Aleph takes screenshots, reads the accessibility tree, synthesizes input, and reaches calendars and contacts: which crates define and implement these capabilities, which process they run in, which calls are handed to a native platform helper, and how failures are recovered.

## What the desktop capability layer is

The desktop capability layer is a set of Rust libraries **compiled directly into `aleph-server`**, not a separate process:

| crate | Path | Role |
|---|---|---|
| `aleph-desktop` | `desktop/shared/` | Capability traits, shared implementations, the Swift helper client |
| `aleph-desktop-macos` | `desktop/macos/` | macOS implementation |
| `aleph-desktop-linux` | `desktop/linux/` | Linux implementation |
| `aleph-desktop-windows` | `desktop/windows/` | Windows implementation |

In the root `Cargo.toml`, `alephcore` depends on `aleph-desktop` directly and on each platform crate per target OS. The platform object is constructed in-process (`src/executor/builtin_registry/builder/constructor/mod.rs`, `src/bin/aleph-server/commands/start/builder/handlers/settings.rs`).

Capabilities are exposed through the aggregate trait `DesktopPlatform` (`desktop/shared/src/platform.rs`). Its `ax()` and `power()` return `Option`, so a platform can declare that it does not provide them.

<Callout type="info" title="Not the Panel bridge">

On this page, "bridge" means the JSON-RPC channel between `aleph-server` and the macOS Swift helper. The desktop host's `desktop/nsh-shell/src/panel_bridge.rs`, which talks to the Panel, is a different thing; see [Panel host](../desktop-hosts/panel).

</Callout>

All traits are defined in `desktop/shared/src/traits/`. The implementation columns only state that a trait implementation exists; per-method completeness on Linux and Windows was not verified in this pass.

## Two implementation paths

### In-process Rust implementations

Most capabilities execute inside the `aleph-server` process. On macOS, for example, the system capability uses native objc2 calls (`desktop/macos/src/system/mod.rs`), automation shells out to `osascript` and the `shortcuts` CLI (`desktop/macos/src/automation.rs`), and sleep inhibition uses an IOPMAssertion (`desktop/macos/src/sleep_inhibitor.rs`). Linux and Windows have no resident helper process; their implementations live in the platform crates and call system APIs or system command-line tools as needed. `docs/reference/DESKTOP_BRIDGE.md` makes this split a design decision: lightweight paths such as clipboard, app launch, window enumeration, and screen recording stay in-process in `aleph-desktop`.

### Delegation to the Swift helper

Only macOS hands the heavier capture and recognition work to a Swift helper process: camera, audio, Vision OCR, speech, EventKit, contacts, and similar (`docs/reference/DESKTOP_BRIDGE.md`). The Swift package lives in `desktop/macos/bridge/`, and a comment in `desktop/macos/src/pim.rs` states that the PIM implementation delegates to the `aleph-bridge` Swift CLI through the long-lived JSON-RPC client. That client, `SwiftBridge`, is defined in `desktop/shared/src/bridge/client.rs` and is used only by the macOS crate.

Each `aleph-server` process owns one shared helper instance, started on first use (`SHARED_BRIDGE` in `desktop/macos/src/lib.rs`). The helper binary is resolved in this order (`resolve_helper_path` in the same file):

1. The `ALEPH_BRIDGE_PATH` environment variable
2. `~/.aleph/helpers/AlephBridge`
3. Next to the current executable
4. The development build output: `.build/release/AlephBridge` inside the Swift package `desktop/macos/bridge/`

The helper has exactly one mode: it starts with no arguments, speaks JSON-RPC over stdin/stdout, and exits on stdin EOF or parent death (`desktop/macos/bridge/Sources/AlephBridge/main.swift`).

### Protocol

The protocol is defined in `shared/protocol/src/desktop_bridge/` as line-delimited JSON-RPC 2.0. Envelope types (`shared/protocol/src/desktop_bridge/envelope.rs`):

```rust
Request       { jsonrpc, id: u64, method, params: Option<Value> }
Response      { jsonrpc, id: u64, result }
ErrorResponse { jsonrpc, id: Option<u64>, error: RpcError }
RpcError      { code: i32, message, data: Option<Value> }
Notification  { jsonrpc, method, params }
```

Request IDs are increasing `u64` values.

Server-defined error codes (`shared/protocol/src/desktop_bridge/errors.rs`):

| Constant | Value | Client maps to `DesktopError` |
|---|---|---|
| `ERR_PERMISSION_DENIED` | -32001 | `PermissionDenied { kind, guide }`; `BridgeFailed` when `data` does not parse as a guide |
| `ERR_NOT_IMPLEMENTED` | -32002 | `NotImplemented` |
| `ERR_PLATFORM` | -32003 | `PlatformError` |
| `ERR_TIMEOUT` | -32004 | `BridgeTimeout` |
| `ERR_HELPER_CRASHED` | -32005 | `BridgeFailed` |
| `ERR_BRIDGE_DISABLED` | -32006 | `BridgeDisabled` |

The mapping function is `map_bridge_error` in `desktop/shared/src/bridge/client.rs`; unknown codes also become `BridgeFailed`.

Methods fall into seven namespaces (`shared/protocol/src/desktop_bridge/methods/`). Each namespace has a default timeout, and some methods override it:

| Namespace | Methods | Default timeout | Overrides |
|---|---|---|---|
| `bridge.*` | `bridge.handshake`, `bridge.ping` | 5 s | `ping` 2 s |
| `ax.*` | `query_focused`, `query_tree`, `query_by_role`, `set_value`, `perform_action`; notification `ax.mutation` | 15 s | `query_focused` 3 s |
| `input.*` | `click`, `double_click`, `type_text`, `key_combo`, `key_button`, `scroll`, `drag`, `hover`, `cursor_position`, `mouse_button` | 2 s | `click`, `double_click` 5 s |
| `media.*` | `media.camera.snap`, `media.camera.clip`, `media.audio.list_devices`, `media.audio.record`, `media.audio.record_start`, `media.audio.record_stop`, `media.speech.transcribe_file` | 60 s | `media.camera.snap` 10 s, `media.audio.list_devices` 5 s, `media.audio.record_stop` 15 s |
| `perm.*` | `perm.check`, `perm.guide`, `perm.open_settings` | 10 s | — |
| `pim.*` | 24 methods in five groups: `notes`, `calendar`, `reminders`, `contacts`, `mail` | 60 s | — |
| `screen.*` | `screen.capture`, `screen.ocr`, `screen.list_displays` | 10 s | `ocr` 20 s, `list_displays` 5 s |

`input.*` supports two delivery modes, `DELIVERY_TARGETED = "targeted"` and `DELIVERY_GLOBAL = "global"` (`shared/protocol/src/desktop_bridge/methods/input.rs`). Window and clipboard operations do not use the helper protocol; they run in-process.

## Helper lifecycle and failure handling

### Lazy start

`SwiftBridge::ensure_running` (`desktop/shared/src/bridge/client.rs`) starts the helper on the first call: all three standard streams are piped, `kill_on_drop(true)` is set, and the helper gets its own process group. Its stderr is forwarded line by line to the tracing target `bridge_stderr`. The handshake protocol version is `BRIDGE_PROTOCOL_VERSION = 2`. The check and the spawn happen under one state lock, so the helper is never spawned twice.

When the reader loop sees EOF on the helper's stdout, it drains in-flight requests, resets the state slot, and records a crash; a generation counter stops a stale reader from touching a newer helper's state. A failed spawn also counts as a crash.

### Backoff and disable

Backoff and disable logic lives in `desktop/shared/src/bridge/supervisor.rs`; the client constructs it as `SpawnGate::new(5, 10 min)`:

| Mechanism | Behavior in code |
|---|---|
| Backoff ladder | `Backoff::next_delay`: 1 s, 2 s, 4 s, 8 s, 16 s, then capped at 30 s |
| Ladder reset | If a helper that lived at least `STABLE_UPTIME` (10 s) dies, the ladder restarts; a successful spawn alone does not reset it |
| Calls during backoff | No spawn happens; the call returns `DesktopError::BridgeBackoff` with a message like `helper recovering; retry in Ns` |
| Disable threshold | When failures within the 10-minute window **exceed** 5, i.e. on the 6th failure, the bridge is disabled |
| Calls after disable | Return `DesktopError::BridgeDisabled("restart threshold exceeded")` immediately until the server restarts |

### Per-call timeouts

A helper that hangs without closing stdout never produces EOF, so every call has a deadline. `SwiftBridge::call` resolves it through `rpc_timeout_for`: the per-method override first, then the namespace default (`suggested_timeout_ms` in `shared/protocol/src/desktop_bridge/methods/mod.rs`), and finally `DEFAULT_RPC_TIMEOUT` (1 minute). A timeout returns `BridgeTimeout` and leaves the helper running.

Calls whose duration depends on their arguments pass an explicit deadline through `call_with_timeout` (`desktop/macos/src/lib.rs`): `media.camera.clip` and `media.audio.record` use the requested duration plus `CAPTURE_TIMEOUT_MARGIN_SECS` (30 s), and `media.speech.transcribe_file` uses `SPEECH_TRANSCRIBE_TIMEOUT` (5 minutes).

### Parent-death watchdog

The `aleph-server` SIGTERM handler calls `std::process::exit`, which bypasses Rust `Drop`, so the helper's stdin is not guaranteed to close. The helper therefore carries a watchdog (`desktop/macos/bridge/Sources/AlephBridge/RPC/ParentWatch.swift`):

- Fast path: a `DispatchSource` process-exit event (kqueue) on the parent PID, with a re-check after registration to close the race;
- Backstop: every 10 s it checks `getppid() <= 1`; if true it prints `aleph-bridge: parent died, exiting` and calls `exit(0)`.

### Error types

`DesktopError` (`desktop/shared/src/error.rs`) has the variants `NotAvailable`, `ScreenCapture`, `InputFailed`, `OcrFailed`, `WindowFailed`, `NotImplemented`, `BridgeFailed`, `BridgeTimeout`, `BridgeBackoff`, `BridgeDisabled`, `PlatformError`, and `PermissionDenied { kind, guide }`. Callers use them to tell "helper unresponsive", "helper in a crash loop", and "OS permission not granted" apart.

## Tool orchestration layer

`src/builtin_tools/desktop/` is the agent-facing tool orchestration. It runs inside `aleph-server` and reaches platform capabilities only through `DesktopPlatform`, never calling system APIs directly:

| File | Responsibility |
|---|---|
| `mod.rs`, `types.rs` | `DesktopTool` and the argument type `DesktopArgs` |
| `native.rs` | Pointer and keyboard actions; picks the input rail |
| `ax.rs` | Three read-only accessibility queries over `DesktopPlatform::ax()` |
| `observe.rs` | Post-action observation |
| `gui_locate.rs` | Natural-language description to screen coordinates (`desktop_gui_locate`) |
| `set_of_marks.rs` | Set-of-marks screenshots (`desktop_som`) |
| `verify_state.rs` | Tri-state postcondition checks against the accessibility tree |
| `focus_gate.rs` | Focus pre-flight before `type_text` |
| `perm.rs` | Permission checks (`desktop_check_permissions`) |

### Two input rails

`enum Rail { Targeted(i32), Global }` in `src/builtin_tools/desktop/native.rs` separates two delivery modes:

- **Targeted**: events go only into one target process's queue and do not move the user's cursor. Naming `pid`, `app`, or `window_id` in the arguments selects the targeted rail.
- **Global**: events go through the system-wide HID event tap and move the user's cursor.

On a platform that supports targeted input, the global pointer is refused by default unless `[desktop] allow_global_pointer = true` is configured (`src/config/types/desktop.rs`). The refusal is a deliberate fail-closed choice; there is no silent fallback to the global rail. Targeted-input support is reported by `supports_targeted_input`: the trait default returns `false` and every `*_targeted` method defaults to `NotImplemented` (`desktop/shared/src/traits/screen.rs`); currently only macOS returns `true` (`desktop/macos/src/screen.rs`).

## Redline mapping

Redline R1, "absolute separation of brain and limbs", forbids calling platform system APIs directly in `src`: Core defines capability contracts only, and the platform side provides the physical implementation (`docs/reference/REDLINES.md`; see also [Redlines](../philosophy/redlines)).

- `src/builtin_tools/desktop/` is tool orchestration that depends only on the `DesktopPlatform` trait, so it does not violate R1.
- All platform implementations live in `desktop/{macos,linux,windows}`. `docs/reference/DESKTOP_BRIDGE.md` states that `src/` in `alephcore` never links AVFoundation, Vision, AppKit, CoreGraphics, or Speech.
- R1 has one explicit exception: process-isolation kernel operations must be issued in place by the parent that spawns the child (`docs/reference/REDLINES.md`). That code is not part of the desktop capability layer.

## History: the standalone aleph-bridge process

- The Swift helper originally worked as a CLI invoked once per call through subcommands. A comment in `ParentWatch.swift` still mentions this one-shot subcommand mode, but the current `AlephBridge/main.swift` keeps only the JSON-RPC mode.
- A set of commits on 2026-04-24 turned it into a long-lived child process: `7ed5a051d` split the bridge into its own module inside `desktop/shared`, `92533821d` introduced the long-lived `SwiftBridge` client (line-delimited JSON-RPC over stdin/stdout), and `1fc069a49` added backoff restarts and the disabled mode.
- Today the helper carries only the heavier capture and recognition work on macOS; macOS media no longer has a Rust-side AVFoundation implementation and always goes through the helper (`desktop/macos/src/lib.rs`).
- On 2026-08-09 the `media.audio.mic_meter` method and its timeout override were removed (comment in `shared/protocol/src/desktop_bridge/methods/media.rs`).
