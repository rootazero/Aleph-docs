## Overview

Aleph ships a comprehensive set of built-in tools covering file operations,
code execution, web interaction, memory, browser automation, sub-agent
delegation, scheduling, and more. All built-in tools implement the
`AlephTool` trait with static dispatch for maximum performance, and are
assembled by the executor's builtin registry (`src/executor/builtin_registry/`)
at startup.

Every tool call funnels through **the same chokepoint** —
`ScopedToolService` (`src/tools/scoped/`). Exec tier, the command-policy
floor, and per-channel permission merging all happen there. Whether a tool
"requires confirmation" is decided by its `ToolDefinitionMetadata`, **not**
its name.

## Code execution

| Tool | Description |
|------|-------------|
| `bash` | Run a bash command (via `WorkspaceSandbox`). |
| `code_exec` | Multi-language code snippet (`shell` / `python` / `javascript`). |

Both dispatch subprocesses through `Arc<dyn Sandbox>`. Naked `Command::new`
is **not** allowed in `src/builtin_tools/`. `code_exec` takes `language` and
`code`, `bash` takes `cmd`; both accept optional `working_dir` and `timeout`
(seconds), and output is bounded by the sandbox wall-clock (default 60 s) and
a 1 MiB output budget.

## Background jobs

`bash` with `background: true` hands the command to a background task and
returns a `process_id` immediately — the way to run builds, installs and long
test suites that outlive the 180 s foreground ceiling. Management uses the
same tool's `process_action`; when `process_action` is set, `cmd` is ignored:

| `process_action` | Behaviour |
|------------------|-----------|
| `poll` | Check the status. While running it returns an 8 KB `partial_stdout` / `partial_stderr` tail; once finished it returns the full `{exit_code, stdout, stderr}`. |
| `wait` | Block until the job ends and return its full output; the wait window defaults to 60 s, can be extended with `timeout`, and caps at 170 s. If the window expires while the job still runs, it returns the `running` status. |
| `kill` | Terminate the background process. |
| `list` | Enumerate this session's background processes. |
| `read` | Read new eligible output with the optional opaque `cursor`. Pass the returned `next_cursor` to continue. Each stream reports whether data was lost, withheld, or is still pending. |

Notes:

- **Only the foreground ceiling is bypassed.** The task runs through
  `call_unclamped`, so the 180 s per-call budget does not apply, but it still
  takes the same sandbox path — capability checks, workspace ownership and
  approvals behave exactly as they do in the foreground
  (`src/builtin_tools/bash_exec.rs:469`).
- **One hour by default.** Without an explicit `timeout` a background job gets
  3600 s; the explicit ceiling is 4 hours (`BACKGROUND_MAX_TIMEOUT_SECS`) and
  larger values are clamped.
- **Scoped per session.** A background process belongs to the session that
  started it — other sessions can neither see nor kill it. Each session may
  have at most 8 running jobs, 32 run globally, the registry holds 64 entries,
  and the command preview is truncated to 120 characters
  (`src/builtin_tools/process_registry.rs:64`).
- **Cannot outlive an owned worktree.** When the workspace is an owned
  worktree, background mode is refused with
  `bash: background commands cannot outlive an owned worktree; run without background or yield_ms`.
- **Output passes a content gate first.** The raw bytes of the live tail only
  reach `poll` / `wait` after the content gate in
  `src/builtin_tools/partial_output.rs`; the live buffer itself lives in
  `src/sandbox/live_tail.rs`.
- **Registry in memory, journal on disk.** `ProcessRegistry` is a pure in-memory
  structure; after a daemon restart the records survive through the
  cross-process journal in `src/builtin_tools/process_journal.rs`.
- **The child sees its identity.** The shell sees `ALEPH_SESSION_ID` and
  `ALEPH_TOOL_NAME=bash`.

## Controlled JSONL input on paired Linux

Aleph exposes this profile only on an eligible paired Linux route with an operator available to approve input. The Gateway launches a fixed jq inspector under the supervised Workspace and Bubblewrap path. Ordinary Bash commands cannot accept interactive input.

- Start with `stdin_profile: "jsonl_inspect"` and either `background: true` or `yield_ms`. The launch accepts only those fields. `yield_ms` ranges from 1 to 10,000 and sets the first observation window in milliseconds.
- Use `process_action: "write_stdin"` with `process_id` and `record` to submit one JSON value, including `null`. Each write requires fresh approval. The serialized record, including its newline, may use up to 4096 bytes, and accepted records may use up to 16 KiB in total. The Gateway rejects values beyond those bounds.
- Use `process_action: "close_stdin"` with `process_id` to send EOF. The first EOF requires operator approval. Use `process_action: "read"` to resume output by cursor. The inspector reports the root type and, for containers, the length.

The schema is defined in `src/builtin_tools/bash_jsonl.rs`; the paired Gateway effect and input limits are in `src/gateway/execution_engine/shell_effect.rs` and `src/sandbox/shell_input.rs`.

## Memory and retrieval

Three complementary retrieval tools, each searching a **different store**.
Descriptions are tuned to avoid tool-choice confusion:

| Tool | Store | Use when |
|------|-------|----------|
| `ctx_search` | Offloaded tool **output** (FTS5 content index) | A tool result is tagged `[Full output persisted: … Indexed N sections …]` and you need only the relevant slice (build log, big grep, web fetch). |
| `recall_events` | **This session's** event timeline (`session_events`, BM25) | An earlier tool action, result, or error was dropped from context by compaction and you need to recover what already happened. |
| `session_search` | **Past conversations across sessions** (memory summaries + transcripts) | You need facts or decisions from *other* sessions (long-term memory). |

Rule of thumb: `ctx_search` = "what did that tool print?"; `recall_events`
= "what did I already do this session?"; `session_search` = "what happened
in past sessions?".

Other memory tools:

| Tool | Description |
|------|-------------|
| `memory_search` | Hybrid retrieval across facts + transcripts, deduplicated by `ContextComptroller`. |
| `memory_explore` | Browse the fact graph (fact clusters, similarity navigation). |
| `memory_timeline` | Time-ordered fact view. |
| `memory_browse` | Browse stored entries. |
| `remember` | Explicitly write a fact to long-term memory. |
| `recall_context` | Pull facts relevant to the current session (for context assembly). |

## MCP bridge tools (capability-gated)

These built-in tools appear in the registry **only while at least one
connected MCP server advertises the matching capability**
(`src/mcp/tool_bridge.rs::reconcile_capability_tools`). The model is never
offered a tool that every call would reject.

| Tool | Capability that triggers it |
|------|-----------------------------|
| `mcp_read_resource` | Any server with `resource_count > 0` or `resource_template_count > 0` |
| `mcp_list_resources` | Same as above (paired with `mcp_read_resource`) |
| `mcp_list_resource_templates` | Same as above |
| `mcp_get_prompt` | Any server with `prompt_count > 0` |
| `mcp_list_prompts` | Same as above (paired with `mcp_get_prompt`) |
| `mcp_login` | Any server whose transport is not `Stdio` (remote OAuth flow) |

`mcp_read_resource` and `mcp_get_prompt` resolve `<server>:<rest>` ids
through `resolve_server_qualified` with **longest-prefix** server match —
shortest/first match mis-routes a resource on a server literally named
`gh:sub` to a server named `gh`.

## Sub-agent and multi-agent

| Tool | Description |
|------|-------------|
| `a2a_delegate` | Delegate to a remote agent over the A2A protocol. |
| `a2a_agents` | List A2A agents available for delegation. |
| `acp_delegate` / `acp_switch` / `acp_session_control` | ACP protocol entry points. |
| `node_list` / `node_invoke` / `node_invoke_many` / `node_file` / `node_manage` | Cluster-node discovery, invocation, and file IO. |
| `team_*` | Team subsystem entry points (dispatcher / broadcast / disband). |

A delegated sub-agent is its own principal in the signed-ledger model: it
holds its own Ed25519 key and signs its own work — it is not a line on its
parent's chain. The acting role is injected by `AllowlistToolService`
(the spawner builds this wrapper from the child's `AgentDef`); the
sub-agent runs on its *parent's* `ScopedToolService` and inherits the
parent's `TURN_CONTEXT`, but the ledger identity is its own.

### Diagnostic surfaces

`doctor` is the ordinary diagnostics entry point.
`capability_projection_diagnostics` is the capability runtime's diagnostic
control surface, off by default: it is advertised only when the process
starts with `ALEPH_CAPABILITY_DIAGNOSTICS=1`; while disabled it is neither
advertised nor dispatched, and its hold / timer state is empty. Even when it
is visible to the model, only an operator process that passes a three-part
check can drive it (operator role, loopback transport, non-empty connection
id) — `ALEPH_GATEWAY_TOOLS_ALLOW` cannot bypass that gate.

Seven operations, discriminated by `operation`: `status` (read the real
applied state and the queue / telemetry counters), `bump_runtime` (advance the
runtime generation), `revoke_tool` (drop one tool from the live tree by
`tool_name`), `dispose_runtime` (drop the whole runtime scope), `hold` (freeze
one `plane` for `duration_ms`, 1 to 5000 ms), `release` (drop the active hold)
and `close` (shut the host down).

| Tool | Description |
|------|-------------|
| `workspace_manage` | Workspace records — list / get / create / update / archive / unarchive. A workspace id IS an agent id (1:1) and names that agent's memory and notes partition. |

## Context plugins, extension catalog and usage

| Tool | Description |
|------|-------------|
| `context_plugin` | Grant or revoke a mounted context plugin for the current session. Requires operator confirmation of these exact arguments. |
| `hub_catalog_search` | Search or browse the Aleph Hub catalog of installable extensions (MCP servers, skills, plugins). Reads the local cache — works offline. |
| `tool_usage` | Invocation records for installed MCP servers, plugins and skills — call counts, last-used dates, and what has gone unused. Read-only. |

`context_plugin` grants expire (default one hour) and do not permit network
access, project writes or other sessions; reload/unload revokes the old
mount, so you must grant again. `hub_catalog_search` is where you get the
`entry_id` that `hub_resolve_spec` and `hub_install_run` require; run
`hub_catalog_sync` first if results look stale. A `—` count in `tool_usage`
means that entry has no tool-call channel to measure (e.g. a hooks-only
plugin) and is NOT evidence it is unused.

## MCP tool naming and registration

Tools discovered from MCP servers are registered as `<server>__<tool>`
(e.g., `github__create_issue`). `McpHandler::qualified_name` is the single
source of naming truth (`src/tools/handlers/mcp.rs`): it strips the
manager's redundant `{server}:` prefix, maps any character outside
`[A-Za-z0-9_-]` to `_`, and truncates to 64 characters. The `__` is a
namespace separator — the LLM sees it as part of the name.

Schemas whose `type` is not `"object"` are **quarantined** — a schema that
every provider would reject would otherwise poison the whole turn with an
HTTP 400.

## Registration summary

Built-in tools are assembled by `BuiltinToolRegistry::with_config()`
(`src/executor/builtin_registry/builder/constructor/mod.rs`). The
authoritative list of names and descriptions is
`src/executor/builtin_registry/definitions.rs:85`
(`BUILTIN_TOOL_DEFINITIONS`); `create_tool_boxed()` (same file, `:907`) builds
an instance by name and returns `None` when a dependency is missing — the tool
is unavailable for that turn rather than conjured into existence.

The registry, while assembling:

- injects a shared `Arc<dyn Sandbox>` into every exec-class tool
  (`bash`, `code_exec`, `code_check`);
- injects `Arc<ProfileManager>` into every browser tool;
- injects `Arc<McpManagerHandle>` into every MCP-bridge tool;
- injects channel context / `ApprovalRequester` into the tools that need
  them.

Tool names live on four registration surfaces; the catalogue covers only the
first:

| Surface | Location | Meaning |
|---------|----------|---------|
| Catalogue | `BUILTIN_TOOL_DEFINITIONS` (`definitions.rs:85`) | Unconditionally registered; the authoritative list shown to agents. |
| Registry-only | `REGISTRY_ONLY_DESCRIPTIONS` (`definitions.rs:1308`) | Registered only when a dependency or health check passes (e.g. `scratchpad`, `permission`, `media`, `system`). |
| Outside the catalogue | `TOOLS_OUTSIDE_DEFINITIONS` (`src/executor/mod.rs:30`) | `subagent` and `tool_search` — not in the catalogue, still callable by the model. |
| Per-request injection | `src/tools/scoped/mod.rs` | e.g. `get_tool_schema`, appended to the tool list per request. |

Six MCP-bridge tools (`mcp_read_resource` and friends) are registered by
capability gate in `src/mcp/tool_bridge.rs`: in no catalogue and at no `reg(`
site.

Every `requires_confirmation` tool is listed once in
`CONFIRMATION_REQUIRED_TOOLS` (vault_store, agent_delete, team_disband, …)
and shares one `ApprovalRequester`. This is fail-closed by construction —
any built-in tool not in `READ_ONLY_TOOLS` requires approval under the
`Ask` tier.
