This page explains how the Gateway identifies callers and how tool permissions, execution approval, sandboxing, and audit govern their actions.

## Security Architecture

| Layer | Responsibility | Implementation |
|-------|----------------|----------------|
| Entry points | Check transport, origin, credentials, or the Unix socket peer | `src/gateway/server/connection/`, `src/gateway/origin_policy.rs` |
| Tool permissions | Apply tool permissions and execution tiers at dispatch | `src/tools/scoped/` |
| Execution approval | Bind the operator's decision to the specific action, not just the tool name | `src/sandbox/exec_approval/` |
| Sandbox | Restrict execution by workspace and capability, and apply the platform sandbox | `src/sandbox/workspace/`, `src/sandbox/platforms/` |
| Audit | Store security events, approval decisions, and signed identity records | `src/security/audit.rs`, `src/tools/scoped/dispatch.rs`, `src/identity/` |

## Network Boundaries and Gateway Credentials

The Gateway listens on loopback by default. Compatibility `/ws` grants implicit `operator` access only to direct loopback clients that omit device credentials. Remote callers need a valid device token, bootstrap ticket, or legacy shared token. Plaintext remote connections are denied by default; use native TLS or a trusted TLS-terminating proxy for the compatibility endpoint. Passing a browser origin check does not authenticate the caller (`src/gateway/config.rs`, `src/gateway/server/mod.rs`, `src/gateway/server/connection/upgrade.rs`, `src/gateway/handlers/connect.rs`).

The default network address does not define trust for every entry point. Desktop IPC verifies the Unix socket peer; Web v1 uses native TLS, same-origin checks, and device sessions. Both expose only a limited set of read-only RPCs (`src/gateway/server/connection/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs`). See [Gateway authentication](../gateway/auth) and [IPC protocol](./ipc).

### Remote TLS and Client Trust

The Gateway can load a supplied certificate or generate a self-signed one. Transport encryption and caller authorization are separate checks. With a self-signed certificate, the client must still trust it. NSH requires HTTPS for remote `--connect` targets (`src/gateway/tls.rs`, `src/gateway/server/connection/upgrade.rs`, `desktop/nsh-shell/src/main.rs`, `shared/client/src/connection_target.rs`).

## Pairing

### Device Pairing

`gateway.ticket.create` creates a single-use bootstrap ticket. Compatibility `/ws` exchanges it through `connect.bootstrap_ticket` for a device token to use on reconnect. Web v1 requires the ticket to be bound to a principal. Use `gateway.devices.revoke` to revoke one device; rotating the shared token revokes Panel device credentials (`src/gateway/handlers/gateway_ticket.rs`, `src/gateway/handlers/connect.rs`, `src/gateway/security/device_token_manager.rs`, `src/gateway/server/connection/web_v1.rs`, `src/gateway/handlers/gateway_devices.rs`, `src/gateway/handlers/gateway_token.rs`).

### Channel Sender Pairing

Pairing an unknown channel sender does not grant a Gateway device identity. A separate store manages pairing codes. Operators inspect requests with `pairing.list`, then handle them with `pairing.approve` or `pairing.reject` (`src/gateway/pairing_store.rs`, `src/gateway/handlers/pairing.rs`).

## Tool Permissions

`ScopedToolService` combines global, agent, and channel tool permissions. Dispatch considers explicit `allow`, `ask`, and `deny` rules alongside the execution tier. `ToolFacts` supplies metadata such as whether the tool is idempotent or requires approval. The sandbox command policy rejects prohibited commands regardless of Gateway authentication (`src/tools/scoped/`, `src/sandbox/command_policy/`).

## Execution Approval Gate

The Panel lets an operator allow or deny a pending sensitive call and sends the decision through `exec.approval.resolve` (`interfaces/webchat/src/components/approval_card.rs`, `interfaces/webchat/src/api/exec_approval.rs`, `src/gateway/handlers/exec_approvals.rs`). The gate uses `ApprovalAction` to bind approval to the tool and original normalized arguments. The redacted summary displayed to the operator does not determine the grant fingerprint (`src/sandbox/exec_approval/action.rs`).

## Sandboxing

`WorkspaceSandbox` constrains execution by workspace and capability. The command policy filters explicitly prohibited commands before execution; approval cannot bypass it. Platform implementations live in `src/sandbox/platforms/macos/`, `src/sandbox/platforms/linux/`, and `src/sandbox/platforms/windows/`. See [Sandboxing](./sandboxing) for platform mechanisms and limitations (`src/sandbox/workspace/`, `src/sandbox/command_policy/`).

## Audit

- Security audit records include remote authentication failures and unauthorized request floods on compatibility WS (`src/security/audit.rs`, `src/gateway/server/connection/mod.rs`).
- Tool dispatch can record `ToolCallApproved` and `ToolCallDenied` as session events (`src/tools/scoped/dispatch.rs`).
- An agent's signed ledger links actions to its identity with Ed25519 signatures and a hash chain (`src/identity/`).

## Cross-Process State Protection

Aleph protects service startup with an instance lock. Vault and JSON files have separate atomic write paths, and SQLite uses a shared safe-open helper. The CLI uses `CommandPolicy` to distinguish commands that need no lock, acquire a lock, or can use administrative IPC (`src/utils/instance_lock.rs`, `src/utils/vault_io.rs`, `src/utils/atomic_io.rs`, `src/utils/sqlite_open.rs`, `src/cli/policy.rs`).
