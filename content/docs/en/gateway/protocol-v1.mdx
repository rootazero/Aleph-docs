## What Protocol v1 is

Protocol v1 is in use on the Gateway’s **Desktop IPC** and **Web v1** endpoints. Both carry JSON-RPC 2.0 in bounded frames and require a `system.hello` handshake before other requests. The legacy `/ws` endpoint remains available for compatibility and does not use length prefixes (`src/gateway/server/connection/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs`, `src/gateway/server/connection/mod.rs`).

| Component | Source |
|-----------|--------|
| Frame encoding and decoding | `shared/protocol/src/framing.rs` |
| Handshake types and negotiation | `shared/protocol/src/system_hello.rs` |
| Server handshake | `src/gateway/handlers/system_hello.rs` |
| JSON-RPC messages and error codes | `shared/protocol/src/jsonrpc.rs` |

<Callout type="info">
The two NSH Panel hosts use different transports.

- **Default Leptos Panel:** `web_view` loads the page from `http://127.0.0.1:18790/` by default. The default Gateway WebSocket is `ws://127.0.0.1:18790/ws` (`desktop/nsh-shell/src/main.rs`, `desktop/nsh-shell/src/shell_host.rs`, `desktop/nsh-shell/src/credentials.rs`).
- **TSX Panel:** Build on macOS with `--features tsx-panel`, then enable it with `ALEPH_SHELL_PANEL=tsx` (not with QA mode). The Panel runs in a native AppView. The host connects only to a local Gateway at the absolute socket path specified by `ALEPH_SHELL_PANEL_IPC`. Other targets report `unavailable`; there is no WebSocket fallback (`desktop/nsh-shell/Cargo.toml`, `desktop/nsh-shell/src/main.rs`, `desktop/nsh-shell/src/panel_surface.rs`, `desktop/nsh-shell/src/panel_host.rs`).
</Callout>

## Frame format

A frame consists of a **4-byte big-endian** `u32` length prefix followed by a UTF-8 JSON payload. The length counts payload bytes only, excluding the header. `HEADER_BYTES` is 4 and `DEFAULT_MAX_PAYLOAD_BYTES` is 8,388,608 (8 MiB). Desktop IPC uses that default for `MAX_FRAME_BYTES`; Web v1 sets `MAX_MESSAGE` to 1 MiB (`shared/protocol/src/framing.rs`, `shared/client/src/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs`).

The codecs in `shared/protocol/src/framing.rs` are:

| Function | Behavior |
|----------|----------|
| `encode_header` | Returns the big-endian header. A zero length returns `Empty`; a length above the supplied cap or outside the `u32` range returns `Oversize` |
| `decode_header` | Applies the same checks to the declared length before reading or allocating the payload |
| `split_frame` | Borrows one UTF-8 payload and the remaining bytes without parsing JSON. An incomplete frame returns `Ok(None)`; invalid UTF-8 returns `InvalidUtf8`. A framing error ends framing for that stream |

The cap is inclusive: a payload at the cap is valid, but one more byte returns `Oversize`. For example, `{"jsonrpc":"2.0","id":2,"method":"health"}` is a 42-byte payload with the header `00 00 00 2A` (`shared/protocol/src/framing.rs`).

```text
00 00 00 2A | 7B 22 6A 73 6F 6E 72 70 63 22 3A 22 32 2E 30 22 ... 7D
4-byte header | 42-byte UTF-8 JSON payload
```

| Payload length | Result at the default cap (`shared/protocol/src/framing.rs`) |
|----------------|---------------------------------------------------------------|
| 12 | `00 00 00 0C` |
| 258 | `00 00 01 02` |
| 8,388,608 | `00 80 00 00` |
| 8,388,609 | `Oversize` |
| 0 | `Empty` |

## The `system.hello` handshake

`system.hello` is the first RPC request on both v1 endpoints. It negotiates the version and features and reports connection limits. It is not a client credential (`shared/protocol/src/system_hello.rs`, `src/gateway/server/connection/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs`).

### Request

This example does not use the NSH host’s actual defaults. The four `client` fields (`name`, `version`, `platform`, `ui_runtime`) are required strings. `features` can be an empty array (`shared/protocol/src/system_hello.rs`). The two features requested here are exactly the ones both v1 endpoints implement; legacy `/ws` implements no optional feature, so those names are never granted there.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "system.hello",
  "params": {
    "protocol": { "major": 1, "minor": 0 },
    "client": {
      "name": "example-client",
      "version": "1.2.3",
      "platform": "linux",
      "ui_runtime": "example"
    },
    "features": ["live_events", "chat_transcript"]
  }
}
```

### Response

This is a successful Desktop IPC response. The server version, connection UUID, and `subject` value are illustrative (`src/gateway/handlers/system_hello.rs`, `src/gateway/server/connection/local_ipc.rs`).

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocol": { "major": 1, "minor": 0 },
    "server": { "name": "aleph-server", "version": "26.9.1" },
    "connection_id": "ipc-3f0c1b52-8a0e-4d0a-9b1a-6a6d2f0a7e11",
    "features": ["live_events", "chat_transcript"],
    "limits": { "max_message_bytes": 8388608, "max_inflight_requests": 8 },
    "subject": "0123456789abcdef0123456789abcdef"
  }
}
```

### `subject`: client storage key

`subject` is an opaque, stable per-user value for client-side storage keys such as the Panel layout key. **It is not an identity or credential; clients must not use it to infer permissions.** `panel_subject` uses the Gateway’s shared-token secret to compute HMAC-SHA256 over `"aleph.panel.subject.v1\0"` (including the trailing NUL) followed by the user ID. It encodes the first 16 bytes as 32 hex characters. The result does not contain the raw user ID. Rotating the secret changes the storage key and affects only client presentation state (`src/gateway/handlers/system_hello.rs`, `src/gateway/security/crypto.rs`, `shared/protocol/src/system_hello.rs`).

Legacy `/ws` always omits `subject`. The v1 endpoints also omit it when the shared-token secret is unavailable. The `skip_serializing_if` attribute on `HelloResult` leaves the field out entirely rather than returning `null` (`src/gateway/handlers/system_hello.rs`, `shared/protocol/src/system_hello.rs`).

### Version negotiation

`negotiate_version` requires matching major versions and selects the lower minor version. The Gateway advertises `1.0`: a major other than 1 fails the handshake, and a successful response always has minor 0 (`shared/protocol/src/system_hello.rs`, `src/gateway/handlers/system_hello.rs`).

### Feature negotiation

`negotiate_features` selects known features common to both peers, removes duplicates, and preserves the client’s preference order. Unknown strings deserialize as `Unknown(String)` without breaking parsing and do not participate in negotiation (`shared/protocol/src/system_hello.rs`).

| Feature string | `Feature` variant (`shared/protocol/src/system_hello.rs`) |
|----------------|---------------------------------------------------------|
| `event_replay` | `EventReplay` |
| `snapshot` | `Snapshot` |
| `binary_channel` | `BinaryChannel` |
| `live_events` | `LiveEvents` |
| `chat_transcript` | `ChatTranscript` |

Unknown strings deserialize as `Unknown(String)`: they parse, but they do not take part in the negotiation (`shared/protocol/src/system_hello.rs`).

All three endpoints call the same `negotiate_features(requested, implemented)`; only `implemented` differs:

| Endpoint | `implemented` | Negotiation result |
|----------|---------------|--------------------|
| Legacy `/ws` | empty list | Always `[]` — the legacy endpoint pushes no events and has no optional features |
| Desktop IPC | `V1_FEATURES` | The intersection of the request with `LiveEvents` and `ChatTranscript` |
| Web v1 | `V1_FEATURES` | The same |

`V1_FEATURES` is exactly `LiveEvents` and `ChatTranscript` (`src/gateway/server/connection/mod.rs`). There is one extra condition: `chat_transcript` presupposes `live_events`, and `negotiate_features` drops `ChatTranscript` when `live_events` was not granted (`shared/protocol/src/system_hello.rs`). Recognizing a feature name does not enable the feature; `event_replay`, `snapshot` and `binary_channel` are still implemented by no endpoint, so they never appear in a negotiation result (`src/gateway/handlers/system_hello.rs`).

## Server behavior

`negotiate()` in `src/gateway/handlers/system_hello.rs` processes requests in this order:

1. Missing `params`: returns `INVALID_PARAMS` with `Missing params`.
2. `params` cannot be parsed as `HelloParams`: returns `INVALID_PARAMS` with a message starting with `Invalid system.hello params:`, followed by the parsing error.
3. Major version is not 1: returns `INVALID_PARAMS` with `incompatible protocol major version`.
4. Success: returns `protocol`, `server` (`name` is `aleph-server`; `version` comes from the compile-time `ALEPH_VERSION`), `connection_id`, `features`, `limits`, and optional `subject`.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": { "code": -32602, "message": "incompatible protocol major version" }
}
```

All three endpoints reuse `negotiate()` but supply their own connection ID, limits, and `subject`:

| Endpoint | `connection_id` | `limits.max_message_bytes` | `limits.max_inflight_requests` | `subject` | Source |
|----------|-----------------|----------------------------|--------------------------------|-----------|--------|
| Legacy `/ws` | `conn-<uuid4>` | 8,388,608 (8 MiB, advisory) | 128 (advisory) | Omitted | `src/gateway/handlers/system_hello.rs` |
| Desktop IPC | `ipc-<uuid4>` | `MAX_FRAME_BYTES` (8,388,608, enforced) | `MAX_INFLIGHT` (8, enforced) | Derived for the Gateway owner if the secret is available | `src/gateway/server/connection/local_ipc.rs` |
| Web v1 | `web-v1-<uuid4>` | `MAX_MESSAGE` (1,048,576, enforced) | 1 (requests handled serially) | Derived for the user bound to the Web session if the secret is available | `src/gateway/server/connection/web_v1.rs` |

On legacy `/ws`, `system.hello` is an optional version probe after `connect`. It neither admits the connection nor sets its identity (`src/gateway/handlers/system_hello.rs`).

## Transport matrix

| Endpoint | Transport | Authentication | Methods | Source |
|----------|-----------|----------------|---------|--------|
| Desktop IPC (Unix) | Unix domain socket with length-prefixed frames | OS verifies that the peer is the same user; grants no network privileges | `system.hello` first, then the 12 mounted methods listed below | `src/gateway/server/connection/local_ipc.rs`, `shared/client/src/local_ipc.rs` |
| Desktop IPC (Windows, not exposed) | Local named-pipe code is in the tree | Account authentication is implemented but not enabled | None: both the client connection and the Gateway listener are gated | `shared/client/src/local_ipc/windows.rs`, `src/gateway/server/connection/local_ipc/windows.rs`, `shared/client/src/local_ipc.rs` |
| Web v1 | WebSocket over native TLS; exactly one frame per Binary message | Same-origin check and session cookie; exchange a device token or bootstrap ticket for a session | `system.hello` first, then the 12 mounted methods listed below | `src/gateway/server/connection/web_v1.rs`, `src/gateway/server/mod.rs` |
| Legacy `/ws` (compatibility) | WebSocket Text messages without a length prefix | Checks transport security and `Origin` (if present) at upgrade, then authenticates with `connect` | Full legacy RPC surface, subject to authorization; see [Method Reference](./methods) | `src/gateway/server/connection/upgrade.rs`, `src/gateway/server/connection/mod.rs` |

The handshake handles `system.hello` separately; it is not part of the post-handshake method list. Both v1 endpoints share `V1_METHODS` and `v1_mounted()`, and they mount these 12 methods:

| Method | Purpose |
|--------|---------|
| `health` | Health check |
| `sessions.list` | Session list |
| `panel.capabilities.snapshot` | Panel capability snapshot (`PANEL_UI_CAPABILITY_SNAPSHOT_METHOD`) |
| `graph.query` / `graph.search` / `graph.node_detail` | Memory-graph query, search and node detail |
| `chat.history` / `chat.send` / `chat.abort` | The chat trio |
| `chat.transcript_details` | Presentation-layer changes of tool calls |
| `trace.tool_output` | Tool output |
| `context.breakdown` | Context breakdown |

These run through the same dispatch, ownership check and idempotency cache as on legacy `/ws`. The state-changing `panel.project.select` is not mounted on v1. Unmounted methods do not reach Core. The server returns `METHOD_NOT_FOUND` unless Web v1 hits its rate limit and closes the connection (`src/gateway/server/connection/mod.rs`, `shared/protocol/src/panel.rs`, `shared/protocol/src/memory_graph.rs`, `shared/protocol/src/chat_transcript.rs`, `src/gateway/server/connection/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs`).

See [Authentication](./auth) for credentials and the [IPC Protocol](../security/ipc) for trust boundaries.

### Desktop IPC

Opt in with `aleph-server start --desktop-ipc <socket>`. The server requires a fresh absolute Unix socket path in a 0700 directory owned by the caller. It does not replace an existing entry or remove the socket entry at shutdown (`src/bin/aleph-server/cli.rs`, `src/gateway/server/mod.rs`, `src/gateway/server/connection/local_ipc.rs`, `shared/client/src/local_ipc.rs`).

| Constant | Value | Meaning | Source |
|----------|-------|---------|--------|
| `MAX_CONNECTIONS` | 8 | Simultaneous IPC connections; the server stops accepting new connections at the cap | `src/gateway/server/connection/local_ipc.rs` |
| `WIRE_BUDGET` | 16 MiB | Per-connection in-flight payload budget, reserved after validating the header and before allocating the payload | `src/gateway/server/connection/local_ipc.rs`, `shared/client/src/local_ipc.rs` |
| `WRITE_TIMEOUT` | 5 seconds | Timeout for writing one frame | `src/gateway/server/connection/local_ipc.rs` |
| `NO_NETWORK_ORIGIN` | `0.0.0.0` | Placeholder origin in the connection state; grants no network privileges | `src/gateway/server/connection/local_ipc.rs` |
| `MAX_FRAME_BYTES` | `DEFAULT_MAX_PAYLOAD_BYTES` | Per-frame payload cap | `shared/client/src/local_ipc.rs` |
| `MAX_INFLIGHT` | 8 | In-flight requests per connection | `shared/client/src/local_ipc.rs`, `src/gateway/server/connection/local_ipc.rs` |
| `HELLO_TIMEOUT` | 5 seconds | Deadline for reading the first request | `shared/client/src/local_ipc.rs`, `src/gateway/server/connection/local_ipc.rs` |

- If the first valid RPC request is not `system.hello`, the server returns `AUTH_REQUIRED` and closes the connection. If the first frame does not arrive in time or is invalid, it closes without a response. The handshake derives `subject` for the Gateway owner (`src/gateway/server/connection/local_ipc.rs`).
- Requests must declare `"jsonrpc": "2.0"` and include a string or integer `id`. Notifications without an `id` and other invalid envelopes close the connection, as do duplicate in-flight IDs and requests beyond `MAX_INFLIGHT` (`src/gateway/server/connection/local_ipc.rs`).
- `parse_payload` limits nesting depth (`MAX_DEPTH`, 64), items per container (`MAX_ITEMS`, 4,096), and bytes per string (`MAX_STRING_BYTES`, 65,536). If a post-handshake response exceeds the size or JSON shape limits, the server substitutes `INTERNAL_ERROR` with the original request `id` (`shared/client/src/local_ipc.rs`, `src/gateway/server/connection/local_ipc.rs`).

### Web v1

`native_tls_router` mounts Web v1 only on the native TLS router (`src/gateway/server/mod.rs`). The endpoints and limits are defined in `src/gateway/server/connection/web_v1.rs`:

| Item | Value |
|------|-------|
| Session exchange | `POST /v1/session`, request body up to 4,096 bytes |
| JSON request body | `{"device_token": "..."}` or `{"bootstrap_ticket": "..."}` |
| Success response | `204 No Content` with `Set-Cookie: __Host-aleph-v1=<uuid>; Secure; HttpOnly; SameSite=Strict; Path=/; Max-Age=300` and `Cache-Control: no-store` |
| Upgrade | `GET /v1/ws` with `Sec-WebSocket-Protocol` set to exactly `aleph.protocol.v1` and the session cookie |
| Session lifetime | 300 seconds (`TTL`) |
| Per-frame payload limit | 1 MiB (`MAX_MESSAGE`), excluding the 4-byte header |
| Sessions / concurrent sockets | 256 (`MAX_SESSIONS`) / 8 (`MAX_SOCKETS`) |
| Request-body read and WebSocket write timeout | 5 seconds (`IO_TIMEOUT`) |

Both routes first use `same_origin` to validate `Origin` against the HTTPS origin of the request target, then use `throttle` to rate-limit by client IP. Common failures include origin mismatch (403), rate limiting (429), invalid request body or subprotocol (400), invalid credentials or cookie (401), capacity or service unavailable (503), and a request-body read timeout (408) (`src/gateway/server/connection/web_v1.rs`).

After upgrade, each RPC message must be Binary and contain exactly one complete frame. A Text message, incomplete frame, trailing bytes, or invalid envelope closes the connection. The first RPC request must be `system.hello` and arrive within 5 seconds or before session expiry, whichever is sooner. After the handshake the server handles one request at a time. It closes the connection on session expiry, device credential invalidation (checked every second), or Gateway shutdown (`src/gateway/server/connection/web_v1.rs`).

When a static package directory is configured, the Gateway serves the TSX Panel web package at `/v1/panel/` on the native TLS router only. This keeps the page on the same origin as the cookie-authenticated `/v1/ws`. `panel_routes` adds `Content-Security-Policy: script-src 'self' 'wasm-unsafe-eval'; img-src 'self' blob: data:; connect-src 'self'` and `X-Content-Type-Options: nosniff` (`src/gateway/server/mod.rs`, `src/gateway/server/connection/web_v1.rs`).

### Legacy `/ws`

The legacy endpoint uses WebSocket Text message boundaries to delimit JSON-RPC messages. It logs and ignores Binary messages (`src/gateway/server/mod.rs`, `src/gateway/server/connection/mod.rs`). It retains the legacy RPC surface, including `panel.capabilities.snapshot` and `panel.project.select` (`src/gateway/handlers/mod.rs`). See [Legacy WebSocket Endpoint](./protocol) for the connection flow.

## Events and subscriptions

Topic events on legacy `/ws` are JSON-RPC notifications without an `id`. The `method` is `event` (`TOPIC_EVENT_METHOD`), and `params` contains the `topic` and `data` (`shared/protocol/src/jsonrpc.rs`, `src/gateway/server/connection/mod.rs`):

```json
{
  "jsonrpc": "2.0",
  "method": "event",
  "params": { "topic": "agent.run.complete", "data": {} }
}
```

- Example topics include `agent.run.complete`, `session.lifecycle.changed`, and `config.changed` (`src/gateway/events/frame.rs`).
- `events.subscribe` takes `topics`: each entry is a string pattern or a `{topic, where}` filter object (`src/gateway/handlers/events.rs`). Only legacy `/ws` mounts this method — the two v1 endpoints negotiate their event surface during the handshake and never subscribe.
- Subscriptions do not bypass visibility checks. Delivery remains subject to owner, session, and role restrictions (`src/gateway/event_visibility.rs`, `src/gateway/event_scope.rs`). See [Event Methods](./methods/events).

### The v1 event plane

Both v1 endpoints start delivering events only after the handshake granted `live_events`. A pushed frame still passes two gates: first the shared admission decision `admit_event` (identity, scope, ownership, projection), then the v1 topic allowlist `V1_EVENT_TOPICS` (`src/gateway/server/connection/event_admission.rs`, `src/gateway/server/connection/mod.rs`).

The allowlist holds six topics:

| Topic | Meaning |
|-------|---------|
| `stream.run_accepted` | A run was accepted |
| `stream.response_chunk` | A response chunk |
| `stream.run_complete` | The run finished normally |
| `stream.run_error` | The run failed |
| `stream.chat_tool` | Presentation-layer changes of a tool call |
| `connection.warning` | A connection-level warning (overflow, dropped frames) |

`stream.chat_tool` is only produced when both `live_events` and `chat_transcript` were granted, and it carries the same presentation projection that the `chat.transcript_details` method returns (`src/gateway/handlers/chat_presentation.rs`). See [chat methods](./methods/chat) for the method side.

A v1 connection subscribes to the event bus directly, so a dropped frame surfaces as `Lagged` on that connection instead of being swallowed by a buffer. When frames are lost the server first sends one `connection.warning` frame (`reason` is `events_overflow`) and then ends the connection, and the client has to resynchronize; a single frame that exceeds the limit only produces a warning and the connection keeps serving (`src/gateway/server/connection/forward.rs`, `src/gateway/server/connection/event_admission.rs`).

## Error model

Framing failures do not produce a JSON-RPC response. Desktop IPC validates the length with `decode_header` (the internal error is `invalid IPC frame length`) and then decodes UTF-8. Web v1 validates completeness and UTF-8 with `split_frame` and rejects trailing bytes. Both endpoints close the connection on failure (`shared/protocol/src/framing.rs`, `shared/client/src/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs`).

Rejections of valid RPC requests normally produce an `error` response with the original `id` and leave an established connection open. A failed handshake instead closes the connection after sending the error. Web v1 uses a separate `web-v1-unsupported:<ip>` rate-limit key for unmounted methods and closes the connection without a reply when the limit is exceeded (`src/gateway/server/connection/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs`).

| Case | Code (`shared/protocol/src/jsonrpc.rs`) | Message | Source |
|------|----------------------------------------|---------|--------|
| First valid request is not `system.hello` | `AUTH_REQUIRED` (-32000) | `system.hello must be first` | `src/gateway/server/connection/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs` |
| Method not mounted on Desktop IPC | `METHOD_NOT_FOUND` (-32601) | `method not mounted on Desktop IPC` | `src/gateway/server/connection/local_ipc.rs` |
| Method not mounted on Web v1, within the rate limit | `METHOD_NOT_FOUND` (-32601) | `method unavailable on Web v1` | `src/gateway/server/connection/web_v1.rs` |
| Desktop IPC post-handshake response exceeds limits | `INTERNAL_ERROR` (-32603) | `response exceeds Desktop IPC limits` | `src/gateway/server/connection/local_ipc.rs` |
| Web v1 response exceeds limits | Original error code (if supplied when producing the response) or `INTERNAL_ERROR` (-32603) | `response exceeds Web v1 limits` | `src/gateway/server/connection/web_v1.rs` |

See [JSON-RPC](../api/jsonrpc) for the complete list of error codes.

## Windows named-pipe Desktop IPC

**Code is in place, but the endpoint is not exposed.** The Windows client code validates explicit local endpoints such as `\\.\pipe\aleph` and implements account authentication. The Gateway side uses `PipeAccount` to bind the named pipe and authenticate the client’s account (`shared/client/src/local_ipc/windows.rs`, `src/gateway/server/connection/local_ipc/windows.rs`). However, `local_ipc::AVAILABLE` is still `cfg!(unix)`. Both the public client connection and the Gateway listener are gated on it, so the endpoint is not currently available on Windows (`shared/client/src/local_ipc.rs`, `shared/client/src/connection.rs`, `src/gateway/server/mod.rs`).

## Migration and compatibility

- **New clients:** Use opt-in Desktop IPC or Web v1 over native TLS, depending on the deployment. Send `system.hello` first, check the returned protocol version and limits, then call the mounted read-only methods. Desktop IPC’s `AlephClient::connect_local` neither falls back to a network transport nor uses device credentials (`src/gateway/server/connection/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs`, `src/gateway/server/mod.rs`, `shared/client/src/connection.rs`).
- **Existing clients:** Keep using `/ws` and `connect`. Optionally call `system.hello` afterward to probe the version; its reported limits are advisory. Clients that need event subscriptions or write operations should still use the legacy RPC endpoint (`src/gateway/server/connection/mod.rs`, `src/gateway/handlers/system_hello.rs`).

It is **not** declared as a `mod` in `desktop/nsh-shell/src/main.rs` and is not part of the current NSH binary. `desktop/nsh-shell/Cargo.toml` has no additional `[[bin]]` or `[lib]` targets. `desktop/nsh-shell/src/runtime.rs`, `desktop/nsh-shell/src/session.rs`, `desktop/nsh-shell/src/supervisor.rs`, and `desktop/nsh-shell/src/components/mod.rs` are also not wired into the binary. Do not treat these files as current connection behavior.
</Callout>

The historical `build_hello_params()` set `platform` to `std::env::consts::OS` and `ui_runtime` to `nsh`. That client rejected a server response with a major other than 1 (`desktop/nsh-shell/src/connection.rs`). See [Desktop Hosts](../desktop-hosts/overview) for current host connections.
