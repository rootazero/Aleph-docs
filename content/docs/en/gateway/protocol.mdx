<Callout type="warn">
`/ws` is a historical compatibility endpoint, not the way to attach a new client (the Desktop IPC / Web v1 entries of Protocol v1). The NSH desktop host has two shapes: the default Leptos `web_view` loads the Panel over `http://127.0.0.1:18790/` and connects to the legacy `/ws` (`desktop/nsh-shell/src/shell_host.rs`, `desktop/nsh-shell/src/credentials.rs`); the TSX Panel host, enabled with `ALEPH_SHELL_PANEL=tsx`, reaches only a local Desktop IPC and reports `unavailable` for any other target (`desktop/nsh-shell/src/panel_host.rs`). New clients should use [Protocol v1](./protocol-v1). This page describes the current state of `/ws` for maintaining older clients and for troubleshooting.
</Callout>

`/ws` carries JSON-RPC 2.0 in WebSocket Text messages: every RPC, event, and connection handshake shares one connection, and message boundaries come from WebSocket itself, with no length prefix. A Binary message is logged as a warning and ignored (`src/gateway/server/connection/mod.rs`).

## Endpoint

```text
ws://127.0.0.1:18790/ws          # default bind, loopback
wss://<host>:<port>/ws           # once native TLS is enabled
```

- The default bind is `127.0.0.1:18790` (`src/gateway/config.rs`); a loopback client is an implicit `operator`.
- The `/ws` route is mounted in `src/gateway/server/mod.rs`; the upgrade handler is `ws_upgrade_handler` in `src/gateway/server/connection/upgrade.rs`.
- A non-loopback bind must enable TLS, a trusted proxy, or `allow_insecure_remote`; otherwise `check_network_exposure` (`src/gateway/server/mod.rs`) makes the process refuse to start.

## Session init (`connect` handshake)

The **first frame** after the connection opens must be `connect`; any other first frame gets `AUTH_REQUIRED` (`First request must be 'connect'`) and the connection is closed (`src/gateway/server/connection/mod.rs`).

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "connect",
  "params": {}
}
```

A loopback connection may omit credentials. For remote connections, the credential resolution order is `resolve_connect_auth` in `src/gateway/handlers/connect.rs`; the accepted fields are `device_token`, `bootstrap_ticket` (together with `device_id`), and the legacy shared `token`. The differences between the three credentials, their lifetimes, and revocation are in [Authentication](./auth).

On success, `handle_connect` supplies the baseline fields and the connection layer overlays the authorization verdict:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "role": "operator",
    "state_version": 17,
    "keepalive": { "ping_interval_secs": 30, "idle_timeout_secs": 90 },
    "authorized": true,
    "needs_token": false
  }
}
```

The `state_version` and `keepalive` values are examples. On `/ws`, `system.hello` is only a version probe after `connect`: it neither admits the connection nor sets identity. See [Protocol v1](./protocol-v1#handshake-systemhello).

## Upgrade gates: TLS, origin, and connection caps

Before the HTTP request is upgraded to WebSocket, `ws_upgrade_handler` checks, in order:

| Check | Failure response | Code |
|-------|------------------|------|
| Non-loopback and connection not encrypted (`refuse_insecure_remote`) | `426`, `TLS required for remote connections` | `src/gateway/server/connection/upgrade.rs` |
| Origin policy (cross-origin and DNS rebinding) | `403`, `origin not allowed` | `src/gateway/origin_policy.rs` |
| Global connection count reached `max_connections` | `503`, `Connection limit reached` | `src/gateway/server/connection/upgrade.rs` |
| Per-IP connection count reached `max_connections_per_ip` | `503`, `Per-IP connection limit reached` | `src/gateway/server/connection/upgrade.rs` |

- `max_connections` defaults to 100 and `max_connections_per_ip` to 64, both in `src/gateway/config.rs`; loopback is exempt from the per-IP cap, and `0` disables it.
- Behind a trusted proxy, the real client address and whether the leg is encrypted are resolved by `resolve_client` in `src/gateway/trusted_proxy.rs`. `trusted_ips` accepts single IPs only, not CIDR ranges (entries that fail to parse are dropped with a warning). Forwarded headers are honored only when the peer is in `trusted_ips`.
- A connection that passes the gates is classified by origin: local is Desktop, anything else is Bot.

The three TLS setups (self-signed, trusted proxy, bring-your-own certificate) and auditing are covered in [Authentication](./auth) and not repeated here.

## Login wall and flood guard

An unauthorized remote connection may only call `connect`:

- Any other method gets `AUTH_REQUIRED` immediately; the predicate is `wall_admits` in `src/gateway/server/connection/auth.rs`.
- `src/gateway/server/flood_guard.rs` counts login-wall rejections per connection and closes the connection after `MAX_UNAUTHORIZED_STRIKES` (10), so a stale client cannot retry forever.
- Requests are also throttled per IP and per method scope by `src/gateway/rate_limiter.rs`.

## Message types

Message shapes match [JSON-RPC](../api/jsonrpc); `/ws` adds no extra envelope.

```json
{ "jsonrpc": "2.0", "id": "req-1", "method": "health" }
```

```json
{ "jsonrpc": "2.0", "id": "req-1", "result": { "status": "healthy", "timestamp": "2026-11-24T00:00:00Z" } }
```

```json
{ "jsonrpc": "2.0", "method": "event", "params": { "topic": "session.lifecycle.changed", "data": {} } }
```

- The `timestamp` in the response is an example value; the fields are defined in `src/gateway/handlers/health.rs`.
- An event is a notification without an `id`, with `method` always `"event"`. Subscribe with `events.subscribe`, whose parameter key is `topics` (`src/gateway/handlers/events.rs`). For the event catalog and the full error-code list, see [Event methods](./methods/events) and [JSON-RPC](../api/jsonrpc).
- The full RPC catalog is in the [Method reference](./methods). Only `/ws` offers the full method surface; the two v1 entries (Desktop IPC and Web v1) share `V1_METHODS` (`src/gateway/server/connection/mod.rs`) and enforce the [Protocol v1 method list](./protocol-v1).

## History: from an unversioned protocol to v1

| Form | Characteristics | Code |
|------|-----------------|------|
| `/ws` + `connect` | The handshake result carries only session fields such as `role`, `state_version`, and `keepalive`: no protocol version and no limit negotiation. Message boundaries rely on WebSocket | `src/gateway/handlers/connect.rs` |
| `system.hello` probe on `/ws` | A version probe after `connect`; the handler comment calls it a legacy probe, and the `limits` in the response are hints, not enforced | `src/gateway/handlers/system_hello.rs` |
| Protocol v1: Desktop IPC and Web v1 | Bounded length-prefixed frames, `system.hello` must be the first frame, limits are enforced by the transport; the two entries share `V1_METHODS` and enforce the [Protocol v1 method list](./protocol-v1) | `src/gateway/server/connection/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs` |

`/ws` keeps the full RPC surface and `connect` authentication, so older clients need no changes; it has not been removed, but it is no longer where new capabilities land. The Desktop IPC and Web v1 entries of Protocol v1 have landed; see [Protocol v1](./protocol-v1) for the frame format, handshake, and transport matrix. The parts of v1 that are not implemented yet (event replay, snapshots, a binary channel, backpressure policy) are listed in [the planned section of Protocol v1](./protocol-v1#planned-not-yet-implemented).
