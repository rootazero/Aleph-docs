This page explains how local and remote clients obtain Gateway permissions, and how transport encryption differs from authentication.

## Authentication by Entry Point

| Entry point | Identity check | Implementation |
|-------------|----------------|----------------|
| Desktop IPC | Verifies the Unix socket peer; read-only and does not inherit the compatibility WS loopback grant | `src/gateway/server/connection/local_ipc.rs` |
| Web v1 | Native TLS; `POST /v1/session` creates a session from a valid device token or principal-bound bootstrap ticket, and `GET /v1/ws` requires a valid session cookie, matching origin, and current device principal | `src/gateway/server/mod.rs`, `src/gateway/server/connection/web_v1.rs` |
| Compatibility `/ws` | The upgrade checks transport and `Origin` separately, then `connect` authenticates the connection. Remote callers with missing or invalid credentials cannot use authenticated RPCs. | `src/gateway/server/connection/upgrade.rs`, `src/gateway/handlers/connect.rs`, `src/gateway/server/connection/mod.rs` |

The two read-only entry points negotiate with `system.hello`, not with the compatibility `/ws` `connect` flow. See [IPC protocol](../security/ipc) for their RPC scope and cross-site protections (`src/gateway/server/connection/local_ipc.rs`, `src/gateway/server/connection/web_v1.rs`).

## Compatibility `/ws` Credentials

`resolve_connect_auth` grants implicit `operator` access only on direct loopback connections that do not present a nonempty `device_token` or `bootstrap_ticket`. A loopback connection that presents a device credential which fails verification does not fall back to the implicit grant. Remote credentials are tried in the order below. A device credential can also resolve a role from the user record; it does not always yield `operator` (`src/gateway/handlers/connect.rs`).

| Order | `connect` parameter | Purpose and storage | Implementation |
|-------|---------------------|---------------------|----------------|
| 1 | `device_token` (`aleph-dt-*`) | Long-lived device credential; the server stores a SHA-256 hash | `src/gateway/security/device_token_manager.rs`, `src/gateway/security/store/tokens.rs` |
| 2 | `bootstrap_ticket` (`aleph-bt-*`) | Single-use pairing credential, valid for 5 minutes by default; exchange returns a new device token | `src/gateway/security/device_token_manager.rs`, `src/gateway/handlers/connect.rs` |
| 3 | `token` (`aleph-<uuid>`) | Legacy shared Gateway token, used only as a remote fallback | `src/gateway/handlers/connect.rs`, `src/gateway/security/shared_token.rs` |

### Pairing and Revocation

An authorized client can issue a bootstrap ticket with `gateway.ticket.create`. A compatibility connection exchanges it via `connect.bootstrap_ticket` and reconnects with the returned `device_token`. The exchange rejects a `device_id` that conflicts with a non-Panel device. The NSH credential service stores device credentials in the OS keyring, with no plaintext file fallback (`src/gateway/handlers/gateway_ticket.rs`, `src/gateway/handlers/connect.rs`, `src/gateway/security/device_token_manager.rs`, `desktop/nsh-shell/src/credentials.rs`, `shared/client/src/credential_store.rs`).

`gateway.devices.revoke` revokes a specific device. `gateway.token.rotate` rotates the shared token and revokes paired Panel devices. Web v1 session validation also rechecks that the device principal is still active (`src/gateway/handlers/gateway_devices.rs`, `src/gateway/handlers/gateway_token.rs`, `src/gateway/server/connection/web_v1.rs`).

### Headless Credential Tools

`aleph-server pair [--ttl SECONDS]` can issue a bootstrap ticket without a running Gateway. Add `--user <id>` when issuing a principal-bound ticket for Web v1. `aleph-server bootstrap-token` prints the legacy shared token in plaintext to standard output; keep that output out of shared logs (`src/bin/aleph-server/cli.rs`, `src/bin/aleph-server/commands/pair.rs`, `src/bin/aleph-server/commands/bootstrap_token.rs`).

## Local and Remote Transport, and TLS

The Gateway's `check_network_exposure` rejects a non-loopback bind without native TLS, a trusted proxy, or explicit permission for plaintext. The compatibility `/ws` upgrade applies `refuse_insecure_remote` per connection: when there is neither native TLS nor a trusted proxy's `X-Forwarded-Proto: https`, and `allow_insecure_remote` is unset, remote upgrades receive `426 Upgrade Required`. Direct loopback can use plaintext, but NSH requires HTTPS for a remote `--connect <origin>`. The `aleph://open` deep link opens the host window; it is not a connection target (`src/gateway/server/mod.rs`, `src/gateway/server/connection/upgrade.rs`, `desktop/nsh-shell/src/main.rs`, `shared/client/src/connection_target.rs`, `desktop/nsh-shell/src/panel_bridge.rs`).

### Native TLS

Set `enabled = true` under `[gateway.tls]`. Provide PEM files in `cert_path` and `key_path`, or leave them empty to generate a self-signed certificate. Clients still need to trust the certificate presented, and TLS alone grants no Gateway permissions. Web v1 is registered only on the native TLS router; neither the compatibility plaintext switch nor proxy-only TLS termination enables it (`src/gateway/config.rs`, `src/gateway/tls.rs`, `src/gateway/server/mod.rs`).

### Trusted Reverse Proxies and Client IPs

If a proxy terminates TLS for compatibility `/ws`, enable `[gateway.trusted_proxy]` with `enabled = true` and put the proxy's actual IP in `trusted_ips` (individual addresses only, no CIDR). Otherwise, a same-host proxy's loopback socket may be mistaken for a direct local connection and receive the implicit grant (`src/gateway/config.rs`, `src/gateway/trusted_proxy.rs`, `src/gateway/server/connection/upgrade.rs`).

`resolve_client` accepts forwarding headers only from a trusted peer. It parses the rightmost nonempty `X-Forwarded-For` entry and falls back to the peer IP if the entry is missing or invalid. That IP is used for rate limits and audit. Connections through a trusted proxy are always marked non-local, even if the fallback IP is loopback (`src/gateway/trusted_proxy.rs`, `src/gateway/server/connection/upgrade.rs`, `src/gateway/server/connection/mod.rs`).

## Browser Origins and Audit

Compatibility `/ws` uses `OriginPolicy::is_allowed`: absent or blank `Origin` passes the origin check; browsers normally need an exact `[gateway] allowed_origins` match or an HTTP(S) IP or loopback origin whose authority matches the request `Host`. The legacy desktop webview's dedicated scheme is still an exception, not an NSH rule. Web v1 uses strict HTTPS same-origin checks instead. Neither check replaces authentication. See [IPC protocol](../security/ipc) for the full rules (`src/gateway/origin_policy.rs`, `src/gateway/server/connection/upgrade.rs`, `src/gateway/server/connection/web_v1.rs`).

Compatibility `/ws` can log remote credential failures (`AuthFailure`) and unauthorized request floods (`RateLimited`). Web v1's `throttle` applies auth rate limits to both session exchange and upgrade (`src/gateway/server/connection/mod.rs`, `src/gateway/server/flood_guard.rs`, `src/security/audit.rs`, `src/gateway/server/connection/web_v1.rs`).
