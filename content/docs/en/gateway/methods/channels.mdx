title: "channels.*"
description: "Communication channel management RPC methods"

Channel RPCs manage both runtime instances in `ChannelRegistry` and channel declarations in `Config`. `register_channel_handlers` registers the core channel and Discord Control-Plane methods (`src/bin/aleph-server/commands/start/builder/handlers/session.rs`). The pairing methods are registered separately and share a pairing store with inbound routing (`src/bin/aleph-server/commands/start/mod.rs`). The binding methods are registered in `src/bin/aleph-server/commands/start/builder/handlers/settings.rs`.

In `channels.list`, a channel with configuration but no runtime instance has one of two statuses: `disabled` for an explicitly disabled cold declaration, or `pending_config` for any other uninstantiated declaration (`src/gateway/handlers/channel.rs`).

## Cold declarations

### Detection and Gateway boot

Only the JSON boolean `"enabled": false` (TOML `enabled = false`) in a channel's configuration makes it a cold declaration. `ChannelInstanceConfig::is_explicitly_disabled` does not treat `true`, non-boolean values, or an absent field as cold. Omitting `enabled` preserves the adapter's existing default. `ChannelInstanceConfig::declared_type` uses the string `type` if present; otherwise, it uses the channel ID if it appears in `CONFIGURABLE_CHANNEL_TYPES`. If neither yields a type, `Config::resolved_channels` logs a warning and skips the declaration (`src/config/structs.rs`, `shared/protocol/src/channels.rs`).

At Gateway boot, `initialize_channels` leaves cold declarations in `Config` without hydrating vault credentials or constructing adapters, including in the iMessage/BlueBubbles branch. The inbound message coalescer also skips explicitly disabled entries when looking for Telegram `coalescing` settings, and uses the defaults if it finds none (`src/bin/aleph-server/commands/start/builder/subsystems.rs`).

For cold declarations whose type can be resolved, startup calls `project_cold_declaration` to populate `ChannelPolicyProjection` without credentials. Inbound routing and system continuations read the same projection. If another malformed field prevents policy parsing, the projection logs `Cold channel requires policy repair before activation`. The fallback still preserves any parseable `tool_permissions` layer so valid denies are not lost (`src/bin/aleph-server/commands/start/builder/subsystems.rs`, `src/gateway/channel_policy.rs`).

### Creation and credential persistence

`channel.create` does not construct an adapter, register a runtime instance, or start the channel when creating a cold declaration. `extract_cold_channel_secrets` removes supplied credentials that are supported, nonempty top-level strings and stages them outside the config. The cold path rejects nonempty `verification_token`, `encrypt_key`, `channel_access_token`, `channel_secret`, and `token` fields. It also rejects nonempty mapped credentials that are nested or have non-string values. Here, nonempty excludes `null` and the empty string. Unsupported credentials return `INVALID_PARAMS`; there is no plaintext fallback (`src/gateway/handlers/channel.rs`).

1. Add the declaration without the submitted credentials to `Config` and call `save_incremental` for `channels`. If that write fails, remove the entry from `Config` and return `INTERNAL_ERROR` with `Failed to persist channel configuration` (`src/gateway/handlers/channel.rs`).
2. Only after the config is saved, use `store_secret_batch` to write the staged credentials to the vault together. If the vault write fails, remove the declaration and save again to roll it back. If the rollback also fails, restore the declaration in `Config`; it remains cold and contains none of the newly submitted credentials. A vault write failure returns `INTERNAL_ERROR` with `Failed to store channel credentials` and never falls back to plaintext (`src/gateway/handlers/channel.rs`, `src/gateway/security/shared_token.rs`).
3. On success, return `id`, `type`, and `status: "disabled"` (`src/gateway/handlers/channel.rs`).

### Explicit activation

Only an explicit `channel.start` activates a cold declaration. When the ID is absent from the registry, `handle_start` takes the config-only path (`src/gateway/handlers/channel.rs`):

1. Read one snapshot of the current shared `Config` for both transport configuration and policy. No vault read or factory call runs under the config lock. An ID missing from config returns `INTERNAL_ERROR` with `Channel <id> not found in config`. If the type cannot be resolved, the handler returns `INVALID_PARAMS` with `Missing channel type` (`src/gateway/handlers/channel.rs`).
2. Release the config lock, inject vault credentials into a runtime copy, then parse the activation policy with `parse_channel_activation_policy`. If parsing fails, return `INVALID_PARAMS` with the policy error without constructing an adapter (`src/gateway/handlers/channel.rs`, `src/gateway/channel_policy.rs`).
3. After constructing the adapter, check that its instance ID matches the requested ID. A mismatch returns `INTERNAL_ERROR` with `Channel factory returned a different instance ID` (`src/gateway/handlers/channel.rs`).
4. `ChannelRegistry::register_and_start_vacant` checks under the registry lock that the ID is vacant. If the ID is occupied, it returns `ChannelError::Busy`, which the RPC reports as a start failure. Otherwise, the handler calls `set_activation` in the `before_publish` callback to publish the policy before inserting the entry and starting the adapter (`src/gateway/channel_registry.rs`, `src/gateway/handlers/channel.rs`).

**Explicit activation does not set `enabled` to `true` on disk.** If the config remains explicitly disabled, the Gateway treats it as cold on its next boot (`src/gateway/handlers/channel.rs`, `src/bin/aleph-server/commands/start/builder/subsystems.rs`).

### Boundaries

A cold declaration is not a channel hot-reload mechanism and does not add a Zahir Gateway mount point. `channel.stop` works only on a registered instance; it does not guarantee that every resource is reclaimed or that native code is unloaded (`src/bin/aleph-server/commands/start/builder/subsystems.rs`, `src/gateway/handlers/channel.rs`, `src/gateway/channel_registry.rs`).

## Methods

### channels.list

Takes no parameters. The list combines the registry and config: if an ID exists in both, the registry status wins and the ID counts once. `configured_channel_info` builds config-only entries: `disabled` for cold declarations and `pending_config` for other uninstantiated declarations. Both return `CapabilitiesResponse::default()` and advertise no runtime capabilities. `summary` counts registered instances and config-only cold declarations. `pending_config` entries appear in the list but do not count toward `total` (`src/gateway/handlers/channel.rs`, `src/gateway/channel_registry.rs`).

**Response:** `channels`, `summary`, and `delivery_queue`. `summary` contains `total`, `connected`, `connecting`, `pairing`, `disconnected`, `error`, and `disabled`. `delivery_queue` reports the durable outbound backlog, or is `null` if no durable queue is attached. Each `ChannelInfoResponse` contains `id`, `name`, `channel_type`, `status`, and `capabilities` (`attachments`, `images`, `audio`, `video`, `reactions`, `replies`, `editing`, `deletion`, `typing_indicator`, `read_receipts`, `rich_text`, `max_message_length`, `max_attachment_size`) (`src/gateway/handlers/channel.rs`).

### channels.status

Read a single channel. If an instance is registered, return its live `ChannelStatus`. With no instance, return the `disabled` entry if `Config` contains a cold declaration for the ID. Otherwise, including for a `pending_config` entry, return `INVALID_PARAMS` with `Channel not found: <id>` (`src/gateway/handlers/channel.rs`, `src/gateway/channel_registry.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `channel_id` | string | yes | Channel ID |

**Response:** the channel's `ChannelInfoResponse` (`src/gateway/handlers/channel.rs`).

### channel.start

Start a channel. The handler reads the current shared `Config`; it does not reload the file from disk. When rebuilding a Telegram adapter, it reattaches the cached `ToolCatalog` if available so the adapter can register slash commands. A config-only channel follows the explicit activation flow above (`src/gateway/handlers/channel.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `channel_id` | string | yes | Channel ID |

**Response:** `{ "channel_id", "status": "started" }` (`src/gateway/handlers/channel.rs`).

### channel.stop

Stop a registered channel instance. A cold declaration with no instance cannot be stopped (`src/gateway/handlers/channel.rs`, `src/gateway/channel_registry.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `channel_id` | string | yes | Channel ID |

**Response:** `{ "channel_id", "status": "stopped" }` (`src/gateway/handlers/channel.rs`).

### channel.create

Create and persist a channel declaration. Explicitly disabled declarations follow the cold creation flow above. Otherwise, the handler attempts to construct an adapter and, if successful, registers and starts it automatically. If it cannot construct the adapter, for example because a required credential is missing, the declaration is still saved and the RPC returns `pending_config`. Supply the missing configuration and start it later (`src/gateway/handlers/channel.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `id` | string | yes | Unique channel ID |
| `type` | string | yes | For example, `telegram`, `discord`, `slack`, or `imessage` (including BlueBubbles) |
| `config` | object | no | Type-specific configuration; defaults to an empty object. See the credential table below. |

**Response:** `id`, `type`, and `status`. The status is `disabled`, `started`, `created_but_start_failed`, or `pending_config`. A `created_but_start_failed` response additionally includes `error` (`src/gateway/handlers/channel.rs`).

### channel.delete

Delete a declaration without activating it first. If an instance is registered, the handler tries to stop and unregister it. It then removes the ID from the shared `Config` and tries to save `channels`; it does not remove vault entries. A save failure is logged but still returns `deleted`. If the ID exists in neither the registry nor the config, the handler returns `INVALID_PARAMS` (`src/gateway/handlers/channel.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `id` | string | yes | Channel ID |

**Response:** `{ "id", "status": "deleted" }` (`src/gateway/handlers/channel.rs`).

### channel.send

Send a message through a registered channel instance. A cold declaration cannot send on its own (`src/gateway/handlers/channel.rs`, `src/gateway/channel_registry.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `channel_id` | string | yes | Channel ID |
| `to` | string | yes | Channel-specific conversation target, such as a chat ID, channel ID, or user ID |
| `text` | string | yes | Nonempty message body |

**Response:** `{ "channel_id", "message_id", "timestamp", "sent": true }` (`src/gateway/handlers/channel.rs`).

### channel.pairing_data

Read pairing data from a registered channel. The channel can supply a QR code or pairing code, or report that no pairing data is available (`src/gateway/handlers/channel.rs`, `crates/aleph-slot-api/src/channel.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `channel_id` | string | yes | Channel ID |

**Response:** the pairing payload supplied by the channel (`src/gateway/handlers/channel.rs`).

### channel_outbox: dead_letters

This is the `channel_outbox` **builtin tool, not a Gateway RPC method**. Use `action: "dead_letters"` to inspect outbound messages retired after exhausting retries or for other safety reasons (`src/builtin_tools/channel_outbox.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `action` | string | yes | `dead_letters` |
| `channel_id` | string | no | Restrict to a channel; omit to include all channels |
| `limit` | number | no | Defaults to 10, capped at 25 |

**Output:** `message`, `durable_queue`, and `dead_letters`. Entries contain `channel_id`, `conversation_id`, `preview` (at most 200 characters), `attempts`, `last_error`, `reason`, `redrivable`, and `age_secs`. Without a durable queue, `durable_queue` is `false` (`src/builtin_tools/channel_outbox.rs`).

### channel_outbox: redrive

A recovery action of the same **builtin tool, not a Gateway RPC method**. Use `action: "redrive"` to move safely replayable dead letters back into the outbound queue. Not every dead letter can be replayed (`src/builtin_tools/channel_outbox.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `action` | string | yes | `redrive` |
| `channel_id` | string | no | Restrict to a channel |
| `confirm_redrive` | boolean | no | Only `true` performs the redrive; omit to preview |

**Output:** `message`, `durable_queue`, and fields such as `redriven`, `skipped_queue_full`, and `skipped_not_replay_safe` where applicable. Inspect the preview and confirm the target before replaying (`src/builtin_tools/channel_outbox.rs`).

### channels.set_agent

Bind or unbind an agent to a channel. This method shares binding logic with `agent_switch`, including agent validation, detection of duplicate binds, and `Bound`/`Unbound` events. If an `AgentRegistry` is available, an unknown agent returns `INVALID_PARAMS`; `agent_registry: None` skips that check (`src/gateway/handlers/workspace.rs`, `src/gateway/agent_binding.rs`, `src/builtin_tools/agent_manage/switch.rs`).

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `channel_id` | string | yes | Channel ID |
| `agent_id` | string | no | Agent ID; `null` or absent to unbind |

**Response:** Binding returns `ok`, `previous_agent` (`null` if unbound before), and `no_op` (`true` for a duplicate bind). Unbinding returns only `ok` and `previous_agent` (`src/gateway/handlers/workspace.rs`).

### agents.bindings

Takes no parameters. Returns a `bindings` object mapping each agent ID to all the channel IDs bound to it, sorted by channel ID (`src/gateway/handlers/workspace.rs`, `src/gateway/agent_env/manager_ops.rs`).

## Channel pairing

The Panel uses these RPCs for manual pairing. They use the same pairing store as inbound routing and track requests by channel (`src/bin/aleph-server/commands/start/mod.rs`, `src/gateway/handlers/pairing.rs`).

| Method | Parameters | Description |
|--------|------------|-------------|
| `channel.pairing.list` | `channel?` | Returns `requests` and `count`, optionally filtered by `channel`. Each request includes `channel`, `sender_id`, `code`, and `created_at`. |
| `channel.pairing.approve` | `channel` and `code` (required), `user_id` (optional) | Returns `approved: true`, `request`, and `user_id`. |
| `channel.pairing.reject` | `channel` and `code` (required) | Returns `rejected: true`, `channel`, and `code`. |
| `channel.pairing.approved` | `channel` (required) | Returns `channel`, `approved` (sender IDs), and `count`. |
| `channel.pairing.revoke` | `channel` and `sender_id` (required) | Returns `revoked: true`, `channel`, and `sender_id`. |

## Discord Control-Plane panel

The following four methods are registered together. Token validation does not depend on a channel instance. The other three require the target channel to be registered and connected and read the token from `DISCORD_BOT_TOKEN` (`src/bin/aleph-server/commands/start/builder/handlers/session.rs`, `src/gateway/handlers/discord_panel.rs`).

| Method | Description |
|--------|-------------|
| `discord.validate_token` | Validate a Discord bot token without persisting it |
| `discord.list_guilds` | List the servers the bot has joined |
| `discord.list_channels` | List channels in the specified server |
| `discord.audit_permissions` | Audit the bot's permissions in the specified server |

## Channel type → secret field map

This table shows typical uses of the fields in `CHANNEL_SECRET_FIELDS`. The vault key is `channel:<id>:<field>`. Cold creation accepts only supported top-level credentials and commits them to the vault after saving the declaration. Unsupported nested credentials are an error. Non-cold creation still uses the existing migration path, which may leave plaintext in the config if the vault write fails (`src/gateway/handlers/channel.rs`).

| Channel family | Secret fields |
|----------------|---------------|
| `telegram` | `bot_token` |
| `discord` | `bot_token` |
| `slack` | `bot_token`, `app_token` |
| `feishu` | `app_secret` |
| `matrix` | `access_token` |
| `xmpp` / `irc` / `email` | `password` |
| `nostr` | `private_key` |
| `webhook` | `secret` |
| `whatsapp` | `session_data` |
| `qq` | `client_secret` |

`has_<field>: true` is a vault credential presence flag in `config.get`, not in `channels.list`. Reading the config does not expose these credentials in plaintext. Saving an empty string in a mapped field does not replace an existing vault value (`src/gateway/handlers/channel.rs`, `src/gateway/handlers/config.rs`).

## History: Earlier health RPC and Teams credential docs

This page previously listed `channel.health` with an optional `channel_id`. It described a single-channel response with `id`, `channel_type`, `status`, `health_status` (`healthy`, `stale`, or `degraded`), `last_event_at`, `failure_count`, and an optional `status_reason`. For all channels, it described `channels` and `summary` (`total`, `healthy`, `stale`, `degraded`). This is not a current RPC contract: the method is not registered. The Gateway's internal health monitor uses registry health snapshots (`src/gateway/method_census.rs`, `src/gateway/channel_health_monitor.rs`, `src/gateway/channel_registry.rs`).

The earlier table listed `app_password` for Teams (`msteams`). The field was removed from `CHANNEL_SECRET_FIELDS` in the Teams cleanup (code commit `fd7fba58d`, `src/gateway/handlers/channel.rs`).
