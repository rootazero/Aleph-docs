This page is the gateway's topic catalogue: for every topic, its canonical name, its wire method name, its payload fields, how subscriptions match it, and who may see it. For the wire shape and the overall delivery chain see [Gateway architecture](../../architecture/gateway); for protocol details see [Protocol v1](../../gateway/protocol-v1).

## How Events Reach Clients

The server wraps internal events into JSON-RPC notifications. A client first subscribes to the topics it cares about, then dispatches each notification by the topic it carries. Notifications exist in two wire shapes.

### The Notification Shape

Frames with a `stream_method()` are emitted under their method name, with the frame body as `params`:

```json
{
  "jsonrpc": "2.0",
  "method": "stream.run_complete",
  "params": {
    "run_id": "run-...",
    "seq": 12,
    "summary": { "...": "..." },
    "total_duration_ms": 4820
  }
}
```

### The Event Shape

Frames without a `stream_method()` are emitted first as a bare event `{"topic": "...", "data": {...}}`, and the delivery layer wraps that into a notification whose method is `event`. `event` is `TOPIC_EVENT_METHOD` (`shared/protocol/src/jsonrpc.rs:85`), and the wrapping happens at `src/gateway/server/connection/forward.rs:228`:

```json
{
  "jsonrpc": "2.0",
  "method": "event",
  "params": {
    "topic": "config.changed",
    "data": { "section": "execution", "value": { "...": "..." } }
  }
}
```

The two shapes differ in exactly one place: the wire method name. The canonical topic name (`agent.run.complete`) and the wire method name (`stream.run_complete`) are two separate namespaces; the canonical name mostly shows up in the `source_topic` diagnostic field, while subscriptions on the wire use the latter.

## Subscribing and Matching

The three methods `events.subscribe`, `events.unsubscribe`, and `events.list` are not in the method registry; they are intercepted separately in the connection loop (`src/gateway/server/connection/mod.rs:630`), with the handlers in `src/gateway/handlers/events.rs`.

The shape of a subscribe request:

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "events.subscribe",
  "params": {
    "topics": ["stream.*", { "topic": "team.changed", "where": [{ "field": "team_id", "equals": "team-1" }] }]
  }
}
```

An empty `topics` array is answered with `INVALID_PARAMS` / `Topics array cannot be empty`. Subscription state is held by `SubscriptionManager` (`src/gateway/handlers/events.rs:17`), one filter per connection.

Matching works on the wire topic string of the event: the `topic` field for the bare event shape, and the `method` field for the notification shape (`extract_topic_and_data` at `src/gateway/server/connection/forward.rs:187`). Stream frames are therefore matched by their `stream.` prefix.

### Wildcard Patterns

Matching lives in `topic_matches` at `src/gateway/event_bus.rs:150`:

| Pattern | Semantics |
|---------|-----------|
| `*` or `**` | Matches every topic |
| Last segment is `*` or `**` | Matches any remaining depth, so `stream.*` matches `stream.run_complete` and also `voice.transcribe.delta` |
| A `*` in the middle | Eats a single segment, so `*.complete` does not match `stream.run_complete` |

Both sides have to be exhausted for a match.

### where Predicates

An element of `topics` may also be an object carrying a `where` array. A predicate is described by `FieldPredicate` (`{"field": "...", "equals": ...}`), and the field path is resolved by `.` segments, not by JSON Pointer. A non-empty predicate whose field is missing from the payload counts as no match.

### Exceptions and Unsubscribing

`except` is a sibling key of `topics` and lists the top-level topics to carve out of the subscription. `events.unsubscribe` removes the given patterns, and `events.list` returns a snapshot of the connection's subscriptions (`subscribed` is the list of patterns, `entries` the full entries).

## Visibility and Authorization

For a frame to reach a connection it has to pass the filter chain at `src/gateway/server/connection/mod.rs:1373` layer by layer. Two of those layers are topic-related, and they have different jobs.

### Scope Rules

`src/gateway/event_scope.rs` holds coarse prefix rules. `default_rules` registers only a few prefixes — pairing, guest, configuration change, node, and PTY — and a matched prefix requires the caller to hold an administrator scope; a topic that matches no rule is admitted by default. `scope_for_role` returns a wildcard scope for operator and an empty one for every other role.

Topics under the `config.changed`, `node.`, and `pty.` prefixes therefore reach operators only.

### Per-Frame Ownership Ruling

`src/gateway/event_visibility.rs` answers "who owns this frame". `classify` (`:440`) maps the topic and the payload onto one identity:

| Identity | Topics covered | Ruling |
|----------|----------------|--------|
| By session | `stream.ask_user`, `stream.clarification_ended`, `stream.run_accepted`, `stream.run_queued`, `stream.session_updated`, `stream.session_user_message`, `session.lifecycle.changed`, `sessions.changed` | Visible to the session's owner |
| By run | `stream.reasoning`, `stream.tool_start`, `stream.tool_update`, `stream.tool_end`, `stream.agent_trace`, `stream.response_chunk`, `stream.context_gauge`, `stream.run_complete`, `stream.run_error`, `stream.uncertainty_signal`, `stream.model_resolved`, `stream.run_retrying` | The `run_id` is resolved to a session first, then the session's ownership decides |
| By session or administrator | `approval.requested`, `approval.reminder`, `approval.resolved`, `approval.expired`, `surface.approval` | Operators pass through; everyone else goes by session ownership |
| By user | `voice.transcribe.delta` | The caller's id equals `owner_user_id` |
| By PTY session | `pty.screen`, `pty.exit` | Decided by PTY session ownership |
| By canvas | `canvas.updated` | Decided by the canvas visibility predicate |
| By project | `projects.changed` | Decided by the project roster, with no administrator exemption |
| Operator only | `workspace.changed`, `config.embedding.providers.changed`, `config.generation.providers.changed`, and the `host.` prefix | The caller's role must be operator |
| Global | `channel.message`, `channel.typing`, `channel.status`, `channel.error`, `acp.sessions.changed`, `gateway.token.rotated`, `gateway.device.revoked`, `cron.job.changed`, `heartbeat.task.changed`, `team.changed`, `surface.notify`, `pairing.requested`, `pairing.completed`, `config.changed`, `system.tick`, `presence.joined`, `presence.left`, `tools.changed`, `config.reloaded`, `config.error`, `extension.reloaded`, `memory.reembed.progress`, `memory.reembed.completed`, `runtimes.install.progress`, `agent.lifecycle.registered`, `agent.lifecycle.deleted`, `agent.lifecycle.bound`, `agent.lifecycle.unbound` | Admitted to every logged-in connection |
| Capability audience | `capability.event`, `capabilities.ui.display`, `capability.event.status` | Decided by the capability audience |

Two additions:

- `config.changed` matches the configuration prefix in the scope rules and is also Global in the per-frame ruling. The prefix rule runs first, so in practice only operators receive it.
- Among the team topics, the ones carrying a team id are ruled by team ownership; only the id-less `team.changed` is Global.

### The Projected Frame

`stream.running_set_changed` is the only projected frame on the chain: it is ruled Global (nobody owns the frame), but its `running` array is narrowed per connection, so each connection sees only the running set that concerns it.

## Replay and Snapshots

There is no event replay and no snapshot subscription in the current implementation.

- `shared/protocol/src/trace_replay.rs` defines query DTOs for persisted traces (`AgentTraceReplay`, `AgentTraceReplayEntry`, `AgentTraceListRow`, and others); they read trace records that are already on disk and are not a replay of the event stream.
- `shared/protocol/src/resume.rs` defines receipts for resumed tasks (`ResumeReceipt`, `ResumeStatus`, and its constants), which are unrelated to event replay.
- The subscription semantics themselves do not support replay: `events.subscribe` records patterns, not a cursor.

> **Status: planned** — the blueprint is `docs/research/NSH_PROTOCOL_V1.md` (chapter 9, Snapshot + Replay, including 9.3 on lossless subscription, 9.4 on unavailable history, and 9.5 on the deduplication cursor); the current implementation is in `shared/protocol/src/trace_replay.rs`, `shared/protocol/src/resume.rs`, and `src/gateway/handlers/events.rs`. `session.get_snapshot` is not registered in `src/gateway/method_census.rs`, so the snapshot interface does not exist yet.

## History: How Event Names Converged

Earlier documents used flat event names, such as agent.completed, agent.started, agent.error, and stream.chunk. None of those strings exist in the current code; they only appear in historical documents and early plans.

After converging on the current namespaces, `agent.run.complete` means one run finished while `session.user.message` means one user message arrived, and the two no longer share a flat name. `stream.chunk` became `agent.response.chunk`, which puts it in the same family as `agent.reasoning` and `agent.trace`.

Another convergence separated the canonical name from the wire method name: the canonical topic name says what the event is, and the wire method name says how it is delivered. While the two namespaces coexisted, `agent.run.complete` mostly appeared as the `source_topic` diagnostic field, and subscriptions on the wire kept using `stream.*`.
