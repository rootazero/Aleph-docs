This page records the core design patterns used across the Aleph Rust codebase. These are not abstract suggestions — they are patterns in active use, with concrete examples extracted from production code. Following them keeps the codebase consistent and makes it easier for new contributors to slot in.

For guidance on file and module structure, see the [Module Organization](#module-organization) section at the bottom of this page.

## Context Pattern

### Problem

As an API evolves, function signatures accumulate parameters. A function with nine parameters is hard to read, hard to extend, and easy to misuse:

```rust
// before: 9 positional parameters
pub async fn handle(
    &self,
    message: InboundMessage,
    channel_id: ChannelId,
    conversation_id: ConversationId,
    session_key: SessionKey,
    is_authorized: bool,
    is_mentioned: bool,
    sender_normalized: String,
    workspace: Option<PathBuf>,
) -> Result<(), GatewayError> { ... }
```

Boolean flags are especially dangerous: `handle(message, route, key, true, false, sender, None)` explains nothing at the call site.

### Solution

Group related parameters into a **context struct**. Required parameters go in the constructor; optional parameters use builder-style `with_*` methods:

```rust
#[derive(Debug, Clone)]
pub struct InboundContext {
    pub message: InboundMessage,
    pub reply_route: ReplyRoute,
    pub session_key: SessionKey,
    pub is_authorized: bool,
    pub is_mentioned: bool,
    pub sender_normalized: String,
    pub voice_reply_hint: bool,
    pub transcribed_input: bool,
    pub workspace: Option<std::path::PathBuf>,
}

impl InboundContext {
    pub fn new(
        message: InboundMessage,
        reply_route: ReplyRoute,
        session_key: SessionKey,
    ) -> Self {
        let sender_normalized = message.sender_id.as_str().to_string();
        Self {
            message,
            reply_route,
            session_key,
            is_authorized: false,
            is_mentioned: false,
            sender_normalized,
            voice_reply_hint: false,
            transcribed_input: false,
            workspace: None,
        }
    }

    pub const fn authorize(mut self) -> Self {
        self.is_authorized = true;
        self
    }

    pub const fn with_mention(mut self, mentioned: bool) -> Self {
        self.is_mentioned = mentioned;
        self
    }

    pub fn with_workspace(mut self, workspace: Option<std::path::PathBuf>) -> Self {
        self.workspace = workspace;
        self
    }
}
```

The signature becomes short and stable:

```rust
// after: 1 parameter
pub async fn handle(&self, ctx: InboundContext) -> Result<(), GatewayError> { ... }
```

Note that `new` takes only the three required parameters; every remaining field is filled in through a `with_*` method. Each `with_*` method consumes and returns `Self`, so calls can be chained.

### Usage

```rust
let route = ReplyRoute::new(channel_id, conversation_id)
    .with_reply_to(message_id);

let ctx = InboundContext::new(message, route, session_key)
    .authorize()
    .with_mention(true)
    .with_workspace(Some(workspace));

let result = router.handle(ctx).await;
```

### When to Apply

- The function has **5 or more** parameters
- Two or more of the parameters are boolean flags
- Several parameters are optional
- The parameters form a logical group
- The API is likely to grow new parameters over time
- The function is called from several places

### Locations in Codebase

- `src/gateway/inbound_context.rs` — the definitions of `InboundContext` and `ReplyRoute`
- `src/gateway/inbound_router/` — routing and command dispatch, where the context flows
- `src/gateway/pipeline/mod.rs` — the pipeline assembly point that consumes the context

## Newtype Pattern

### Problem

Primitive types carry no meaning. A function that takes two `String` parameters (for two different kinds of ID) compiles even when the arguments are swapped:

```rust
fn assign(skill_id: String, plugin_id: String) { ... }

// compiles, but wrong — the arguments are swapped
assign(plugin_id, skill_id);
```

### Solution

Wrap the primitive in a **newtype struct** so the types themselves carry distinct identities:

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct SkillId(String);

impl SkillId {
    pub fn new(id: impl Into<String>) -> Self {
        let id = id.into();
        debug_assert!(!id.is_empty(), "SkillId must not be empty");
        Self(id)
    }

    pub fn as_str(&self) -> &str {
        &self.0
    }
}

impl fmt::Display for SkillId {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{}", self.0)
    }
}

impl From<&str> for SkillId {
    fn from(s: &str) -> Self {
        Self(s.to_string())
    }
}
```

Now the compiler catches the mistake:

```rust
fn assign(skill_id: SkillId, plugin_id: PluginId) { ... }

let skill = SkillId::new("core:search");
let plugin = PluginId::new("core");

assign(skill, plugin);   // correct
assign(plugin, skill);   // compile error!
```

Aleph's newtypes deliberately **do not implement `Deref`**. Callers must write `as_str()` explicitly, so "is this actually a string?" is never decided implicitly. The only `Deref` implementation in the whole repository is `HookReadGuard<'_>` in `src/extension/hooks/registry.rs`, pointing at `HookExecutor` — a special case for a lock guard, not a convention for ID types.

### Collection Newtypes

Newtypes also apply to collections that carry domain-specific meaning. `DedupKey` is the dedup identity of a telecom event:

```rust
/// Opaque, collision-free dedup identity (parts are compared as a vector, so
/// no delimiter can be spoofed by a provider id containing one).
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub struct DedupKey(Vec<String>);

/// Derive the dedup key of an event from provider identity only.
pub fn dedup_key(env: &TelecomEnvelope) -> DedupKey { ... }
```

Collection newtypes are produced by a **named constructor** rather than collected from an iterator. The composition rule of a dedup key (provider account + event kind + provider event id) is part of the protocol; hiding it inside a `collect` would make that rule impossible to review.

### Standard Trait Checklist

Every newtype should implement a consistent set of traits:

**Required:**
- `Debug` — debug output
- `Clone` — value copying
- `PartialEq`, `Eq` — equality
- `Hash` — use in `HashMap`/`HashSet`

**Recommended:**
- `Display` — user-facing string output
- `as_str()` — explicit access to the inner string
- `From<&str>`, `From<String>` — ergonomic construction
- `Serialize`, `Deserialize` — JSON/TOML support

**Optional:**
- `FromStr` — parse from a string (mostly for enum-shaped IDs)
- `Default` — when a sensible default exists

**Not recommended:**
- `Deref` — it lets callers forget "this is an ID". Use `as_str()` instead

## Builder Pattern

### Problem

Complex objects have many fields, some required and some optional. A ten-argument constructor is unusable, and filling in every field by hand is both verbose and error-prone.

### Solution

Provide a **constructor** for required parameters and fluent `with_*` methods for optional ones:

```rust
impl AgentDef {
    // only the required parameters in the constructor
    pub fn new(id: impl Into<String>, mode: AgentMode) -> Self { ... }

    // optional parameters set through builder methods
    pub fn with_description(mut self, desc: impl Into<String>) -> Self {
        self.description = desc.into();
        self
    }

    pub fn with_when_to_use(mut self, hint: impl Into<String>) -> Self {
        self.when_to_use = Some(hint.into());
        self
    }

    pub fn with_system_prompt(mut self, prompt: impl Into<String>) -> Self {
        self.system_prompt = Some(prompt.into());
        self
    }
}
```

Usage reads like a sentence:

```rust
let def = AgentDef::new("explore", AgentMode::SubAgent)
    .with_description("Read-only exploration of unfamiliar modules")
    .with_when_to_use("When a new area of the codebase needs to be mapped first")
    .with_system_prompt("You are an exploration sub-agent. Report findings; do not modify files.");
```

### Benefits

- **Fluent API** — the method chain reads naturally
- **Self-documenting** — every `with_*` method names the parameter it sets
- **Compile-time safety** — required parameters are enforced by the constructor
- **Backward compatible** — adding a new `with_*` method breaks no existing caller

Note that in Aleph the Builder pattern is usually combined with the Context pattern rather than used as a standalone `Builder` struct.

## FromStr Trait Pattern

### Problem

Many types need to be parsed from strings — configuration values, enum variants, user input. Without a standard interface, each type invents its own `parse` or `from_string` method.

### Solution

Implement `FromStr` so the type plugs into Rust's standard `str::parse()`:

```rust
impl std::str::FromStr for TaskStatus {
    type Err = String;

    fn from_str(s: &str) -> Result<Self, Self::Err> {
        if s.eq_ignore_ascii_case("pending") {
            Ok(Self::Pending)
        } else if s.eq_ignore_ascii_case("running") {
            Ok(Self::Running)
        } else if s.eq_ignore_ascii_case("completed") {
            Ok(Self::Completed)
        } else if s.eq_ignore_ascii_case("failed") {
            Ok(Self::Failed)
        } else {
            Err(format!("Unknown task status: {s}"))
        }
    }
}
```

This gives you the standard `.parse()` API and generic parsing helpers:

```rust
// parse directly
let status: TaskStatus = "pending".parse()?;

// during configuration loading
let status = config.get("status")?.parse::<TaskStatus>()?;

// a generic helper
fn parse_config<T: FromStr>(value: &str) -> Result<T, T::Err> {
    value.parse()
}
```

### Types with FromStr in Aleph

The following types implement `FromStr` for consistent parsing:

- **Team types:** `TeamStatus`, `TeamMemberKind` (`src/teams/types.rs`)
- **Memory context types:** `NoteType`, `FactSource`, `FactSpecificity`, `TemporalScope`, `MemoryLayer`, `MemoryCategory` (`src/memory/context/enums.rs`)
- **Event and ledger types:** `EventActor` (`src/memory/events/mod.rs`), `LedgerAction`, `LedgerOutcome` (`src/identity/record.rs`)
- **Skill and install types:** `Os`, `PromptScope`, `InstallKind` (`src/domain/skill.rs`)
- **Resilience types:** `TaskStatus`, `RiskLevel`, `Lane` (`src/resilience/types.rs`)
- **Extension and hook types:** `ExtensionKind` (`src/hub/types.rs`), `ThinkLevel` (`crates/aleph-slot-api/src/ai.rs`), `HookKind`, `HookPriority` (`crates/aleph-slot-api/src/hooks.rs`)
- **MCP runtime types:** `RuntimeKind` (`src/mcp/external/runtime.rs`)

Note that `SessionStatus` and `EventType` exist but **do not** implement `FromStr` — not every enum deserves string parsing.

### Convention

- Compare case-insensitively with `eq_ignore_ascii_case`, branch by branch, without allocating a lowercase copy
- The error type is usually `String` (simple, no extra dependency); `Os` uses a dedicated `ParseOsError`
- Match every known variant and return `Err` for unknown values
- Include the original input in the error message, for example `Unknown task status: {s}`

## Pattern Combinations

Patterns in Aleph are rarely used alone. The common combinations:

### Context + Builder

`InboundContext` uses the Context pattern to group parameters and the Builder pattern for optional fields:

```rust
let ctx = InboundContext::new(message, route, session_key)
    .authorize()
    .with_mention(true)
    .with_workspace(Some(workspace));
```

### Newtype + FromStr

Many enum-shaped newtypes implement `FromStr` so they can be parsed from configuration:

```rust
let status: TaskStatus = "pending".parse()?;
let note: NoteType = config.get("note_type")?.parse()?;
```

### Newtype + Explicit Accessor

Newtypes wrapping `String` expose the inner string through `as_str()` instead of implementing `Deref`:

```rust
let id = SkillId::new("core:search");
if id.as_str().starts_with("core:") { ... }
```

## Error Handling Conventions

Aleph uses a two-layer error handling approach:

### Boundary Errors: `thiserror`

For errors that cross module boundaries and that callers need to match on, derive a structured error type with `thiserror`:

```rust
#[derive(Debug, thiserror::Error)]
pub enum GatewayError {
    #[error("Failed to bind to {addr}: {source}")]
    BindFailed {
        addr: SocketAddr,
        source: std::io::Error,
    },
    #[error("Connection error: {0}")]
    ConnectionError(String),
    #[error("Protocol error: {0}")]
    ProtocolError(String),
}
```

`thiserror` fits errors where "the caller branches on the variant". Keep the variant count small and orthogonal — needing a dozen variants usually means the error type mixes several concerns.

### Internal Errors: `anyhow`

For errors handled inside a module where callers do not need to distinguish variants, use `anyhow::Result`:

```rust
use anyhow::{Context, Result};

fn load_manifest(dir: &Path) -> Result<PluginManifest> {
    parse_manifest_from_dir_sync(dir).context("invalid plugin manifest")
}
```

### Rule of Thumb

- If the error crosses a **crate boundary** or is part of a **public API**, use `thiserror`
- If the error is handled inside a **single module** or a **binary entry point**, use `anyhow`
- Add a human-readable description with `.context()` on `anyhow` errors
- Keep domain error types in the domain's `error.rs` and provide a `Result` alias alongside them (for example `ExtensionResult`)

## Module Organization

These principles dictate the structure of files and modules. See the [code organization guide](https://github.com/rootazero/Aleph/blob/main/docs/reference/CODE_ORGANIZATION.md) for the full reference.

### Core Principles

**Single responsibility.** Every file owns exactly one concept. If you need the word "and" to describe what a file does, it needs to be split.

**Separation of concerns.** Split along natural seams:

| Concern | File name |
|--------|--------|
| Type definitions (struct/enum) | `types.rs` |
| Business logic | the module's main file |
| External integrations (database, network) | `store.rs`, `executor.rs` |
| Test doubles | `mock.rs`, under `#[cfg(test)]` |
| Error types | `error.rs` |

**Minimal visibility.** Use `pub(crate)` for cross-module access. Reserve `pub` for a crate's public API surface. Internal details should be `pub(super)` or private.

### Standard File Names

The actual distribution under `src/` (by file count):

| File name | Contents | Files under `src/` |
|--------|------|------|
| `types.rs` | Enums and value objects | 72 |
| `error.rs` | Domain-specific error enums | 18 |
| `store.rs` | Persistence implementations | 18 |
| `registry.rs` | Lookup, registration and query logic | 16 |
| `executor.rs` | Logic that calls out to external systems | 6 |
| `builder.rs` | Construction and assembly | 5 |
| `manager.rs` | Long-lived managers | 5 |
| `callback.rs` | Event handlers and hooks | 4 |
| `factory.rs` | Factory functions | 3 |
| `pool.rs` | Connection/resource pools | 1 |
| `mock.rs` | Test doubles (under `#[cfg(test)]`) | 1 |

`model.rs` appears **nowhere** under `src/` — aggregate roots live in the module's main file, so do not add that name again.

### When to Split a File

**Must split** when:
- The file reaches 500+ lines and covers several concepts
- There are multiple `impl Trait for T` blocks for different types
- Production code and test doubles are mixed
- A single struct has 20+ public methods spanning unrelated concerns

**Consider splitting** when:
- A single `impl` block exceeds 300 lines
- A function exceeds 100 lines
- `use` imports span more than three unrelated modules

### Module Patterns

**Single-struct module** — for modules centred on one struct:
```
src/capability/
├── provider.rs          # ProviderId, ProviderState, ProviderLifecycle
├── provider_registry.rs # ProviderRegistry, ProviderActivator
└── events.rs            # CapabilityEvent
```

**Domain model module** — for rich domain models with several types:
```
src/memory/context/
├── mod.rs          # module entry point, re-exports
├── enums.rs        # NoteType, FactSource, MemoryLayer, MemoryCategory, etc.
├── fact.rs         # MemoryFact (aggregate root)
├── compression.rs  # CompressionResult
└── paths.rs        # path derivation
```

**Manager Facade** — for large managers that delegate to sub-components:
```
src/extension/
├── mod.rs          # ExtensionManager (lean facade, delegates)
├── loader.rs       # plugin loading and discovery
├── lifecycle.rs    # mount / unmount / reload
├── registry/       # plugin registry
├── types/          # ExtensionConfig, LoadSummary, etc.
├── manifest/       # manifest parsing
└── error.rs        # ExtensionError
```

**Startup Builder** — for complex initialization sequences:
```
src/bin/aleph-server/commands/start/
├── mod.rs               # entry point: parse args, call the builder
├── builder/
│   ├── mod.rs           # ServerBuilder
│   ├── agent_init/
│   ├── handlers/
│   ├── startup_resources.rs
│   └── subsystems.rs
├── capability_init.rs
└── runtime_warmup.rs
```

### Anti-Patterns to Avoid

- **God object:** one struct with 40+ methods spanning unrelated concerns. Split it into a facade that delegates to focused sub-components.
- **Flat script:** a 700-line initialization function. Extract a builder with separate `initialize_*` methods.
- **Type dumping ground:** 14 types and 31 impl blocks in one file. Separate them into `types.rs` and domain-specific files.

## Migration Guide

### Adding the Context Pattern

1. Identify a function with 5+ parameters (several optional, or with two or more boolean flags)
2. Create a context struct holding the required fields plus `Option` fields for the optional ones
3. Implement `new()` with only the required parameters
4. Add a `with_*` builder method for each optional parameter
5. Update the function signature to take the context
6. Update every call site
7. Export the context type from the module's public API

### Adding a Newtype

1. Identify a primitive that carries semantic meaning
2. Create a tuple struct wrapping that primitive
3. Derive `Debug`, `Clone`, `PartialEq`, `Eq`, `Hash`
4. Implement `new()` and `as_str()` (or an equivalent accessor)
5. Implement `Display` and `From<T>` as needed; **do not** implement `Deref`
6. Update all usage sites to use the newtype
7. Add the type to the newtype catalog

## Hard Constraints Established Since 26.7.x

### Rust Toolchain 1.99+

The current `rust-version` is **1.99**, and `rust-toolchain.toml` pins the toolchain to `1.99.1` (including `rustfmt`, `clippy`, and the `wasm32-unknown-unknown` target). During development use `rustup install 1.99`, or simply rely on `rust-toolchain.toml`.

### Harness 12 Files + Line-Count Ratchet

**The code is authoritative** — any number in this documentation is just a copy of `CEILING`:

- 8 top-level files + 4 in `agent/` = **12 files** (test files live in `tests/` and are outside the ratchet)
- Line counts are guarded by the ratchet in `src/harness/tests/budget.rs`, which binds the constant `CEILING`
- The current `CEILING` is **5535** (`src/harness/tests/budget.rs:795`); do not treat the number in this section as a copy
- Before adding code, answer three questions: scaffolding or cognition? Is it still needed after the next model upgrade? How many real consumers does it have?

### YAGNI Withdrawal

Any abstraction with zero consumers is deleted immediately. The harness dissolution removed roughly 5,200 lines of dead code.

### Fail-Closed

Strengthened in 26.7.21: a missing policy file, an unreadable one, one over the 1 MiB limit, or one that fails to parse **refuses authorization** — it falls back to the safe default (`safe_default()`), where every action lands on `Ask` for a human to decide. The one exception is allowlist compilation failure, which fails open.

### Process-Isolation Kernel

26.7.x: the sandbox issues restricted-token / job-object / AppContainer / integrity-level / SID·ACL system calls in place at spawn time — a legitimate opening beyond the R1 intent.

### `aleph-server prompt-size`

The R9 prompt-skeleton size check command.

### Full RPC Catalog

The gateway currently exposes **396** RPC methods (the census in `src/gateway/method_census.rs` defines the count) — see the [gateway method reference](/docs/en/gateway/methods) when adding a new one.
