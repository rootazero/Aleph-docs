This page explains Gateway JSON-RPC message semantics, not individual method parameters.

## Message forms

Gateway JSON-RPC 2.0 messages are requests, responses, and notifications. Shared types are `JsonRpcRequest`, `JsonRpcResponse`, and `JsonRpcError` in `shared/protocol/src/jsonrpc.rs`. See the [method index](../gateway/methods) for method names.

## Requests and responses

`JsonRpcRequest.id` is `Option<Value>`, not a string-only type: `new()` generates a string ID and `with_id()` accepts a JSON value. Requests expecting a response carry an `id`; `notification()` sets it to `None`, serialization omits it, and `is_notification()` checks for `None`. Do not use explicit JSON `null` as a client correlation ID. Optional `params: Option<Value>` is not restricted to objects. See `shared/protocol/src/jsonrpc.rs`.

A response carries the corresponding `id: Value`. The `success()` and `error()` constructors populate only `result` or `error`, respectively. Errors contain `code`, `message`, and optional `data`. This exclusivity is a constructor convention, not a mutually exclusive enum. See `shared/protocol/src/jsonrpc.rs`.

The request and success response below use `echo` (`src/gateway/handlers/echo.rs`); a separate example illustrates the error envelope:

```json
{"jsonrpc":"2.0","id":"req-1","method":"echo","params":{"text":"hello"}}
```

```json
{"jsonrpc":"2.0","id":"req-1","result":{"echo":{"text":"hello"}}}
```

```json
{"jsonrpc":"2.0","id":"req-1","error":{"code":-32602,"message":"Invalid params: missing field"}}
```

## Error codes

Each row matches a constant and its defined meaning in `shared/protocol/src/jsonrpc.rs`; not every transport necessarily emits every code.

| Code | Constant | Meaning | When applicable |
|---|---|---|---|
| -32700 | `PARSE_ERROR` | Parse error | Invalid JSON received |
| -32600 | `INVALID_REQUEST` | Invalid request | JSON is not a valid request object |
| -32601 | `METHOD_NOT_FOUND` | Method not found or unavailable | No available method matches the request |
| -32602 | `INVALID_PARAMS` | Invalid parameters | Method parameter validation fails |
| -32603 | `INTERNAL_ERROR` | Internal error | An internal JSON-RPC error occurs |
| -32000 | `AUTH_REQUIRED` | Authentication or role authorization required | Authentication required; also used for operator-only refusals |
| -32002 | `RATE_LIMITED` | Rate limited | A rate limit is exceeded |
| -32003 | `AGENT_ERROR` | Agent execution error | Agent execution fails |
| -32004 | `TOOL_ERROR` | Tool execution error | Tool execution fails |
| -32008 | `PERMISSION_DENIED` | Permission denied | An operation is not permitted |
| -32009 | `RESOURCE_NOT_FOUND` | Resource not found | The requested resource cannot be found |
| -32010 | `TIMEOUT_ERROR` | Operation timeout | An operation times out |
| -32031 | `REVISION_CONFLICT` | Canvas revision conflict | canvas.apply supplies a stale base_revision |

## Operator refusal message

`ADMIN_REQUIRED_MESSAGE` is defined in `shared/protocol/src/jsonrpc.rs` with the exact text below. At runtime, `method_requires_admin` in `src/gateway/method_admin.rs` classifies operator-only methods. Authenticated members receive `AUTH_REQUIRED` (-32000), not `PERMISSION_DENIED`. The gate is called in `src/gateway/server/connection/dispatch.rs`.

```text
Not authorized: this method requires operator privileges
```

## Event notifications

`TOPIC_EVENT_METHOD = "event"` names the topic envelope’s `method`, not the topic itself. Notifications omit `id`; `params` carries `topic` and `data`, as documented in `shared/protocol/src/jsonrpc.rs`. This differs from streaming events that use per-frame method names. See [Gateway events](../gateway/methods/events) for topics.

Owner and scope checks in `src/gateway/event_visibility.rs` constrain visibility: subscribing does not grant access to other users’ events.

```json
{"jsonrpc":"2.0","method":"event","params":{"topic":"agent.run.complete","data":{}}}
```

This shows the envelope only; event definitions in `src/gateway/events/frame.rs` determine the actual `data` schema.

## Tool-call envelopes

Reverse-RPC payloads in `shared/protocol/src/jsonrpc.rs` let the server request client-side tool execution and the client return a result. They are payloads within JSON-RPC, not replacements for its outer `id`.

| Type | Fields and constraints |
|---|---|
| `ToolCallParams` | `call_id: String`, `tool_name: String`, `params: Value`, `context: ToolCallContext` (defaults when omitted) |
| `ToolCallContext` | All optional: `run_id: String`, `session_key: String`, `timeout_ms: u64` |
| `ToolCallResult` | `call_id: String`, `success: bool`; optional: `result: Value`, `error: String`, `duration_ms: u64` |

The result’s `call_id` must match the call. `ToolCallResult::success()` / `error()` populate a value or error string; `with_duration()` adds elapsed time. See `shared/protocol/src/jsonrpc.rs`.

## Relationship to Protocol v1

JSON-RPC defines message semantics; see [Protocol v1](../gateway/protocol-v1) for framing, handshakes, and transports. Corresponding code lives in `shared/protocol/src/framing.rs`, `shared/protocol/src/system_hello.rs`, and `src/gateway/server/connection/`.
