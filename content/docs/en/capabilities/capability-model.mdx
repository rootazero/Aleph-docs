This page answers one question: what makes up a runtime "capability" in Aleph, how it is authorized and revoked, and how a consumer avoids ending up with a stale handler. The code lives in `src/capability/` (33 files) and the contract crate `crates/aleph-slot-api/`.

<Callout type="warn" title="Read this first">
  The 2026-11-25 **capability convergence** removed several modules from `src/capability/` that were "written and tested but not mounted on a production path": the old ambient / audit / grant modules, plus the capability's own lifecycle and activation state machines. A capability's "alive or dead" state is now carried by the provider lifecycle (see "Provider lifecycle and generations").
  This page describes the state after the convergence and distinguishes production paths from defined but unmounted contracts and from plans in the blueprints.
</Callout>

## What a capability is

A capability’s **descriptor** (`CapabilityDescriptor`) records its **owner** (`OwnerRef`), its **visibility scope** (`VisibilityScope`), and a set of **behavior facets** (`CapabilityFacet`). The descriptor is defined in `src/capability/descriptor.rs`; the ownership and visibility types are in `src/capability/ownership.rs`.

A descriptor only describes; it grants no authority. Authorization comes from ownership bindings, policy, and leases. The module comment in `src/capability/descriptor.rs` says it directly: the descriptor is the "kind-agnostic capability contract", the Tool and special-capability backends provide executable adapters, and the other kinds stay descriptive until their owning backend is mounted.

```text
CapabilityDescriptor ──describes──▶ what the capability is (id / kind / schema / facets)
OwnershipTree        ──binds─────▶ who owns it, which generation (owner / generation)
Zahir::resolve       ──issues────▶ BackendLease (a lease carrying owner_generation)
Zahir::validate_lease──rechecks──▶ checked again before use; refused once stale
```

See `src/capability/ownership.rs` for the binding and `src/capability/zahir_facade.rs` for lease validation.

### The boundary between the contract crate and the runtime

`crates/aleph-slot-api/src/` contains 33 Rust source files, with the browser contracts organized under `crates/aleph-slot-api/src/browser/mod.rs`. The dependency runs one way, from `alephcore` to `aleph-slot-api`. The contract crate does no I/O, has no platform or LLM dependencies, uses Tokio’s `sync` feature but not its runtime, and holds no hidden state. `alephcore::error` re-exports the contract types rather than defining them a second time (`crates/aleph-slot-api/src/lib.rs`).

`crates/aleph-slot-api/src/capability.rs` defines capability identity and service-graph relations shared by all hosts. `crates/aleph-slot-api/src/descriptor.rs` is the authoritative definition of tool-registry descriptors, replay contracts, and implementation contracts. `ContractVersion` is the slot contract type (`crates/aleph-slot-api/src/slot.rs`), not the protocol constant `HOOK_CONTRACT_VERSION` (`shared/protocol/src/hook.rs`).

## Descriptor

### Fields

`CapabilityDescriptor` (`src/capability/descriptor.rs`):

| Field | Type | Meaning |
|---|---|---|
| `id` | `CapabilityId` | `{namespace, name}`; Tools use the namespace `aleph/tools` (`TOOL_NAMESPACE`, `src/capability/backend.rs`) |
| `kind` | `CapabilityKind` | Primary classification, see below |
| `schema` | `SchemaRef` | Schema version plus a SHA-256 fingerprint |
| `revision` | `CapabilityRevision` | Monotonic revision, assigned by the owning registry on every successful mutation |
| `lifetime` | `LifetimeScope` | How long the owner binding lives |
| `visibility` | `VisibilityScope` | Who may see it |
| `owner` | `OwnerRef` | Who owns it |
| `services` | `Vec<Service>` | Relation edges: `requires` / `provides` / `conflicts` |
| `metadata` | `ProjectionMetadata` | Projection metadata, see the warning below |
| `facets` | `CapabilityFacets` | Behavior-facet bit set |

`CapabilityId`, `Service`, and `ServiceRelation` are defined in `crates/aleph-slot-api/src/capability.rs` and re-exported by the descriptor module. A `Service` is a pure relation edge: it carries no data and is never invocable.

### CapabilityKind and CapabilityFacet

`CapabilityKind` has 12 variants (`src/capability/descriptor.rs`):

```rust
pub enum CapabilityKind { Tool, Ambient, Terminal, Ui, Skill, Agent, Task, Resource, EventSource, Subscription, Plugin, Hook }
```

(The source puts one variant per line; it is folded here for layout.) `CapabilityKind::UI` is a compatibility spelling of `Ui`.

Tool and special-capability backends provide executable adapters, but the enum alone does not tell you whether a backend is mounted (`src/capability/descriptor.rs`). `Ambient` is still in the enum, but the module it used to live in, `src/capability/ambient.rs`, was removed by the 2026-11-25 capability convergence: that module declared itself unmounted, and exposing process identity and environment variables is a security decision, so there is no replacement today.

`CapabilityFacet` is a behavior axis orthogonal to kind, with 5 variants: `Callable`, `EventSource`, `Subscription`, `ProviderLifecycle`, `ExternalEffect`. One provider can expose both an event source and callable operations without pretending the whole provider is a `Tool`.

`CapabilityFacets(u8)` is a 5-bit set with `new` / `with` / `contains`; on a descriptor, `supports(facet)` queries it. Facets are descriptive metadata and confer no authority (`src/capability/descriptor.rs`).

### SchemaRef and the fingerprint

`SchemaRef` is defined in `src/capability/descriptor.rs`:

```rust
pub struct SchemaRef {
    pub version: u32,
    pub fingerprint: [u8; 32],
}
```

`fingerprint` is the SHA-256 of the canonicalized input schema, computed by `capability::backend::to_descriptor` (`src/capability/backend.rs`). The same schema with different key order yields the same fingerprint; change the schema and the fingerprint changes. The facade’s `validate_lease` checks the fingerprint as part of verifying descriptor freshness (`src/capability/zahir_facade.rs`).

## Ownership and lifetime

### Lifetime scopes and owners

`LifetimeScope` (`src/capability/ownership.rs`) has 5 variants; `External` falls outside the in-process lifetime hierarchy:

| Variant | Meaning |
|---|---|
| `Runtime` | Bound to the process; lives for the whole runtime |
| `Session` | Bound to one session |
| `Run` | Bound to one run |
| `Task` | Bound to one task |
| `External` | Owned externally, outside this process's lifetime model |

`OwnerRef` (`src/capability/ownership.rs`) says who owns a capability binding: `Runtime`, `Session(SessionKey)`, `Run(RunId)`, or `Task(TaskId)`.

<Callout type="info">
  The codebase does **not yet** have a canonical run-id or task-id type. `RunId(pub String)` and `TaskId(pub String)` are temporary wrappers in `src/capability/ownership.rs`, and the comments say to align them with a canonical type as soon as one exists.
</Callout>

On top of these scopes, `OwnershipTree` forms a five-level tree: Runtime → Session → Run → Task → EffectClaim (comment in `src/capability/ownership.rs`). Two orthogonal axes apply: `LifetimeScope` is the RAII axis (how long a binding lives) and `VisibilityScope` is the ACL axis (who can see it).

### OwnerGeneration and FencingToken

See `src/capability/ownership.rs` for generations, fencing tokens, and binding mutations:

- `OwnerGeneration(pub u64)`: each binding has a current generation. A lease is valid only while the generation it recorded equals the binding's current one; re-issuing ownership or bumping the lifetime scope changes it.
- `FencingToken(u64)`: private field, `Copy`. The only constructor is the owner layer's `pub(crate) fn new(nonce: u64)`, and counter monotonicity is the owner layer's contract. Every `claim` mints a fresh token, so a stale lease can never present an old token as live.

`OwnershipTree` mutation operations:

| Method | Effect |
|---|---|
| `bump(scope)` | Raises the owner nonce, rewrites every binding at that scope and below to the new generation, and clears their claims; returns `Result<OwnerGeneration, OwnershipError>`, with `GenerationExhausted` when the counter runs out |
| `rotate_capability(id)` | Re-generations every binding of one capability and clears its claims |
| `revoke(id)` | Irreversible: removes all bindings of that capability and adds the id to the revoked set |
| `dispose(scope)` | Irreversible: removes every binding at that scope and below and adds the scope to the disposed set |

Once revoked or disposed, state cannot be undone, and every later `resolve` / `claim` is rejected.

### OwnershipChange: the only observer-visible side effect

`OwnershipChange` is defined in `src/capability/ownership.rs`:

```rust
pub enum OwnershipChange {
    Bumped { generation: OwnerGeneration, scope: LifetimeScope },
    Rotated { capability: CapabilityId, generation: OwnerGeneration },
    Revoked { capability: CapabilityId },
    Disposed { scope: LifetimeScope },
}
```

(Multi-line in the source; condensed here.) It is emitted under `OwnershipTree`'s own mutex, in the same critical section that mutates state, and is the **only** observer-visible side effect of the tree's mutation methods. Observers subscribe through `OwnershipTree::subscribe_changes`; the stream does **not** route through any global bus, session event store, or approval authority. Subscribing is pure observation: it changes no state, does not advance the nonce, and registers no binding. A receiver that falls behind gets a lagged count and should reconcile against a fresh snapshot.

### Provider lifecycle and generations

A capability’s "alive or dead" state is carried by the **provider lifecycle**. `ProviderLifecycle` in `src/capability/provider.rs` is a pure state machine, and `ProviderTransport` has only two variants, `InProcess` and `Bridge`, naming the runtime boundary of a provider implementation.

| State | Meaning |
|---|---|
| `Discovered` | Discovered, but no admitted declaration yet |
| `Cold` | Declaration admitted; no runtime effects and no executable lease |
| `Disabled` | Explicitly disabled |
| `Starting` | Starting up |
| `Ready` | Ready to be called |
| `Stopping` | Stopping; no new calls are admitted |
| `Stopped` | Stopped |
| `Failed` | Startup or runtime failure |

`ProviderLifecycle::transition` accepts only the transitions below and returns `ProviderLifecycleError::InvalidTransition { provider_id, from, to }` for anything else:

```text
Discovered → Cold | Disabled | Starting
Disabled   → Cold | Starting
Cold       → Disabled | Starting
Starting   → Ready | Failed | Stopping
Ready      → Stopping | Failed
Stopping   → Stopped | Failed
Stopped    → Starting | Disabled
Failed     → Starting | Stopped | Disabled
```

**Every entry into `Starting` increments the generation**, and an exhausted generation returns `ProviderLifecycleError::GenerationExhausted`. That is the mechanism behind "a restart invalidates old leases": leases from an older generation are invalid while the provider restarts, and they stay invalid after the replacement reaches `Ready`.

Every accepted transition produces one `ProviderTransition { provider_id, transport, from, to, generation }`, broadcast as a `broadcast::Receiver<ProviderTransition>` through `ProviderHandle::subscribe_changes`.

`ProviderHandle` is the thread-safe control handle (an `Arc<Mutex<ProviderLifecycle>>` plus a `broadcast::Sender` inside): `snapshot` returns `(ProviderState, u64)`; `acquire_call(expected_generation)` returns `ProviderCallError { provider_id, state, expected_generation, actual_generation }` when the generation does not match or the state is not `Ready`; `with_ready_commit`, `with_call_admission`, and `with_admitted_completion` are crate-internal staged-commit primitives (`src/capability/provider.rs`).

<Callout type="warn" title="The old capability lifecycle state machine was removed">
  The 2026-11-25 capability convergence removed `src/capability/lifecycle.rs` (`LifecycleState`, the lifecycle `Lease`, `transition_to`) and `src/capability/activation.rs` (`CapabilityActivationController`). Runtime policy used those two files for exactly two things — comparing generations and noticing revocation — and both now live in the constraint attachment described below and in the provider lifecycle. To recover the old implementation, read the git history: `git log --diff-filter=D -- src/capability/lifecycle.rs`.
</Callout>

### Runtime admission: the constraint attachment

The production path has no "activation gate" step; constraint checking lands directly on **admission**. `PolicyEngine::admit_runtime` in `src/capability/policy_runtime.rs` checks in this order:

1. Does the id have a rule in the runtime rule table? If not, the call is admitted immediately and no attachment is consumed.
2. Does an attachment exist and match the id? Otherwise `PolicyDenial::AttachmentUnavailable { id }`.
3. Does the attachment’s recorded binding match the lease (id, revision, generation, owner, visibility)? Otherwise `AttachmentUnavailable`.
4. Is the fact-source snapshot readable? Otherwise `PolicyDenial::ConstraintDenied { reason: "facts_unavailable" }`.
5. Is the fact source’s key unchanged? Otherwise `AttachmentUnavailable`.
6. Recheck the lease captured at admission time (`validate_captured_lease`).
7. Is the attachment still in the attachment table (compared with `Arc::ptr_eq`)? Otherwise `AttachmentUnavailable`.
8. Evaluate the constraints: `ResourceUse::Allocate` runs the full evaluation, while `Existing` and `Release` run the non-allocating evaluation. A failure is `PolicyDenial::ConstraintDenied { reason: "runtime_constraints" }`.

Revocation is **not** a second flag: it is "removed from the attachment table". `admit` is reachable only for a state that is still listed, and listing and removal share one lock, so a removed state never admits again (`src/capability/policy_runtime.rs`).

A successful admission returns a `RunningCapabilityCall` guard. It must be held until the real operation finishes — asynchronous cancellation included — before the resource counter is released (`src/capability/policy_runtime.rs`).

When a dependency is unavailable, tool dispatch turns `ResolveError::DependencyUnavailable` into a model-visible `ToolError::Execution` during resolution, with text like "`memory.runtime` is currently unavailable (state Stopped); retry later or ask the user to enable it". The tool itself stays in the tool list, so the model can see why the call failed and retry (`src/tools/scoped/dispatch.rs`).

<Callout type="warn" title="The compatibility activation entry point was removed">
  The scoped-tool layer used to accept an optional compatibility controller per tool name, held as `Arc<dyn CapabilityActivation>`, and production deliberately never installed one. The 2026-11-25 capability convergence removed that entry point together with `src/capability/activation.rs` (`src/tools/scoped/builder.rs`, `src/tools/scoped/dispatch.rs`). The `ActivationError` of the same name in `src/capability/provider_registry.rs` belongs to provider activation and has the variants `Rejected`, `Failed`, `Unknown`, and `NotVisible`; it has nothing to do with the capability lifecycle.
</Callout>

## Visibility

`VisibilityScope` (`src/capability/ownership.rs`) has 6 fields, **all `Option`, where `None` means unrestricted on that dimension**, so `VisibilityScope::default()` is "visible everywhere":

| Field | Type |
|---|---|
| `principal` | `Option<String>` |
| `workspace` | `Option<String>` |
| `session` | `Option<SessionKey>` |
| `allowed_kinds` | `Option<Vec<String>>` |
| `allowed_ids` | `Option<Vec<String>>` |
| `approval` | `Option<String>` |

`allowed_kinds` and `allowed_ids` are `String` on purpose rather than `CapabilityKind`: the `ownership` module must not depend on `descriptor::CapabilityKind`, or `descriptor` ↔ `ownership` would become a cycle. See `src/capability/policy.rs` for kind and name comparisons; which dimensions are checked depends on the call path.

`src/scope/` handles a different set of scope concerns. `src/scope/authority.rs` resolves the execution identity when a background task fires, `src/scope/carried.rs` uses task-local state to carry memory, project, and agent context, and `src/scope/directory.rs` caches user names for display. These are not the ACL fields of `VisibilityScope` (`src/capability/ownership.rs`).

## Policy

### The live path: binding checks in the facade

In production, the facade resolves and rechecks the binding, and runtime policy checks call restrictions (`src/capability/zahir_facade.rs`, `src/capability/policy_runtime.rs`). The facade checks bindings as follows:

- After looking up the backend entry, `resolve` looks up the binding in `OwnershipTree`. A missing binding with a revoked id can return `ResolveError::Revoked`, a missing binding that is not revoked returns `NotVisible`; on success the owner and owner generation at that moment are written into the `BackendLease`.
- `validate_lease` rechecks that the provider generation has not changed, that the descriptor's `id`, `revision`, and schema `fingerprint` are unchanged, and, through `OwnershipTree::with_current_bindings`, that the binding is still the one the lease recorded (revoked → `Revoked`; missing or disposed → `Unknown`; generation or binding mismatch → `StaleOwner`).

### The three-gate model

`PolicyEngine` (`src/capability/policy.rs`) defines a three-gate model. Every method is fail-closed: a denial at any gate rejects the whole request.

1. **Visibility gate**: does the request's visibility scope match what the descriptor allows.
2. **Principal gate**: does the requesting principal match the binding's owner.
3. **Authority gate**: is the binding live, not revoked, not disposed, and at the expected generation.

When `PolicyEngine::resolve` passes, it issues an opaque `CapabilityLease` whose fields are all `pub(crate)`, so callers outside the crate cannot forge one; `PolicyEngine::validate_lease` rechecks it later.

<Callout type="warn" title="The three-gate resolve is not mounted in production">
  The comments in `src/capability/policy.rs` record the 2026-11-20 severed-wire audit’s finding: `PolicyEngine::resolve` and its helper `validate_visibility_scope` have no production call sites. Do not treat their descriptor comparisons for `allowed_kinds` / `allowed_ids` / `approval` / `workspace` / `session` as production guarantees. Startup constraints and live admission do not depend on this `resolve` (`src/capability/production_init.rs`, `src/capability/policy_runtime.rs`).
</Callout>

### Startup constraints (mounted)

In production, `PolicyEngine` actually carries **startup constraints**. `build_capability_policy` (`src/capability/production_init.rs`) assembles `PolicyEngine::with_shared_tree` from the shared `OwnershipTree` and the `capability_constraints` configuration under `policies`; `aleph-server` calls it at startup (`src/bin/aleph-server/commands/start/capability_init.rs`). Its comment calls it "pure assembly, not authorization or a second ownership authority".

Constraints are configured per capability id, and each rule may carry a time window, a resource limit, and required conditions:

```toml
[policies.capability_constraints."aleph/tools/example"]
required_conditions = { provider_ready = true }
```

The rule shape is in `src/config/types/policies/capability_constraints.rs`: `time` (`start_hour` / `end_hour`), `resource` (`unit` is `active_calls` or `pty_sessions`, plus `max_active`), and `required_conditions` (name to boolean). The struct uses `deny_unknown_fields`, so unknown keys are rejected. Violations are reported as `ConstraintViolation` (`src/capability/constraints.rs`), for example `TimeWindowClosed`, `ResourceLimitExceeded`, and `ConditionNotMet`.

### Call context and runtime admission

`CapabilityCallContext` records facts captured by an authenticated entry point (actor, principal, session, workspace, connection, and call id), not deserialized client claims. Runtime policy combines startup rules with current facts from the source that owns them. It manages restrictions, not descriptors, handlers, or ownership. The operation selects a `ResourceUse` of `Allocate`, `Existing`, or `Release`; The latter two skip allocation-only resource limit checks (`src/capability/policy_runtime.rs`, `src/capability/constraints.rs`).

Tool dispatch checks admission with the trusted context (`src/tools/scoped/dispatch.rs`), and the registry tracks in-flight calls with `RunningCapabilityCall` (`src/tools/registry.rs`). The UI gateway entry point also builds a trusted context and checks admission (`src/gateway/capability_ui.rs`). When a connection closes, the connection layer delegates cleanup of its surfaces to the UI gateway (`src/gateway/server/connection/mod.rs`).

Async special capabilities have a private dispatch boundary. `DomainToolCall` carries the trusted context, an optional owner actor, and a cancellation token through the task-local `DOMAIN_TOOL_CALL`. `CapabilityInvocationOrigin` is a `pub(crate)` enum: only the canonical authenticated entry points produce origin evidence, and client fields cannot construct it (`src/capability/special_dispatch.rs`, `src/tools/scoped/dispatch.rs`, `src/capability/tool_adapters.rs`, `src/capability/zahir_facade.rs`).

## Effect claims

`EffectClaim` is defined in `src/capability/ownership.rs`:

```rust
pub struct EffectClaim {
    pub request_id: String,
    pub fence: FencingToken,
    pub owner: OwnerRef,
}
```

`OwnershipTree::claim` records a claim against a binding and mints a fresh `fence`. It returns `None` if the binding is missing, the capability is revoked, its lifetime has been disposed, the owner does not match, or the fence counter is exhausted. `claim_state` returns `ClaimState::Active` only if the binding is still live and the fence record matches the binding’s current generation and the claim’s owner. Revocation, disposal, a parent bump that clears the record, or a missing claim all yield `Unknown` (`src/capability/ownership.rs`).

`src/capability/effect_claim.rs` is a pure reducer over `SessionEvent::EffectClaim*` event histories (states `Prepared` / `Claimed` / `Invoking` / `Succeeded` / `Failed` / `Unknown`) that stays fail-closed on duplicate active claims and illegal migrations.

<Callout type="warn" title="effect_claim is not wired yet">
  The header comment of `src/capability/effect_claim.rs` says there is no production construction point for `SessionEvent::EffectClaim*`, so the reducer has no producer and no consumer outside its own tests. It is a documented deferral (see the Capability Phase 4 section of `AGENTS.md`), not a silent dead module. So "recognize a duplicate submission by its fence" is currently a contract of the reducer and `OwnershipTree`, not an end-to-end behavior.
</Callout>

## Backend evidence and resolution

### BackendSourceEvidence

`BackendSourceEvidence` (`src/capability/facade.rs`) records which kind of backend a lease came from. Source identity is kind-specific, and Resources never manufacture Tool entries:

| Variant | Payload |
|---|---|
| `Tool` | `canonical_entry: CanonicalEntryLease`, `provider_generation: u64` |
| `Provider` | `provider_id: ProviderId`, `provider_generation: u64` |
| `MemoryResource` | `Weak<MemoryRuntime>` (`Weak` so it does not extend the memory runtime's lifetime) |
| `Special` | `capture: CapturedSpecialEntry`, `provider_generation: u64` |

### BackendLease and ResolveError

See `src/capability/facade.rs` for the type definitions and `src/capability/zahir_facade.rs` for resolution and validation.

```rust
pub struct BackendLease {
    pub descriptor: CapabilityDescriptor,
    pub owner_generation: OwnerGeneration,
    pub owner: OwnerRef,
    pub source: BackendSourceEvidence,
    // required_resources is pub(crate); omitted here
}
```

There is one rule, and it cannot be broken: **a consumer must treat a lease as invalid the moment the owner generation changes, fail closed, and never use a stale handler.** The lease also records `owner`, because the generation alone cannot tell an ownership transfer from an unchanged binding. `resolve` returns a lease, not a live handler; recheck with `validate_lease` before use.

`ResolveError` is a closed set:

| Variant | Meaning |
|---|---|
| `Unknown` | Lookup miss, missing binding (and not revoked), descriptor freshness mismatch, or any unclassifiable failure |
| `NotVisible` | There is no binding for the id in the scope specified by the `visibility` field of the caller’s `Reference` (resolve only) |
| `Revoked` | The binding has been revoked |
| `StaleOwner` | The lease's ownership binding or `owner_generation` differs from the current record (validate only) |
| `StaleProvider` | The provider instance was stopped or replaced after the lease was minted |
| `DependencyUnavailable { target, state }` | A dependency's provider is visible but not ready (`Cold` / `Starting` / `Stopping` / `Stopped` / `Failed` / `Disabled`). The capability stays listed, and the call is refused with the dependency's current state |

An unavailable dependency (`DependencyUnavailable`) travels on to tool dispatch, where it becomes model-visible `ToolError::Execution` text (see "Runtime admission: the constraint attachment"). The event label given in `src/capability/zahir_facade.rs` is `dependency_unavailable`.

`StaleOwner` is never a resolve-time error: a freshly minted lease carries the generation read at resolve time, so it cannot be stale at construction.

### Snapshots and change streams

These types belong to the in-process snapshot and registry change path, not to capability observation events (`src/capability/facade.rs`, `src/capability/zahir_facade.rs`).

- `CapabilitySnapshot { capabilities, committed_cursor }`: contents are **frozen** for the snapshot's lifetime. A later mutation does not rewrite a held snapshot; it produces a new snapshot or a `CapabilityChange::Invalidated` event.
- `Cursor(pub u64)`: a monotonic subscription position; `0` means "from the beginning". Note that `ZahirFacade::subscribe` ignores the caller's cursor: this synchronous, snapshot-anchored API has no replay, so it starts from the snapshot position, and a caller cursor ahead of the snapshot fails closed to the snapshot cursor.
- `CapabilityChangeStream`: a pure value state machine holding no store, registry, or subscription wiring. It provides `from_snapshot`, `append`, `append_cohort`, and `invalidate_and_resync`, and keeps only the latest 256 changes of history.
- `invalidate_and_resync(snapshot, delta)`: drops stale-tail entries whose cursor is not beyond the old position, dedups entries exactly equal to changes already seen, pushes one `Invalidated` followed by the surviving delta in input order, and advances the cursor to the maximum of all parties, **never regressing**. It returns `false` only when the snapshot's cursor is below the subscriber's current one (the resync source lags); in that case the stream is not mutated (fail-closed).

`CapabilityChange` variants: `Registered`, `Replaced`, `Unregistered` (each with `id` and `revision`), and `Invalidated`.

## Events and observation

The stream in `src/capability/events.rs` records bounded, instance-scoped observations. It is neither an authority nor a replay log. It is separate from the facade’s `CapabilityChangeStream` (`src/capability/facade.rs`) and the ownership tree’s `OwnershipChange` notifications (`src/capability/ownership.rs`).

A record commits to memory first, broadcasts next, and then runs the optional persistence hook. Persistence failures are reported after commit, so retrying produces duplicate observations. Hooks run outside the buffer lock and can finish out of order; sinks that need to reconstruct the order must sort by record sequence (`src/capability/events.rs`).

`CapabilityEventType` serializes in `snake_case`. Its variants are `Created`, `Activated`, `Invoked`, `Revoked`, `ConstraintViolation`, `PolicyViolation`, and `ExecutionFailed`. The enum describes what the stream can represent, not which variants have production emitters (`src/capability/events.rs`).

### Trusted audiences and production wiring

`EventAudience` distinguishes `OperatorOnly` from `Principal(PrincipalEventAudience)`. The latter records a `user_id`, and optional `session_key`, `workspace`, and `source_incarnation` fields. Trusted producers capture the audience at their boundary; clients cannot establish that authority through deserialization (`src/capability/event_audience.rs`). The gateway checks visibility for the connection before forwarding each record (`src/gateway/capability_events.rs`, `src/gateway/server/connection/mod.rs`).

Server startup builds and mounts the stream (`src/bin/aleph-server/commands/start/capability_init.rs`, `src/bin/aleph-server/commands/start/mod.rs`). Source evidence and observations come through the PTY manager’s `SourceObservationReceipt` (`src/gateway/pty/manager.rs`), the tool registry (`src/tools/registry.rs`), and dispatch’s `InvocationObservation` (`src/tools/scoped/dispatch.rs`). The capability-side collector in `src/capability/audit.rs` had no production readers and was removed by the 2026-11-25 capability convergence; production auditing goes through `SecurityAuditLog`, and the live path is `src/gateway/capability_events.rs`.

## Zahir

`Zahir` is a trait in `src/capability/facade.rs`: it defines a uniform interface for consumers to read capabilities, without implying that every transport is mounted. It never invokes a capability directly; it describes (`describe`), resolves into a lease (`resolve` / `validate_lease`), subscribes to change (`subscribe`), and projects (`project`), plus one entry point, `activate`, that runs a provider's activation hook.

`ZahirFacade` (`src/capability/zahir_facade.rs`, module comment "The one live Zahir host") is its only live implementation. It is built by `ProjectionHost::mount*` (`src/capability/projection_host.rs`), and `aleph-server` calls `ProjectionHost::mount_with_runtime_and_events` at startup (`src/bin/aleph-server/commands/start/mod.rs`). It composes:

- `ToolBackendAdapter`: its inner `ToolHandlerRegistry` is the **single callable-Tool source of truth** (`src/tools/registry.rs`);
- `Arc<OwnershipTree>`: the **single owner / revoke / dispose source**.

The struct also holds a provider adapter, an optional `MemoryRuntime`, a `PolicyEngine`, the special-capability registry, and an event stream. It holds **no** second descriptor map, handler map, or owner counter.

The registry broadcast is a live notification tap (256 slots, lag can drop), not a durable recovery source. `subscribe` drains it synchronously into a pure `CapabilityChangeStream`; a lagged receiver resyncs from a fresh snapshot and emits `CapabilityChange::Invalidated` rather than pretending it delivered every event. The broadcast does not support durable recovery (`src/capability/zahir_facade.rs`); session event storage is a separate interface (`SessionEventStore` in `src/session/store.rs`).

## Process-wide capability handles

With a bare `OnceLock<Arc<T>>`, an install function, and a getter that falls back to a default, readers cannot tell “startup never installed it” from “startup installed this very value.” `CapabilitySlot::install` encapsulates writing the value and recording the outcome in one operation, writing first and then stamping the outcome in the `MetaGuard` pattern. The `else` branch of a conditional installation can call `CapabilitySlot::decline`. Name the missing input rather than the symptom: operators see `because` verbatim (`src/capability/mod.rs`).

`Outcome` has two variants: `Installed` and `Declined { because }`. An outcome of `None` is not `Declined`: it means startup never reached that slot. `MissingSemantics` records what happens when a handle is absent: `IndistinguishableDefault { reads_as }`, `ConsumerDecides`, `FailsClosed`, or `FailsOpen`. The inventory is for capability handles whose absence could yield a wrong answer rather than a crash, not for every process-wide cache (`src/capability/mod.rs`).

`MutableCapabilitySlot` deliberately omits `decline` (`src/capability/mod.rs`). Its only instance is `GLOBAL_POLICY` (`src/spend/mod.rs`), which the live configuration update path replaces (`src/config/live_apply.rs`).

### Derived handle inventory

The test-only census derives its inventory from installations in the file that defines the container, not a hand-maintained exclusion list (`src/capability/census.rs`). For `OnceLock`, `OnceCell`, and the `ArcSwap` family, `Written` means a call to `set`, `store`, or `swap`. First-caller-wins means `get_or_init` or `get_or_try_init` with an initializer that depends on an enclosing function’s arguments. An initializer that uses only data reachable from the container itself is a lazy cache: “not initialized yet” is the correct answer, so that container does not count as a handle.

### The capability UI surface

`src/capability/ui.rs` and `src/capability/ui_surface.rs` are the **runtime-owned** `aleph/ui` surface capability (`UI_NAMESPACE = "aleph/ui"`). The live UI path runs through `src/capability/ui_surface.rs` and `src/gateway/capability_ui.rs` for rendering and input transport. It has **nothing to do** with plugin UI: plugin UI goes through `src/extension/panel_publication/`.

## From plugin declarations to runtime descriptors

Manifest adapters parse plugin components into `CapabilityDeclaration` values (`src/extension/capability.rs`, `src/extension/manifest/adapter.rs`). The extension host validates those declarations and registers each component with its owning registry. Once a callable tool reaches `ToolHandlerRegistry`, `ToolBackendAdapter` can project that entry as a runtime descriptor (`src/capability/backend.rs`). Zahir manages the runtime owner binding and lease. Skills and agents continue to operate through their respective registries. See [Extensions](../concepts/extensions) and the [Capability Overview](./overview).

## History: the removed legacy UI handler

The 2026-11-20 severed-wire audit removed the legacy UI handler in `src/capability/ui.rs` that was never registered in production, along with the in-memory display / input stub: no production path ever registered that synchronous handler, so the whole "legacy UI handler" arm was a severed wire (`review-results/sev-wire-2026-11-20/cap-ui-REPORT.md`, CUI-02). `src/capability/ui.rs` now keeps only the typed UI capability contract (the namespace, the schema, and the descriptor the gateway publishes).

## History: modules removed by the capability convergence

The 2026-11-25 capability convergence (designed in `docs/superpowers/specs/2026-11-25-zahir-capability-convergence-design.md` in the Aleph repository) removed several modules because they duplicated production authority or were never mounted:

- `src/capability/ambient.rs`: the ambient handler that declared itself unmounted.
- `src/capability/audit.rs`: the capability-side audit collector had no production reader; production auditing goes through `SecurityAuditLog`.
- `src/capability/grant.rs`: the capability-side `GrantRegistry` was unmounted; sandbox approval uses `GrantStore` in `src/sandbox/exec_approval/grants.rs`.
- `src/capability/lifecycle.rs` and `src/capability/activation.rs`: the capability's own lifecycle state machine and activation controller. Runtime policy used them for exactly two things — comparing generations and noticing revocation — and both now live in the constraint attachment and the provider lifecycle.
- The compatibility entry point in `src/tools/scoped/` that accepted an `Arc<dyn CapabilityActivation>` per tool name, which production deliberately never installed.
- The legacy handler registry and the `Legacy*` types in `src/capability/backend.rs`; `ToolBackendAdapter` is what stayed.

To recover the old implementation, use git: `git log --diff-filter=D -- src/capability/lifecycle.rs`.
